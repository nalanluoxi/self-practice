## Q104：Spark 数据倾斜排查与解法（项目深挖）

### 原题
> UpdateFrequencyTableJob 按 domain GROUP BY 聚合 compositeScore，超大站（百度/淘宝）几千万 URL 会导致 Spark 数据倾斜，任务卡在最后几个 Task。你当时遇到过吗？如何排查、如何解决？

### 我的回答
未实际遇到。排查策略：查看数据阻塞位置，判断哪些数据倾斜；尝试把小表广播到其他实例（Map Join）；如果 OOM 则提高 partition 并行度；提高每个实例的 CPU 数量，观察效果。

### ⚠️ 评价
方向有，但两个问题：
1. **混淆场景**：广播小表（Map Join）解决的是 JOIN 倾斜，不是 GROUP BY 聚合倾斜。compositeScore 是 GROUP BY 场景，解法是 Key 加盐+两阶段聚合
2. **加资源治标不治本**：热点 key 所有数据仍在同一 Task，加再多 CPU 也只有一个 Task 在跑

### ✅ 完整技术方案

**第一步：Spark UI 定位倾斜**
```
Jobs → 最耗时 Stage → Tasks 列表
→ 对比各 Task 的 Duration 和 Input Size
→ Max >> Median：数据倾斜确认
→ Shuffle Read 中最大分区远超均值
```

**第二步：区分场景用对手段**

| 场景 | 原因 | 解法 |
|------|------|------|
| GROUP BY domain 聚合 | 热点 key 数据极大 | Key 加盐 + 两阶段聚合 |
| 大表 JOIN 小表 | 小表不能放内存 | Map Join（Broadcast Join）|
| 大表 JOIN 大表，某 key 倾斜 | 热点 key 记录太多 | 热点单独处理 + UNION |

**核心方案：Key 加盐 + 两阶段聚合**
```python
# 第一阶段：给 domain 加随机盐 0~9，打散热点
df_salted = df.withColumn("salt", (rand() * 10).cast("int")) \
              .withColumn("salt_key", concat(col("domain"), lit("_"), col("salt")))

# 局部聚合（每个盐桶内先 sum）
stage1 = df_salted.groupBy("salt_key").agg(
    sum("new_url_count").alias("partial_count"),
    first("domain").alias("domain")
)

# 第二阶段：去盐，全局 sum
stage2 = stage1.groupBy("domain").agg(
    sum("partial_count").alias("total_new_url_count")
)
```

**现代化方案：Spark 3.x AQE 自适应查询执行**
```scala
spark.conf.set("spark.sql.adaptive.enabled", "true")
spark.conf.set("spark.sql.adaptive.skewJoin.enabled", "true")
// 运行时自动检测倾斜分区，拆分大分区为多个子分区
// 无需手写 salt 逻辑，生产推荐
```

**方案三：业务层热点隔离**
```python
# 预统计热点 domain（URL 数 > 100万）
hot_domains = df.groupBy("domain").count().filter("count > 1000000").select("domain")

hot_df = df.join(hot_domains, "domain")              # 热点：高并行度单独跑
cold_df = df.join(hot_domains, "domain", "left_anti") # 非热点：正常

hot_result = hot_df.repartition(200, "domain").groupBy("domain").agg(...)
cold_result = cold_df.groupBy("domain").agg(...)
final = hot_result.union(cold_result)
```

**方案对比**

| 方案 | 适用场景 | 改动成本 | 效果 |
|------|---------|---------|------|
| Key 加盐+两阶段聚合 | GROUP BY 聚合倾斜 | 中（需重写逻辑） | 高 |
| Map Join（Broadcast） | 大表 JOIN 小表 | 低 | 高 |
| AQE（Spark 3.x） | 通用，自动处理 | 极低（配置项）| 高 |
| 热点业务隔离 | 已知超大 key | 中 | 高 |
| 提高并行度/资源 | 轻微不均 | 低 | 低（热点无效）|

### 💡 新薄弱点
- GROUP BY 倾斜 vs JOIN 倾斜的解法区分不清楚，需加强

## Q104 补充：三种倾斜场景的本质区别

### 我的总结（订正后）
- **GROUP BY 加盐**：给 key 加随机后缀，打散到多个分区，两阶段聚合；不是复制数据，是重新分配
- **JOIN 小表广播**：小表装进 Driver，广播到所有 Executor，不触发 Shuffle
- **大表 JOIN 大表热冷分离**：热点 key 单独处理，广播的是 **dim 表热点部分（极少行）**，不是 URL 热点数据（体积大，不能广播）

### ⚠️ 订正点
原来说"把数量大的热点数据广播"——说反了。
广播的是 domain_info 热点侧（只有 3 行元数据），不是 url_table 热点侧（1.5 亿行）。

### ✅ 工程判断加分点
离线 Spark 任务（每天凌晨跑一次，SLA=当天完成）：
- 优先保证正确性和资源控制，不需要极致调优
- Spark 3.x AQE 默认开启，大部分倾斜自动处理
- 只有任务耗时从 1 小时异常变成 6 小时，影响下游数据窗口时，才手动介入 → Spark UI 定位 → 判断场景 → 选方案

## Q105：Hive INSERT OVERWRITE vs INSERT INTO + 并发写幂等性

### 原题
> UpdateFrequencyTableJob 写 Hive 分区表，INSERT OVERWRITE 和 INSERT INTO 区别？并发写同一分区会怎样？如何保证幂等性？

### 我的回答
OVERWRITE 覆盖（先建新表替换引用），INTO 追加；并发写会报错或覆盖；幂等性靠强制单进程操作。

### ⚠️ 两个订正点
1. **OVERWRITE 内部机制**不是"建新表替换引用"：Spark 先写 `_temporary/` 临时目录，全部 Task 完成后 HDFS rename（原子操作）替换分区目录，旧文件删除
2. **并发写不是"报错"**，而是静默数据损坏：OVERWRITE 并发 → 后 commit 覆盖前者，数据丢失无报错；INTO 并发 → 两份数据都追加，记录翻倍无报错

### ✅ 完整技术方案

**INSERT OVERWRITE vs INSERT INTO**

| | INSERT OVERWRITE | INSERT INTO |
|--|--|--|
| 行为 | 删除分区旧文件 → 写新文件 | 追加新文件到分区 |
| 重跑结果 | 天然幂等 | 数据翻倍 |
| 底层机制 | 写 _temporary/ → 完成后 HDFS rename 原子替换 | 直接追加写文件 |
| 适合场景 | 全量覆盖（频度评分）| 只增不改的追加 |

**并发写风险（静默损坏，无报错）**：
- OVERWRITE 并发：后 commit 覆盖先 commit → 数据丢失
- INTO 并发：两份数据都写入 → 记录翻倍

**幂等性保障方案**：

| 方案 | 原理 | 适用 |
|------|------|------|
| 强制 INSERT OVERWRITE | 重跑覆盖，天然幂等 | 全量覆盖场景，最简单 |
| 调度系统互斥 | DolphinScheduler 串行依赖，根本避免并发 | 生产推荐 |
| 写临时分区 + 原子 rename | dt=xxx_tmp 验证通过后 rename 到正式分区，无中间态 | 要求强一致的场景 |
| Hive ACID 事务表 | ORC + 事务支持，行级 UPSERT | 代价重，一般不用 |

**项目实际**：INSERT OVERWRITE dt=${bizdate} + 调度系统单实例 + 写完 COUNT 验证行数

## Q107：Kafka 进程崩溃消息不丢不重（银河驿站原题补考）⭐⭐⭐⭐

### 原题
> 进程 kill -9 崩溃，线程池里正在处理的 50 条消息怎么办？已提交 offset 的消息怎么办？未提交 offset 的消息怎么办？重启后如何保证不丢不重？

### 我的回答（比银河驿站版本好很多）
处理前写 Redis（key=URL，TTL=预计完成时间）→ 处理完删除 Redis key → 定时任务扫描超时未删除的 key → 投递死信队列补偿 → 12h TTL URL 去重防重复消费

### ⚠️ 唯一缺口：没有显式说清楚顺序
Redis 写入和 offset 提交的顺序是关键，必须说出来。

### ✅ 关键顺序（面试必说）
```
正确顺序：写 Redis → 提交 offset → 提交线程池 → 处理 → 删 Redis key

顺序搞错（先提交 offset 再写 Redis）：
offset 提交后进程崩溃 → Redis 无记录 → Kafka 不重发 → 消息永久丢失
```

### ✅ 三种崩溃场景分析
- **Redis 写入前崩溃**：offset 未提交 → Kafka 重发 → 正常处理 ✅
- **Redis 写入后、offset 提交前崩溃**：offset 未提交 → Kafka 重发 → URL 去重命中 → 跳过 ✅
- **offset 提交后崩溃（线程池处理中）**：Kafka 不重发 → Redis key 超时未删 → 定时任务投死信队列补偿 ✅

### ✅ TTL 设置
TTL = max(单条处理耗时) × 3，留安全余量；设太短 → key 提前过期 → 误判为失败 → 重复投递

### ✅ 补充：线程池 submit 失败时不提交 offset
SynchronousQueue + AbortPolicy：submit 抛 RejectedExecutionException → 不提交 offset → sleep(50ms) → Kafka 重投
Redis 是进程崩溃的异常兜底，不是 submit 失败的正常路径

## Q108：IO 多路复用 select/poll/epoll（高频薄弱点补考）

### 我的回答
select 是阻塞 IO（等 CPU 拷贝数据）；poll 非阻塞（fd 数组注册，遍历查找）；epoll 两个数组（等待集合 + 就绪集合，就绪数据移动，无需遍历，无大小限制）

### ⚠️ 根本性概念错误
"select 是阻塞 IO，发起请求后等 CPU 把数据拷到磁盘缓冲区"——这描述的是 BIO（同步阻塞 IO），不是 IO 多路复用。
三者都是 IO 多路复用，区别是**实现效率**，不是"阻塞 vs 非阻塞"。

### ✅ 完整答案

| | select | poll | epoll |
|--|--|--|--|
| 数据结构 | 固定位图 fd_set | 动态数组 pollfd[] | 内核红黑树 + 就绪链表 |
| FD 上限 | 1024（硬编码）| 无限制 | 无限制 |
| 每次调用 | 全量拷贝到内核 | 全量拷贝到内核 | 无需拷贝（FD 已注册在内核）|
| 检测就绪 | O(N) 遍历所有 FD | O(N) 遍历所有 FD | O(1) 直接从就绪链表取 |
| 返回结果 | 就绪数量，需再遍历找哪些就绪 | 同 select | 直接返回就绪 FD 列表 |

**epoll 快的原因**：10000 连接只有 10 个有数据，select/poll 扫 10000 次，epoll 直接拿 10 个

**ET vs LT**：
- LT（默认）：有数据就一直通知，没读完下次继续通知，编程简单
- ET：状态变化时通知一次，必须一次读完（while 读到 EAGAIN），否则不再通知；需配合非阻塞 IO；通知少，Nginx 用 ET 提升性能

口诀：LT = "有数据就一直叫"；ET = "来了叫一声，没读完别怪我"

## Q109：Tomcat 打破双亲委派 + 热部署类卸载（快手2场均失败的薄弱点）

### 我的回答
Tomcat 打破双亲委派是为了让多个 web 应用各自用独立 ClassLoader；通过自定义类加载器实现；热部署不知道。

### ⚠️ 原因说错了
"不打破只能创建一个 web 应用"——错误。
真正原因是**版本隔离**：App A 用 commons-logging-1.1，App B 用 1.2，默认委派会导致 B 拿到 A 的版本造成冲突。

### ✅ 完整答案

**ClassLoader 层次**：Bootstrap → Extension → System → Common（共享）→ WebApp（每 App 独立）

**打破方式**：重写 loadClass()，反转顺序：先查 WEB-INF/lib 自己的 → 找不到再委派父；JDK 核心类（java.*）仍委派父（安全）

**热部署类卸载流程**：
1. 检测到文件变化 → 创建新 WebApp ClassLoader
2. 用新 ClassLoader 加载新版本类
3. 旧 ClassLoader 引用置 null → 无引用 → GC 回收
4. Class 对象在 Metaspace，随 ClassLoader 一起被回收

**内存泄漏风险**（加分点）：ThreadLocal 未 remove、静态变量持有旧 ClassLoader 加载的对象、JDBC Driver 注册 → 旧 ClassLoader 无法 GC → Metaspace OOM

## Q113：对话记忆摘要压缩实现细节（项目深挖）

20轮触发，压缩最早10条；发给LLM要求精简非核心内容；同步执行；读最新消息；失败继续用20条，下次21条再触发。

### ⚠️ 两个缺口
1. **没说压缩 Prompt 内容**：保留什么（意图/决策/结论），删除什么（闲聊/重复/中间步骤）
2. **同步执行有延迟代价**：第20轮要等压缩LLM（1~3s）+回答LLM（2~5s），用户感知到卡顿；异步更优

### ✅ 关键补充
**异步压缩并发处理**：压缩时 Copy-on-Write，新消息读当前已提交版本（不读中间态），压缩完成后 Redis Lua 原子替换历史列表

**失败限速**：连续失败 < 3次，忽略继续；≥3次，强制截断最早5条 + 告警；防止历史无限增长撑爆 LLM Context Window

**升级不限速**（只说了降级限速，漏了升级）：
- 降级限速（每次最多-1级）：单天噪音不影响长期频度
- 升级不限速：站点质量变好，应尽快响应，错过是真实损失

**DI 表 rate_score 存储细节**（加分点）：
- 存的是已乘权重的值（0.5 × rateScore），不是原始档位值
- 直接读该字段会得到被压缩过的数，理解时需区分

## Q110：pgvector 底层算法 + IVFFlat 原理 + vs Milvus（百度露怯补考）

### 我的回答
不清楚，只知道计算余弦距离做向量搜索。

### ✅ 完整答案

**相似度计算**：三种运算符：`<->` L2 距离、`<#>` 内积、`<=>` 余弦距离；RAG 用余弦距离（只看语义方向）

**无索引**：暴力搜索 O(N×d)，百万数据不可用

**IVFFlat 原理**：
1. 建索引：K-means 聚类生成 N 个 centroid，每个向量归属最近 centroid，建倒排索引
2. 查询：先找最近的 K 个 centroid，只在这 K 个 centroid 的向量列表里搜，返回 Top-N
3. 参数：lists（centroid 数量）、probes（查几个 centroid，越大越准但越慢）

**HNSW**（pgvector 0.5+）：分层小世界图，上层稀疏跳跃，下层密集精搜；比 IVFFlat 快、召回高，生产推荐

**pgvector vs Milvus**：
- pgvector：PG 扩展，单机，天然 SQL 支持，适合 < 100万条、开发测试
- Milvus：独立分布式向量 DB，水平扩展支持数十亿向量，高 QPS，适合生产
- Spring AI VectorStore 接口屏蔽差异，开发用 pgvector，生产换 Milvus 无需改业务代码

## Q106：任务依赖失败处理 + 上下游解耦设计（项目深挖）⭐⭐⭐⭐⭐

### 原题
> UpdateFrequencyTableJob 下游有 FrequencyDeliverySitemapJob 依赖。上游写入失败、写一半数据时，下游如何感知？如何防止读到"半截数据"？

### 我的回答（完整，高质量）
**第一层：失败回滚保障**
- INSERT OVERWRITE 先写 `_temporary/`，失败时 rename 不触发，旧分区完好，不会产生脏数据
- 生产平台设置重试机制，失败自动重试（最多3次），超时 kill，超过3次失败触发大象告警

**第二层：上下游解耦设计（工程演进亮点）**
- 早期：下游强依赖上游任务执行成功的信号
- 问题：上游链接产出任务产出时间不稳定，有时上游失败导致下游 update 超时或未执行
- 演进：与上游解耦，下游直接读取频度评分表的**最大分区 dt**，以该 dt 的数据作为当次调度参考
- 原理：INSERT OVERWRITE 写完后才 rename 到真实分区，最大 dt 天然等于最后一次成功写入的完整分区，不会读到半截数据
- 效果：凌晨 2 点 update 未完成 → freq 任务读到昨天的 max dt，用昨天数据跑；update 完成后 rename → freq 任务读到今天 dt，用今天数据

### ✅ 补充两个追问点
**风险：数据新鲜度无感知**
- 如果 update 任务连续失败多天，freq 任务会静默使用过期数据，无任何告警
- 改进：读出 max_dt 后校验与当前日期差值，超过 N 天则告警 + 降级

**更标准的方案：_SUCCESS 文件**
- Spark 任务成功后在输出目录写空文件 `_SUCCESS`
- 下游检查 `dt=${today}/_SUCCESS` 是否存在，存在则用今天数据，否则用昨天
- DolphinScheduler/Airflow 支持配置"等待 _SUCCESS 文件出现"作为上游就绪信号，比读最大 dt 更标准明确

## Q115：while+sleep背压优化（项目深挖）

### 原题
> while循环检查线程池状态、sleep 1秒、synchronized加锁这个背压方案有没有问题？高并发场景下哪里可以优化？

### 我的回答
业务场景够用。有考虑Semaphore，但分析：优势只在初始化阶段（多线程同时提交），线程池满后两者差别不大；Semaphore引入额外复杂度；synchronized不需手动释放更简单可靠。

### ✅ 评价：有真实设计思考，但Semaphore分析角度偏了

### ⚠️ 关键遗漏
Semaphore核心优势不是"多线程同时提交"，而是**响应及时性**：
- while+sleep(1s)：线程空出来后最多等1秒才感知到
- Semaphore.acquire()：release()时OS立刻唤醒，毫秒级响应，零CPU消耗

### ✅ 完整参考答
当前方案业务场景够用（单线程拉取，1秒延迟可接受）。
优化方向：Semaphore替代while+sleep——acquire()阻塞在OS层，release()立刻唤醒，响应从"最多1秒"降至毫秒级，零CPU消耗。
不用的理由：1秒延迟业务不敏感；Semaphore需在线程完成时手动release，增加代码耦合，此场景属过度设计。
