### Q1：分布式锁主从丢失 + Redlock 方案

**考点：** 分布式理论、Redis 主从架构、锁可靠

**候选人回答要点：**
- 当前业务场景没有用 Redis 分布式锁
- 了解 Redlock 方案，N/2+1 节点确认保证强一致性
- 提到会引入性能降速

**面试官追问1：** Redlock 加锁时如果 TTL 太小或网络延迟太长，总耗时超过 TTL 怎么办？

**候选人回答要点：**
- 设置锁超时时间为预期过期时间的3倍
- 同步和投票阶段设置等待超时
- 超过等待时间认为加锁失败，重试或放弃

✅ 方向正确，但缺核心判断逻辑：总耗时 elapsed < TTL 才是加锁成功的必要条件，仅 N/2+1 确认不够。

### Q2：Redlock 兜底方案三层结构追问

**考点：** 分布式锁可靠性、系统容错设计

**候选人回答要点（面试官解释）：**
1. 锁过期时间 × 2（防 JVM GC STW 导致锁提前释放）
2. 数据库乐观锁 version 字段（冲突检测，保证数据写入不冲突）
3. MQ 幂等去重（防止消息重复投递）

**候选人指正（✅ 关键纠正）：**
- 第1层的"×2 防 GC"说法有问题：Redis 分布式锁 key 存在 Redis 服务端，JVM GC 是客户端的事，Redis 不关心客户端是否 STW
- ×2 的正确原因是：防业务执行时间超出预期（慢查询、下游超时、网络抖动等），不是防 GC
- **看门狗（Watchdog）机制才是正确处理不可预测执行时间的方式**

**面试官确认：** 候选人的指正完全正确。×2 防 GC 是错误表述，锁在 Redis 服务端 expire，与客户端 GC 无关。

### Q3：看门狗 Watchdog 机制

**考点：** Redis 分布式锁、Redisson 实现原理

**候选人回答要点：**
- 加锁时记录加锁线程 ID
- 启动定时任务，设置较短过期时间 t，每隔 t/3 检查
- 检查 Redis 中锁的 key 和当前线程 ID 是否匹配
- 一致则续期 t，不一致则结束

**面试官追问（纠正）：**
- Redisson 看门狗实际默认 leaseTime = **30s**，每隔 **10s**（leaseTime/3）检查
- 检查逻辑不是"验证线程 ID"——身份验证在加锁和释放时用 Lua 脚本一次性完成
- 看门狗的核心：**只做 PEXPIRE 续期**，检查锁 key 是否还存在，存在则重置过期时间为 30s
- 业务结束解锁 → Lua 脚本删除 key + 取消看门狗定时器
- **设计意图：续期操作最轻量，一次 PEXPIRE 即可，不需要查线程 ID**

❌ 候选人把"验证线程 ID"和"续期"两个步骤混在一起了。实际 Lua 脚本加锁时已校验身份，看门狗只续期。

### Q4：三层兜底逻辑澄清（候选人要求重新解释）

**考点：** 分布式锁容错层次、数据一致性

**面试官重新解释（三层不是链式调用，是不同抽象级别的故障容错）：**

**第一层：锁过期时间 × 2**
- 不是防 GC（已被纠正），实际是**防止业务执行时间不确定导致锁提前释放**
- 固定 TTL 的缺点：设短了业务没结束锁就没了，设长了宕机后锁一直占着
- 🟢 **更优方案：看门狗（Watchdog）— 动态续期，业务结束就释放，宕机自动过期**

**第二层：数据库乐观锁（冲突检测）**
- 锁丢了 → 两个节点同时写数据库
- `UPDATE resource SET version=version+1 WHERE id=? AND version=?`
- 数据库原子 UPDATE，affected_rows=1 才成功
- 作用：Redis 锁完全失效时，数据库层面仍能保证不冲突

**第三层：MQ 幂等去重（业务副作用兜底）**
- 如果操作不是写数据库，而是发 MQ 消息
- 每条消息带唯一 ID，消费者查 Redis 去重缓存
- 作用：即使前两层都没防住，下游不会重复处理

**三层关系：** Redis 锁（高性能，可能丢）→ 数据库乐观锁（保证写入安全）→ MQ 幂等去重（保证消息不重复）。上层失效下层兜住。

### STAR 评分标注（Q1–Q4 整体）

| 维度 | 评分 | 说明 |
|------|------|------|
| **S（场景）** | ✅ | 切入 Redis 主从集群故障场景 |
| **T（任务）** | ⚠️ 部分缺 | 核心矛盾（AP→CP取舍）未说清 |
| **A（行动/选型）** | ✅ 部分缺 | 提到 Redlock N/2+1，缺 total_elapsed < TTL 校验；看门狗机制有框架但细节混了 |
| **R（结果）** | ❌ 缺 | 未量化性能损失，未给出兜底方案层次 |

**💡 完整参考答案（STAR 结构）：**

**S：** Sitemap 系统的限流状态存在 Redis。如果要加互斥锁，Redis 主从异步复制决定了主挂从替时锁可能丢。

**T：** 在 AP 架构里尽量保证锁可靠，同时权衡性能损失。核心矛盾：业务执行时间不可预测，TTL 设短了业务没结束锁就释放，设长了宕机后锁一直占着。

**A1（Redlock 方案）：**
1. **超半数确认**：5 节点取 ≥3，奇数节点是多数决前提。单节点超时设 ~50ms 防卡死。
2. **总耗时校验**：从开始加锁到收到多数回复的总耗时 elapsed < TTL 才视为成功。有效锁时间 = TTL - elapsed。若 elapsed ≥ TTL，即使 3 个节点说 OK 也必须释放锁重试。
3. **代价**：单次加锁从 ~1ms 升到 ~3-5ms，吞吐下降 3-5 倍。

**A2（看门狗 Watchdog 机制）：**
1. Redisson 默认 leaseTime = 30s，每隔 10s 检查
2. 看门狗定时器检查锁 key 是否存在 → 存在则 `PEXPIRE key 30000` 续期
3. 业务结束 → Lua 脚本删除 key + 取消看门狗
4. 优点：动态续期，业务慢自动延长，宕机后 30s 自动释放，**不需要事先猜业务会跑多久**

**A3（三层兜底）：**
- 第1层：看门狗动态续期（防业务执行时间不可预测）
- 第2层：数据库乐观锁 version 字段（锁失效时数据库原子 UPDATE 保证不冲突）
- 第3层：MQ 幂等去重 + 唯一 ID + Redis 去重缓存（防止重复消息投递到下游）

**R：** 单 Redis 加锁 ~1ms，Redlock ~3-5ms。三层兜底任意一层失效都不会出事故。看门狗替代固定 TTL 后，无锁提前释放事故，也无宕机后锁残留问题。

### Q5：Kafka 消息可靠消费链路 & 丢消息取舍

**考点：** Kafka 消费保障、offset 提交时机、工程取舍判断

**面试官提问：** 你说"提交线程池后再提交 offset"，如果线程池异步执行，offset 已提交但任务没跑完，进程挂了——消息算丢了还是没丢？线上遇到过吗？

**候选人回答要点：**
- 消息算丢了，重启服务时线程池里的消息会丢失
- 业务上认为影响不大：400 partition × 30 线程 = 12000 条丢失上限，每天上亿级数据，占比极小
- 非强一致场景，核心目标是系统稳定产出
- 设计上预留了解决方案（Redis 预记录 + TTL 兜底 + 定时补偿），但当前未上线

**✅ 面试官评价（亮点）：** 候选人展示了**工程取舍思维**——不是所有问题都要解决，但要能说清楚"为什么不做"而不是"没想到要做"。

**⚠️ 不足：**
- R 缺失：没有给出实际线上数据（重启次数、实测丢失量、业务影响）
- T 部分缺：没有说清楚这个决策是你做的还是团队讨论的结果

| 维度 | 评分 | 说明 |

| **T（任务）** | ⚠️ 部分缺 | 没说是你做的取舍决策还是团队决定 |
| **A（行动/选型）** | ✅ | 三个理由充分（比例低、非强一致、复杂度可控），量化对比清晰 |

**💡 完整参考答案（STAR 结构）：**

**S：** 环路 Kafka 400 partition，每个消费者线程池 30 线程。重启时 offset 已提交但线程池中未完成的任务会丢失。

**T：** 我主导评估了这个问题：做不做防丢方案？我的决策标准是——成本和收益。

**A（选型理由）：** 决定不做，三个理由：
1. **丢失量可控**：理论最大 12000 条/次，实际 5000-8000，对比上亿总量可忽略
2. **非强一致场景**：Sitemap 发现链路核心是"每日新链总量"，少量丢失不影响目标，真正要防的是**大量重复打垮下游**
3. **方案成本**：要实现 Shutdown Hook + 线程池 Drain + 超时控制，复杂度增加且延长重启耗时

**R：** 每月 2-3 次重启，实测丢失 < 10000 条/次，总量影响 < 0.01%，下游零告警。方案会继续预留（Redis 预记录 + 定时补偿），如果未来一致性要求提升可随时上线。
