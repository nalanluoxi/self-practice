## Q44：Spark 任务数据链路与 API 选型

### 原题
> llm-spider-jobs 里 compositeScore 计算任务，输入数据来自哪里？整体计算流程？用的什么 API？

### 我的回答
数据来自 Hive 表。流程：原始链接结果表 → Spark 布隆过滤历史链接得到新链 → join 原始表按 sitemapURL+时间戳计算一天产出次数（新链接分）→ join 黑名单表过滤（博彩/色情等）→ join 模糊留存表计算留存率分（留存数/调度数，分段打分避免小站点极端数据）→ 规模分（按投递量分级）→ 三维加权 compositeScore。使用 Spark SQL + UDF 计算。

### ✅ 评价
数据链路完整，三维打分逻辑清晰，能说出用 SQL+UDF 而非 RDD 的选型。回答有实战深度。

### ✅ 更完善的回答
**为什么用 Spark SQL + UDF 而非 RDD**：SQL 表达力强、可读性好，适合多表 join 和聚合；UDF 封装打分逻辑可复用且可单独单元测试（CalcCompositeGradeTest）。RDD 适合自定义复杂计算，此场景 SQL 已够用。

## Q45：Spark 宽窄依赖与 Shuffle

### 原题
> Spark 宽依赖和窄依赖是什么？join 属于哪种？Shuffle 有什么性能代价？

### 我的回答
不清楚，没了解过。

### ⚠️ 回答缺陷
完全不了解，需要从零掌握

### ✅ 完整知识点（必须背熟）
**窄依赖**：父RDD每个分区只被子RDD一个分区使用，不需要跨节点传输，可流水线执行。例：map、filter、union

**宽依赖**：父RDD每个分区被子RDD多个分区使用，必须触发Shuffle。例：groupByKey、reduceByKey、join、distinct

**Shuffle 四大代价**：
1. 磁盘IO：Map端按key分桶写磁盘，Reduce端从各节点拉取
2. 网络IO：数据跨节点传输，大表join时极大
3. 内存压力：Reduce端聚合，量大时溢写
4. Stage边界：每个Shuffle是Stage切分点，Stage间串行等待

**关键优化：Map Join（Broadcast Join）**：小表广播到每个Executor内存，大表本地join，完全避免Shuffle。大表join小表的标准优化手段。

## Q60：Hive/Spark SQL 优化

### 原题
> 两张亿级表的 LEFT JOIN SQL，在 Hive/Spark 上有哪些性能问题？怎么优化？

### 我的回答
不清楚。

### ⚠️ 回答缺陷
需要从零掌握，大数据岗必考点。

### ✅ 完整知识点（必须掌握）
**四个主要问题与优化**：

1. **全表扫描**：没有分区表，WHERE dt='xxx' 扫全表。优化：**建分区表**，只读当天分区，IO减少99%

2. **大表join大表Shuffle**：亿级表join触发大量Shuffle，可能数据倾斜。优化：若一张表相对小，用 **Broadcast Join**（`/*+ BROADCAST(b) */`）广播小表避免Shuffle

3. **数据倾斜**：热门域名数据量远超小站。优化：加盐打散或AQE自动处理

4. **LEFT JOIN产生大量NULL行**：浪费后续计算资源。优化：根据业务改为INNER JOIN或提前过滤

**核心优化原则**：
- 分区裁剪（Partition Pruning）：只读需要的分区
- 列裁剪（Column Pruning）：只查需要的列
- Broadcast Join：小表广播避免Shuffle
- 谓词下推（Predicate Pushdown）：WHERE条件尽早过滤

## Q59：OOM 排查 — byte[] 堆积

### 原题
> 爬虫服务偶发OOM，堆dump分析发现大量byte[]堆积，怎么排查？通常是什么原因？你们场景最可能是哪里？

### 我的回答
导出堆快照分析，排查内存泄漏或大对象未释放。爬虫场景：抓取内容以字节数组暂存，超大页面是主要原因。解决：添加监控，超过阈值丢弃该页面，保证主线稳定。

### ✅ 评价
结合自己系统实际分析，超大页面阈值丢弃方向完全正确。

### ✅ 更完善的回答
**排查步骤**：
1. `jmap -dump:format=b,file=heap.hprof <pid>` 导出堆快照
2. MAT 分析 `byte[]` 引用链，找 GC Root 路径
3. 看 Retained Heap，找最大保留堆

**byte[] 堆积常见原因**：
1. 超大响应体：多线程并发，每线程持有大byte[]，线程池满载时N个大数组同时存在
2. 内存泄漏：被静态集合/缓存持有未释放
3. 流未关闭：InputStream 未在 finally 中关闭

**解决方案**：
1. 设置响应体大小阈值（如5MB），超过直接丢弃（你的方向）
2. 流式处理替代全量读取，边读边解析（GZIP已这么做）
3. 调大堆内存或调小线程池，减少并发持有的大对象数量

## Q58：进程 vs 线程，Java 线程与 OS 线程关系

### 原题
> 进程和线程核心区别？线程切换为什么代价更小？Java 线程和 OS 线程是什么关系？

### 我的回答
进程是资源分配最小单位，线程是调度最小单位。线程切换不需要切换资源（同进程共享内存），进程切换需要记录资源信息代价更大。Java线程和OS线程关系不记得了。

### ⚠️ 回答缺陷
- **线程切换代价小的原因没说全**：关键是不需要切换**内存地址空间（页表/TLB）**
- **Java线程与OS线程关系不记得**：JDK 1.2后1:1映射内核线程，JDK 21引入虚拟线程

### ✅ 更完善的回答
**线程切换代价小**：只需保存/恢复寄存器、PC、栈指针，不需要切换页表。进程切换需要切换页表导致 TLB 全部失效，代价高出几十倍。

**Java线程与OS线程**：
- JDK 1.2+ ：1:1映射内核线程，调度由OS负责，创建开销大（约1MB栈），所以需要线程池
- **JDK 21 虚拟线程**：M:N模型，大量虚拟线程映射到少量内核线程，由JVM调度，可创建百万级，专为IO密集型设计

## Q57：分布式定时任务只跑一次

### 原题
> 多实例部署，每天凌晨需要清理 Redis 过期缓存，只需要一台机器执行，怎么保证？

### 我的回答
并发清理会出现重复操作。方案：① 只在一台机器部署定时任务 ② 配置中心配置IP，启动时对比本机IP，不匹配跳过。主动质疑设计：批量清理可能引发缓存雪崩，应该用TTL自动过期替代批量清理，更合理。MQ里排队时间过久的URL也应该丢弃。

### ✅ 评价
三个层次都答到：识别问题、给出方案、质疑需求合理性。主动质疑设计前提是加分项。

### ✅ 更完善的回答（补充 Redis 分布式锁抢占方案）
**三种方案**：
1. 单机部署：最简单，但单点故障
2. 配置中心IP绑定：启动时对比本机IP，不匹配跳过
3. **Redis分布式锁抢占（推荐）**：`SET task:cleanup "" NX EX 60`，抢到锁的执行，抢不到跳过，扩缩容无需改配置

**更合理的设计**：TTL自动过期（被动过期）替代批量清理（主动清理），更优雅，避免集中清理引发缓存雪崩。

## Q56：综合场景题 — 秒杀系统设计

### 原题
> 设计秒杀系统：库存1000件，10万用户并发下单，保证不超卖、系统不崩、用户体验好

### 我的回答
限流降级（阈值返回默认页面）、容灾备份（MySQL/Redis集群主从同步）、分布式锁防超卖、分段锁（1万库存分10段提高并发）、Canal监听Redis binlog同步MySQL保证强一致性。

### ⚠️ 回答缺陷
- **最核心的防超卖手段没说**：Redis 原子扣减（Lua脚本）是秒杀防超卖的标准方案
- **Canal 用法说错**：Canal 监听的是 **MySQL binlog**，不是Redis。Redis没有binlog
- **MQ 异步下单没有说**：抢到库存后发MQ异步创建订单，是秒杀系统标准架构
- **请求漏斗思想没有体现**：核心是把请求拦截在最前面，保护数据库

### ✅ 更完善的回答（四层漏斗架构）
**第一层：流量拦截**：Nginx限流 + 用户维度限频（Redis计数）+ 提前预热库存到Redis

**第二层：Redis原子扣减（核心防超卖）**：Lua脚本原子执行 `if stock>0 then decr`，单线程天然防超卖，99%请求在此拦截

**第三层：MQ异步下单**：抢到库存发MQ立即返回"排队中"，消费者异步创建订单。订单超时未支付则回补库存。

**第四层：MySQL乐观锁兜底**：`UPDATE stock SET count=count-1 WHERE id=? AND count>0`，影响行数为0说明库存不足

**容灾**：Redis主从集群 + MySQL主从，Canal监听**MySQL** binlog同步从库

**核心原则**：请求漏斗——10万请求逐层拦截，数据库只承受最终成功的1000次操作

## Q55：Redis 分布式锁与 Redisson

### 原题
> SET NX EX 实现分布式锁有缺陷吗？Redisson 如何解决？

### 我的回答
有缺陷：业务超时导致锁提前释放，其他线程进入。Redisson 用看门狗机制，不设固定过期时间，定期检查事务是否继续执行，还在则续期，否则释放锁。

### ⚠️ 回答缺陷
- **漏了"误删别人的锁"这个缺陷**：锁过期后线程B获锁，线程A执行完误删线程B的锁
- **Lua脚本原子释放没有说**：GET+DEL两步不原子，需要Lua脚本

### ✅ 更完善的回答
**两个主要缺陷**：
1. **锁提前过期**：业务执行超过TTL，锁自动释放，其他线程进入
2. **误删别人的锁**：value存UUID，释放时用**Lua脚本**原子执行"判断UUID + 删除"，防止删掉别人的锁

**Redisson 解决方案**：
- **看门狗**：默认TTL 30秒，后台线程每10秒续期，业务结束主动释放
- **唯一标识 + Lua脚本原子释放**：防止误删
- **可重入**：Hash结构记录重入次数，同一线程多次加锁不死锁
- **RedLock**：在多个独立Redis节点加锁，超过半数成功才算获锁，防主从切换锁丢失

## Q54：MySQL 行锁与死锁

### 原题
> Lock wait timeout exceeded 说明什么？MySQL 行锁怎么工作？什么情况出现锁等待，什么情况死锁？

### 我的回答
说明任务超时。MySQL 行锁依靠主键加锁。线程1持有A锁等B锁，线程2持有B锁等A锁，形成死锁。

### ⚠️ 回答缺陷
- **行锁锁的是索引记录，不是主键**：WHERE 条件没走索引会退化为表锁
- **三种行锁类型没说**：Record Lock / Gap Lock / Next-Key Lock
- **InnoDB 自动检测死锁**：选择回滚代价小的事务作为牺牲者
- **排查工具没说**：`SHOW ENGINE INNODB STATUS`

### ✅ 更完善的回答
**Lock wait timeout**：事务 A 持锁未提交，事务 B 等待超过 `innodb_lock_wait_timeout`（默认50秒）报错。

**行锁机制**：锁的是**索引记录**，不是数据行。WHERE 条件不走索引 → 退化为**表锁**。

**三种行锁类型**：
- Record Lock：锁单条索引记录
- Gap Lock：锁索引间隙，防止幻读（RR级别）
- Next-Key Lock：Record Lock + Gap Lock，锁记录及前面间隙

**死锁**：InnoDB 自动检测，选择回滚代价较小的事务作为牺牲者，另一个正常提交。

**排查**：`SHOW ENGINE INNODB STATUS` 查看锁等待和死锁详情；检查WHERE条件是否走索引；检查事务内是否有外部调用导致持锁时间过长。

## Q53：线程池拒绝策略

### 原题
> 线程池拒绝策略是什么？Java四种内置拒绝策略分别是什么？消息不丢失场景下哪种最合适？

### 我的回答
使用抛出异常的拒绝策略。四种：调用线程执行（阻塞主线程）、丢弃任务、丢弃最老的任务。设计：AbortPolicy抛异常→try-catch捕获→返回MQ消费失败→MQ重新投递，保证消息不丢。（补充：机器是8核）

### ⚠️ 回答缺陷
- **四种策略只说了3种**，漏了 DiscardPolicy（静默丢弃）
- **策略名字没说出来**：AbortPolicy/CallerRunsPolicy/DiscardPolicy/DiscardOldestPolicy

### ✅ 更完善的回答
**四种拒绝策略**：
1. **AbortPolicy（默认）**：抛出 `RejectedExecutionException`，调用方捕获处理
2. **CallerRunsPolicy**：由提交任务的线程自己执行，天然背压，不丢任务但变慢
3. **DiscardPolicy**：静默丢弃，不抛异常，只适合允许丢失的场景（如埋点）
4. **DiscardOldestPolicy**：丢弃队列中最老的任务，适合新数据优先级更高的场景

**你们的设计**：AbortPolicy 抛异常 → try-catch 捕获 → 返回MQ消费失败 → MQ重新投递，把重试职责交给MQ，消息不丢且主线程不阻塞，设计合理。

**8核机器用35线程说明**：HTTP等待时间极长（几百毫秒），等待比例很高，需要更多线程填满CPU空闲，实测结果优先于公式。

## Q52：线程池核心线程数设置

### 原题
> 业务线程池核心线程数设置多少？怎么考虑的？IO密集型和CPU密集型公式分别是什么，逻辑是什么？

### 我的回答
设置 35，最开始是5，逐步提高同时监控线上CPU/内存和大环抓取的成功率等指标，提高到35后达到预期。IO密集型=CPU核数×2，CPU密集型=CPU核数-1。

### ✅ 评价
有实战调参经验，"逐步调大+监控线上影响"思路是真实工程经验，面试官认可。公式基本对。

### ✅ 更完善的回答
**实战调参思路**：没有万能公式，核心是**压测+监控**。从小线程数开始逐步增大，观察吞吐量提升、CPU/内存消耗、其他服务影响，找到吞吐量提升趋于平缓的拐点。

**IO密集型：CPU核数 × 2**
逻辑：IO任务大部分时间等待IO（不占CPU），更多线程可以让CPU持续工作，提高利用率。爬虫抓取=大量HTTP等待，典型IO密集型。

**CPU密集型：CPU核数 或 CPU核数+1**
逻辑：CPU密集型任务持续计算，线程超过核数会增加上下文切换开销。+1是为了某线程偶发停顿时有备用线程顶上。

**线程数35说明机器约16-18核**，符合IO密集型量级。公式只是起点，最终靠实测。

## Q51：操作系统 D 状态进程排查

### 原题
> 大量进程处于 D 状态（不可中断睡眠），CPU 使用率低但系统响应慢，说明什么？怎么排查？

### 我的回答
D 状态是不可中断睡眠，说明系统在等待IO，可能是写入数据或HTTP请求阻塞。通过日志监控查看耗时，jstack 查看阻塞位置。

### ✅ 评价
核心方向正确，D 状态=等待IO 答对了。

### ✅ 更完善的回答
**D 状态**：等待IO完成，无法被信号中断（kill -9也杀不掉）。内核设计防止IO操作被强制中断导致数据损坏。

**常见原因**：
1. 磁盘IO瓶颈：写入速度跟不上，用 `iostat -x 1` 查看，`%util`接近100%说明磁盘打满
2. NFS/网络文件系统无响应：挂载远端文件系统卡住
3. 内存不足触发大量Swap：频繁换页导致IO暴增

**排查命令**：
- `iostat -x 1`：查磁盘IO利用率
- `iotop`：查哪个进程IO最高
- `vmstat 1`：查内存/swap（si/so列）
- `dmesg | tail -50`：看内核IO错误日志

**注意**：jstack 看JVM线程栈能看到在做什么，但磁盘IO瓶颈要用 `iostat`/`iotop` 在OS层确认。

## Q50：Flink vs Spark Streaming 选型

### 原题
> 如果业务要求实时感知站点更新，每抓到新链接立刻更新得分，用 Spark Streaming 还是 Flink？

### 我的回答
没用过Flink，业务场景没遇到实时感知需求。

### ⚠️ 回答缺陷
需要从零了解，以下是必备知识

### ✅ 核心知识点（必须掌握）
**Spark Streaming**：微批处理，按时间切成小批次跑Spark Job，延迟**秒级**，和Spark生态无缝集成。

**Flink**：真正的流处理，每条数据到来立刻处理，延迟**毫秒级**，有强大的状态管理和精确时间窗口。

**此场景选 Flink，原因**：
1. 实时性：每条新链接立刻更新得分，需毫秒级，Spark秒级不满足
2. 状态管理：compositeScore 需累积历史数据，Flink 有状态计算每条消息直接更新domain状态，不需全量重算
3. Checkpoint容错：定期持久化状态，崩溃后从断点恢复不丢数据

**一句话记忆**：Spark=微批（秒级），Flink=真流（毫秒级），有状态实时计算选Flink。

## Q49：场景题 — Spark 任务变慢排查

### 原题
> compositeScore Spark 任务正常1小时，今天跑了6小时还没完，怎么排查？

### 我的回答
查看日志，找耗时最大的部分，排查原因。

### ⚠️ 回答缺陷
- 太笼统，没有说具体排查工具和步骤
- 没有说出常见原因（数据倾斜、内存不足、资源争抢等）

### ✅ 更完善的回答
**第一步：看 Spark UI（最重要）**
- 找到慢 Stage，看 Task 分布
- 少数Task极慢 → 数据倾斜
- 所有Task都慢+GC频繁 → 内存不足
- Shuffle量暴增 → 上游数据量异常

**常见原因对照表**：
| 现象 | 原因 | 解决 |
|------|------|------|
| 少数Task极慢 | 数据倾斜 | 加盐/Map Join/AQE |
| 所有Task慢+频繁GC | 内存不足 | 增加Executor内存 |
| Shuffle量暴增 | 上游数据量暴增 | 检查原始表分区数据量 |
| Task频繁重试 | DataNode故障/网络抖动 | 排查节点健康 |
| Stage卡住不动 | YARN资源不足 | 检查资源队列 |

**结合场景**：检查布隆过滤Stage历史数据量、join Stage热门域名是否倾斜、上游Hive表分区数据量是否异常。

## Q48：HDFS 架构与读写流程

### 原题
> HDFS 的 NameNode 和 DataNode 分别负责什么？文件怎么存储和读取？

### 我的回答
HDFS 是文件系统，根据给定地址或表名查询对应文件地址读取。

### ⚠️ 回答缺陷
完全不了解内部架构，需要从零掌握。

### ✅ 完整知识点（必须背熟）
**NameNode**：存储**元数据**（文件名、目录结构、Block分布），不存实际数据，相当于目录索引。**单点风险，生产必须配HA**。

**DataNode**：存储实际**数据块（Block）**，默认128MB/块，默认**3副本**分散在不同节点，保证容灾。

**写文件流程**：
1. 客户端告诉NameNode要写文件
2. NameNode分配Block ID和目标DataNode列表
3. 客户端把文件切块，链式写入DataNode（D1→D2→D3副本传输）
4. 写完通知NameNode更新元数据

**读文件流程**：
1. 客户端问NameNode文件在哪里
2. NameNode返回Block列表及DataNode地址
3. 客户端**直接连DataNode读取**（不经过NameNode），优先读最近副本

**Hive表与HDFS关系**：Hive Metastore 记录表名→HDFS路径映射，Spark读Hive表时先查Metastore拿路径，再走HDFS读流程。

## Q47：布隆过滤器原理与误判率

### 原题
> 布隆过滤器底层原理是什么？为什么空间极小能判断海量数据？缺陷是什么，误判率怎么控制？

### 我的回答
位数组 + 多个hash函数，插入时多个hash计算位置全置1，查询时同样计算，位置全为1说明存在，有0说明不存在。以位数组极大减少空间。缺陷是数据增多后哈希碰撞导致误判，解决方式是重建布隆、优化hash函数、增加hash函数数量。误判率主要由hash函数决定。

### ✅ 评价
核心原理正确。补充几个重要细节。

### ✅ 更完善的回答
**核心特性**：只有**假阳性**（误判存在），没有**假阴性**（不会漏判）。"一定不存在"是精确的，"可能存在"才有误差。

**空间极小原因**：每个元素只占 k 个 bit 位，不存储完整数据。百亿URL用几GB内存即可。

**误判率由三因素决定**：
- 位数组大小 m：m越大碰撞概率越低
- hash函数数量 k：有最优值 `k = (m/n) × ln2`，太少或太多都会提高误判率
- 已插入元素数量 n：n越多位数组越密，误判率越高

**缺陷**：
1. 有误判率（假阳性）
2. **不支持删除**：清0某位可能影响其他元素，这是最核心的缺陷
3. 数据量增大后需要重建

## Q46：Spark 数据倾斜

### 原题
> 大表 join 大表时什么是数据倾斜？你们场景里可能在哪里出现？有哪些解决方案？

### 我的回答
数据集中在几台机器上，其他机器没有这些数据。解决是减少执行器数量。

### ⚠️ 回答缺陷
- **定义不准确**：倾斜是数据集中在少数**分区/Task**，不是机器
- **解决方案说反了**：应该打散数据增加并行度，不是减少执行器

### ✅ 更完善的回答
**数据倾斜**：Shuffle 后大量数据分配到少数 Task，这些 Task 处理时间远超其他 Task，整个 Stage 被拖死。根本原因是某些 key 数据量远大于其他 key（如热门域名 vs 小站点）。

**你们场景触发点**：按 domain 做 join key 时，百度/淘宝等大站数据量是小站千倍，join 时该 key 的 Task 极慢。

**解决方案**：
1. **Map Join（Broadcast Join）**：小表广播，不发生Shuffle，根本上避免倾斜
2. **加盐打散（Salting）**：倾斜key加随机前缀拆成多个Task并行，另一表复制对应份数，join后去盐聚合
3. **过滤大key单独处理**：识别超大key单独处理后union回主流程
4. **提高并行度**：调大`spark.sql.shuffle.partitions`（治标不治本）
5. **AQE（Spark 3.0+）**：自动检测倾斜分区并拆分，无需手动干预

## Q67：JDK 动态代理 vs CGLIB（薄弱点二次补考）

### 原题
> Spring AOP 在对一个类创建代理时，什么情况下用 JDK 动态代理？什么情况下用 CGLIB？两者底层实现分别是什么？

### 我的回答
当需要代理的类可以通过继承创建子类时使用 JDK 动态代理，如果要代理的类实现了接口，使用 CGLIB。JDK 通过继承相同父类重写父类方法实现，CGLIB 通过实现相同接口实现。

### ❌ 二次答错（核心方向仍然反了）
这是该知识点第二次答错，JDK 和 CGLIB 的触发条件与底层原理完全说反。

### ✅ 更完善的回答

| | JDK 动态代理 | CGLIB |
|---|---|---|
| **触发条件** | 目标类**实现了接口** | 目标类**没有实现接口** |
| **底层原理** | `java.lang.reflect.Proxy` 生成实现**相同接口**的代理类，通过 `InvocationHandler` 反射调用 | ASM 字节码框架，运行时**生成目标类的子类**，重写父类方法插入增强逻辑 |
| **核心限制** | 只能代理接口方法 | `final` 类和 `final` 方法无法代理 |

**记忆口诀**：JDK = 接口（J对J）；CGLIB = Child子类继承（C创造Child）

**补充**：Spring Boot 2.x 后默认强制使用 CGLIB，即使类有接口也用 CGLIB，除非配置 `spring.aop.proxy-target-class=false`。

## Q69：Spring 三级缓存循环依赖（联动追问）

## Q71：ConcurrentHashMap JDK8 原理

### 原题
> JDK 8 的 ConcurrentHashMap 底层结构？怎么实现线程安全？与 JDK 7 分段锁相比有什么改进？

### 我的回答
数组+链表+红黑树。线程安全通过：数组修改用 CAS，变成链表/红黑树时在头节点加 synchronized 锁再 CAS 修改节点。JDK7 对整个段加锁，并发能力低；JDK8 对头节点加锁，64个槽可同时并发64。

### ✅ 评价
核心全部答到，CAS + synchronized 头节点的组合策略表述准确。

### ✅ 更完善的回答

**两种策略组合**：
- 槽位为空 → CAS 直接写入（无锁）
- 槽位有节点 → `synchronized(头节点)` 加锁操作链表/红黑树
- **读取完全无锁**：Node 的 `val` 和 `next` 均为 `volatile`

| | JDK 7 | JDK 8 |
|---|---|---|
| 锁粒度 | Segment（默认16段，ReentrantLock） | 单个桶头节点（synchronized） |
| 最大并发 | 16 | 数组容量（默认16，可更高） |
| 结构 | 两层数组 | 一层数组 |

**额外改进**：扩容时多线程协同迁移（`ForwardingNode` 标记已迁移桶，其他线程帮忙迁移其他桶）。

## Q72：HTTPS TLS 握手流程

### 原题
> Sitemap 爬虫抓取 HTTPS 站点，从 TCP 建立到第一个 HTTP 请求发出，经历哪些步骤？TLS 握手做了什么？

### 我的回答
TCP 三次握手后进行 TLS 握手。客户端发客户端随机数，服务端响应服务端随机数+客户端随机数+1 及密码套件、TLS版本；用两个随机数计算椭圆曲线参数；携带服务端 CA 证书，客户端本地验证证书真实性；第三次发送用密码套件加密的消息，服务端解密成功后第四次握手可携带数据。

### ⚠️ 回答缺陷
- "服务端随机数+客户端随机数+1" 是 TCP ACK 序号概念混入了，TLS 里没有这个
- CA 证书验证不是"对比本地缓存"，而是用本地根证书的公钥逐级验证证书链签名
- 会话密钥推导三要素（C_random + S_random + Pre-Master Secret）没说清楚

### ✅ 更完善的回答（TLS 1.2）

```
① Client Hello：C_random + 支持的TLS版本 + 密码套件列表
② Server Hello + Certificate + ServerKeyExchange：
   S_random + 选定密码套件 + CA证书 + ECDHE服务端公钥
③ Client：验证证书链签名 → 生成Pre-Master Secret → 推导会话密钥
   发送 ClientKeyExchange + Finished（加密握手摘要）
④ Server：确认密钥一致，Finished → 开始对称加密通信
```

**会话密钥** = C_random + S_random + Pre-Master Secret 三者推导，非单一来源。

**TLS 1.3 改进**：2-RTT → 1-RTT，Server Hello 直接带 ECDHE 参数，客户端立刻推导密钥，下一包即可携带加密数据。

## Q73：虚拟内存与缺页中断

### 原题
> 进程虚拟地址空间怎么映射到物理内存？什么是缺页中断？JVM 堆内存申请时会触发缺页中断吗？

### 我的回答
通过页表记录虚拟地址和物理内存的映射关系。缺页中断是查询的数据不在当前页表中，需要重新去查询其他页表。JVM 不会触发缺页中断，会申请一块连续内存空间。

### ⚠️ 回答缺陷
- 缺页中断定义说成"查询其他页表"，那是 **TLB Miss**，不是缺页中断
- JVM 结论反了：**会触发缺页中断**（OS 延迟分配物理内存，首次写入才触发）

### ✅ 更完善的回答

**TLB Miss vs 缺页中断**：
- TLB Miss：TLB 未命中，查多级页表，找到映射 → 不触发中断
- **缺页中断（Page Fault）**：页表中根本无映射，OS 介入从磁盘加载页到物理内存，代价大

**JVM 堆与缺页中断**：
- `mmap` 申请虚拟地址，OS **不立刻分配物理内存**（延迟分配）
- 首次写入某页时触发缺页中断，OS 才分配物理页
- 所以 `-Xmx8g` 启动时不占用 8G 物理内存
- 生产优化：`-XX:+AlwaysPreTouch` 启动时预触发所有缺页中断，避免业务高峰期延迟抖动（美团/字节线上常用）

## Q74：YARN 三组件与 Spark 任务提交流程

### 原题
> YARN 的 ResourceManager、NodeManager、ApplicationMaster 分别负责什么？Spark Job 从提交到第一个 Task 执行经历哪些步骤？

### 我的回答
不知道。

### ✅ 知识点

| 组件 | 职责 |
|------|------|
| ResourceManager（RM） | 全局资源调度，掌管集群 CPU/内存总量，决定资源分给谁 |
| NodeManager（NM） | 每台机器的代理，向 RM 汇报本机资源，启动/管理 Container |

⑦ 全部完成，AM 通知 RM 释放资源

**关键记忆**：RM 管资源分配，AM(Driver) 管任务调度，Container 是 CPU+内存的资源封装。

- "保存临时表再比对"不是大表 join 的优化方案

### ✅ 更完善的回答

**问题根因**：默认 Shuffle Hash Join，1亿行大表按 join key 重新分区，大量网络 IO + 磁盘溢写，代价极高。

**最优解：Broadcast Join**
```sql
SELECT /*+ BROADCAST(b) */ d.* FROM domain_table d
LEFT JOIN blacklist b ON d.domain = b.domain
-- 或配置：spark.sql.autoBroadcastJoinThreshold = 50MB
```
将 10万行小表广播到每个 Executor 内存，大表本地直接查哈希表过滤，**完全消除 Shuffle**。

| | Shuffle Join | Broadcast Join |
|---|---|---|
| 网络传输 | 全部数据重分区 | 只广播小表一次 |
| 适用 | 两张大表 | 一大一小 |

**补充方案**：黑名单更新频繁时，可用**布隆过滤器预过滤**减少 join 数据量（与 Sitemap 项目布隆过滤器场景相同）。

## Q76：飞书文档协同编辑高写入量设计（场景题）

### 原题
> 飞书文档高峰期 5000 次/秒写请求，数据库最多承受 500 QPS，如何设计写入链路保证系统稳定？

### 我的回答
限流控制 → 数据库集群分片+主从 → Redis 缓存缓解 DB 压力先写 Redis 再异步同步 MySQL → 发现异步双删在高频写场景失效 → 改为把 Redis 当 DB，用 Canal 监听 Redis binlog 同步 MQ 再写 MySQL。

### ⚠️ 关键错误
**Canal 监听的是 MySQL binlog，Redis 没有 binlog。** Canal 是 MySQL → 下游的同步工具，不能监听 Redis。

### ✅ 更完善的回答

**核心方案：MQ 做写缓冲 + 合并写入**

| 层级 | 组件 | 职责 |
|------|------|------|
| 接入层 | 令牌桶限流 | 防突发打穿 |
| 缓冲层 | Kafka | 接收 5000 QPS（Kafka 百万级无压力） |
| 热数据层 | Redis | 存文档最新状态，读请求直接命中 |
| 消费层 | Consumer + 合并写入 | 按 doc_id 聚合时间窗口内多次修改，只取最新状态写 DB |
| 存储层 | MySQL + 按 doc_id 分片 | 实际落库 QPS 远低于 500 |
| 同步层 | Canal 监听 MySQL binlog | 同步到 ES/数仓等下游 |

**合并写入是关键**：同一文档 1 秒 100 次编辑 → 只写最终状态 → 实际落库 QPS 可压缩 10x 以上。

**Canal 正确用法**：MySQL binlog → Kafka → ES/数仓，是 DB 到下游的单向同步，不是 Redis → DB。

## Q77：TCP 四次挥手 + TIME_WAIT（字节飞书方向）

### 原题
> TCP 为什么需要四次挥手？TIME_WAIT 状态是什么，为什么等 2MSL？

### 我的回答
四次挥手：客户端发 FIN，服务端回 ACK，服务端还有数据没发完继续发，发完再发 FIN，客户端回 ACK 断开。TIME_WAIT 是服务端发 FIN 后进入的状态，超过 2MSL 没收到 ACK 就默认断开，2MSL 是请求来回的时间。

### ⚠️ 回答缺陷
- **TIME_WAIT 主体说反了**：是**主动关闭方（客户端）**在发出最后一个 ACK 后进入 TIME_WAIT，不是服务端
- 2MSL 原因只说了一个，缺少第二个（防旧包污染新连接）

### ✅ 更完善的回答

**四次 vs 三次**：三次握手时 SYN+ACK 可合并；四次挥手时服务端必须先单独回 ACK（还有数据未发完），等发完再发 FIN，不能合并，故四次。

**TIME_WAIT = 主动关闭方（客户端）发出最后 ACK 后的等待状态**

**2MSL 两个原因**：
1. 最后一个 ACK 可能丢失 → 服务端重发 FIN → 客户端重传 ACK（需要一来一回 2MSL）
2. 确保本次连接所有旧数据包在网络中彻底消亡 → 防止新连接收到旧包造成数据错乱

**工程问题（字节高频）**：高并发短连接会堆积大量 TIME_WAIT 占用端口。解法：`tcp_tw_reuse` 复用端口、长连接复用。

## Q78：Java 内存模型 JMM + 指令重排序（字节飞书方向）

### 原题
> JMM 规定了什么？happens-before 是什么？代码中 ready=true 在 data=42 之后，线程B 可能打印 0 吗？

### 我的回答
JMM 规定工作线程从主内存 copy 数据作缓存，不直接修改主存，执行结束后刷新。volatile 通过内存屏障强制刷新。代码有问题，但不一定打印0，因为 B 可能先执行 ready=false 不打印。

### ⚠️ 回答缺陷
- JMM 只说了可见性，**漏掉了指令重排序**（这才是本题核心考点）
- 没答出"可以打印0"的根本原因：A 的 `ready=true` 可能被重排到 `data=42` 之前执行
- happens-before 原则未解释

### ✅ 更完善的回答

**JMM 规定两件事**：
1. **可见性**：工作内存缓存主内存副本，修改不立即对其他线程可见
2. **有序性**：编译器/CPU 会重排序指令（JMM 允许，除非有 happens-before 约束）

**指令重排序导致打印 0 的场景**：
```
线程A 实际执行顺序（重排后）：
  ready = true   ← 被提前
  data = 42      ← 被延后

线程B：if(ready) → true → 打印 data → 打印 0 ！
```

**修复**：`volatile boolean ready` — volatile 写禁止与之前普通写重排序，保证 `data=42` 一定先于 `ready=true` 对外可见。

**happens-before**：操作A happens-before 操作B，则A的结果对B可见且顺序在B之前。volatile写→读、锁释放→加锁、thread.start/join 等都能建立 happens-before 关系。

## Q79：G1 GC 原理 + Full GC 排查（字节飞书方向）

### 原题
> JVM 用什么垃圾回收器？G1 和 CMS 最大区别？线上频繁 Full GC 怎么排查？

### 我的回答
不知道。

### ✅ 知识点

**G1 vs CMS**：

| | CMS | G1 |
|---|---|---|
| 内存划分 | 物理分代（固定 Young/Old） | 逻辑分代（等大 Region 动态充当各代） |
| 回收方式 | 只回收 Old 区 | 优先回收垃圾最多的 Region（Garbage First） |
| 内存碎片 | 有（标记-清除） | 无（复制算法） |
| 停顿控制 | 无法精确控制 | `-XX:MaxGCPauseMillis` 设置目标停顿时间 |
| 适用 | 4G 以下堆 | 大堆（4G+），JDK9 默认 |

**Full GC 排查**：
1. `jstat -gcutil <pid> 1000` 看各区占用率和 FGC 增速
2. 看 GC 日志触发原因：
   - Old 区打满 → 内存泄漏 → `jmap -dump` + MAT 分析
   - Metaspace 打满 → 动态代理/CGLIB 类加载过多 → 调大 `-XX:MaxMetaspaceSize`
   - 大对象直接进 Old → 调大 `G1HeapRegionSize`
3. G1 关键参数：`-XX:MaxGCPauseMillis=200`、`-XX:InitiatingHeapOccupancyPercent=45`、`-XX:+AlwaysPreTouch`

## Q80：AQS 原理 + ReentrantLock 挂起唤醒机制

### 原题
> AQS 的 state 和 CLH 队列分别是什么？线程抢锁失败后怎么被挂起和唤醒？

### 我的回答
state 标记线程是否获取到锁，大于1记录重入次数，释放时-1到0表示完全释放。CLH 队列存放抢锁失败的线程，封装成 Node 放队尾排队，前一个节点释放锁时唤醒。

### ✅ 评价
核心答到了，state 和 CLH 队列描述正确。缺少挂起和唤醒的具体机制。

### ✅ 更完善的回答

**抢锁失败完整流程**：
1. CAS(state, 0→1) 失败
2. 封装成 Node 插入 CLH 队列尾部（CAS 保证线程安全）
3. 若前驱是 head 节点，再自旋尝试一次
4. 失败 → `LockSupport.park(this)` 挂起（OS 级阻塞，不占 CPU）

**释放锁唤醒流程**：
1. state - 1，到 0 完全释放
2. 取 CLH 队列 head 的 next 节点
3. `LockSupport.unpark(next.thread)` 唤醒
4. 被唤醒线程从 park 处继续，重新 CAS 抢锁

**补充**：AQS CLH 队列是**双向链表**（有 prev/next），方便取消等待时删除中间节点。state 修改全程用 CAS，无锁。

## Q81：ReentrantLock vs synchronized 选型

### 原题
> 实际开发中怎么选择？ReentrantLock 有哪些 synchronized 没有的能力？

### 我的回答
一般选 synchronized，代码复杂度低，不需要手动释放，JDK8 后锁升级机制在低竞争场景性能好。ReentrantLock 有公平锁/非公平锁，有 Condition 实现线程通信，synchronized 需要用 await/join 通信。

### ⚠️ 小纠错
synchronized 配套的是 `Object.wait()` / `Object.notify()`，不是 await（那是 Condition 的方法）和 join（那是等待线程结束）。

### ✅ 更完善的回答

**ReentrantLock 独有能力**：

| 能力 | ReentrantLock | synchronized |
|------|--------------|--------------|
| 公平锁 | ✅ `new ReentrantLock(true)` | ❌ |
| 可中断等待 | ✅ `lockInterruptibly()` | ❌ |
| 超时抢锁 | ✅ `tryLock(timeout)` | ❌ |
| 多条件变量 | ✅ 多个 `Condition` | ❌ 只有 wait/notify |

**选型原则**：默认 synchronized；需要超时/可中断/公平/多条件变量时才换 ReentrantLock。

### 追问：Schema 超 token 怎么处理？

**我的回答**：
建立分层索引结构（类似意图树）：DB 级 → Table 级，进行渐进式披露。先识别大方向命中哪个 DB，再在 DB 内进一步识别相关表。同时加一层兜底全局搜索，两者结果做二次精排，避免意图识别错误漏掉相关表。

**✅ 评价**：优秀。把 RAG 意图树思路迁移到 Schema 发现，与工业界 Hierarchical Schema Linking 方案高度吻合。

**✅ 更完善的表述**：

| 层级 | 内容 | 粒度 |
|------|------|------|
| DB 路由 | 向量检索 DB 级语义描述，命中 1~2 个 DB | 粗分 |
| Table 路由 | 在命中 DB 内检索最相关 2~5 张表（带字段注释） | 精分 |
| 兜底层 | 意图置信度低时触发全局 BM25 关键词检索 | 兜底 |
| 精排 | 向量路由 + BM25 结果合并 Re-rank，取 Top-K 注入 Prompt | 融合 |
