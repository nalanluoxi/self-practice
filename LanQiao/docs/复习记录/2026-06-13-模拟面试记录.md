## Q88：RAG 召回率低排查（场景题 · 百度/银河驿站方向）

### 原题
> 智析RAG 系统上线后，用户反馈某些问题明明文档里有答案，但系统总是回答"未找到相关信息"或者给出错误内容。你作为开发者，会从哪几个环节排查这个"召回率低"的问题？每个环节你会怎么定位？

### 我的回答
检索链路全链路打点监控。从用户查询输入开始记录：语义分析/错误词判断/短对话短路判断；提示词优化模板记录；意图树匹配结果；意图树绑定知识库是否正确；意图检索+全局检索出的文档列表，是否包含目标文档；rerank精排结果是否遵循意图检索优先原则。知识库质量层面：分块策略是否符合预期（避免语义割裂，按段落/句号等语义标识切分，保留上下文窗口）；元数据补充（Spring AI metadata enhancer：对chunk内容提炼、上一个/下一个文档提炼，解决分割导致的语义割裂）。

### ✅ 评价
回答有相当深度，明显结合自己系统真实经验。五个维度都覆盖（查询输入→意图树→检索→精排→入库质量）。Spring AI metadata enhancer具体技术点是加分项。

### ⚠️ 三个缺口
1. 没提 Embedding 模型本身的问题（领域专业词汇在通用模型向量距离天然远）
2. 相似度阈值太严没说（confidence-threshold=0.6，相关文档0.55就被过滤）
3. 没提 Query 改写/扩展（用户口语 vs 文档正式表述，HyDE假设文档生成）

### ✅ 更完善的回答（六层排查框架）

**召回率低 = 文档在库里但没被找到**

**第一层：入库验证**
- 检查 ingestion 流水线各节点日志（Fetch→Parse→Chunk→Index）
- 确认目标文档 chunk 真实存在于向量库，embedding 不为空

**第二层：Chunk 质量**
- 按语义切（段落/句号），不能硬截字数
- Spring AI metadata enricher：SummaryMetadataEnricher（补充上下文摘要）、KeywordMetadataEnricher（提取关键词）

**第三层：Embedding 模型**
- 查询和文档是否用同一个 embedding 模型
- 领域术语在通用模型的向量表示是否准确
- 验证：直接算目标 query 和目标 chunk 的余弦相似度

**第四层：检索配置**
- 相似度阈值太严：confidence-threshold=0.6，相关文档0.55被过滤
- Top-K 不够：答案在K之外
- 意图树路由错误：分错知识库，全局检索未触发

**第五层：Query 表示问题**
- Query Rewriting：LLM改写为更正式的检索词
- HyDE（Hypothetical Document Embeddings）：先生成假设答案，用假设答案向量检索，比原始query向量更接近真实文档

**第六层：全链路打点 + 黄金测试集**
- 每阶段记录：query → 意图识别结果 → chunk ID列表 → rerank排序 → 最终答案
- 人工标注50条"query→期望chunk"黄金测试集，定期量化每层召回率

**快速定位三步**：
```
Step 1: 直接算目标query和目标chunk相似度 → 判断Embedding问题 vs 检索配置问题
Step 2: 关闭相似度阈值过滤，看Top-20里有没有 → 判断阈值太严
Step 3: 看意图树命中节点和绑定知识库 → 判断路由问题
```

## Q89：数据血缘系统设计（场景题 · 小红书Dataverse方向）

### 原题
> 小红书 Dataverse 平台要实现"数据血缘追踪"：一张 Hive 结果表 T，你需要知道它的数据来自哪些源表、经过了哪些 SQL 转换任务。如果上游某张源表的某个分区数据异常，你如何快速找到所有受影响的下游表？整个血缘系统你会怎么设计？

### 我的回答
有美团SQL万象数据可视化平台经验，可以看到表库的上下游关系及绑定的Spark任务，从任务追溯列的计算逻辑和数据来源表。分区数据异常（数据量少/dt分区丢失）应排查对应的Spark生产任务：任务当天是否成功启动，原因是上游任务产出超时被kill了，还是任务队列资源紧张没有排到。

### ✅ 评价
有真实美团SQL万象平台经验，分区异常排查方向（任务没启动/上游超时/资源队列）非常接地气，是真实工程经验。

### ⚠️ 两个核心缺口
1. 没回答"如何设计"这个问题——题目问从零设计血缘系统，描述的是使用现有平台
2. 影响范围扩散分析没说——上游异常后，如何自动找到所有下游受影响表（DAG BFS/DFS图遍历）

### ✅ 更完善的回答（血缘系统设计）

**第一步：血缘采集（两种方式结合）**

| 方式 | 原理 | 优缺点 |
|------|------|--------|
| 静态解析 | 解析SQL AST，提取INSERT INTO T SELECT...FROM A JOIN B的表依赖 | 不需运行覆盖全；复杂UDF可能解析不全 |
| 动态采集 | Spark QueryExecutionListener运行时钩子，捕获实际表读写 | 精准含UDF展开；只有跑过才有血缘 |

**第二步：血缘存储（有向无环图DAG）**
```
node表：table_id, db, table_name, owner
edge表：src_table_id, dst_table_id, task_id, column_mapping(JSON)
```
列级血缘：column_mapping记录{dst_col, src_col, src_table, expression}

**第三步：影响范围分析（核心）**
上游A表dt分区异常 → 对血缘DAG做BFS广度优先遍历：
```
A → B, C → D, E
受影响集合：{B, C, D, E}
```
自动触发：告警推送各表owner + 依赖A的下游任务标记"上游异常建议暂停"

**第四步：数据质量监控联动**
- 行数规则：今天行数 < 昨天×0.8 → 触发异常
- 分区存在性：dt=今天分区是否按时产出
- 异常触发 → 查血缘图BFS找下游 → 通知owner

**排查思路在系统中的位置：**
```
分区异常告警 → 血缘反查上游任务实例
  ├── 任务没启动：资源队列满/依赖未就绪
  ├── 任务失败：OOM/数据倾斜/上游数据为空
  └── 任务成功但数据少：过滤逻辑变更/数据源问题
```

**一句话总结**：SQL静态解析建DAG，Spark Listener动态补全，邻接表存血缘，BFS做影响范围扩散，数据质量规则触发告警。

## Q90：Flink实时任务点赞数偏少排查（场景题 · 小红书/字节方向）

### 原题
> Flink实时任务消费Kafka用户行为事件，统计每个用户当天点赞数写入Redis。运行一周后，某些用户点赞数比实际少。怎么排查？

### 我的回答
先看是每天都有还是偶发，查变更记录（限流/回溯MQ/机器下线）。全链路打点找数据量断层。排查：OOM、Redis并发控制拒绝请求、Kafka生产者确认机制、Kafka消费者offset提交（手动/自动，是否提前提交）、Redis QPS/连接数/限流记录。

### ✅ 评价
排查思路完整，Kafka offset提前提交是最高频真实故障原因，抓得准。

### ⚠️ 三个缺口
1. Flink Checkpoint机制没说（任务重启从哪里恢复决定数据是否丢失）
2. 每天凌晨重启的offset问题没分析（latest会丢0点到启动这段数据）
3. Flink时间语义没说（EventTime+watermark配置不当会丢晚到数据）

### ✅ 更完善的回答（五层排查）

**第一层：确认问题范围**
每天都少 vs 偶发；所有用户 vs 部分用户（部分用户→特定Kafka分区问题）；查变更记录

**第二层：Flink任务数据完整性**
- Checkpoint：关闭或间隔太长 → 崩溃重启后中间数据丢失
- 每天凌晨重启的offset：latest=丢0点到启动这段；earliest=无持久化offset则重复消费
- 最佳实践：开启Checkpoint + Flink Kafka Connector托管offset → 精确一次语义

**第三层：Kafka消费语义（已答到）**
- 先commit offset再处理 → 崩溃后数据跳过丢失
- 先处理再commit → 崩溃重复消费但不丢

**第四层：Redis写入并发问题**
- INCR：原子操作，安全 ✓
- GET→+1→SET：非原子，并发覆盖导致少计 ✗
- 多Flink Task并行写同一userId时GET+SET会丢数据

**第五层：Redis侧（已答到）**
- QPS超限写入被拒，无重试直接跳过
- Key TTL：凌晨0点key过期被清零

**排查优先级：**
```
① Flink日志：崩溃重启记录 + Checkpoint是否开启
② Kafka consumer group offset：凌晨重启从哪里消费
③ Redis写入命令：INCR还是GET+SET
④ Redis监控：写入失败率、连接数、key TTL
⑤ 全链路打点：Kafka消费数 vs Redis写入成功数
```

### 我的回答

## Q93：Full GC频繁 + Old区不降排查（字节飞书方向）

### 原题
> 线上Java服务频繁Full GC，每次GC后老年代内存没有明显下降，Old区一直在涨。第一步做什么？怎么定位根因？

### 我的回答
考虑内存泄漏，大对象没有及时回收。

### ⚠️ 评价
方向对但太简略，没有具体工具和步骤，面试会被追问。

### ✅ 完整排查流程（五步）

**第一步：jstat确认是否内存泄漏**
```bash
jstat -gcutil <pid> 1000
# 看O（Old区）：每次GC后不降反涨 → 内存泄漏
# GC后回到正常水位 → 正常，调参即可
```

**第二步：导出堆快照**
```bash
jmap -dump:live,format=b,file=heap.hprof <pid>
```

**第三步：MAT分析**
- Leak Suspects Report：自动分析泄漏嫌疑
- Dominator Tree：按Retained Heap排序找大对象
- Path to GC Root：找谁持有这个对象导致无法回收

**第四步：常见泄漏场景**
| 场景 | 原因 |
|------|------|
| 静态集合无限增长 | static Map只加不删，缓存没有上限 |
| ThreadLocal未remove | 线程池复用，请求结束没调remove() |
| 监听器未注销 | 注册listener但对象销毁时没反注册 |
| Metaspace打满 | CGLIB动态代理类无限生成 |

**你们系统高危点**：
- PlaywrightDownLoader缓存Map只加不清理
- 线程池无界队列堆积任务对象
- ThreadLocal持有PlaywrightDownLoader未remove

**排查三板斧**：jstat确认趋势 → jmap导出堆 → MAT找持有链

## Q94：Linux CPU低+Load高排查（字节飞书方向）

### 原题
> 8核机器，CPU使用率20%，load average=15，说明什么？怎么排查？

### 我的回答
CPU利用率只有20%说明资源有空间提升，load average 15不清楚说明什么。

### ⚠️ 核心概念缺失：不了解load average含义

### ✅ 完整知识点

**Load average ≠ CPU使用率**

```
Load average = 正在用CPU的进程数
             + 等待CPU（可运行）的进程数
             + 等待IO（D状态，不可中断睡眠）的进程数
```

**此场景结论**：CPU低+Load高 = 大量进程卡在D状态等待IO → **IO瓶颈，不是CPU瓶颈**

**排查步骤**：
1. `iostat -x 1`：看磁盘IO，%util接近100%=磁盘打满
2. `iotop`：看哪个进程IO最高
3. `vmstat 1`：看swap（si/so不为0=内存换页IO暴增）
4. `ps -eo pid,stat,comm | grep ' D'`：确认D状态进程
5. `dmesg | tail -50`：内核IO错误日志

**爬虫系统高危点**：
- 日志写磁盘太频繁 → 异步写日志
- S3上传阻塞主线程 → 异步上传
- Chrome进程占内存太大触发Swap → 减小downloadThreadNum

**一句话**：CPU低+Load高=等IO；CPU高+Load高=在干活。

## Q95：Kafka消费者数量上限 + Partition设计（项目深挖）

### 原题
> Kafka consumer group消费者数量上限由什么决定？400台消费者但只有10个partition会发生什么？

### 我的回答
消费者上限由partition数决定。一个消费者可消费多个partition，但一个partition最多只能被一个消费者消费（避免重复消费）。400台消费者10个partition→只有10台分配到partition在消费，其余空闲等待，故障/新成员加入触发rebalance重新分配，最终最多10台分配。

### ✅ 评价
核心全部答对，答得扎实。

### ✅ 补充细节
**为什么这样设计**：同一partition内消息有序，两个消费者同消费一个partition会破坏顺序。

**工程含义**：想增加消费能力 → 光加机器没用 → 必须同时增加partition数，建议partition数≥消费者数。

**rebalance三种触发条件**：
1. 消费者数量变化（新加入/宕机/心跳超时）
2. partition数量变化
3. 订阅关系变化

**rebalance代价**：期间整个consumer group停止消费（Stop The World），频繁rebalance会造成消息积压。

## Q96：SynchronousQueue背压设计选型（项目深挖·方案质疑风格）

### 原题
> SynchronousQueue没有缓冲区，高并发会不会成为瓶颈？为什么不用LinkedBlockingQueue？

### 我的回答
系统性排除：无界队列→OOM（千万级任务）；有界队列→很快打满走拒绝策略，推迟问题；所以不用队列缓冲。拒绝策略：丢弃=丢消息❌；CallerRunsPolicy=阻塞拉消息线程，线程池有2个空闲但消费者线程在执行下载，无法感知空闲❌；最终选AbortPolicy+sleep轮询检查线程池空闲+异常捕获返回MQ消费失败→重投递。检查和投递非原子，AbortPolicy是保底机制。

### ✅ 评价
今天最好的回答！完整技术决策链路，每步都有清晰业务理由。

### ✅ 补充：专业叫法"背压（Back Pressure）"
主消费线程sleep等待线程池空闲 = 反压机制：下游（线程池）处理不过来 → 反向施压上游（拉消息）慢下来，整个链路速度自动匹配消费能力，不OOM也不丢消息。

**三个设计优势**：
1. 职责分离：拉消息和下载执行完全隔离
2. 天然背压：线程池满→sleep→拉消息变慢→MQ不积压在本地
3. 消息不丢：AbortPolicy抛异常→返回MQ消费失败→重投递，不需要本地重试逻辑

## Q97：三级限流迁移到RAG系统（场景延伸题）

### 原题
> 美团三级限流迁移到RAG系统，"用户每分钟最多调用LLM 10次"，哪些复用，哪些需要改？

### 我的回答

### ⚠️ 三个缺口

2. 固定窗口边界突刺问题没说

### ✅ 完整方案

**可复用**：集群限流（Rhino）+ 单机限流（本地计数器），逻辑完全一样

**需要改造**：用户维度限流
- 美团：站点维度+本地计数器（单机有效）
- RAG：用户维度+Redis分布式计数（多实例部署必须用Redis）

**方案一：Redis INCR+TTL（固定窗口）**
```lua
key = "rate:user:{userId}:{minute_bucket}"
INCR key; if count==1 then EXPIRE 60; if count>10 return限流
```
缺点：边界突刺（59s发10次+61s发10次=2秒20次）

**方案二：Redis ZSET滑动窗口（@ChatRateLimit用的）**
```lua
ZREMRANGEBYSCORE key 0 (now-60s)  -- 清过期
ZCARD key >= 10 → 限流
ZADD key now now → 记录
```
优点：任意60秒内严格不超10次，无边界突刺

**LLM场景额外考虑：双维度限流**
- 请求次数（10次/分钟）+Token消耗（N token/分钟）
- 按请求数限流对大Token请求约束不足

**加分项**：RAG系统@ChatRateLimit = Redis ZSET+Lua+Pub/Sub排队，是对美团限流经验的复用和升级。
