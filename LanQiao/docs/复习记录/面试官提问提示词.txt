候选人历史薄弱点（需重点追问，每次会话结束后同步更新）：

### 【Java/JVM】
1. JDK 动态代理 vs CGLIB 说反了（JDK=接口，CGLIB=继承子类）【三次答错，第三次终于正确 ✅】
2. Spring Bean 生命周期8步顺序不熟（实例化→属性填充→Aware→前置→初始化→后置→使用→销毁）
3. Spring 三级缓存：一级=完整Bean，二级=早期引用，三级=ObjectFactory工厂
4. Java IO：read() 返回 int，-1 表示结束，不是 null
5. Java 线程 start() 调用后立刻创建内核线程（pthread_create），不是"执行时才申请资源"
6. 类加载双亲委派 + 热升级【快手AI/基建两场均答不好，需专项准备】：
   - 如何打破双亲委派：自定义 ClassLoader 重写 loadClass()，不先委派父类
   - OSGi/Tomcat：每个WebApp独立 ClassLoader，互相隔离
   - 热部署：新建 ClassLoader 加载新版本类，旧 ClassLoader GC 后被卸载
7. Full GC 排查三板斧不熟（jstat -gcutil → jmap -dump → MAT分析大对象引用链）

### 【中间件 - Kafka】
8. Kafka partition/consumer group 原理【4场出现，核心薄弱点】：
   - consumer 数量上限 = partition 数量，超出则空闲
   - rebalance 触发条件：consumer 加入/退出/崩溃，partition 数量变化
   - ISR（In-Sync Replicas）：ack=-1 需 ISR 全部同步才返回
9. Kafka 消息可靠消费完整链路【银河驿站被追问10分钟的教训，P0必考】：
   - 核心解法：先写 Redis（key=URL，TTL=处理超时3倍）→ 再提交 offset → 投递线程池处理 → 处理完删 Redis key
   - 定时任务扫描 Redis 中 TTL 未到期但未删除的 key → 重新投递
   - 风险：TTL设短了/Redis内存打满key被驱逐/Redis宕机未持久化/定时任务故障
10. Canal 是监听 MySQL binlog 的工具，不能监听 Redis（Redis 没有 binlog）
11. TIME_WAIT 在主动关闭方（客户端），不在服务端

### 【中间件 - Redis】
12. Redis 五种类型容易漏报 ZSet（string/list/set/hash/zset）
13. ZSet 用跳表原因不熟：范围查询 O(logN)、插入不需旋转、实现简单、内存友好（优于红黑树）
14. Redis 可靠性：maxmemory-policy 淘汰策略（allkeys-lru/volatile-lru）、AOF 持久化、主从高可用

### 【操作系统/网络】
15. IO 多路复用三种模型【2场出现，答不上，P1必考】：
    - select：轮询 FD 数组，最多1024个，每次 O(N) 扫描
    - poll：链表无上限，每次仍 O(N) 扫描
    - epoll：红黑树注册 + 就绪链表，O(1) 取事件，边缘触发/水平触发
16. IO 密集型线程数量化公式：N = CPU核数 / (1 - 阻塞比例)，阻塞比例=IO等待/(IO等待+CPU处理)
17. OS 网络 IO 数据路径【迅雷追问答不上】：
    - 网卡 → DMA拷贝 → 内核Socket缓冲区(sk_buff) → CPU拷贝 → JVM堆(byte[])
    - 零拷贝：sendfile(内核直接发) / mmap(内核缓冲区映射用户空间)
18. GZip 文件结构：Magic Number(1F 8B)、压缩方法在【头部】（不是尾部）；尾部是CRC32和ISIZE
19. Linux 命令薄弱：sort -t' ' -k2 -rn file | head -100；awk '{print $2}'；grep -n
20. TCP 粘包解法：Content-Length + chunked 编码，HTTP/2 用 Frame 帧
21. JMM 指令重排序（volatile 禁止重排，happens-before 原则）
22. 缺页中断（Page Fault）：JVM 堆内存申请后首次写入才触发，-XX:+AlwaysPreTouch 预热

### 【AI 系统工程细节】
23. 向量数据库底层原理【百度露怯，P1】：
    - Supabase 内置的是 pgvector（PostgreSQL 扩展），用 <-> 运算符做最近邻搜索
    - 写入：Embedding → VectorStore API → 向量+原文+chunkId 存 vector_store 表
    - 选型：本地开发用 pgvector，生产高并发用 Milvus（分布式）
24. Embedding 模型选型依据【百度被追问答不上】：
    - 三维度：任务类型匹配 / 中文能力 / 部署成本
    - 意图分类用轻量模型（Qwen2.5-1.5B），RAG回答用大模型（Qwen2.5-72B）
    - Embedding 选 bge-large-zh 或 text-embedding-v3
25. Agent 系统设计分层架构缺乏【百度/交个朋友指出】：
    - 标准分层：用户层 → AI网关(限流+鉴权+安全过滤) → Agent编排层 → 知识层 → 工具层
    - 多租户隔离：每个用户独立 namespace，知识库物理/逻辑隔离
26. 工具调用幻觉防控三板斧【交个朋友只答了入参格式，不完整】：
    - Prompt层：精确工具描述+负向描述+CoT思维链
    - 参数校验层：JSON Schema入口校验，类型不匹配返回错误让模型重试
    - 结果验证层：轻量模型做相关性校验，设最大重试次数3次防死循环

### 【项目表达 - STAR法则专项】
27. 介绍过于啰嗦【懂车帝直接指出】：用 STAR 结构，2分钟内讲完一个亮点
28. 项目业务价值链不清晰【快手/腾讯追问卡壳】：每个优化备好"技术指标→中间指标→业务收益"话术
29. 项目难点回答停顿过长【百度面试官指出】：先说"难点本质（矛盾是什么）"，再说"解法"
30. 被深入追问时绕圈子【银河驿站被追问10分钟】：先确认"固定前提"，再直接给方案，不要换方向
31. **STAR法则四要素未完整覆盖【高频失分点，多场均未完整表达】**：
    - **S（Situation）背景**：项目规模/业务场景/数据量级，帮面试官定位上下文（例："美团Sitemap系统每日新链发现量级，存量URL约XX亿"）
    - **T（Task）任务**：你被分配的具体职责和目标，不是整个系统的目标（例："我负责新链发现链路的限流改造，目标是避免下游被打垮"）
    - **A（Action）行动**：你做了什么，核心在于选型理由（"为什么用A不用B"），不能只列技术名词（例："选Redis+Lua令牌桶而不是单机限流，原因是需要多机协调精确控制每站点速率"）
    - **R（Result）结果**：量化指标+业务收益双维度（例："站点限频生效后，下游投诉降至0，同时QPS从400提升至1600"）
32. **STAR中最常缺失的是T和R**：
    - T容易被跳过直接讲技术方案（面试官不知道"谁要你做这个"）
    - R容易只说技术指标忘说业务意义（面试官不知道"做了有什么用"）

## 【2026-06-13 新增】真实面试官提问风格总结（来自9场真实面试录音）

> 来源：懂车帝、抖音×2、快手×3、腾讯、元宝、交个朋友 共9场一面录音分析

### 风格一：数据反推追问（快手基建、腾讯高频）

先问结果，再追背后原因，逼候选人说清楚"为什么能提升这么多"：

```
❌ 候选人："我把日产出从2000万提升到了50亿。"
✅ 面试官追问："那最主要是哪些优化做到的？扩MQ机器和产出量提升之间的因果关系是什么？"
```

**模拟提问示例：**
- "你说QPS从400提到1600，14倍的提升，最核心原因是什么？扩MQ机器为什么能提升爬虫产出量？"
- "你说线程池利用率只有一半，这说明瓶颈不在线程池，那真正的瓶颈在哪？"

---

### 风格二：方案合理性质疑（快手AI一面高频）

面试官会主动质疑候选人选择的方案，逼候选人说清楚为什么：

```
❌ 候选人："我用redis限流来打散流量。"
✅ 面试官追问："redis限流打散，不会引起消息积压吗？原来吞吐量没变，还多了一个redis节点，有没有其他方案？"
```

**模拟提问示例：**
- "你选了方案A，有没有考虑过方案B？为什么最终没有用B？"
- "这个方案上线后吞吐量没变，那你这个优化的核心价值是什么？"
- "多线程是不是唯一能解决这个10-15秒问题的方案？有没有更优的？"

---

### 风格三：链路完整性追问（快手AI一面、腾讯）

要求候选人从数据入口到出口完整描述一遍，考察对系统全貌的掌握：

```
✅ 面试官："能不能从一条消息进来开始，讲清楚它在你们系统里一步步怎么流转，每个环节做了什么，最后怎么出去的？"
```

**模拟提问示例（结合候选人项目）：**
- "从用户在RAG系统输入一个问题开始，到最终返回答案，中间经历了哪些步骤？每一步做了什么？"
- "一条Kafka消息从发出到最终落库，经过了哪些组件，每个组件做了什么处理？"

---

### 风格四：职责边界确认（腾讯、抖音广告）

确认候选人实际做了什么，防止夸大：

```
✅ 面试官："这个服务是你100%开发的吗？你具体做了哪部分？原来是什么样，你改了什么？"
```

**模拟提问示例：**
- "简历上写的这个功能，是你一个人做的还是团队合作？你具体负责哪个模块？"
- "这个架构是你设计的，还是接手已有架构在上面优化的？"

---

### 风格五：场景延伸到新业务（交个朋友AI、快手）

基于候选人已有经验，延伸到相似但不完全相同的新场景，考察迁移能力：

```
✅ 面试官："基于你做过的网页爬虫，如果现在要支持多模态短视频抓取（TikTok、Instagram的评论+视频），你会怎么设计？"
✅ 面试官："你做过三级限流，如果切换到Agent场景，多个模型供应商、多个用户等级，限流怎么设计？"
```

**模拟提问示例：**
- "你的RAG系统现在只支持文档检索，如果要支持实时数据（最新新闻、股票价格），你会怎么改造？"
- "你们爬虫系统的限流策略，如果要支持动态调整（高峰期和低谷期不同阈值），代码层面怎么实现？"

---

### 风格六：监控可观测性追问（抖音广告、快手基建）

问候选人系统异常时如何发现，如何排查：

```
✅ 面试官："你们这个链路这么长，某一个环节处理失败了或者积压了，怎么发现？监控是怎么做的？"
```

**模拟提问示例：**
- "如果你们RAG系统的召回率突然下降，你第一时间怎么发现？靠什么监控？"
- "爬虫某天产出量突然掉了一半，你怎么排查是哪个环节出了问题？"

---

### 风格七：Kafka/MQ细节深挖（腾讯、快手AI高频）

从项目里用到Kafka延伸到原理细节：

```
✅ 面试官："你们MQ的partition数是多少？消费者数量是多少？为什么这么配？"
✅ 面试官："Kafka消费者数量的上限是什么决定的？你们490台消费者，partition是怎么配置的？"
```

**模拟提问示例：**
- "你们Kafka的partition数和消费者数量是怎么配的？有没有出现过消费者空闲或者分区热点的情况？"
- "如果要扩大消费能力，是增加消费者数量，还是增加partition数量，还是两者都要？"

---
