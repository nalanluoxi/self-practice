## Q98：Redis+Lua令牌桶1000万站点key问题（项目深挖）

### 原题
> Redis+Lua令牌桶站点限频，1000万站点就有1000万个key，会有什么问题？怎么解决？有没有更好方案？

### 我的回答
内存估算（200B/domain × 预估domain数量 = 总内存需求）；三层保护避免Redis被QPS打穿；容量规划+告警水位线+临时扩容；本地限流补充（不精确但低延迟）；本地粗过滤+Redis精确控制双层结合。

### ✅ 评价
非常全面，内存估算、容量规划、告警水位、本地vs分布式权衡全答到。

### ⚠️ 两个补充点
1. **Key TTL**：令牌桶key设24小时TTL，站点停投后自然清理，实际常驻key = 近24h活跃站点数
2. **Redis Cluster Hash Tag**：Lua脚本要求相关key在同一slot，用`rate:{domain}:token`固定slot

### ✅ 完整技术方案对比

| 方案 | 精度 | Redis压力 | 延迟 | 实现复杂度 | 适用场景 |
|------|------|---------|------|-----------|---------|
| Redis+Lua令牌桶 | 高（全局精确） | 高 | 有网络RTT | 低 | 中等流量，精确限速 |
| 纯本地限流 | 低（单机精度） | 无 | 极低 | 极低 | 粗粒度打散，快速保护 |
| 本地+定期同步Redis | 中（秒级误差） | 低 | 极低 | 中 | 高吞吐+近似全局限速 |
| Sentinel集群限流 | 高（全局精确） | 无 | 极低 | 低（开箱即用）| 生产推荐 |

**现代化改进**：引入Sentinel替换自写Lua脚本，获得可观测性+Token Server挂了自动降级本地限流的高可用能力。

## Q99：自适应Daemon线程限流响应速度问题（项目深挖）

### 原题
> Daemon线程每分钟检查线程池状态调整阈值，流量秒级变化，阈值调整太慢会发生什么？

### 我的回答
澄清是每秒检查；三层限流兜底作为硬上限；线程池满→while自旋等待（加锁保护）→实现背压不拉新消息。

### ✅ 评价
澄清频率正确，三层兜底+背压逻辑完整，方向正确。

### ⚠️ 两个深化点
1. while持锁自旋是忙等待，消耗CPU，sleep让出CPU更优
2. 没说更现代的方案

### ✅ 完整技术方案对比

**原始方案**：Daemon每秒轮询，线性±1调整阈值，while+sleep(50ms)背压

**替代A：Semaphore替代while自旋**
- semaphore.acquire()阻塞等待，OS级挂起，零CPU消耗，有空位立刻唤醒

**替代B：AIMD拥塞控制（类TCP）**
- 正常：阈值+1缓慢放松；拥塞（活跃率>90%或出现Rejected）：阈值÷2快速收紧
- 比线性-1快得多，避免突刺时收紧太慢

**替代C：Resilience4j**
- 开箱即用的RateLimiter+CircuitBreaker，自动熔断，无需手写Daemon线程

| 方案 | 响应速度 | CPU消耗 | 复杂度 |
|------|---------|---------|-------|
| Daemon轮询（原） | 秒级 | 低 | 低 |
| Semaphore | 毫秒级 | 极低 | 低 |
| AIMD | 毫秒级(÷2) | 低 | 中 |
| Resilience4j | 毫秒级 | 低 | 极低 |

## Q100：GZIPInputStream流式解压性能问题（项目深挖）

### 原题
> GZIPInputStream单线程串行解压，500MB的gzip会不会成为瓶颈？有没有并行解压方案？

### 我的回答
真正瓶颈是网络IO下载（10-15s），不是解压。线程池并行处理多个URL，每个URL独立线程解压，已是多线程并行。超大文件通过Content-Length预判，超阈值直接丢弃打点告警，防止OOM和超MQ消息大小限制。

### ✅ 评价
核心判断正确：瓶颈是网络IO不是解压。多线程并行+超大文件拦截两个设计点都答到。

### ✅ 补充技术深度

**为什么用流式解压（GZIPInputStream）而不是全量解压**：
- 全量：500MB压缩→2GB解压→全在内存，10线程并发=20GB，OOM
- 流式：边下边解边解析，内存只有当前chunk（几十KB），无论多大文件内存占用恒定

**超大文件阈值怎么定**：
- 约束1：MQ单条消息大小限制（Kafka默认1MB）
- 约束2：线程池内存水位（每线程最大数据 × 线程数 < 可用内存）
- 实践：设保守阈值（5MB）→上线观测丢弃率→统计4%→18%→阈值合理维持

**为什么不换更快的压缩算法**：
- 网站返回gzip，格式由对方决定，无法替换
- 内部传输可选LZ4（极快）或zstd（速度+压缩率均优于gzip）

**三板斧总结**：流式处理解决内存问题 + 多线程解决并发问题 + 超大文件早期拦截解决异常数据问题

## Q101：DSL规则引擎热更新线程安全（项目深挖）

### 原题
> Copy-on-Write+volatile热更新，窗口期有没有问题？Pattern存哪里？多线程并发读安全吗？

### 我的回答
① 窗口期：系统天级处理，业务允许短暂使用旧规则，下游有兜底过滤，可接受
② Pattern存List，遍历匹配，打点监控0.001-0.002ms/次，性能无影响
③ 线程安全：volatile List引用 + CoW（新建List→全部编译→替换引用），volatile的happens-before保证其他线程读到完整新List
④ 为什么不用synchronized：规则引擎是读多写少场景，加锁使高频读串行化，即使0.001ms单次也会积累成性能瓶颈；volatile+CoW实现无锁读，只有极低频的写时才创建新List

### ✅ 技术精确补充
volatile写 happens-before volatile读 = 安全发布（Safe Publication）
其他线程要么看到旧List（完整），要么看到新List（完整），永远不会看到半完成的List

## Q102：正则规则匹配O(N)优化方案（项目深挖）

### 原题
> 1000条规则List遍历，O(N)匹配，有没有办法优化到O(1)？

### 我的回答
当时0.001ms可接受，没有进一步优化。

### ✅ 完整优化方案

**方案一：正则合并|（最简单，推荐首选）**
```java
String combined = patterns.stream()
    .map(p -> "(?:" + p.pattern() + ")")
    .collect(Collectors.joining("|"));
Pattern bigPattern = Pattern.compile(combined);
bigPattern.matcher(url).find();  // 一次调用，NFA内部并行检查所有分支
```
时间复杂度：O(1)次调用，实现改动极小

**方案二：Aho-Corasick自动机**
- 适合关键词匹配（无复杂正则）
- 构建一次自动机，O(文本长度)扫描，与规则数无关
- "博彩词、色情词"场景最适合

**方案三：Bloom Filter预过滤**
- 99%正常URL → Bloom Filter一票否决 → O(1)跳过
- 1%可疑URL → 再跑完整正则 → O(N)
- 平均复杂度接近O(1)

| 方案 | 复杂度 | 适用 | 改动成本 |
|------|-------|------|---------|
| 原始遍历 | O(N) | 规则少 | 极低 |
| 正则合并 | O(1)调用 | 复杂正则 | 低 |
| Aho-Corasick | O(文本长) | 关键词 | 中 |
| Bloom Filter | 平均O(1) | 阴性率高 | 中 |

**推荐路径**：当前够用→规则增长→先试正则合并→关键词为主改Aho-Corasick

## Q103：三态熔断器状态转换细节（项目深挖）

### 原题
> OPEN→HALF_OPEN靠什么触发？探测失败怎么处理？10并发只放1个探测，其他9个怎么办？

### 我的回答
定时任务扫描超时的OPEN模型→改为HALF_OPEN队列；探测失败→回OPEN队列重置超时；其他请求走可用模型，模型全满→返回默认值让用户重试。

### ⚠️ 两个缺口
1. 定时任务是次优方案，更好是请求到来时惰性检查时间戳（零额外线程，响应及时）
2. HALF_OPEN并发控制：CAS(AtomicBoolean probeInFlight)保证只有1个探测线程，其他CAS失败→走备用

### ✅ 完整状态流转
```
CLOSED → (失败率>阈值) → OPEN → (冷却时间到+CAS) → HALF_OPEN
  ↑                                                      │
  └──────────(探测成功)─────────────────────────────────┘
                                  │
                             (探测失败)→ OPEN（重置冷却）
```

### ✅ ProbeStreamBridge（RAG系统特有）
SSE流式输出特殊处理：先缓冲前N个token确认无错误，再推给用户。
避免"已发送100个token后报错→用户看到半截回答"的问题。
探测阶段发现错误→静默切换备用模型，用户无感知。

### ✅ 惰性检查代码模式
```java
if (state == OPEN && now > openTimestamp + openDurationMs) {
    if (stateRef.compareAndSet(OPEN, HALF_OPEN)) {
        return doProbe(); // CAS成功才是唯一探测线程
    }
}
return fallback(); // CAS失败或未到冷却时间→走备用
```
