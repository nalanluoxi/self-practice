## Q1：CompletableFuture 多通道超时处理 + 兜底设计（智析RAG）

**问题：** 并行3个检索通道，一个超时怎么处理？高召回通道超时怎么权衡？

**候选人最终回答摘要：**
- 文档入库时同步写入 ES，建立倒排索引
- 正常路径：意图检索 + 向量检索并行，completeOnTimeout 兜住单通道超时，聚合非空结果进 Rerank
- 第一层兜底：聚合结果为空或置信度低时，切换 ES BM25 全文检索，结果交 Rerank 排序
- 第二层兜底：ES 结果置信度仍低 → 返回默认话术 + 触发人工介入告警
- 诚实说明初版未实现超时策略，以上是完善方向

**STAR 评分：**
| 维度 | 评分 | 说明 |
|------|------|------|
| S（背景）| ✅ | 意图检索+向量检索依赖外部服务，高并发时有超时风险 |
| T（任务）| ✅ | 保证检索链路不因单点失败返回空结果 |
| A（行动）| ✅ | 三层降级设计：聚合非空结果 → ES兜底 → 人工介入 |
| R（结果）| ❌ | 未量化，缺"用户侧空结果率"等指标 |

**关键知识点（本轮学习）：**
- `completeOnTimeout(defaultVal, t, unit)` → 超时返回默认值，不抛异常，适合降级
- `orTimeout(t, unit)` → 超时抛 TimeoutException，适合必须感知超时的场景
- 内存BM25 = 4张HashMap（倒排索引+词频+文档长度+文档存储），文档量小时可用
- 文档量持续增长 → 内存BM25不可持续 → 生产必须用 ES 或 PostgreSQL tsvector
- BM25 兜底核心价值：不依赖外部服务（ES是外部服务，不是真正兜底，是平行通道）
- 混合检索（Hybrid Search）= 向量检索 + BM25 同时跑 + RRF融合打分

**三层降级完整设计：**
```
正常：向量检索 + 意图检索 → completeOnTimeout → 聚合非空 → Rerank
          ↓ 聚合为空或置信度低
第一层：ES BM25全文检索 → Rerank
          ↓ 仍低于阈值
第二层：默认话术 + 人工介入告警
```

**更完善的参考回答（STAR）：**
> S：智析RAG 并行发起意图检索和全局向量检索，两者均依赖外部服务，高并发或服务抖动时存在超时风险，两通道同时失败则返回空结果，用户体验极差。
>
> T：完善检索链路降级策略，目标是任意通道失败时仍能返回有效结果，用户侧零空结果。
>
> A：三层降级：① completeOnTimeout(emptyList, 800ms) 兜住单通道超时，聚合非空结果进Rerank；② 聚合结果空或置信度低于阈值，切换 ES BM25 检索，按词频匹配后交Rerank；③ ES结果仍低于阈值，返回默认话术+触发人工介入告警。
>
> R：用户侧空结果率接近零；ES 作为兜底通道 SLA 99.99%，两层兜底覆盖绝大部分异常场景。

## Q12：Spark compositeScore评分任务执行流程（小红书面试针对性复盘）

**问题：** compositeScore Spark任务从数据入口到写出结果表的完整流程？涉及哪些算子/SQL？有无数据倾斜？

**候选人回答摘要：**
- 输入：新链接产出表（聚合URL产出量+更新频率）+ 模糊留存表（留存率+规模）
- 处理：三维加权计算composite score
- 输出：DI表（当天快照，三维分数便于排查）+ DF表（全量历史，有更新则覆盖，无则保留）
- 业务价值：历史链接自动调节投递频率召回
- 数据倾斜：未遇到，但知道解法（广播/加盐/冷热分离）

**STAR 评分：**
**S✅** | **T✅** | **A⚠️** 业务流程清晰，缺Spark技术实现细节（用哪些SQL/算子） | **R✅**

**完整任务链（4个Job串行）：**
1. StatisticDomainSaveInfoJob：按domain聚合留存统计
2. SitemapBloomFilterJob：构建布隆过滤器新链去重
3. UpdateFrequencyTableJob（核心）：JOIN+GROUP BY+加权计算，输出DI/DF表
4. FrequencyDeliverySitemapJob：按grade过滤投递Mafka

**打分公式：** compositeScore = 0.5×newUrlScore + 0.5×(0.5×rateScore + 0.5×scaleScore)

**数据倾斜解法：**
- 小表+大表 → broadcast hint / Map Join（无Shuffle）
- 大表groupBy倾斜key → 加盐打散（key加随机前缀→预聚合→去前缀再聚合）
- 大表+大表 → 热点key单独广播，其余正常join，结果union

## Q11：缓存击穿/穿透/雪崩三种场景

**问题：** 三者区别？缓存击穿解决方案及各自优缺点？

**候选人回答摘要：**
- 缓存雪崩：大量缓存同时过期→大量请求打DB，解法：TTL加随机数 ✅
- 缓存击穿：热点key过期→大量请求打DB（雪崩特殊情况），解法：互斥锁/逻辑过期 ✅
- 缓存穿透：缓存和DB都不存在的数据被大量查询，解法：布隆过滤器/缓存空值 ✅

**STAR 评分：**
**S❌** | **T❌** | **A✅** 三概念+解法方向正确 | **R❌**

**需要补充的点：**
1. 逻辑过期描述太简单：关键是"key永不过期+数据内存expire_time字段+过期时返回旧数据+异步刷新"
2. 互斥锁"其他请求返回默认值"不准确，应是"短暂等待后重试缓存"

**方案对比：**
| 方案 | 适用场景 | 优点 | 缺点 |
|------|--------|------|------|
| 互斥锁 | 数据一致性要求高 | 不返回脏数据 | 锁等待期间有延迟毛刺 |
| 逻辑过期 | 高并发热点，允许短暂不一致 | 无阻塞，性能最好 | 刷新窗口内有旧数据 |
| 永不过期 | 超级热点且数据变化极少 | 最简单 | 数据更新需手动触发 |

## Q10：MySQL 5亿大表查询优化

**问题：** 5亿条记录表，WHERE domain + crawl_status + create_time范围 + ORDER BY DESC + LIMIT 100，性能问题和优化方案？

**候选人回答摘要：**
- LIMIT 100 先查全部再丢弃（部分正确）
- SELECT * 触发回表 ✅
- 优化：对 domain、create_time、crawl_status 加联合索引 ✅
- 只查需要列，不走 SELECT * 回表 ✅
- 还慢：开慢查询日志 → EXPLAIN 分析 → 是否命中索引 ✅
- 终极：分库分表 ✅

**STAR 评分：**
**S✅** 5亿条大表 | **T✅** 查询性能优化 | **A⚠️** 索引列顺序分析缺失，低选择性陷阱未说，EXPLAIN关键字段未说 | **R❌** 未提效果

**缺失的关键点：**
1. **索引列顺序**：(domain, crawl_status, create_time)
   - domain最左：等值+高选择性
   - crawl_status中间：等值过滤，但选择性极低（0/1），MySQL可能放弃走此索引
   - create_time最右：范围查询+ORDER BY，避免filesort
2. **crawl_status低选择性陷阱**：90%都是status=0时，MySQL可能不走此索引
3. **EXPLAIN关键字段**：
   - type: ALL=全表扫描❌，range/ref=走索引✅
   - key: 实际使用的索引
   - rows: 预估扫描行数
   - Extra: Using filesort=排序开销❌，Using index=覆盖索引✅
4. **覆盖索引**：只查需要的列+加入索引，Extra显示Using index，无回表

**完整优化路径：**
加联合索引(domain,crawl_status,create_time) → SELECT具体列(覆盖索引) → EXPLAIN验证(type=range,无filesort) → crawl_status选择性低则改为(domain,create_time) → 数据继续增长→分表

## Q9：线程池七参数 + 项目设计选型

**问题：** 线程池七个核心参数？任务提交完整流程？四种拒绝策略？项目里用哪种，为什么？

**候选人回答摘要：**
- 七参数：核心线程数、最大线程数、任务队列、拒绝策略、存活时间、存活时间单位、线程工厂 ✅
- 提交流程：活跃线程<核心线程→创建线程执行；超过→入队；队满→创建应急线程；达最大→拒绝策略 ✅
- 四种拒绝策略：抛异常/调用线程执行/静默丢弃/丢弃最老任务 ✅
- 项目设计：
  - core=max：避免应急线程创建销毁开销
  - SynchronousQueue（0缓冲）：无界队列OOM；有界队列意义小（MQ已削峰+持久化，线程池重启会丢任务）
  - AbortPolicy：配合while循环背压，线程池打满→拒绝→捕获异常→MQ消费失败→消息重新消费
  - while+synchronized：保证检查-提交原子性，应对临界竞态问题

**STAR 评分：**
**S✅** 爬虫系统MQ消费背压场景 | **T✅** 不丢消息+背压控制 | **A✅** 七参数+选型理由完整 | **R✅** 消息不丢，MQ大量消息安全

**补充：IO密集型线程数公式**
`N = CPU核数 / (1 - 阻塞比例)`，网络爬虫IO占比高，线程数可设CPU核数的5-10倍

## Q8：持久化对话记忆 + 摘要压缩设计（智析RAG深挖）

**问题：** 为什么需要摘要压缩？触发时机？摘要和最近对话如何组合？LLM压缩失败怎么处理？

**候选人回答摘要：**
- S：对话历史过长→token消耗大+注意力机制失效；不能简单截断→会丢失早期重要上下文
- T：主导设计持久化记忆+摘要压缩策略，维持上下文的同时控制token成本
- A：
  - 对话完成后：user输入+model返回成对存Redis队列（userId+sessionId为key），插队尾
  - 异步线程池：提交"压缩检查+MySQL持久化"任务，避免阻塞主线
  - 触发条件：Redis队列长度>20时触发，取队头10条交LLM压缩
  - 并发安全：压缩完成后获取互斥锁+CAS校验（队头10条与提交时一致），通过后弹出10条插入摘要
  - 持久化：摘要记录到MySQL摘要历史表，带压缩最大对话编号
  - 会话恢复：加载MySQL最新摘要+最大编号后的原始记录 → 恢复上下文现场
  - LLM失败：放弃本次，等下次对话触发二次尝试
  - 改进方向：引入MQ替代线程池（削峰+持久化防丢），当前demo阶段未引入
- R：上下文窗口维持在20条以内，节约模型推理消耗

**STAR 评分：**
**S✅** | **T✅** | **A✅** 设计完整，CAS+互斥锁亮点 | **R✅** 有结果但缺token节省量化数据

## Q7：布隆过滤器原理 + Sitemap 去重场景

**问题：** 布隆过滤器底层原理？误判率怎么控制？误判在Sitemap场景的后果？怎么处理？

**候选人回答摘要：**
- 原理：大位数组 + 多个hash函数，插入时置位，查询时比对所有位 ✅
- 结论：说不在的一定不在，说在的可能误判（hash碰撞）✅
- 误判率：受hash函数数量、质量、位数组大小影响 ✅
- 业务后果：新链接被误判为已存在 → 被丢弃 → 下游抓取链接库减少 ✅
- 处理策略：重建更大位数组+更多hash函数的过滤器，载入历史数据替换旧过滤器 ✅
- 诚实说明：非主负责人，收益数据不了解

**STAR 评分：**
**S✅** 几十亿链接去重场景 | **T⚠️** 非主负责人 | **A✅** 原理+误判率+重建策略均说到 | **R❌** 不了解收益数据

**补充的关键点（未答到）：**
1. **布隆过滤器不能删除元素**：位一旦置1无法撤销，删除会影响其他key判断
   - Sitemap场景影响：高频站点需要周期性重抓，但链接还在过滤器里会被误判丢弃，这也是需要定期重建的原因
2. **重建过渡期数据安全**：双写策略——新旧过滤器同时运行，查询时两个都查（OR关系），新过滤器ready后切换下线旧的

**误判率公式：** `p ≈ (1 - e^(-kn/m))^k`，k=hash函数数量，n=已插入元素数，m=位数组大小

## Q6：多模型三态熔断路由设计（智析RAG深挖）

**问题：** 主模型熔断后怎么处理？备用模型全熔断怎么办？HALF_OPEN 怎么触发和探测？SSE流式输出中途报错怎么解决？

**候选人回答摘要：**
- 主模型熔断 → 走备用模型，用户无感知切换
- 优先级按配置中位置/权重靠前决定
- 全部备用模型熔断 → 返回"服务不可用"默认值
- HALF_OPEN触发：定时任务扫描熔断队列，检查过期时间到期则移入半熔断队列
- HALF_OPEN探测：只允许一个请求探测（加锁/记录），成功→移入可用队列，失败→继续用其他模型
- SSE中途报错问题：未考虑

**STAR 评分：**
**S✅** 单模型故障场景 | **T✅** 用户无感知切换 | **A⚠️** HALF_OPEN设计对但有小逻辑错误，SSE问题盲区 | **R❌** 未量化

**小逻辑错误：**
"过期时间超过当前时间" → 应为"当前时间超过过期时间"（OPEN持续时长到了才触发HALF_OPEN）

**SSE流式输出中途报错解法（ProbeStreamBridge）：**
```
模型开始输出 → 不立即转发用户 → 先缓冲第一个SSE chunk
    ├── 第一个chunk正常 → 开始透传，后续实时流式输出
    └── 第一个chunk报错 → 用户侧什么都没收到 → 切换下一个模型重试
```
关键：只缓冲第一个chunk（<100ms延迟），能拦截"一开口就报错"的模型故障，防止脏数据到用户

**完整三态熔断状态机：**
```
CLOSED（正常）
    ↓ 连续失败N次（failure-threshold）
OPEN（熔断，直接返回空/切备用）
    ↓ 当前时间 > 熔断开始时间 + open-duration-ms
HALF_OPEN（只允许1个请求探测）
    ↓ 成功 → CLOSED / 失败 → OPEN
```

## Q5：站点频度调度 compositeScore 三维打分设计（深挖）

**问题：** 频度调度业务背景？三维打分分别是哪三维？Redis TTL 怎么和打分结合？

**候选人回答摘要：**
- S：早期每天固定投递，小时级更新站点无法感知，链接召回率低
- T：主导设计自主感知调度系统，动态调节站点投递频率
- V1：单一链接产出打分 + 3天滚动评判，上线收益不明显
- V2 三维打分：
  - 产出分：sitemap链接多时间戳 → 多时段有更新 → 更新频次高
  - 留存分：下游模糊留存表，调度链接数÷留存链接数=留存率
  - 规模分：留存绝对数量分级（>1万满分，>1000中高分），避免小站极端数据干扰
  - 加权：compositeScore = 0.5×newUrlScore + 0.5×fuzzyScore，fuzzyScore = 0.5×rateScore + 0.5×scaleScore
- 投递侧：按评分等级启动多个定时任务，高频站点一天投递多次
- Redis TTL：V1统一12小时；V2消息携带站点等级，抓取成功后按等级设置不同TTL，高频站TTL短，低频站TTL长
- R：每日链接产出 10-30亿 → 200亿，为下游提供丰富链接资源

**STAR 评分：**
| 维度 | 评分 | 说明 |
|------|------|------|
| S（背景）| ✅ | 链接召回率低、小时级更新未感知、历史数据未利用 |
| T（任务）| ✅ | 明确说"主导设计了站点频度调度策略" |
| A（行动）| ✅ | V1→V2迭代完整，三维打分+Redis TTL均说清楚 |
| R（结果）| ✅ | 10-30亿 → 200亿/天，量化有力 |

**不足：**
- 三维没有先报名字再展开，听起来结构散
- 阈值来源描述模糊（建议说：基于全量站点留存数量P50/P75/P90分位数分级，而非固定绝对值）

**追问：大站规模分满分 = 变相回到大站优先？**
- 候选人回答：①阈值相对化（历史数据分析） ②多维加权制衡（留存分+产出分） ③消费侧流量打散兜底
- 面试官补充：更精准表述是用分位数（P50/P75/P90）作为分级阈值，随数据自动校准

**分级映射：** ≥0.75→HIGH(多次/天)、≥0.50→MIDDLE、≥0.25→LOW、以下按rateScore→DISUSE/PENDING

## Q4：Spring Bean 生命周期 + AOP代理生成时机

- 把 AOP 前置/后置/环绕通知混入了 Bean 生命周期，是两个不同概念

**S❌** | **T❌** | **A❌** 缺 Aware/前置处理/后置处理三步，AOP通知类型答非所问 | **R❌**

**历史薄弱点标记：** Spring Bean 生命周期顺序不熟，本次仍不完整 ⚠️

**完整8步生命周期：**
```
1. 实例化         createBeanInstance()，内存分配，属性默认值
2. 属性填充       populateBean()，注入 @Autowired 依赖
3. Aware 回调     setBeanName() / setBeanFactory() / setApplicationContext()

7. 使用
8. 销毁           @PreDestroy → destroy() → destroy-method
```

**AOP代理生成时机：第6步**
AbstractAutoProxyCreator 实现 BeanPostProcessor，在 postProcessAfterInitialization() 里判断是否需要代理，生成 JDK/CGLIB 代理对象替换原始 Bean 放入容器。

## Q3：Spring AOP 底层代理实现（JDK动态代理 vs CGLIB）

**问题：** Spring AOP 底层两种代理实现分别是怎么实现的？Spring 什么情况下选哪种？各自限制？

**候选人回答摘要（第二次，第一次说反了）：**
- JDK动态代理：基于接口，生成实现相同接口的代理对象，重写接口方法，只能代理接口中定义的方法 ✅
- CGLIB：基于继承，生成被代理类子类，重写父类方法，被代理类不能是... （未说完）

**STAR 评分：**
**S❌** | **T❌** | **A⚠️** 核心区别答对（第一次说反），限制说不完整，Spring选择规则未提 | **R❌**

**历史薄弱点标记：** JDK vs CGLIB 已答错三次，本次第一遍仍说反，第二遍纠正 ⚠️

**完整知识点：**

| | JDK 动态代理 | CGLIB |
|--|------------|-------|
| 原理 | 基于接口，实现相同接口 | 基于继承，生成子类重写父类方法 |
| 前提 | 被代理类必须实现接口 | 被代理类不能是 final 类 |
| 限制 | 只能代理接口中定义的方法 | final 方法无法代理 |
| 核心API | Proxy.newProxyInstance() + InvocationHandler | Enhancer + MethodInterceptor |

**Spring 选择规则：**
- 目标类实现了接口 → JDK动态代理
- 目标类没有接口 → CGLIB
- proxyTargetClass=true → 强制全部CGLIB
- Spring Boot 2.x 以后 → 默认全部 CGLIB

**口诀：JDK=接口（必须有接口），CGLIB=继承子类（不能是final）**

## Q2：IO多路复用（select/poll/epoll）

**问题：** 单机1万个Socket长连接，用select/poll/epoll三种方案分别怎么实现？各自瓶颈？选哪个？

**候选人回答摘要：**
- select：固定长度fd数组（上限1024），用户态↔内核态拷贝，遍历整个数组找就绪事件
- poll：突破1024限制，但仍需两次拷贝+全量遍历
- epoll：红黑树维护监听fd，就绪队列保存就绪事件，只需检查就绪队列，无需全量遍历
- 选择：爬虫场景选 epoll，减少拷贝和遍历开销

**STAR 评分：**
**S（背景）✅** 爬虫大量HTTP长连接 | **T（问题）✅** 监听哪个连接就绪 | **A（选型）✅** 三模型区别+选epoll理由清晰 | **R（效果）❌** 未提

**不足之处：**
1. "两次拷贝"描述不精确：select/poll 是每次调用都全量拷贝，不是总共两次
2. 漏掉 ET（边缘触发）vs LT（水平触发）区别
3. epoll_ctl / epoll_wait 两个 API 的职责未区分

**核心知识点：**
- select：fd_set 上限1024，每次调用全量拷贝+O(N)扫描
- poll：pollfd数组无上限，每次调用全量拷贝+O(N)扫描（本质没变）
- epoll：epoll_ctl 注册一次到红黑树，epoll_wait 只返回就绪链表 O(1)
- LT（水平触发，默认）：未处理下次继续通知，安全不漏事件
- ET（边缘触发）：状态变化只通知一次，性能高但必须一次读完否则丢事件
- 爬虫场景选 epoll + LT：连接数上万，ET编程复杂，LT更安全

| | select | poll | epoll |
|--|--------|------|-------|
| fd上限 | 1024 | 无限制 | 无限制 |
| 每次拷贝 | 全量 | 全量 | 只注册一次 |
| 查找就绪 | O(N)扫描 | O(N)扫描 | O(1)就绪链表 |
| 触发模式 | - | - | LT / ET |
