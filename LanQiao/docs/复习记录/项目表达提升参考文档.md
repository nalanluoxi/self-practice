## 一、去口语化专项

### 1.1 高频口语词对照表（来自录音分析）

| 口语词（禁用） | 书面替换 | 示例 |
|---|---|---|
| 嗯、呃 | 【直接停顿】 | 说之前想清楚再开口 |
| 那个、这个 | 【删除】或"该"/"此" | "那个线程池" → "线程池" |
| 就是说、也就是说 | "即"/"换言之" | "就是说它会等待" → "它等待" |
| 相当于是 | "本质上是"/"等价于" | "相当于是背压" → "本质上是背压机制" |
| 对对对 | 【沉默或"正是"】 | 面试官确认时不要重复说"对" |
| 然后然后 | "接着"/"随后"/"第X步" | "然后然后投递" → "第三步投递" |
| 我记得好像是 | 直接说确切数字 | "我记得好像200台" → "200台机器" |
| 就就就 | 【删除冗余】 | "就就就是因为" → "原因是" |
| 不是、呃不对 | "更准确地说" | "不是不对，是那个…" → "更准确地说" |

### 1.2 句式去冗余示例

**原始录音版（银河驿站）：**
> "嗯这个的话就是当它成功投递到线程池之后，它才会返回手动提交这个呃offset偏移量，啊来确保这个消息已经被消费。"

**去口语化版：**
> "消息成功投递到线程池后，才手动提交offset，确保消息已消费。"

**原始录音版（腾讯）：**
> "呃就是最开始的时候呢，它是呃对这些所有流量并没有进行处理的。呃所以说呢，它有很多这种大站和小站一起在消息队列中进行排队。"

**去口语化版：**
> "早期所有流量未作区分，大站小站共用同一队列排队，导致小站长期被挤兑。"

### 1.3 练习方法
- 每次模拟面试结束后，把自己的回答逐字默写出来，删掉所有"嗯/呃/然后/就是"
- 练习"先想3秒再开口"：宁可停顿也不说废话
- 用"首先/其次/最后"或"第一点/第二点"替代"然后然后"

## 二、STAR法则实战话术

### 2.1 美团Sitemap项目 — 多线程重构亮点

**标准STAR话术（背诵版）：**

> **S（背景）**：美团Sitemap站点发现环路，为大模型预训练提供语料，日产出目标百亿级链接。
>
> **T（我的职责）**：我主导负责消费链路的并发重构，目标是将单机吞吐量提升至少10倍。
>
> **A（方案+选型理由）**：
> 原架构是单线程串行，一条消息处理10-15秒，性能瓶颈在HTTP网络IO等待。
> 改造方案是一个整体工程，多线程重构和partition扩容必须同步推进，单独做一个都无法达到效果：
> - **多线程重构**：引入线程池将下载任务异步并行，选SynchronousQueue而非有界队列（日任务量上亿，有界队列必然被打满，缓冲无意义）；选抛出异常拒绝策略而非CallerRuns（CallerRuns让调度线程阻塞，感知不到线程池空闲）；同步设计while+sleep背压，控制消息拉取速率与线程池容量匹配。
> - **partition扩容（与多线程重构配套）**：多线程只解决单机并发问题，但Kafka约束是1个partition最多1个消费者，原来100台机器对应分区数远不足，大量消费者空闲。因此同步将partition数扩至与消费机器数（490台）匹配，让集群并发能力真正被利用起来。
> 两个改动缺一不可：没有多线程，单机消费仍是串行；没有扩partition，99%的消费机器永远空闲。
>
> **R（结果+业务价值）**：单机吞吐量从4条/分钟提升至约1600条/分钟，集群消费机器从100台扩容至490台，日新链产出从约3000万提升至52亿+，有效加速了大模型预训练语料的积累周期。

**常见追问 & 标准回答：**

| 追问 | 标准回答 |
|---|---|
| "最核心的改动是哪个？" | "两个改动是一个整体工程，缺一不可。多线程重构解决的是单机维度：把串行IO等待并行化，单机吞吐从4条/分钟提升至1600条；partition扩容解决的是集群维度：原来100台机器对应分区数严重不足，大量消费者空闲，扩到490台+490个partition后集群并发才真正释放。单独只做线程池，集群大部分机器仍空闲；单独只扩partition，单机仍是串行瓶颈。" |
| "为什么不用CallerRuns？" | "CallerRuns让调度线程去执行下载，阻塞期间无法感知线程池空闲出来的线程，造成空转浪费，两个职责耦合。" |
| "线程池线程数怎么定的？" | "IO密集型场景，公式：N = CPU核数 / (1-阻塞比例)。实践中先设10，灰度上线观测利用率，发现长期在50%以下，再结合本地限流调整。" |

### 2.2 三级限流体系亮点

**标准STAR话术：**

> **S**：环路处于高并发场景，下游Redis集群每秒QPS有上限，单纯站点级限流会直接把Redis打满。
>
> **T**：我设计了三级限流保护体系，目标是在精确控制站点流量的同时，保护Redis不被打垮。
>
> **A**：
> - 第一层：集群级限流（Rhino框架），控制整集群总QPS上限
> - 第二层：单机级限流，每台机器本地控制，减少Redis压力
> - 第三层：Redis+Lua令牌桶，按domain精确限频（每站点每秒N条）
> 选Redis+Lua而非纯本地限流，因为需要多机协调、全局精确控制同一站点速率；外层两层是为了在精确控制之前过滤掉大部分超量请求，保护Redis集群。
>
> **R**：大站挤兑问题基本消除，小站每天均能被正常调度抓取，下游投诉降零。

---

### 2.3 站点频度调度 compositeScore 亮点

**标准STAR话术：**

> **S**：早期调度策略只看链接产出量，导致更新频率低的站点被过度抓取，高频更新站点被低频调度。
>
> **T**：我主导设计了第二版评分体系，目标是让调度频次与站点真实更新频率精确匹配。
>
> **A**：
> 设计了compositeScore多维评分，由三部分构成：
> - rateScore（留存率评分）：用下游模糊留存表计算留存率，分5档（≥80%→满分，逐步递减）
> - scaleScore（规模评分）：对投递链接数做归一化，避免大站因绝对量大拿高分、小站因绝对量小被忽视
> - 最终合并为grade等级（1-5），用Redis TTL差异化控制调度间隔（高频=天级，低频=周级）
> 选Redis TTL方案而非定时任务，因为TTL天然支持分布式、无需额外组件、自然过期兜底。
>
> **R**：高质量站点召回率显著提升，链接日产出从3亿增长至52亿+，站点覆盖广度和质量均提升。

### 2.5 Sitemap 业界实现横向比较（对应小红书2面失分点1）

**⚠️ 先理解真实架构，再回答（避免说错）：**

我们的系统是**三层分离**的混合架构：
```
上游（两路来源）：
  ① 固定数据集定时投递：每天定时把存量站点全量投入 Mafka（保证覆盖广度）
  ② 频度调度模块多轮投递：compositeScore 高分站点一天多轮投递，高质量站点抓取更频繁
          ↓
中层（实时流式）：SitemapRequestConsumer Mafka 实时消费 → 多级过滤（去重+限流） → 线程池即时下载 sitemap → 解析 URL 写回 Mafka
          ↓
下游（日级批次）：Spark 定时任务消费结果 MQ → 同步 Hive 表 → 更新 compositeScore → 下一轮调度
```

**关键认知：**
- 上游有**两路**：全量覆盖（保广度）+ 频度调度多轮（保高质量站点时效），高分站点一天可以被抓多次
- 中层消费是**纯实时**：消息到了立刻处理，不等批次
- 下游聚合是**日级**：Spark 每天跑一次，更新评分，驱动下一天的调度
- 这和 Nutch 的本质区别是：**中层执行层是流式的**，Nutch 的执行层是批处理闭环

---

**标准话术（面试官追问"业界怎么做的"时必须能说出）：**

> "Sitemap 协议本身是 sitemaps.org 制定的行业标准，Google、Bing 等主流搜索引擎都遵循这套协议进行链接发现。
>
> 业界框架主要分两类：
> - **Apache Nutch**（传统分布式爬虫）：MapReduce 批处理模型，完整的 Generate → Fetch → Parse → Update CrawlDb 闭环。优点是开箱即用，内置 Robots.txt、礼貌策略、PageRank。核心缺陷是**批处理语义强耦合**：一条新发现的 URL 必须等本轮所有 MapReduce 任务全部跑完、CrawlDb 更新后，下一轮才能被调度抓取，单 URL 时效是小时级。
> - **MQ 驱动的流式架构（我们的选择）**：上游有两路来源——固定数据集每天定时全量投递（保广度），频度调度模块按 compositeScore 评分对高质量站点一天多轮投递（保时效）。消费端（`SitemapRequestConsumer`）实时消费 Mafka，SynchronousQueue 线程池即时处理，一条 URL 进队到开始下载是秒级。
>
> 我们和 Nutch 的核心差异有三点：
> 第一，**单 URL 处理时效**：Nutch 是批处理闭环（小时级）；我们消息到达即处理（秒级）。
> 第二，**调度精细度**：Nutch 礼貌策略全局配置；我们对每个 domain 独立令牌桶 + 三级限流，被限流消息重投而不是丢弃。
> 第三，**高质量站点可多轮抓取**：频度调度模块对 compositeScore 高分站点一天投递多轮，保证高更新率站点的语料时效，这在 Nutch 里无法精细控制。"

**常见追问 & 标准回答：**

| 追问 | 标准回答 |
|---|---|
| "你们上游不也是每天定时调度的吗？算批处理吗？" | "上游有两路：固定数据集每天全量投一次（保广度）；频度调度模块对 compositeScore 高分站点一天多轮投递（保时效）。但无论哪路，**抓取执行层是实时流式的**——消息进 Mafka，消费端立刻处理，不等这批全部跑完。Nutch 的瓶颈在执行层本身是批处理闭环，我们的执行层是事件驱动的，两者本质不同。" |
| "Nutch 和你们方案最核心的区别？" | "批处理闭环 vs 流式消费。Nutch 是强批处理语义：Generate→Fetch→Parse→Update 必须走完一轮，中间发现的新链接无法插队，最快小时级。我们 Mafka 消费端是事件驱动的，一条消息到达就立刻进线程池处理，时效是秒级。两者对单 URL 的端到端延迟差了一两个量级。" |
| "为什么不直接用 Nutch？" | "四个原因：一是**技术栈不兼容**，Nutch 深度绑定 Hadoop/MapReduce，我们用 Mafka + Spark + MDP 框架，强行引入需要大量 ETL 适配；二是**限流精细度不够**，Nutch 礼貌策略是全局配置，我们需要对每个 domain 独立令牌桶限频 + 三级保护；三是**被限流消息重投机制**，我们限流后把消息重投回 MQ 而不是丢弃，Nutch 没有这个语义；四是**热更新能力**，我们通过 @MdpConfigListener 可以在线动态修改线程数、黑名单、正则规则，Nutch 需要重启集群。" |
| "你们高分站点怎么保证时效？" | "频度调度模块对 compositeScore 高分站点（grade 1/2）的 Redis TTL 设置更短，所以一天之内可以被重复触发多轮投递，不是等第二天。低分站点（grade 4/5）TTL 长，可能一周才投一次，节省抓取资源。这样高更新率站点的语料时效和低质量站点的资源消耗都得到了精细控制。" |
| "你们架构有什么不足？" | "下游是日级批次短板。Spark 每天定时同步 Hive，当天抓到的新链接最早第二天才能进训练语料。如果对时效要求更高，需要把下游改造成 Flink 流式写入，但会引入实时数仓额外复杂度。目前日级对大模型预训练够用，是合理的工程取舍。" |
| "你们和业界最核心的差异化是什么？" | "差异化在**公平调度 + 工程化保护**。通用框架只解决'能抓到'，我们还解决了'公平调度'和'不打垮目标站点'：compositeScore 三维评分让高质量小站每天都能被调度到；三级限流 + 被限流消息重投，保证大站洪峰不冲垮下游也不打垮小站；频度调度多轮投递让高更新率站点的语料时效有保障。这是亿级多样性语料场景下通用方案覆盖不到的。" |

**选型理由深度分析（面试被追问"为什么自研而不用开源"时的底层逻辑，四点）：**

---

**第一点：可观测性 — Nutch 是黑盒，MQ 驱动是白盒（最重要）**

Nutch 将抓取、解析、URL 管理全部封装在 MapReduce 内部，中间节点无法插入自定义监控。
我们的 MQ 驱动架构中，每个关键漏斗节点都有 CAT 打点：

```
消息进入 → 过期过滤 → URL格式校验 → 黑名单过滤 → Redis去重
→ 动态限流 → 三级限流 → 线程池投递 → 下载执行
```

每一层丢了多少、为什么丢，监控上一目了然。出了问题可以精确定位到哪个漏斗层，而不是在 Hadoop 日志里大海捞针。**大规模系统的可维护性，可观测性比功能更重要。**

---

**第二点：配置热更新 — Nutch 需重启，我们秒级生效**

Nutch 修改任何参数（抓取间隔、并发数、黑名单）都需要重新打包、重启集群，线上变更窗口长、风险高。

我们通过配置中心 `@MdpConfigListener` 实现热更新：
- 线程数调整 → 秒级生效，不停机
- 黑域名列表更新 → 实时拦截新增恶意站点
- 正则过滤规则变更 → 立刻应用，无需重新部署

这在需要频繁调整策略的大规模爬虫场景下是**运维层面的核心优势**。

---

**第三点：时效性 — Nutch 批处理闭环，MQ 驱动流式实时**

Nutch 是强批处理语义：Generate → Fetch → Parse → Update CrawlDb，**必须等整个数据集合处理完成后，新发现的 URL 才能进入下一轮**，单 URL 时效小时级。

MQ 驱动是事件驱动：一条消息进 Mafka，消费端立刻触发处理，**不需要等这批所有任务跑完**，单 URL 时效秒级。高质量站点还能通过频度调度模块一天多轮投递，进一步保证语料时效。

---

**第四点：技术栈不兼容 — 补充说明（回应"可以新建服务解决"的质疑）**

> 有人会说：可以新建一个独立服务，专门跑 Nutch，不就解决兼容性了？

反驳：Nutch 只提供了基础抓取能力，**三级限流、compositeScore 多维评分、被限流消息重投、热更新黑名单、过期消息过滤**这些核心业务逻辑，在 Nutch 插件体系里实现改造成本极高——最终结果是：Nutch 负责基础抓取 + 自研一大堆插件覆盖业务逻辑 + 还要维护 Hadoop 和 MDP 两套技术栈。还不如直接用 MQ 驱动自研，技术栈统一、可控性更强。

---

**对比总结表：**

| 维度 | Nutch | 我们的 MQ 驱动方案 |
|---|---|---|
| 可观测性 | 黑盒，中间节点无法打点 | 全链路漏斗 CAT 埋点，每层丢弃原因清晰 |
| 配置变更 | 需重启集群 | 配置中心热更新，秒级生效 |
| 单 URL 时效 | 批处理闭环，小时级 | 消息到达即处理，秒级 |
| 限流粒度 | 全局礼貌策略，一刀切 | 每个 domain 独立令牌桶，被限流重投不丢失 |
| 技术栈 | Hadoop/HDFS/HBase | Mafka + Squirrel + MDP（与现有体系统一） |

**一句话总结（背诵版）：**
> "Nutch 解决的是'如何爬互联网'，是通用搜索引擎场景下的开箱即用工具。我们的场景是大模型预训练语料收集，需要可观测、可热更新、流式实时、每 domain 精细限频这四个能力，而这四点恰好是 Nutch 的短板。自研成本虽高，但换来的是对整个抓取链路的完全掌控。"

---

**⚠️ 高频追问：「为什么不用成熟开源框架，要自研？」**

**标准答法（三段结构，诚实 + 展示横向调研 + 讲清楚成本）：**

> **第一段（交代背景）：**
> "接手时这个系统已经有了一套基于 MQ 驱动的初步抓取框架，核心链路是 Mafka 消费 + 线程池下载，我在这个基础上负责了消费链路的并发重构和三级限流体系。
>
> **第二段（说明做过横向调研）：**
> 我了解过业界方案，Apache Nutch 是目前比较成熟的分布式爬虫框架，在通用网页发现场景下被广泛使用，有完善的 Sitemap 解析、Robots.txt 遵守等开箱即用能力。
>
> **第三段（讲清楚为什么没迁移）：**
> 但评估下来，迁移到 Nutch 的成本比较高，主要三块：
> - **内部生态适配成本大**：现有系统深度依赖 Mafka、MDP、CAT、Squirrel，Nutch 是 Hadoop 生态，两套体系之间需要做 ETL 适配层（把 Nutch 的 HDFS Segment 文件转换成 Mafka/Hive 能识别的格式），改动范围很广；
> - **定制逻辑迁移成本高**：三级限流、被限流消息重投、热更新黑名单、过期消息过滤这些业务逻辑，在 Nutch 插件体系里实现的改造代价大，基本等于重写；
> - **版本迭代影响面大**：一旦引入 Nutch，后续每次 Nutch 版本升级都会牵动整个适配层，维护成本持续叠加。
>
> 综合评估下来，在现有框架基础上迭代优化，收益更高、风险更低。"

**ETL 补充说明（被追问"什么是 ETL"时）：**
> "ETL 是 Extract-Transform-Load，把数据从一个系统搬到另一个系统时，中间经过抽取、格式转换、加载三步。Nutch 输出是 Hadoop 私有的 SequenceFile 二进制格式，存在 HDFS Segment 目录里，必须用 Hadoop API 才能读取，不能直接被 Mafka 或 Hive 消费——需要写额外的转换程序做格式适配，这就是 ETL 成本。而且上下游格式只要一变，这个转换层也要跟着改，是持续的维护负担。"

---

### 2.4 智析RAG项目 — 多模型三态熔断路由

**标准STAR话术：**

> **S**：RAG系统依赖多个LLM供应商（Qwen2.5-72B/7B等），生产中模型服务偶发超时或报错，需要高可用路由。
>
> **T**：我独立设计并实现了多模型三态熔断路由模块，目标是主力模型故障时无感知切换，用户体验不中断。
>
> **A**：
> 为每个模型维护独立三态熔断器（CLOSED→OPEN→HALF_OPEN）：
> - CLOSED：正常路由，失败率超阈值转OPEN
> - OPEN：冷却期内拒绝请求走备用模型，冷却结束后CAS竞争转HALF_OPEN
> - HALF_OPEN：用ProbeStreamBridge缓冲首个SSE chunk判断是否真正恢复，成功转CLOSED，失败重置冷却
> 选CAS+惰性检查而非定时任务，因为定时任务有额外线程开销，请求到来时检查时间戳更及时。
> SSE流式特殊处理：探测阶段先缓冲N个token确认无错误再推给用户，防止"已发100个token后报错"的脏输出。
>
> **R**：主力模型故障期间用户无感知切换至备用模型，系统可用性从偶发中断提升至全天稳定。

## 三、系统设计思维专项

### 3.1 回答系统设计题的标准框架

面试官问"你来设计一个XXX系统"，标准答题顺序：

```
1. 澄清规模：QPS多少？数据量多大？用户规模？一致性要求？
2. 核心链路：数据怎么流转（入口→处理→出口）
3. 关键模块：每个模块做什么，为什么这样划分
4. 技术选型：每个选型给出理由（为什么选A不选B）
5. 瓶颈分析：最可能的瓶颈在哪？如何应对
6. 可观测性：异常如何发现？如何排查？
```

### 3.2 「为什么选A不选B」话术模板

```
选择[A方案]，而非[B方案]，原因是：
1. [A的核心优势] —— 在[具体场景]下更合适
2. [B的局限性] —— 在[具体场景]下会导致[具体问题]
3. [折中考量] —— 当[条件变化]时，B才是更好选择
```

**示例（SynchronousQueue vs 有界队列）：**
> 选SynchronousQueue而非有界队列，原因是：
> 1. 业务特点：任务量每天上亿，有界队列设再大也必然被打满，缓冲没有意义
> 2. 背压效果：SynchronousQueue线程池满时直接阻塞拉取，天然背压；有界队列满了才触发拒绝策略，响应滞后
> 3. 如果是离线批处理场景（任务量有限、允许积压），有界队列才更合适

### 3.3 「瓶颈在哪」思维框架

被问"系统瓶颈在哪/如何优化"时，按以下顺序排查：

```
网络IO（下载/外部调用）→ 计算（CPU密集型任务）→ 存储IO（DB/Redis/MQ读写）→ 内存（对象创建/GC）→ 锁竞争（并发瓶颈）
```

**美团Sitemap场景标准答：**
> 瓶颈在网络IO（HTTP下载10-15秒），而非CPU计算（解析轻量）。所以优化手段是增加并发线程数，让多个IO等待并行，而非优化算法复杂度。线程数上限受内存约束（每线程栈默认512KB，100线程=50MB），需在压测中找平衡点。

### 4.2 技术选型理由备忘（来自快手AI追问暴露）

每个方案都要准备"为什么用/为什么不用另一种"：

**Redis+Lua令牌桶 vs 纯本地限流**
- 选Redis：需要多机协调，同一domain在不同机器上要共用限频计数；本地限流只能单机精确，跨机器时同一站点实际QPS = N倍阈值
- 何时选本地：单机部署、允许轻微超量、低延迟优先场景

**SynchronousQueue vs LinkedBlockingQueue**
- 已见上文，核心：任务量无界时有界队列无意义

**流式解压(GZIPInputStream) vs 全量解压**
- 选流式：500MB压缩文件→解压后可能2GB，10线程并发=20GB，直接OOM；流式只需当前chunk内存，恒定几十KB

**三级限流 vs 单层Redis限流**
- 单层Redis：集群QPS上限会被打满；外层两层是保护Redis的护盾，不是功能重叠

>   - DF表（每日全量累积）：只保存最新状态，适合查当前值，但历史不可追溯
>   - DI表（按dt分区的每日快照）：每天一份完整记录，任意一天的数据都可单独查询，便于回溯、对比和故障排查
>   - 生产上频度调度最终同时维护两张表：DF表供在线查询当前频度等级，DI表供离线追溯和数据质量核查
>   - 在海量数据场景下，"能追溯"不是锦上添花，是基本工程规范——出了故障如果没有历史快照，根本无法定位是哪天哪个batch的数据问题

### 5.2 实习最难的部分

**核心答案（背诵版）：**

> **S（背景）**：接手Sitemap模块时，系统是单线程串行消费、且消费机器只有100台，日产出仅3000万，离目标差距巨大。完成多线程重构+partition扩容（100台→490台）这个整体工程后，产出大幅提升，但仍未到52亿。监控显示线程池利用率偏低，加更多线程也没有线性提速。
>
> **T（难点本质）**：这个难点的本质是：**多线程重构和partition扩容是两个必须联动的改动，而当集群瓶颈暴露后，症状和单机瓶颈很像，容易误判方向继续加线程而不是查partition。**
>
> **A（如何解决）**：
> - 难点一（联动工程的瓶颈误判）：线程池利用率偏低时，直觉是"继续加线程"，但仔细查consumer group偏移量，发现大量消费机器的偏移量长时间不变——根因是原始partition数严重不足，100台机器里多数消费者永远空闲。正确解法是多线程重构和partition扩容同步推进：多线程解决单机串行，partition扩容解放集群并发，两者缺一不可。
> - 难点二（数据倾斜）：集群消费能力释放后，发现小站点每天产出接近0——大站点单个domain有几十万链接，把整个队列打满。这不是纯技术问题，是**调度公平性**设计问题，需要三级限流打散+compositeScore多维评分，才能让小站点每天被正常调度到。
>
> **R（结果）**：两个难点解决后，日产出从3000万提升至52亿+，小站点每天均能被正常调度抓取，下游投诉降零。这是我第一次真正体验到"技术方案联动"和"技术+业务联合设计"缺一不可的实战感受。

### 6.1 最推荐讲的亮点：多模型三态熔断路由

**为什么推荐讲这个？**
- 有完整的工程设计（不是CRUD）
- 有明确的业务问题驱动
- 有清晰的选型理由
- 涉及并发编程（CAS）、流式处理（SSE）、系统可用性设计
- 来自真实生产代码（ragent/infra-ai模块）

**标准STAR话术（精简背诵版，90秒内）：**

> **S**：RAG系统依赖多个LLM供应商（主力Qwen2.5-72B，备用7B等），模型服务偶发超时/限流报错，用户请求直接失败体验极差。
>
> **T**：我独立设计了多模型三态熔断路由，目标是主力模型故障时用户无感知切换，系统全天稳定可用。
>
> **A（核心设计+选型理由）**：
> - 三态转换：CLOSED正常路由 → 失败率超阈值进OPEN → 冷却期用备用模型 → 冷却结束CAS竞争进HALF_OPEN探测 → 恢复则转CLOSED，失败则重置冷却
> - 为什么用CAS+惰性检查而非定时任务：定时任务有额外线程开销，且"请求到来时检查时间戳"比"定时扫描"更及时，不会出现"模型已恢复但等待下次扫描"的窗口
> - SSE流式特殊处理（这是最难的部分）：普通HTTP可以在收到响应头后判断成功，但SSE是流，前100个token正常、第101个token报错时，用户已经看到了内容，此时切换会造成"脏输出"。解法是ProbeStreamBridge：探测阶段缓冲首N个token，确认无错误后再推给用户，失败则直接走备用模型重新生成。
>
> **R**：主力模型故障期间用户无感知切换，系统可用性从偶发中断提升至全天稳定。Chat/Embedding/Rerank三类服务均复用同一套熔断路由机制。

---

**常见追问 & 标准回答：**

| 追问 | 标准回答 |
|---|---|
| "HALF_OPEN为什么用CAS而不是直接放行？" | "防止雪崩。主力模型刚从OPEN恢复时，如果并发100个请求全部放行，模型可能立刻再次被打垮，重新进OPEN。CAS保证同一时刻只有1个请求进入探测，其余仍走备用模型，只有探测成功后才全部切回主力。" |
| "缓冲N个token会增加首包延迟吗？" | "会，约增加N*平均token生成时间的延迟。N的设置是个trade-off：太小容易误判（1个token就放行，错误还没暴露），太大则用户感知延迟。实际设置的是首个chunk（通常是第一个标点或换行），兼顾两者。" |
| "为什么不直接用Resilience4j？" | "Resilience4j是HTTP请求粒度的熔断，不理解SSE流式语义。SSE是一个HTTP连接持续发数据，对Resilience4j来说这条请求'成功'了（连接建立），但实际上中间可能报错。需要自定义流式感知的熔断器才能覆盖这个场景。" |

---

### 6.2 第二推荐讲的亮点：多通道并行检索

**标准STAR话术（60秒版）：**

> **S**：单通道向量检索召回率有限，当用户问题与知识库措辞差异大时，相似度低，优质结果排不上来。
>
> **T**：我设计了多通道并行检索引擎，目标是在不牺牲延迟的前提下提升召回率。
>
> **A**：两个通道并行执行：IntentDirectedSearchChannel（高精度，按意图命名空间检索）+ VectorGlobalSearchChannel（高召回，全局检索，仅当意图置信度<0.6时触发）。并行用CompletableFuture，结果合并去重用LinkedHashMap保序。选LinkedHashMap而非HashSet是因为需要同时保证去重和顺序（高分在前）。
>
> **R**：双通道架构下，意图明确时精确命中，意图模糊时兜底全局检索，整体召回率相比单通道显著提升，且延迟仅增加了最慢通道的等待时间（而非两通道串行之和）。

### 6.3 RAG 文档分块策略（基于真实代码分析）

**⚠️ 先理解真实设计再回答：项目里有两种分块策略，按文件类型自动选择**

```
文件类型判断（DocumentIngestionService.selectStrategy）：
  Markdown（.md）→ StructureAwareChunker（结构感知分块）
  PDF / TXT 等  → FixedSizeChunker（固定大小分块）
```

---

**策略一：FixedSizeChunker — PDF/TXT 固定大小分块**

按字符数硬切，加 overlap 保证跨块上下文连续：

```
文档 1000 字符，chunkSize=512，overlapSize=50：

块1：字符 0   → 512
块2：字符 462 → 974   ← 前50字符 = 块1的尾部（overlap）
块3：字符 924 → ...
```

overlap 的代码实现：把**上一块最后 overlapSize 个字符**拼到下一块开头：
```java
// materialize() 方法核心逻辑
body = prevTail + body;   // prevTail = 上一块尾部 50 字符
```

**chunk_size 选取理由（面试必须能说出数字和依据）：**
- 太长（如 1024）：召回时引入不相关内容多，Rerank 压力大
- 太短（如 128）：单块语义不完整，模型难以理解上下文
- 512 是 LangChain、LlamaIndex 等主流框架的默认推荐值，工程实践中验证最多的起点

**overlap 选取理由：**
- 比例约为 chunkSize 的 10%（50/512 ≈ 10%）
- 保证跨块的句子不被切断，既不浪费存储，又能覆盖边界信息

---

**策略二：StructureAwareChunker — Markdown 结构感知分块**

不按字符数硬切，而是先识别 Markdown 结构，再在结构边界合并打包，三步走：

**第一步：扫描识别结构块**
```
# 机器学习简介            → HEADING 块（标题，独立不拆分）

机器学习是人工智能...     → PARA 块（段落，空行为边界）
深度学习是其子集...

\`\`\`python              → CODE 块（代码围栏，整体保留，绝不从中间切断）
model.fit(X, y)
\`\`\`

![图片](url)              → ATOMIC 块（图片/链接，独立不拆分）
```

**第二步：按 min/target/max 预算打包**
```java
target = chunkSize          // 目标大小（配置值）
max    = chunkSize * 4/3    // 上限（约 1.33 倍，允许一定超出）
min    = chunkSize / 2      // 下限（太小则与前一块合并）
```
核心逻辑：相邻结构块持续合并，直到超过 max 才切分。若超 max 但 size < min，忍一次超限（保证语义完整性优先于大小约束）。**只在块边界切，不在段落或代码块中间切。**

**第三步：物化 + overlap**
把上一个 chunk 的尾部字符追加到下一个 chunk 开头（与固定分块相同）。

---

**完整入库流水线（DocumentIngestionService）：**

```
读文件字节（DB）
    ↓
解析为纯文本
  PDF（有文字层）→ Spring AI PagePdfDocumentReader
  PDF（无文字层）→ OCR 兜底（Tesseract，中英文混合，最多30页）
  Markdown       → MarkdownDocumentReader
  TXT/其他       → 直接 UTF-8 解码
    ↓
选策略分块（Markdown=结构感知，其他=固定大小）
    ↓
元数据增强（可选，受配置控制）
  关键词增强：从每块提取关键词写入 metadata.excerpt_keywords
  摘要增强：调 LLM 生成 PREV/CURR/NEXT 摘要（默认关闭，慢）
    ↓
逐块写入 PgVector
  VectorStore.add() 内部自动调 EmbeddingModel 向量化（Ollama bge-m3）
    ↓
更新文档状态 success / failed（单块失败不终止整体，记录警告继续）
```

---

**常见追问 & 标准回答：**

| 追问 | 标准回答 |
|---|---|
| "所有文件分块策略一样吗？" | "不一样。我们按文件类型自动选策略：Markdown 用结构感知分块，先识别标题/代码块/段落等结构单元，在块边界合并，不会切断代码块或段落；PDF/TXT 用固定大小分块，按 chunkSize 字符数切割加 overlap。核心原则是'切断位置不能破坏语义单元'。" |
| "overlap 具体怎么实现的？" | "把上一块的最后 overlapSize 个字符拼到下一块开头。比如 overlap=50，块2的内容 = 块1尾部50字符 + 块2正文。这样跨块的句子不会被完全切断，召回时两块都能覆盖边界信息。" |
| "代码块会被切断吗？" | "不会。StructureAwareChunker 把 ``` 围栏内的代码识别为 CODE 块，整体作为一个原子单元，打包时不会从中间切割。代码块太大超过 max 预算时，会单独成一块而不是强行拆分。" |
| "chunk_size 用字符数还是 token 数？" | "我们用字符数（`chunkSize` 参数单位是字符）。Spring AI 的 TokenTextSplitter 用 token 数，两者都有项目里用到——TokenTextSplitter 在早期 demo 里用过，生产入库流水线用的是字符数分块，更直观且不依赖特定 tokenizer 实现。" |
| "为什么 PDF 要有 OCR 兜底？" | "扫描版 PDF 没有文字图层，直接用 PDF Reader 提取是空文本。OCR 兜底用 Tesseract 把每页渲染成图片再识别，支持中英文混合，最多处理30页防止超时。" |

### 6.4 RAG 评测指标体系（对应小红书2面失分点3）

**标准话术（被问"如何评测 RAG 系统"时主动说出，不要等面试官引导）：**

> "RAG 评测分两层：
>
> **检索层**（评估召回质量）：
> - **Recall@K**：前 K 个召回结果中是否包含正确文档，K 通常取 3 或 5，衡量覆盖面
> - **MRR（Mean Reciprocal Rank）**：正确文档排在第几位的倒数均值，越靠前 MRR 越高，衡量排序质量
>
> **生成层**（评估答案质量）：
> - **Answer Faithfulness（忠实度）**：答案是否忠于召回的上下文，防止模型幻觉，核心反幻觉指标
> - **Answer Relevance（相关性）**：答案是否真正回答了用户的问题
>
> 工具链：RAGAS 框架提供上述指标的完整自动化评测，不需要全人工标注。人工评估作为补充，对 RAGAS 打分异常的样本做抽样复核。"

**常见追问 & 标准回答：**

| 追问 | 标准回答 |
|---|---|
| "Recall@K 和 MRR 有什么区别？" | "Recall@K 是'有没有'的问题：前 K 个里有没有对的，有就算 1，没有算 0。MRR 是'在哪'的问题：排第 1 名是 1.0，排第 2 名是 0.5，排第 3 名是 0.33，越靠前越好。两者互补：Recall@K 衡量覆盖面，MRR 衡量排序质量。" |
| "Faithfulness 怎么自动评估？" | "RAGAS 的方法：把召回的 chunk 和生成的答案都给一个 LLM，让它判断'答案里每个陈述能不能从上下文里找到依据'，能找到的陈述比例就是 Faithfulness 分数。本质是用 LLM 做裁判。" |
| "除了这四个还有什么指标？" | "RAGAS 还提供 Context Precision（召回的 chunk 有多少是真正有用的，衡量精度）和 Context Recall（正确答案需要的信息有多少被召回了）。实际落地优先看 Faithfulness（防幻觉）和 Recall@K（覆盖面），这两个最直接反映用户体验。" |

---
