### Q1：IO 多路复用（select/poll/epoll 三模型区别）—— P0 薄弱点复考

**考点：** 操作系统、IO 模型、高并发网络编程（历史 3 场答不上，2026-06-30 已考过一次仍需巩固）

**面试官提问：** 你们的 Sitemap 抓取系统的下载环节，需要同时对接海量站点发起 HTTP 请求（高峰期 96 万+/小时）。假设不依赖现成 HTTP 客户端库的连接池封装，自己在 Java 层面设计这个"海量并发下载"的网络 IO 模型：你会选择 BIO（每连接一线程）还是基于 NIO 做 IO 多路复用？为什么？如果选多路复用，你会用 select、poll 还是 epoll？说说三者在数据结构、注册方式、事件获取方式上的差异。

**候选人第一次回答：**
> "使用nio到多路复用，采用epoll，去实现一个海量并发的下载模式。"

**⚠️ 面试官反馈：** 只有结论，没有任何论证（无场景铺垫、无选型理由、无机制细节），要求候选人补充。

**候选人补充回答：**
- BIO：会阻塞，大量资源等待
- select：底层用定长数组存储句柄，有数量上限；等待时拷贝2次；需要遍历整个数组找就绪资源，耗时
- poll：使用可变数组，突破了定长数组数量上限，但依旧2次拷贝，依旧需要遍历整个集合找就绪资源
- epoll：注册时候注册一个"就绪的红黑树"；就绪时候从等待队列移除到"就绪队列这个红黑树"下；不需要拷贝2次；不需要遍历整个集合，直接看就绪事件的红黑树/队列即可
- 主动承认：ET/LT 两种模式不了解

**✅ 做对的部分：** BIO 阻塞点、select 定长数组+上限+遍历、poll 可变数组+无上限+仍需遍历+仍2次拷贝，方向基本正确。

**❌ 关键错误：** 把 epoll 的"红黑树"和"就绪链表"职责搞混了。正确结构是**两个独立数据结构**：
- 红黑树：存储**全部已注册**的 fd，用于 epoll_ctl 增/删/改，O(logN)
- 就绪链表（双向链表）：只存储**已就绪**的 fd

fd 就绪时，是内核通过**中断回调**把对应节点**加入就绪链表**，而不是"从等待队列移到红黑树"——红黑树自始至终只是全量注册表，不参与就绪状态的存取，epoll_wait 取的是就绪链表，不是红黑树。

**❌ 明确空白：** ET（边缘触发）vs LT（水平触发）机制完全不了解 —— 历史 P0 薄弱点，本场需重点讲解。

**💡 完整参考答案（STAR 结构）：**

**S：** 爬虫下载环节需要同时维持数万个 HTTP 连接，绝大多数连接在等待网络响应（IO 密集型），只有少数连接在某一时刻真正有数据可读。

**T：** 设计一个低 CPU 开销、fd 数量无上限、能高效感知"哪些连接就绪"的网络 IO 模型。

**A（方案选型）：**

| 特性 | BIO | select | poll | epoll |
|------|-----|--------|------|-------|
| 并发模型 | 每连接一线程 | 单线程轮询 | 单线程轮询 | 单线程/少量线程事件驱动 |
| 数据结构 | - | 位图 FD_SET（最大1024） | pollfd 数组（无上限） | 红黑树（全量注册）+ 就绪链表（仅就绪） |
| 注册方式 | - | 每次调用全量传入 | 每次调用全量传入 | epoll_ctl 一次注册，长期生效 |
| 事件获取 | - | O(N) 遍历全部 fd | O(N) 遍历全部 fd | O(1)，直接取就绪链表 |
| 拷贝代价 | - | 每次调用2次拷贝（用户态↔内核态） | 每次调用2次拷贝 | 注册时一次，后续 epoll_wait 无需重复拷贝全量 fd |
| 触发模式 | - | 仅 LT | 仅 LT | 支持 LT + ET |

为什么不用 BIO：万级连接 = 万级线程，线程栈内存（默认1MB/线程）+ 上下文切换开销直接打爆系统。
为什么不用 select/poll：每次调用都要把全量 fd 集合拷贝进内核 + O(N) 遍历找就绪项，连接数越大、就绪比例越低，浪费越严重（万级连接里可能同时只有几十个就绪）。
为什么选 epoll：注册一次常驻内核，就绪回调直接进链表，epoll_wait 只返回就绪的少量 fd，复杂度与"当前就绪数"成正比而非"总连接数"，天然适合"连接多、就绪少"的场景。

**R：** epoll 是 Linux 高并发网络编程标配，Nginx、Redis、Netty 底层均基于 epoll。单机可支撑十万级并发连接，是爬虫/网关/IM 类系统的基石。

### Q1-追问：边缘触发（ET）vs 水平触发（LT）

**考点：** epoll 触发模式、非阻塞 IO、EAGAIN（历史 P0 空白点）

**候选人回答：** ❌ 明确表示不了解

**💡 完整参考答案：**

一句话：**LT 是"没读完就一直通知"，ET 是"只在状态变化那一刻通知一次，不读完也不会再提醒"。**

场景：某个 socket 缓冲区来了 8KB 数据，应用只读了 4KB。

**LT（水平触发，默认）：** 只要缓冲区还有数据没读完，每次 epoll_wait 都会再次通知你 → 编程简单，不容易漏数据，但可能重复触发多次系统调用。

**ET（边缘触发）：** 只在"从不可读变为可读"这个边缘时刻通知一次；剩下的 4KB 不会再单独触发通知，除非有新数据到达。因此 **ET 必须配合非阻塞 IO + while 循环读到 EAGAIN**（`read()` 返回 -1 且 `errno == EAGAIN` 表示当前缓冲区已读空）才能保证不漏数据。ET 的优势是减少 epoll_wait 调用次数，性能更高，但编程复杂度更高。

Netty 默认策略：ET + 非阻塞 IO + 循环读完，兼顾性能与正确性。

### Q1-追问2：ET 模式下只 read() 一次不循环到 EAGAIN 会有什么后果？

**面试官提问：** 结合爬虫下载场景，如果下载线程池基于 epoll 的 ET 模式运行，某个连接的处理逻辑只 `read()` 一次就去处理业务、没有 while 循环读到 EAGAIN，会导致什么后果？如果这个连接后续再也没有新数据到达，会发生什么？

**候选人回答：**
> 可能会导致每次有多个请求到达缓冲区，但是只读取一条，处理完业务逻辑后释放线程池，之后发起新的请求，之后缓冲区一直有旧的请求的响应，但是每次只读取一条，把整个操作变成串行，没有充分发挥 IO 多路复用的优点，依旧是单线程处理……极大程度降低吞吐量。**如果没有新请求，在缓冲区的响应会一直在缓冲区等待，无法被及时处理。**

**✅ 做对的部分：** 结尾这句"没有新数据的话，旧数据会一直卡在缓冲区里、无法被处理"——这正是本题的核心答案，抓住了。

**❌ 归因错误：** 把问题定性成"退化成串行处理、吞吐量降低"是不准确的。这不是一个"效率问题"，而是一个**正确性/数据丢失（数据不可达）问题**：
- ET 模式下，某个 fd 只在"从不可读→可读"这个边缘时刻通知一次
- 只读一次没读完，剩下的数据留在内核缓冲区里，**epoll 不会因为"你没读完"而重新通知你**
- 这不是变慢，而是这部分遗留数据**永远不会被应用层感知到**，除非该 fd 后续有新数据到达、产生新的边缘事件，你才会顺带把这批新数据连同旧的一起读到
- 如果连接后续再无新数据（比如对端只发一次响应就不再发送），这部分数据会**一直卡死在内核缓冲区里**，这个 TCP 连接实质上"卡死"了——上层业务永远收不到完整响应，会一直等待直到连接超时/被动断开，属于连接级别的处理停滞，而不是"整体吞吐下降"

**💡 参考答案：** ET 模式下漏读的后果本质是"**该连接的剩余数据从此失联**"，必须用 `while(read() != EAGAIN)` 保证一次事件把缓冲区读干净，这是 ET 模式的编程强约束，不是可选的性能优化项。

**STAR 评分：** S ❌ | T ❌ | A ⚠️（结论正确但机制归因错误）| R ❌
