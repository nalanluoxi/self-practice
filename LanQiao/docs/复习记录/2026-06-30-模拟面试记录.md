### Q1：IO 多路复用（select/poll/epoll 三模型区别）

**考点：** 操作系统、IO 模型、高并发网络编程（P0 薄弱点，2场答不上）

**面试官提问：** 你在美团的 Sitemap 爬虫系统中做了多线程并发重构，实现了从 2.5 万到 96 万的产出提升。在这个场景下，多个爬虫 worker 需要同时维持大量 HTTP 连接去抓取目标站点。如果让你来设计这个爬虫网络层的 IO 事件检测，操作系统的 select、poll、epoll 三种 IO 多路复用模型有什么区别？结合你的爬虫场景，你觉得哪个更适合？为什么另外两个不行？

**候选人回答要点：**
- select：fd 数组记录资源，每次访问从用户态→内核态→用户态拷贝两次，需要扫描整个数组，数组长度有限制
- poll：突破了数组长度限制，但仍需每次拷贝整个 fd 结构集合两次，扫描整个集合
- epoll：注册事件到红黑树，就绪任务保存到就绪队列，省略了磁盘拷贝和扫描整个集合的消耗

**✅ 面试官评价：** 框架正确，三个模型核心区别基本说清。

**⚠️ 不足：**
1. ❌ "磁盘拷贝"说法不准确——实际是**用户态↔内核态的内存拷贝**，不是磁盘 IO
2. ❌ 未提及 **epoll 的两种触发模式（ET/LT）**——这是高频考点
3. ❌ epoll 的"省略拷贝"描述不精确——实际是 epoll_ctl 注册时一次拷贝到红黑树，后续 epoll_wait 只需取就绪链表

**💡 完整参考答案（STAR 结构）：**

**S：** 美团 Sitemap 爬虫系统有数百台机器同时维持数万个 HTTP 长连接去抓取目标站点，需要高效检测哪些 Socket 有数据可读/可写。如果用传统阻塞 IO，每个连接需要一个线程，数万连接直接打爆系统。

**T：** 设计一个能支撑万级并发连接的网络 IO 事件检测机制，要求 CPU 开销低、文件描述符无上限。

**A（方案选型）：**

| 特性 | select | poll | epoll |
|------|--------|------|-------|
| 数据结构 | 位图 FD_SET（最大1024） | pollfd 链表（无上限） | 红黑树 + 就绪链表 |
| 注册方式 | 每次调用全量传入 | 每次调用全量传入 | epoll_ctl 一次注册，长期生效 |
| 事件获取 | O(N) 扫描全部 fd | O(N) 扫描全部 fd | O(1) 只取就绪的 fd |
| 拷贝代价 | 每次调用两次拷贝（用户↔内核） | 每次调用两次拷贝 | 注册时拷贝一次，后续无拷贝 |
| 触发模式 | 仅水平触发(LT) | 仅水平触发(LT) | 支持 LT + ET（边缘触发） |

**epoll 核心优势：** 回调机制——fd 就绪时内核回调放入就绪链表，应用层 epoll_wait 直接取，不需要轮询。ET 模式只有状态变化时才通知，配合非阻塞IO + 循环读，一次 EPOLLIN 事件读完所有数据，减少 epoll_wait 调用次数。

**R：** epoll 是 Linux 下高并发网络编程的标配，Nginx、Redis、Netty 底层都依赖它。单机即可支撑数十万并发连接，是爬虫/IM/网关类系统的基石。

### Q2：边缘触发（ET） vs 水平触发（LT）

**考点：** epoll 触发模式、非阻塞 IO、EAGAIN

**面试官追问：** 边缘触发(ET)和水平触发(LT)的区别到底是什么？结合你的爬虫场景，如果某个 socket 一次来了 8KB 数据，而你的应用只读了 4KB，在 ET 和 LT 模式下分别会发生什么？

**候选人回答：** ❌ 不知道

**💡 完整参考答案：**

**一句话：LT 是"只要没读完就反复通知"，ET 是"只通知一次，没读完不再通知，直到下次有新数据到来"。**

**具体场景：** socket 缓冲区来了 8KB 数据

**LT 模式（默认）：**
- epoll_wait 返回，告诉你 fd 可读
- 你读了 4KB，还剩 4KB
- **下次 epoll_wait 还会通知你** → 直到读完
- ✅ 编程简单，不容易丢数据
- ❌ 可能重复触发，多系统调用

**ET 模式：**
- epoll_wait 返回，告诉你 fd 可读（从"不可读"变为"可读"的边缘变化）
- 你读了 4KB，还剩 4KB
- **下次 epoll_wait 不会通知你** → 没有新数据到达，状态未变
- 剩下 4KB 卡在缓冲区，直到新数据到达触发下一次 ET 通知
- ❌ **必须用 while 循环读到 EAGAIN**（返回 -1 且 errno=EAGAIN 表示读完了）
- ✅ 减少 epoll_wait 调用次数，性能更高

**ET 标准编程模式：**
```c
set_nonblocking(fd);
epoll_event.events = EPOLLIN | EPOLLET;

while (1) {
    n = read(fd, buf, sizeof(buf));
    if (n == -1) {
        if (errno == EAGAIN) break;  // 读完了
        else handle_error();
    }
    process(buf, n);
}
```

**Netty 默认策略：** ET 模式 + 非阻塞IO + 每次循环读完，兼顾性能和正确性。

### Q3：一致性哈希（P0 薄弱点 - 腾讯1面直接说忘记了）

**考点：** 分布式理论、一致性哈希、虚拟节点、Redis Cluster hash slot

**面试官提问：** 你在美团的站点频度调度里用 Redis 存每个站点的 TTL 和频度数据。假设未来数据量大了，Redis 要从 8 节点扩容到 16 节点。如果用传统的 hash(key) % N 做分片，扩容会发生什么问题？一致性哈希是怎么解决这个问题的？虚拟节点又解决了什么问题？

**候选人回答要点：**
- 一致性哈希通过 hash 环解决问题
- 创建虚拟节点随机分布在 hash 环上
- 对 Redis 节点进行 hash 计算，与最近的虚拟节点绑定
- 举例说明：虚拟节点 15、40、88；Redis 节点 hash=22 → 绑定到 40 虚拟节点
- key 查询同理：hash(key) 找最近的下一个虚拟节点
- 扩缩容只影响相邻节点的数据，不需全量迁移
- 主动补充：Redis 没有用一致性哈希，用了 16384 个 hash slot（hash 桶）分片，扩缩容重新分配桶、迁移桶

**✅ 面试官评价：** 比腾讯1面"直接说忘记了"进步巨大！hash 环、虚拟节点、扩容只影响相邻节点三个核心点全部说清，且主动对比 Redis Cluster hash slot。

**⚠️ 不足：**
1. ❌ **物理节点和虚拟节点的关系说反了**：不是说"计算 redis 节点 hash 值找最近虚拟节点绑定"，实际是**每个物理节点映射 150~200 个虚拟节点**，虚拟节点散列在环上
2. ❌ **虚拟节点的核心目的没说清楚**：解决**数据倾斜**——物理节点少时，环上节点分布不均匀会导致大量 key 落到同一个节点；虚拟节点通过分散成上百个点让负载更均衡

**💡 完整参考答案（STAR 结构）：**

**S：** Sitemap 频度调度系统的 Redis 集群，每天数十亿 URL 的频度状态存在 Redis。需要支持节点扩缩容而不引发大面积缓存失效，否则下游（爬虫/解析链路）会因大量 cache miss 打爆后端。

**T：** 设计一种分片方案——节点增减时数据迁移量最小，且不影响正在服务的其他节点。

**A（方案选型对比）：**

| 特性 | 传统取模 %N | 一致性哈希 | Redis Cluster hash slot |
|------|------------|------------|------------------------|
| 数据映射 | key直接对节点数取模 | key在hash环上顺时针找最近虚拟节点 | 16384个固定槽，key→槽→节点 |
| 扩容影响 | 几乎所有key重新映射→缓存雪崩 | 只影响相邻节点的key | 重新分配槽，迁移对应槽数据 |
| 数据倾斜 | 无（均匀分布） | 少量节点时严重 → 虚拟节点解决 | 槽均匀分配，很少倾斜 |
| 复杂度 | 最低 | 中等 | 较高（需处理槽迁移状态） |

**核心原理：**
1. **哈希环**：0 ~ 2³²-1 构成虚拟环
2. **虚拟节点**：每个物理节点创建 150~200 个虚拟节点（通过 hash(ip#1)、hash(ip#2)... 生成）散列在环上——解决物理节点少时的数据倾斜
3. **路由**：key 计算 hash，顺时针找到第一个虚拟节点 → 映射到物理节点
4. **扩缩容**：只影响相邻节点的数据，其他节点零迁移

**R：** Redis Cluster hash slot 是工程上更确定性的方案（16384个槽，精确控制）。一致性哈希更通用（不需要槽的概念），适合分布式缓存/存储系统。

**📊 STAR 评分：**

| 维度 | 评分 | 说明 |
|------|------|------|
| **S（场景）** | ❌ | 没有说出"为什么需要扩展到16个节点"的业务背景 |
| **T（任务）** | ❌ | 没有说明分解到的具体任务是什么 |
| **A（方案选型）** | ⚠️ 核心框架正确 | 哈希环/虚拟节点/扩缩容影响范围都说清了，但虚拟节点和物理节点的绑定关系说反了 |
| **R（结果对比）** | ✅ 较好 | 主动对比了 Redis Cluster hash slot（16384个桶），有横向比较意识 |

### Q3-追问：一致性哈希 vs Redis Cluster hash slot 设计思想对比

**横向比较追问（规则10）：** 你提到了 Redis Cluster 用 16384 个 hash slot 做分片。一致性哈希（虚拟节点散列在环上）和 Redis Cluster 的固定 hash slot 方案，在设计思想上有什么本质区别？各自适合什么场景？为什么 Redis 选择 hash slot 而不是一致性哈希？

**候选人回答：** ❌ 不清楚

**💡 完整参考答案：**

**一致性哈希（去中心化、弹性扩缩）：**
- key 归属每次查询实时计算，无中心化元数据
- 优点：节点增减无需数据迁移协调，适合节点频繁变动场景
- 缺点：概率均匀不是精确均匀；相邻节点数据迁移边界模糊

**Redis Cluster hash slot（固定槽、精确控制）：**
- 将全量 key 空间固定16384个槽，key→CRC16(key)%16384→槽号，槽→节点映射由gossip同步
- 优点：
  1. **精确负载控制**：16384槽均分3节点=约5461槽/节点，可手动迁移槽调负载（CLUSTER SETSLOT）
  2. **元数据仅2KB**：16384 bit，再大膨胀再小不均匀
  3. **迁移可观测**：SETSLOT IMPORTING/MIGRATING 精确按槽迁移，可查进度
  4. **客户端简单**：本地缓存2KB槽映射表，MOVED/ASK 重定向清晰
- 缺点：实现复杂（gossip + 槽迁移协议）

**为什么 Redis 选 hash slot 而不是一致性哈希？**
Redis 把**确定性和运维可控性**放在第一位：
- 槽迁移精确可控，可观测进度
- 手动调整热点分区（用 CLUSTER SETSLOT 迁移特定槽）
- 16384 是精确计算的 trade-off：每个节点心跳包带这 2KB 的槽位信息，再多则心跳膨胀，再少则不够均匀

**方案对比总结：**

| 维度 | 一致性哈希 | Redis Cluster hash slot | 传统取模 %N |
|------|-----------|------------------------|------------|
| 确定性 | 概率均匀 | 精确均匀 | 精确均匀 |
| 元数据量 | 虚拟节点数×N（可能大） | 16384槽=2KB | 无 |
| 扩缩容影响 | 相邻节点 | 被迁移的槽对应节点 | 全部节点 |
| 运维可控性 | 低（自动扩散） | 中（手动/自动迁移槽） | 低（全量重分布） |
| 典型应用 | Memcached、负载均衡 | Redis Cluster | 简单分片 |
| 实现复杂度 | 中等（需客户端支持） | 较高（gossip+槽迁移） | 最低 |

**现代化方向：**
- Codis：proxy层+1024槽（比16384少，支持动态迁移）
- Google Maglev：一致性哈希+哈希表实现确定性O(1)查找
- Kafka partition：固定分片思路，broker增减触发partition reassign

### Q4：CAP 理论（P0 薄弱点 🔴 腾讯1面最严重失分）

**考点：** 分布式理论、C/A/P 定义、CP vs AP 选型

**面试官提问：** 你的 Sitemap 系统里限流状态存在 Redis（AP架构），分布式协调用 ZooKeeper（CP架构）。假设机房网络突然断开，出现分区（Partition）——这时候 Redis 还能正常读写吗？ZooKeeper 还能正常选主吗？它们的区别恰恰对应了分布式系统最核心的 CAP 理论。说出 C、A、P 三个字母分别代表什么，以及为什么三者最多同时实现两个？Redis 和 ZooKeeper 分别属于 CA/CP/AP 中的哪个组合？

**候选人回答要点：**
- C（一致性）：所有节点的数据都是一致的
- A（可用性）：服务请求返回正常响应
- ❌ P（分区容错性）：一个分区节点故障后，其他机器可以快速故障修复使用 【严重错误】
- 最多三个可以实现2个：CA/CP/AP
- 强一致+分区容错 → 牺牲可用性，降低吞吐
- 高可用+弱一致 → 选AP，最终一致性
- 结合 Sitemap：用 Redis 做消息去重幂等，非强一致场景，选AP最终一致性。即使节点故障，其他节点升级为读节点，消息重复消费后后续数据模块对 URL 过滤处理

**✅ 面试官评价：** C 和 A 的定义正确，能结合 Sitemap 项目分析为什么选 AP——这是最好的地方。

**❌ 严重错误：P 的定义完全说错。** P（Partition Tolerance）是**网络分区（Network Partition）**——节点间通信中断，不是节点挂了。你说的是"节点故障后快速故障修复"——那是**高可用（HA）/故障转移**，与 P 无关。

**💡 完整参考答案（STAR 结构）：**

**S：** Sitemap 系统跨多机房部署，Redis 做去重/限流状态存储，ZooKeeper 做分布式协调。网络分区（机房断网、交换机故障）是分布式系统的必然事件。

**T：** 设计分布式系统架构时，必须在一致性、可用性、分区容错性之间做出取舍——没有"全都完美"的方案。

**A（CAP 三个字母精确定义）：**
- **C（Consistency 一致性）**：所有节点**同一时刻**看到的数据一致。Client 写入节点 A，节点 A 同步给 B 之前，Client 读 B 应读到什么？CP：等同步完再返回；AP：直接返回旧数据。
- **A（Availability 可用性）**：每次请求都能获得**非错误响应**（但不保证数据最新）。CP 系统在分区时：部分节点返回错误或超时 → A 被牺牲。
- **P（Partition Tolerance 分区容错性）**：**节点间网络通信中断**（不是节点挂了）时，系统仍能正常服务。跨机房部署、网络抖动、交换机故障都是 P 问题。
- ⚠️ P ≠ 故障恢复/HA。节点宕机是另一回事。P 是**两台机器网线被拔了，各自还在跑，但互相联系不上**。

| 组合 | 含义 | 典型系统 | 分区时表现 |
|------|------|---------|-----------|
| CA | 一致性+可用性 | 传统单机MySQL | 没有分区时完美，一旦分区只能停服 |
| CP | 一致性+分区容错 | ZooKeeper/etcd | 分区时少数派节点不可写入（不可用） |
| AP | 可用性+分区容错 | Redis Cluster/Eureka/DNS | 分区时各节点各自服务，最终一致 |

**为什么 P 是必选项？** 网络分区是分布式系统的**必然事件**。所以实际上你只能在 **CP 和 AP 之间选**。

**R（Sitemap 选型分析）：** Sitemap 选 AP 正确——非强一致场景，重复消费有下游 Bloom Filter 兜底（URL 级去重）。如果选 CP（强一致同步），分区时大量节点不可用，业务直接中断，损失更大。

**📊 STAR 评分：**

| 维度 | 评分 | 说明 |
|------|------|------|
| **S（场景）** | ✅ | 结合了 Sitemap 项目的实际选型 |
| **T（任务）** | ❌ | 没有说清楚"为什么要在 CAP 之间做取舍，业务矛盾是什么" |
| **A（方案选型）** | ⚠️ C/A 正确 | C 和 A 定义基本对，但 **P 定义完全错误**（节点故障≠网络分区） |
| **R（结果分析）** | ✅ | 能结合项目场景分析选 AP 的理由，以及对下游的影响 |

### Q4-追问：AP→CP 改造场景题

**场景题追问（规则 E）：** 如果你现在有一个新的核心业务——同一个 URL 绝对不能爬两次，否则会产生重复计费。这时候你还能选 AP 吗？如果必须改成 CP，你会怎么改造你当前的 Redis 去重链路？

**候选人回答：** （等待回答中...）
