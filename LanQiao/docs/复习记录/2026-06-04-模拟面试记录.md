## Q35：Spring IoC 与 AOP 底层原理

### 原题
> Spring IoC 核心思想是什么？AOP 底层怎么实现？JDK 动态代理和 CGLIB 区别？

### 我的回答
IoC 是依赖注入，从手动 new 改为容器创建 Bean 注入。AOP 底层通过反射实现，JDK 动态代理通过继承创建子类重写父方法；CGLIB 通过接口实现同一接口代理。

### ⚠️ 回答缺陷
- **JDK 动态代理和 CGLIB 描述完全说反了**：
  - JDK 动态代理 = 基于**接口**，不是继承
  - CGLIB = 基于**继承**（生成子类），不是接口

### ✅ 更完善的回答
**IoC**：将对象创建和依赖管理交由 Spring 容器，开发者只声明依赖（@Autowired），容器启动时创建 Bean 并自动注入，降低耦合。

**AOP 两种动态代理**：
- **JDK 动态代理**：目标类必须**实现接口**，代理类与目标类实现同一接口，通过 `Proxy.newProxyInstance()` + `InvocationHandler` 拦截
- **CGLIB**：目标类**不需要接口**，生成目标类的**子类**重写父类方法，`final` 类和 `final` 方法无法代理

**Spring 选择规则**：有接口默认用 JDK 动态代理；无接口用 CGLIB。Spring Boot 2.x 之后默认统一用 CGLIB。

## Q36：Spring Bean 生命周期

### 原题
> Spring Bean 的生命周期是什么？从容器启动到 Bean 可以被使用经历了哪些阶段？

### 我的回答
加载、初始化、实例化，记不清楚了。

### ⚠️ 回答缺陷
- **顺序不对**：实例化在前，初始化在后
- **缺少关键阶段**：属性填充、Aware 回调、BeanPostProcessor 前后置处理、销毁阶段

### ✅ 完整生命周期（必须背熟）
1. **实例化**：反射调用构造方法创建对象（属性未赋值）
2. **属性填充**：依赖注入，填充 @Autowired、@Value 等
3. **Aware 接口回调**：让 Bean 感知容器信息（BeanNameAware、ApplicationContextAware 等）
4. **BeanPostProcessor 前置处理**：`postProcessBeforeInitialization()`，AOP 代理在此生成
5. **初始化**：@PostConstruct → InitializingBean.afterPropertiesSet() → 自定义 init-method
6. **BeanPostProcessor 后置处理**：`postProcessAfterInitialization()`
7. **Bean 可以正常使用**
8. **销毁**：@PreDestroy → DisposableBean.destroy() → 自定义 destroy-method

**记忆口诀**：实例化→属性填充→Aware→前置处理→初始化→后置处理→使用→销毁

**关联项目**：简历中 DSL 规则引擎的 `@PostConstruct` 正则预编译在第5步执行，此时属性已注入完毕，可以安全读取配置。

## Q37：Spring 循环依赖与三级缓存

### 原题
> Spring 循环依赖是什么？怎么解决的？三级缓存分别存什么？

### 我的回答
Bean A 依赖 B，B 依赖 A 导致循环依赖。Spring 通过三层缓存解决：Bean 加载工厂、半成品缓存、完全加载的 Bean 对象。

### ⚠️ 回答缺陷
- **三级缓存名称和内容不准确**：顺序说反了，且没有说清楚每级存什么
- **为什么需要三级而不是两级没有解释**：三级缓存的核心价值是延迟生成 AOP 代理

### ✅ 更完善的回答
**三级缓存**（从一到三）：
- **一级** `singletonObjects`：完全初始化好的 Bean（可直接使用）
- **二级** `earlySingletonObjects`：早期暴露的 Bean（已实例化未完成属性填充）
- **三级** `singletonFactories`：Bean 工厂（ObjectFactory，用于生成早期 Bean 或 AOP 代理）

**解决流程**：
1. 创建 A，实例化后将 A 的工厂放入三级缓存，开始属性填充
2. 发现依赖 B，去创建 B
3. B 实例化后发现依赖 A，从三级缓存取出 A 的工厂生成早期引用，放入二级缓存
4. B 拿到 A 的早期引用，完成初始化进入一级缓存
5. A 拿到完整的 B，完成初始化进入一级缓存，清除二三级缓存记录

**为什么需要三级**：三级存工厂而非对象，目的是延迟生成 AOP 代理，让代理生成时机更灵活。

**注意**：构造器注入的循环依赖 Spring 无法解决，实例化阶段就需要依赖，还没机会放入三级缓存。

## Q38：场景题 — 并发更新同一行记录

### 原题
> 多个消费线程同时对同一域名的 crawl_count 做 +1 更新，MySQL 层面会出现什么问题？有哪些解决方案？

### 我的回答
并发请求会给 MySQL 带来压力（连接数上限），使用限流控制并发数。多请求同时修改同一行会出现数据不一致。解决：① MQ 削峰异步减少 DB 压力 ② 时间戳比较，只保留最新记录，丢弃旧记录 ③ 按 dt/hour 分区避免修改同一条记录。

### ⚠️ 回答缺陷
- **核心问题没答到**：并发读-改-写导致**丢失更新（Lost Update）**——两个线程同时读到 count=100，各自+1后写回101，少加了一次
- **解决方案不够系统**：没有说出乐观锁、悲观锁、MySQL 原子更新等标准方案

### ✅ 更完善的回答
**核心问题**：`SELECT count → count+1 → UPDATE` 三步非原子，并发时互相覆盖，导致**丢失更新**。

**解决方案对比**：
1. **MySQL 原子更新**：`UPDATE t SET count=count+1 WHERE id=?`，数据库引擎保证原子性，最简单高效
2. **乐观锁（版本号）**：`UPDATE ... WHERE version=?`，CAS 思想，失败重试，适合冲突概率低的场景（时间戳比较是乐观锁的变体）
3. **悲观锁**：`SELECT ... FOR UPDATE` 加行锁，串行执行，冲突概率高时使用，性能代价大
4. **MQ 按 domain 分区**：同一域名消息路由到同一分区，单线程消费，从根源消除并发（关键是要指定 domain 为分区 key）
5. **Redis INCR + 异步落库**：`INCR` 原子累加，定期批量写 MySQL，减少 DB 压力

**此业务场景最优**：方案1，直接 MySQL 原子更新，简单可靠无额外依赖。

## Q39：场景题 — 线上 CPU 飙高排查

### 原题
> 线上接口响应从 200ms 飙到 8s，CPU 使用率 95%，怎么一步步排查？

### 我的回答
查看监控大盘确认耗时步骤，top 查看 CPU 消耗最大的任务，配合日志和监控打点定位请求，先限流降级降低吞吐，查看线程池是否过多导致上下文切换，排查 Redis/MySQL 等下游中间件。

### ⚠️ 回答缺陷
- **缺少精确定位代码的手段**：`top -H` 找热点线程 TID → 转十六进制 → `jstack` 找对应线程栈，是定位到具体代码行的核心步骤
- **没有提到 GC 排查**：CPU 飙高 + 响应慢的常见原因是频繁 Full GC，需用 `jstat -gcutil` 确认

### ✅ 更完善的回答（三板斧）
**第一步**：看监控大盘，确认单机/多机、GC 频率是否异常

**第二步：精确定位 CPU 热点**
```bash
top -H -p <pid>           # 找 CPU 最高的线程 TID
printf '%x\n' <TID>       # TID 转十六进制
jstack <pid> | grep <hex> # 找到该线程正在执行的代码
```

**第三步：常见原因判断**
- 线程栈在正则/JSON → CPU 密集计算
- 线程栈在 GC 方法 → 频繁 Full GC，用 `jstat -gcutil <pid> 1000` 确认
- 线程栈在等锁 → 死锁/锁竞争，jstack 会直接提示 deadlock
- 下游慢 → IO 等待，CPU 不高但响应慢

**第四步**：先限流降级保服务，再扩容/重启争取时间，最后修复根因

## Q40：场景题 — 文件重复入库防重设计

### 原题
> 两个用户同时上传相同文件到同一知识库，怎么保证不重复入库？

### 我的回答
用文件名去重，插入前查询同名文件是否存在。升级方案：计算文件 hash 作为数字签名做去重。并发问题：开启事务，保证线程 A 修改后影响线程 B 的查询。

### ⚠️ 回答缺陷
- **文件名去重不可靠**：同文件改名会漏，同名不同内容会误判
- **事务解决不了并发查重问题**：两个请求同时查询时 A 未提交，B 查不到，都认为"不存在"然后都插入，仍然重复
- **没有说出唯一索引兜底和分布式锁**

### ✅ 更完善的回答
**文件去重**：计算文件内容 MD5/SHA256 作为唯一指纹，在 `(knowledge_base_id, file_hash)` 上建**唯一索引**。

**并发安全两种方案**：
1. **唯一索引 + 捕获异常**：直接 `INSERT IGNORE` 或捕获 `DuplicateKeyException`，数据库唯一约束兜底，两个并发请求只有一个成功。最简单可靠。
2. **Redis 分布式锁**：以 `knowledgeBaseId+fileHash` 为 key，`SET NX` 获取锁，持锁期间完成查重+插入，释放锁。适合插入前有复杂逻辑的场景。

**完整流程**：计算 hash → Redis 分布式锁 → 查重（存在返回已有记录）→ 插入 DB（唯一索引兜底）→ 释放锁 → 触发异步分块向量入库

## Q41：场景题 — HTTP 状态码处理与循环重定向

### 原题
> 爬虫抓取返回 301 和 404，分别怎么处理？业务含义是什么？循环重定向怎么发现和处理？

### 我的回答
301 是浏览器有缓存进行重定向，404 是抓取失败/死链，直接丢弃。循环重定向未回答。

### ⚠️ 回答缺陷
- **301 含义说错**：301 是**永久重定向**，不是浏览器缓存。浏览器缓存相关的是 **304 Not Modified**
- **循环重定向检测方案未回答**

### ✅ 更完善的回答
**301 永久重定向**：URL 已永久迁移。处理：跟随重定向用新 URL 替换旧 URL，旧 URL 标记"已迁移"，建立新旧 URL 映射防重复入库。

**404 死链**：记录到死链库跳过调度，通知下游过滤，多次 404 的域名降低调度优先级。

**循环重定向检测（A→B→C→A）**：
- 每次跳转前用 `Set` 记录已访问 URL，新 URL 在 Set 中则判定为循环立即终止
- 设置最大跳转次数上限（如5次），超过直接放弃
- 告警通知人工核查

**HTTP 状态码核心**：301永久重定向、302临时重定向、**304缓存未变更**、404不存在、403无权限、500服务端错误

## Q42：HTTP 长连接与 HTTP/2 多路复用

### 原题
> 爬虫频繁请求同一域名，每次重建 TCP 有什么问题？HTTP/1.1 怎么解决？HTTP/2 做了哪些优化？

### 我的回答
重建 TCP 浪费时间在三次握手和四次挥手上。HTTP/1.1 引入长连接，超时才断开。HTTP/2 多路复用，一个 TCP 连接并发发送多条请求，奇数流 ID 是客户端发起，偶数是服务端推送。业务上主动限制请求频率（反爬、保护小站、带宽限制）。

### ✅ 评价
回答完整，流 ID 奇偶数细节正确，结合业务场景说明是加分项。

### ✅ 补充知识点
- **HTTP/1.1 队头阻塞**：Keep-Alive 虽然复用连接，但同一连接内请求串行，前一个卡住后面全卡住
- **HTTP/2 解决队头阻塞**：帧+流 ID 并发传输，彻底消除 HTTP 层队头阻塞
- **HTTP/2 头部压缩（HPACK）**：减少重复 header 传输开销
- **注意**：HTTP/2 解决了 HTTP 层队头阻塞，但 TCP 层仍有队头阻塞（丢包时整条连接等待重传），HTTP/3 用 QUIC（UDP）彻底解决

## Q43：ReentrantLock vs synchronized，AQS 原理

### 原题
> ReentrantLock 和 synchronized 核心区别？ReentrantLock 底层的 AQS 是什么，核心数据结构是什么？

### 我的回答
ReentrantLock 用状态量记录是否获取锁，CLH 队列记录等待线程。synchronized 使用 monitor 锁，有偏向锁→轻量级锁→重量级锁升级过程。

### ⚠️ 回答缺陷
- **ReentrantLock 功能优势没说**：可中断、超时获取、公平锁、多 Condition
- **AQS state 的含义没说清**：0=未锁，>0=重入次数
- **没有说 park/unpark 机制**：获取锁失败入队挂起，释放后唤醒队头

### ✅ 更完善的回答
**ReentrantLock vs synchronized**：
- ReentrantLock：可中断等待、超时获取、公平锁选项、多 Condition 精细控制，必须手动 unlock()
- synchronized：JVM 自动释放，有锁升级优化，使用更简单

**AQS 核心数据结构**：
- `state` 整型变量：ReentrantLock 中 0=未锁，>0=重入次数
- CLH 变体**双向链表**：等待线程封装为 Node 排队
- 获取锁失败 → 入队 → `park()` 挂起；锁释放 → `unpark()` 唤醒队头下一个节点
