## Q1：SynchronousQueue 背压机制 vs LinkedBlockingQueue

### 原题
> 将系统从单线程消费 Mafka 重构为"回调线程 + 业务线程池异步并行模型"，并用 SynchronousQueue 实现背压。SynchronousQueue 是如何实现背压的？它和 LinkedBlockingQueue 的核心区别是什么？

### 我的回答
SynchronousQueue 是无缓冲队列，有任务直接提交给线程池，没有就走拒绝策略；LinkedBlockingQueue 是有界队列，核心线程满了先进队列排队，队列满了再创建应急线程。通过在提交前检查线程池活跃线程数来控制 MQ 拉取速度，保证消息不丢。

### ⚠️ 回答缺陷
- 说"走拒绝策略"与"消息不丢"目标矛盾，没有主动解释清楚。
- 实际背压核心是：**主线程自旋等待**，而不是依赖拒绝策略。

### ✅ 更完善的回答
SynchronousQueue 是无缓冲的阻塞队列，每一次 `put()` 都必须等待对应的 `take()`，因此当线程池所有线程都在忙碌时，无法直接入队，`submit()` 会触发拒绝策略。

但在我们消息不丢的设计目标下，不能真正走到拒绝策略，而是在提交线程池之前，**主动用 while 循环检查 `getActiveCount() < maximumPoolSize`**，线程池满时 `Thread.sleep()` 自旋等待，直到有空闲线程才提交。这样 SynchronousQueue 的"无缓冲"特性配合主线程自旋，天然实现了背压效果：消费速度被线程池的处理能力所制约，避免消息堆积在内存中。

与 LinkedBlockingQueue 的核心区别：LinkedBlockingQueue 有缓冲区，线程池满时任务先排队，会消耗大量内存，且无法感知到真正的消费压力；SynchronousQueue 迫使生产方感知到消费方的处理能力，是更直接的背压机制。

## Q2：check-then-act 竞态条件

### 原题
> `getActiveCount() < maximumPoolSize` 这个判断不是原子操作，检查完之后提交之前线程池状态可能已变化，会造成什么问题？你们有没有处理？

### 我的回答
有概率出现检查时有空闲线程，但提交时线程池满了，导致消息丢弃。解决方案是对检查+提交步骤加 synchronized 锁，保证只有一个任务持有锁进行检查和提交，提交完释放锁。

### ✅ 评价
回答方向正确，能识别竞态并给出加锁方案，是及格回答。

## Q3：synchronized 锁的性能瓶颈与 Semaphore 优化

### 原题
> 每秒300条消息提交，全部串行化后会不会成为瓶颈？如何优化？

### 我的回答
使用 Semaphore 信号量替代 synchronized：信号量数量同步线程池最大线程数，提交前 acquire()，任务完成后 release()，获取失败则自旋等待超时后重投 MQ。同时注意异常情况下信号量未释放的问题（类似死锁），但守护线程检测方案复杂度较高，未采用。

### ⚠️ 回答缺陷
- 提到"异常导致信号量未释放"时，没有说出最简单的解法：**try-finally 保证 release() 必然执行**，这是 Semaphore 标准用法，不需要守护线程。

### ✅ 更完善的回答
用 Semaphore 替代 synchronized：初始化 `new Semaphore(maxPoolSize)`，配置变更时同步调整（`release(delta)` 或 `acquire(delta)`）。

关键点：
```java
semaphore.acquire(); // 获取令牌，获取不到则阻塞/自旋
try {
    threadPool.submit(task);
} finally {
    // 注意：release 应在任务执行完毕后调用，而非提交后立即调用
    // 实际上信号量在这里代表"线程池槽位占用"，应在任务内部 finally 中 release
}
```
异常场景下，通过 `try-finally` 块在任务执行体内保证 `semaphore.release()` 必然被调用，完全不需要守护线程，也不会出现信号量泄漏。

## Q5：令牌桶 Lua 脚本核心逻辑

### 原题
> 令牌桶 Lua 脚本里存了哪些字段？每次请求过来做了哪几步？

### 我的回答（Rhino 底层实现）
存储字段：补充速度、最大令牌数、当前令牌数、上次访问时间。
执行步骤：
1. 加载上述字段
2. 计算 (当前时间 - 上次访问时间) × 补充速度 = 新增令牌数
3. 当前令牌 + 新增令牌，取 min(结果, 最大令牌数)
4. 判断当前令牌是否 >= 请求令牌数，决定放行或拒绝
5. 更新令牌数和上次访问时间（不管放行与否都要更新，避免下次过度补偿）

### ✅ 评价
回答完整，"避免过度补偿"细节说明对原理理解深入。

## Q6：环形缓冲连续 3 次判断的防抖设计

### 原题
> 为什么用环形缓冲连续判断 3 次，而不是一次超过 80% 就立刻收缩？

### 我的回答
避免某一时刻突发流量导致误判。

### ✅ 评价
核心是**防抖**思想，回答正确但较简短。

### ✅ 更完善的回答
线程池活跃线程数是瞬时值，短暂的流量毛刺（如一次大请求批量涌入）可能瞬间拉高水位，但很快恢复正常。如果一次超过就收缩，会导致频繁的"收缩-恢复-收缩"抖动，增加系统不稳定性。

用环形缓冲记录最近 N 次采样，**连续 N 次都超过阈值才触发收缩**，本质是对信号做**滑动窗口滤波**，过滤掉短暂毛刺，只响应持续性的压力。这是自适应限流中经典的防抖设计模式。

## Q8：GZIP 流式解压 vs 全量解压

### 原题
> 为什么要用流式解压，而不是先把整个 .gz 字节数组一次性解压成完整字节数组再处理？

### 我的回答
HTML 大小不确定，有些页面内容很大，如果一次性解压需要申请很大的内存空间。

### ✅ 评价
核心点正确，简洁到位。

### ✅ 更完善的回答
一次性解压需要在内存中同时持有压缩数据和解压后数据两份内容，对于大页面可能触发频繁 GC 甚至 OOM。流式解压每次只读 1KB 进内存，内存占用恒定，且在高并发场景下多个任务并行处理时，总内存压力大幅降低。这是典型的**用时间换空间**的设计取舍。

## Q9：GZIPInputStream.read() 返回值与循环结束条件

### 原题
> 这个循环读取代码大概怎么写？GZIPInputStream.read() 返回值是什么，循环结束条件是什么？

### 我的回答
创建 1KB buffer 数组，字节数组转 ByteArrayInputStream 再转 GZIPInputStream，循环读取解压数据，转 UTF-8 字符串后追加到 StringBuilder，直到 next 是 null 后结束循环。

### ⚠️ 回答缺陷
- **`read()` 返回的是 `int`，不是对象，结束条件是返回值 == -1，不是 null**。这是 Java IO 基础，面试必考点。

### ✅ 更完善的回答
```java
ByteArrayInputStream bais = new ByteArrayInputStream(compressedBytes);
GZIPInputStream gzis = new GZIPInputStream(bais);
StringBuilder sb = new StringBuilder();
byte[] buffer = new byte[1024];
int len;
while ((len = gzis.read(buffer)) != -1) {
    sb.append(new String(buffer, 0, len, StandardCharsets.UTF_8));
}
```
`read(buffer)` 返回实际读入的字节数，-1 表示流结束。注意要用 `new String(buffer, 0, len, ...)` 而不是 `new String(buffer, ...)`，否则最后一次读取不满 1KB 时会包含无效字节。

## Q10：GZIP 技术选型——为什么不在网络层解压

### 原题
> 为什么不从网络层或框架层解决 GZIP 解压，而是在业务代码里手动处理？

### 我的回答
主要是为了适配现有代码框架，最小程度改动代码，减少对其他模块的影响。现有框架以字节数组方式记录抓取结果，用 Java 标准库 GZIPInputStream 可以实现热插拔效果，对接原始服务补全能力。从网络层修改改动较大，涉及面广，复杂度高。

### ✅ 评价
工程判断很务实，能说出"最小改动、热插拔"是加分项。

### ✅ 更完善的回答
技术选型的核心考量是**改动范围最小化**。现有链路已经以字节数组形式存储抓取结果，如果从网络层（如 OkHttp `addInterceptor` 自动解压、或 Nginx 层透明解压）介入，需要改动抓取框架本身，影响面广、风险高。选择 Java 标准库 `GZIPInputStream` 的优势在于：仅在解析模块新增一个判断分支，入参和出参类型不变，对上下游完全透明，符合**开闭原则**。其他可选方案：OkHttp 拦截器层（时机已过）、Apache Commons Compress（支持更多压缩格式，可作为后续扩展方向）。

## Q11：正则预编译性能影响

### 原题
> Java 中正则不预编译用 String.matches() 会有什么问题？Pattern.compile() 预编译原理是什么？

### 我的回答
不预编译每次都要把正则字符串编译成 Pattern 对象，每次匹配编译一次规则 + 构建匹配对象，N 条规则就是 N 次编译，请求量大时性能影响明显。Pattern.compile() 原理不太清楚。

### ⚠️ 回答缺陷
- `Pattern.compile()` 原理不熟悉。

### ✅ Pattern.compile() 原理补充
正则表达式本质是**有限自动机（NFA）**。`Pattern.compile()` 把正则字符串**解析成语法树，再编译成 NFA 状态机**，描述所有匹配路径。这个过程涉及词法解析、语法分析、状态构建，代价高。预编译后 `Pattern` 对象保存已构建好的状态机，每次 `matcher(input)` 只是把输入喂给状态机跑一遍，省去重建开销。

## Q12：HashSet 存 Pattern 能去重吗？

### 原题
> 你把预编译后的 Pattern 缓存到 HashSet，HashSet 去重依赖 equals() 和 hashCode()。Pattern 有没有重写这两个方法？两个相同正则字符串编译的 Pattern 能去重吗？

### 我的回答
使用 HashMap，以正则字符串作为 key，Pattern 作为 value 实现去重。或者继承 Pattern 重写 hashCode 和 equals。

### ⚠️ 回答缺陷
- 继承 Pattern 方案不可行：**Pattern 构造器是私有的，无法直接继承**。
- 实际代码确认用的是 `HashSet<Pattern>`，去重是失效的，属于轻微 bug，但因为匹配是遍历所有 Pattern，功能正确性不受影响，只是有重复匹配的冗余开销。
- 简历写"缓存至 HashSet"不准确，建议改为"预编译缓存"或"缓存至 Map"。

### ✅ 更完善的回答
`Pattern` 未重写 `equals()` 和 `hashCode()`，`HashSet<Pattern>` 的去重依赖对象引用地址，无法对同一正则字符串的不同 Pattern 实例去重。正确做法是用 `HashMap<String, Pattern>`，以正则字符串为 key 天然去重，同时保留预编译的 Pattern。继承方案不可行，因为 Pattern 构造器是私有的。面试时可主动指出这个实现细节，体现对代码的深度思考。

## Q13：热更新多线程安全问题

### 原题
> @MdpConfigListener 触发重编译热更新时，100 个请求线程正在遍历旧规则集合，同时配置变更替换集合，会发生什么问题？你们怎么处理的？

### 我的回答
使用 volatile 关键字保证数据一致性。监听到配置更新后，先创建新集合进行预编译缓存，全部缓存好后替换旧集合引用。volatile 会添加读写屏障，强制其他缓存失效从主存读取新内容。由于不是强实时性场景，短暂读取旧集合在业务上可接受。

### ✅ 评价
思路完全正确。能说出"先构建新集合、整体替换引用"是核心设计亮点，体现了并发安全意识。

### ✅ 更完善的回答（补充 Copy-on-Write 概念）
热更新采用 **Copy-on-Write + volatile** 双重保障：
- 监听到配置变更后，先在本地构建全新规则集合并完成所有 Pattern 预编译
- 再用 `volatile` 修饰的字段做原子引用替换
- `volatile` 的写屏障保证新集合对所有线程立即可见
- 旧集合替换后不再被修改，正在遍历旧集合的线程可安全完成本次匹配
- 由于规则更新不是强实时性场景，短暂过渡窗口业务可接受，无需引入锁

**关键概念**：这个模式叫 **Copy-on-Write（写时复制）**，`volatile` 保证引用替换的可见性，不修改原集合保证读线程安全，两者缺一不可。

## Q14：volatile 能保证原子性吗？

### 原题
> volatile 能保证原子性吗？volatile count++ 是线程安全的吗？为什么？

### 我的回答
不能保证原子性，只能保证可见性。volatile 底层通过插入读写屏障实现，禁止 JVM 指令重排，修改 volatile 数据时通知其他缓存失效，读取时强制重新读取主存。volatile count++ 不是线程安全的。

### ✅ 评价
回答正确，核心点全到位。

### ✅ 更完善的回答
`volatile` 只保证**可见性和有序性**，不保证原子性。底层通过插入内存屏障实现：写操作前后插入 StoreStore/StoreLoad 屏障，强制写入主内存并通知其他 CPU 缓存行失效；读操作前插入 LoadLoad 屏障，强制从主内存重新加载。

`volatile count++` 不是线程安全的，因为它对应三条字节码指令（getstatic、iadd、putstatic），线程可能在任意两条指令之间被切换，两个线程同时读到相同旧值各自加 1 后写回，产生数据丢失。

要保证原子自增，应使用 `AtomicInteger.incrementAndGet()`，底层基于 **CAS（Compare-And-Swap）** 硬件指令实现无锁原子操作。

## Q15：CAS 原理与缺陷

### 原题
> CAS 的原理是什么？CAS 有哪些经典缺陷？

### 我的回答
CAS 可能出现 ABA 问题：一个字段是 1，CAS 操作先获取当前值，计算目标值，检查是否匹配来判断期间是否被修改。但如果期间从 1 改为 2 又改回 1，CAS 无法感知。解决方案是添加版本号（单向递增），通过版本号规避 ABA 问题。

### ✅ 评价
ABA 问题和版本号解法正确，Java 对应实现是 `AtomicStampedReference`。

### ✅ 更完善的回答
**CAS 原理**：包含三个操作数——内存地址 V、预期值 A、新值 B。只有当 V 的当前值等于 A 时才将 V 更新为 B，否则不操作，整个过程由 CPU 的 `cmpxchg` 指令保证原子性，无需加锁。

**CAS 三个经典缺陷**：
1. **ABA 问题**：值 A→B→A，CAS 无法感知中间变化。解决：`AtomicStampedReference`，同时比较值和 stamp 版本号
2. **自旋开销**：CAS 失败后循环重试，高并发竞争激烈时 CPU 空转严重。解决：`LongAdder` 分段累加降低单点竞争
3. **只能保证单变量原子性**：多变量联动时无法覆盖。解决：`AtomicReference` 封装多变量为对象，或加锁

## Q16：synchronized 锁升级过程

### 原题
> synchronized 在 JDK 6 之后做了哪些优化？锁升级过程是怎样的？

### 我的回答
引入锁升级使锁更轻量化。无竞争时先用偏向锁，Mark Word 记录线程 ID，下次进入检查一致性直接进入；不一致时检查原线程是否退出同步块，退出则 CAS 修改；竞争激烈时升级轻量级锁，栈上创建锁记录通过 CAS 操作；更激烈时升级重量级锁，使用 Monitor 对象，含 owner 指针、wait 队列（wait() 挂起的线程）、等待队列（未获取锁的线程）。

### ⚠️ 回答缺陷
- **偏向锁撤销时机不准确**：不是检查原线程退出就直接 CAS，而是需要等到**全局安全点（STW）** 才能撤销，撤销代价较高。这也是 JDK 15 开始默认禁用偏向锁的原因。

### ✅ 更完善的回答
JDK 6 引入锁升级，锁状态存在对象头 **Mark Word** 中，升级路径单向不可逆：**无锁 → 偏向锁 → 轻量级锁 → 重量级锁**。

- **偏向锁**：首次获取时将线程 ID 写入 Mark Word，下次同一线程进入只需检查 ID 是否一致，零 CAS 进入。其他线程尝试获取时需在**安全点（STW）** 撤销，代价高，JDK 15 起默认禁用。
- **轻量级锁**：线程在栈帧上创建 Lock Record，CAS 将 Mark Word 替换为指向 Lock Record 的指针，失败则**自适应自旋**，超过阈值升级重量级锁。
- **重量级锁**：依赖 OS Mutex，Monitor 含三个结构：`_owner`（持锁线程）、`_EntryList`（竞争被阻塞线程）、`_WaitSet`（调用 wait() 挂起的线程）。涉及用户态→内核态切换，开销大。

## Q17：ThreadLocal 原理与内存泄漏

### 原题
> ThreadLocal 底层原理是什么？每个线程怎么拥有独立副本？内存泄漏怎么产生的？

### 我的回答
每个线程内部维护一个 ThreadLocalMap，key 是 ThreadLocal 的弱引用，value 是实际存储数据。每个线程有独立的 map 副本，修改不互相影响。由于 key 是弱引用，不使用时会被 GC 回收，但 value 是强引用，没有 key 后无法被回收导致内存泄漏。解决方案是使用完后在 finally 中 remove。

### ✅ 评价
回答完整正确，理解深入，finally 里 remove 的解法也到位。

### ✅ 更完善的回答（补充线程池场景）
每个 `Thread` 对象内部持有一个 `ThreadLocalMap`，key 是 `ThreadLocal` 实例的**弱引用**，value 是实际数据的强引用。`get()/set()` 本质是操作当前线程的 map，不同线程 map 相互独立，天然实现线程隔离。

**内存泄漏原因**：`ThreadLocal` 对象无外部强引用时，key 被 GC 回收变为 null，但 value 是强引用不会被回收，产生 null key → value 的"僵尸条目"。**在线程池场景下线程长期存活，ThreadLocalMap 一直存在，随请求累积持续占用内存，问题尤为严重。**

**解决方案**：使用完后在 `finally` 块中调用 `threadLocal.remove()`，主动清理当前线程的 map 条目。

## Q18：双亲委派机制

### 原题
> 双亲委派的流程是什么？为什么要设计这个机制？有没有打破双亲委派的场景？

### 我的回答
类加载时有四个类加载器，从最底层开始不直接加载，向上委托，直到最高级尝试加载，不能加载才向下回退。主要是为了避免 String 等基础类被修改。打破场景：Tomcat 打破了双亲委派。

### ⚠️ 回答缺陷
- **四个类加载器名字没说出来**：BootstrapClassLoader、ExtClassLoader、AppClassLoader、自定义 ClassLoader
- **Tomcat 打破原因没说清楚**：没解释为什么要打破、怎么打破的
- **缺少 SPI 机制场景**：JDBC DriverManager 是另一个经典打破场景

### ✅ 更完善的回答
**四个类加载器**（从高到低）：Bootstrap（JDK 核心类，C++ 实现）→ ExtClassLoader（JDK 扩展）→ AppClassLoader（应用 classpath）→ 自定义 ClassLoader

**流程**：收到加载请求先委托父加载器，直到 Bootstrap。Bootstrap 加载不了才往下回退。

**设计目的**：保证核心类唯一性和安全性，防止用户自定义 `java.lang.String` 替换 JDK String 导致系统异常。

**打破场景**：
1. **Tomcat**：多个 Web 应用可能依赖同一库的不同版本，为每个 Web 应用创建独立 `WebAppClassLoader`，优先加载自己应用下的类
2. **SPI 机制（JDBC）**：`DriverManager` 在 Bootstrap 加载，但需要加载 classpath 下的第三方驱动，Bootstrap 无法加载，通过**线程上下文类加载器**反向委托 AppClassLoader
3. **热部署/OSGi**：需要动态替换类，双亲委派缓存机制会阻止重新加载

## Q19：JVM 垃圾回收算法、G1 vs CMS

### 原题
> JVM 常见垃圾回收算法？G1 和 CMS 核心区别？为什么 G1 替代了 CMS？

### 我的回答
三种算法：标记-清除（有碎片）、标记-整理（整理消除碎片）、复制算法（内存利用率只有一半）。分代回收：Eden → Survivor（两块，复制算法，增加年龄）→ Old。G1 用 Region 替代物理分代，减少 STW，提高 GC 效率。

### ⚠️ 回答缺陷
- **CMS 的核心缺陷没说**：标记-清除产生碎片，并发模式失败退化为串行 Full GC，STW 时间不可控
- **G1 的 Garbage First 含义没说**：优先回收垃圾最多的 Region
- **G1 可预测停顿时间没说**：MaxGCPauseMillis 是 G1 最核心的优势

### ✅ 更完善的回答
**基础算法**：
- 标记-清除：有内存碎片
- 标记-整理：无碎片，但整理阶段 STW 时间长
- 复制算法：无碎片，内存利用率 50%，新生代常用

**分代回收**：Eden + Survivor(S0/S1) + Old，Young GC 用复制算法，对象年龄到阈值（默认15）晋升 Old，Old 区满触发 Full GC。

**CMS vs G1**：
- CMS：老年代并发标记-清除，碎片多，并发模式失败时退化串行 Full GC，STW 不可控
- G1：堆划分为等大 Region，逻辑上区分 Eden/Survivor/Old/Humongous，物理不连续。每次优先回收**垃圾最多的 Region**（Garbage First），用标记-整理无碎片。核心优势：可设置 **MaxGCPauseMillis 目标停顿时间**，根据历史数据预测保证停顿可控

**G1 替代 CMS 原因**：CMS 碎片问题导致 Full GC STW 不可控；G1 停顿时间可预测，对延迟敏感服务更友好。JDK 9 起 G1 为默认 GC，JDK 14 彻底移除 CMS。

## Q20：MVCC 原理与可见性判断

### 原题
> MVCC 是什么？解决了什么问题？InnoDB 中 MVCC 怎么实现的？ReadView 有哪几个字段？可见性判断规则是什么？

### 我的回答
MVCC 是多版本并发控制，解决脏读、幻读、不可重复读。依赖 ReadView 和 undo log。ReadView 四个字段：活跃事务 ID 列表、创建 ReadView 的事务 ID、活跃事务最小 ID、最大事务 ID+1。隐藏字段：行 ID（无主键时）、roll_pointer（指向上一版本）、trx_id（修改该记录的事务 ID）。可重复读隔离级别下，同一事务内所有查询使用第一个 ReadView。

### ⚠️ 回答缺陷
- **可见性判断具体规则不记得**：这是 MVCC 核心算法，面试必考

### ✅ 可见性判断完整规则
拿到数据行的 `trx_id`，按顺序判断：

1. `trx_id == creator_trx_id` → **可见**（自己修改的）
2. `trx_id < min_trx_id` → **可见**（修改时已提交）
3. `trx_id >= max_trx_id` → **不可见**（未来事务，未开始）
4. `min_trx_id <= trx_id < max_trx_id`：
   - 在 `m_ids` 中 → **不可见**（当时未提交）
   - 不在 `m_ids` 中 → **可见**（当时已提交）

若不可见，沿 `roll_pointer` 找 undo log 上一版本，重复判断。

**RC vs RR 区别**：
- RR：事务开始时创建一个 ReadView，全程复用 → 可重复读
- RC：每次 SELECT 重新创建 ReadView → 能读到其他事务新提交的数据

## Q21：InnoDB 索引为什么用 B+ 树

### 原题
> InnoDB 索引底层用什么数据结构？为什么不用哈希表或普通二叉树，而选 B+ 树？

### 我的回答
用 B+ 树。哈希表不支持范围查询；普通二叉树数据多时树高过高，增加磁盘 IO。

### ✅ 评价
两个核心原因答对，简洁准确。

### ✅ 更完善的回答（补充 B+ 树 vs B 树）
- **vs 哈希表**：不支持范围查询、排序，只适合等值查询
- **vs 二叉树/红黑树**：百万数据树高约 20 层，每层一次磁盘 IO，性能差
- **vs B 树**：B 树非叶子节点也存数据，单节点存键数少，树更高；B+ 树非叶子节点只存索引键，叶子节点存全部数据并通过**双向链表**连接，树更矮（3-4 层覆盖千万级数据），范围查询只需遍历叶子链表无需回溯

## Q22：回表与覆盖索引

### 原题
> 什么是回表？什么是覆盖索引？如何用覆盖索引避免回表？

### 我的回答
查询非主键字段时，二级索引叶子节点存的是主键 ID，需要再根据主键查完整行数据，这叫回表，查询两次。覆盖索引：查询 a、b 列，建联合索引 (a,b)，直接从索引拿到数据，不需要回表。

### ✅ 评价
回答准确完整，本质理解正确。

### ✅ 更完善的回答
**回表**：InnoDB 二级索引叶子节点存**主键值**而非完整行。查询列不在索引中时，先通过二级索引找主键，再回到聚簇索引查完整行，这次额外查询叫回表。

**覆盖索引**：查询所需所有列都在索引中，直接从叶子节点拿结果无需回表。`EXPLAIN` 中 `Extra` 列显示 `Using index` 即走了覆盖索引。

**实战优化**：`SELECT a, b FROM t WHERE a = 1`，建联合索引 `(a, b)`，a、b 全在索引中，直接覆盖无需回表。设计时把高频查询字段加入联合索引，用空间换时间。但索引列不宜过多，写入时维护索引代价增加。

## Q23：联合索引最左前缀原则

### 原题
> 联合索引 (a,b,c)，三个查询哪些能走索引：WHERE a=1 AND b=2 AND c=3；WHERE a=1 AND c=3；WHERE b=2 AND c=3

### 我的回答
查询1完全命中索引；查询2中 a 命中索引，c 因跳过 b 不命中；查询3违背最左前缀法则，不走索引。

### ✅ 评价
三个都答对，最左前缀原则理解准确。

### ✅ 更完善的回答
- **查询1**：完整命中 (a,b,c)，全部走索引
- **查询2**：a 走索引，b 缺失导致索引链断开，c 无法利用索引。实际是用 a 走索引过滤后，c=3 在回表后额外过滤
- **查询3**：跳过最左列 a，整个联合索引完全失效，全表扫描

**延伸考点**：`WHERE a=1 AND b>2 AND c=3`，a 和 b 能走索引，但 b 是范围查询，**c 失效**。范围查询右边的列无法利用索引。

## Q24：缓存穿透、击穿、雪崩

### 原题
> 说出缓存穿透、击穿、雪崩的区别及解决方案

### 我的回答
雪崩：大量数据同时过期，请求直打 DB，解决：TTL 加随机数。穿透：请求 Redis 和 DB 都不存在的数据，解决：布隆过滤器。击穿：热点 key 过期，大量请求同时打 DB，解决：分布式锁。

### ✅ 评价
三个区别和解决方案都答对，回答简洁准确。

### ✅ 更完善的回答
**雪崩**：大量 key 同时过期，请求全部打到 DB。解决：① TTL 加随机值错开过期 ② 热点数据永不过期+异步更新 ③ 服务降级熔断保护 DB

**穿透**：查询根本不存在的数据，Redis 和 DB 都没有，每次必穿透。解决：① 布隆过滤器前置拦截 ② 缓存空值（设短 TTL，防止数据写入后缓存旧空值）

**击穿**：单个热点 key 刚好过期，大量并发同时涌入 DB 重建缓存。解决：① 分布式锁：只让一个线程查 DB 重建，其他等待 ② 逻辑过期：value 里存过期时间，发现逻辑过期后异步重建，其他请求先返回旧数据（牺牲一致性换高可用）

**一句话区别**：雪崩=大量key同时过期；穿透=查不存在的数据；击穿=单个热点key过期

## Q25：Kafka 消息不丢失三环节保障

### 原题
> Kafka 如何保证消息不丢失？从生产者、Broker、消费者三个环节分别说。

### 我的回答
生产者：ack 机制。Broker：多节点多分区多副本，ack=0 leader 收到响应，ack=1 所有从节点同步完成响应，ack=-1 忘了。消费者：手动/自动提交 offset，成功消费才提交。

### ⚠️ 回答缺陷
- **ack=1 和 ack=-1 搞反了**：ack=1 是 leader 写入即响应；ack=-1/all 才是等所有 ISR 副本同步
- **缺少幂等生产者**：`enable.idempotence=true` 防止重试导致重复
- **缺少 min.insync.replicas**：与 acks=-1 配合使用，防止 ISR 只剩 leader 时形同虚设

### ✅ 更完善的回答
**生产者**：
- `acks=0`：不等确认，可能丢消息
- `acks=1`：leader 写入即响应，leader 宕机未同步时丢消息
- `acks=-1/all`：等所有 ISR 写入后响应，最安全
- 配合重试机制 + `enable.idempotence=true`（幂等生产者，防重试重复）

**Broker**：多副本（replication.factor>=2）+ `min.insync.replicas` 设最少同步副本数，与 acks=-1 配合防止 ISR 缩水后形同虚设

**消费者**：关闭自动提交（`enable.auto.commit=false`），手动提交 offset，消息处理完再提交。代价是可能重复消费，需业务层做**幂等处理**

## Q26：Kafka 重复消费幂等处理实战

### 原题
> 你们系统里具体怎么做幂等？消费者收到重复消息怎么识别去重？

### 我的回答
通过 Redis 记录处理过的 URL，设置 12h TTL。消费流程：MQ 拉取 → 限流控制 → 查询 Redis 是否存在该 URL → 存在则跳过，不存在则进入线程池抓取解析保存 → 处理后写入 Redis。设置 12h TTL 是因为 URL 对应页面内容每天可能更新，需要定期重新抓取保证内容时效性。

### ✅ 评价
回答有背景有设计理由，逻辑自洽，能主动解释 TTL 设计原因是加分项。

### ✅ 更完善的回答（补充边界问题）
以 Redis 为去重中心，消费链路：MQ → 限流 → Redis 查重 → 线程池处理 → 写 Redis（12h TTL）。

TTL 设 12h 而非永久：兼顾去重防重复消费和内容时效性，允许周期性重新抓取最新内容。

**需注意的边界问题**：
1. **先写 Redis 还是先处理**：应先处理完再写 Redis，否则处理失败但已记录，消息永久丢失。代价是崩溃重启后可能重复处理（at-least-once 语义），业务需能接受
2. **Redis 故障降级**：Redis 不可用时去重失效，需降级策略（允许重复处理或拒绝消费等待恢复）

## Q28：三态熔断器设计

### 原题
> 三态熔断器三个状态是什么？转换条件怎么设计？为什么需要 HALF_OPEN，直接从 OPEN 恢复到 CLOSED 不行吗？

### 我的回答
CLOSED：正常态，模型正常输入输出；OPEN：连续失败/异常时进入熔断，记录时间戳+熔断时长，定时检查是否到期；HALF_OPEN：熔断到期后进入，加锁允许首个请求发起探测，成功恢复 CLOSED，失败重新进入 OPEN。

### ✅ 评价
三态转换逻辑完整正确，加锁只允许一个探测请求的细节说明真正实现过，回答很有深度。

### ✅ 更完善的回答（补充 HALF_OPEN 必要性）
**三态**：
- `CLOSED`：正常放行，统计失败次数，超阈值转 OPEN
- `OPEN`：直接拒绝请求，记录熔断时间戳，到期后转 HALF_OPEN
- `HALF_OPEN`：加锁允许**一个探测请求**通过，成功转 CLOSED，失败重置计时重回 OPEN

**为什么需要 HALF_OPEN**：直接 OPEN→CLOSED 会在熔断时间到期后立刻放开全部流量，若服务未完全恢复，大量请求再次失败导致反复抖动。HALF_OPEN 用单次探测以最小代价验证服务健康，是**渐进式恢复**策略。

## Q29：持久化对话记忆 + 摘要压缩设计

### 原题
> 为什么压缩"最旧的一半"而不是直接丢弃？核心权衡是什么？为什么选阈值触发而非每次对话触发？

### 我的回答
直接丢弃会导致模型失忆，忘记最初需求。引入摘要压缩是为了：保留长对话记忆、避免过长历史填满上下文窗口、节约 Token、避免注意力偏移问题（模型集中注意首尾内容，过长对话影响注意力机制）。区分需要摘要的内容（用户提出的代码规范）和可省略的内容（临时闲聊）。每次触发会增加响应耗时和额外 Token 消耗，所以用阈值触发。

### ✅ 评价
能说出"注意力偏移（Lost in the Middle）"是加分亮点，说明对 LLM 底层特性有真实理解。回答完整有深度。

### ✅ 更完善的回答
**为什么不直接丢弃**：截断会导致模型丢失早期建立的用户需求、偏好、约束，长对话场景严重影响体验。摘要保留语义信息，只压缩表达形式。

**核心权衡**：
- Token 消耗：历史全量传入线性增加调用成本
- Lost in the Middle：LLM 对超长上下文中间部分注意力显著下降，过多历史反而降低质量
- 信息保留：保留关键语义（需求/约束/决策），过滤低价值内容（闲聊/临时请求）

**为什么阈值触发**：每次触发 = 每次额外一次 LLM 调用，增加延迟和成本；阈值触发 = 只在必要时压缩，短对话无额外开销。

**为什么压缩最旧的一半**：最近对话最相关，保留完整性；远期历史语义密度低，摘要损失小。

## Q30：多通道并行检索合并去重

### 原题
> 两条检索通路结果返回后怎么合并去重？意图定向优先具体合并逻辑是怎样的？

### 我的回答
意图树作为知识库目录索引，LLM 语义分析匹配意图树 → 意图定向检索 Top10 + 全局向量检索 Top10。用 chunk ID 作为 key，LinkedHashMap 合并去重。意图定向优先：先插入意图定向结果，再插入全局结果，LinkedHashMap 保序，已存在 key 不覆盖。合并后按来源类型+相似度排序，再进行 Rerank。

### ✅ 评价
回答完整，LinkedHashMap 保序去重实现思路清晰，意图定向优先通过插入顺序体现也答到了。

### ✅ 更完善的回答
**两条通路**：意图定向（精度高、范围窄）+ 全局向量（召回率高、有噪声），通过 `CompletableFuture.allOf()` 并行发起避免串行等待。

**合并去重**：以 chunk ID 为 key，`LinkedHashMap` 保插入顺序：
1. 先插入意图定向结果（高优）
2. 再插入全局结果，已存在 key 自动跳过
3. 意图定向结果排序位置不被全局结果覆盖

**两级排序**：合并后先按来源类型+向量相似度预排序，再交 LLM Rerank 语义精排取 Top-3 注入 Prompt。预排序提升 Rerank 输入质量，精排效果更好。

## Q31：向量相似度 vs LLM Rerank

### 原题
> 为什么不直接用向量相似度排序，还要引入 LLM Rerank？两者本质区别是什么？代价是什么？

### 我的回答
向量相似度是根据文字相似度计算数值排序，可能和实际语义关系不大。LLM Rerank 是对向量检索结果从语义层面进一步打分排序。前者负责从大量知识库中抽出相关文档，后者负责对抽出结果语义精排。代价是消耗增加。

### ⚠️ 回答缺陷
- 代价只说了"消耗增加"，没有说延迟增加、需要控制候选数量等具体点

### ✅ 更完善的回答
**向量相似度局限**：Embedding 是有损压缩，擅长整体语义相似度，但对细粒度语义关联（文档是否真正回答问题）判断弱。如"苹果手机价格"和"苹果公司营收"向量相似度高，但后者不回答前者的问题。

**LLM Rerank 本质**：将文档片段和问题同时输入 LLM，从理解层面判断"这段文字是否能回答这个问题"并打分，是真正的语义相关性判断。

**两者分工**：向量检索负责大范围快速召回（Top-N），Rerank 负责精排（Top-K），兼顾效率和精度。

**Rerank 代价**：① 延迟增加（额外一次 LLM 调用）② Token 消耗增加（每个候选都要和问题拼接）③ 候选数量需控制（一般向量召回 10-20 条，Rerank 后取 Top-3）

## Q32：RAG 系统高并发瓶颈与优化

### 原题
> 1000 QPS 并发对话，每个请求需向量检索+Rerank+LLM 生成，最大瓶颈在哪？怎么优化？

### 我的回答
瓶颈：向量数据库 QPS 压力。优化：① 限流熔断保护向量库 ② 查询缓存（相似问题复用结果）③ 意图短路（闲聊用小模型不走 RAG）。

### ⚠️ 回答缺陷
- **最大瓶颈判断不准**：LLM 调用（秒级延迟，2-3次/请求）才是最大瓶颈，向量检索延迟低得多
- **查询缓存 key 设计没说清楚**：直接用原始文本做 key 命中率极低，应用**语义缓存**（查询向量化后做相似度匹配）

### ✅ 更完善的回答
**瓶颈排序**：LLM 调用（秒级，2-3次/请求）> 向量数据库 > 连接池

**优化方向**：
1. **语义缓存**：查询向量化后与历史问答向量做相似度匹配，超阈值直接返回缓存，命中率远高于精确文本匹配
2. **意图短路**：闲聊/系统指令用小模型直接回答，跳过检索+Rerank+大模型，节省 80%+ 成本
3. **限流熔断**：向量库和 LLM 服务前各加限流，过载时快速失败避免堆积
4. **异步流式**：SSE 流式响应降低用户感知延迟，队列削峰避免瞬时并发压垮 LLM

## Q33：HashMap 底层结构与树化阈值

### 原题
> HashMap JDK 8 底层数据结构是什么？什么时候链表转红黑树？为什么阈值是 8？

### 我的回答
数组+链表+红黑树。数组长度等于64，链表长度大于8会转红黑树。大于8后链表遍历效率低于红黑树。

### ⚠️ 回答缺陷
- **为什么是8没有深入解释**：泊松分布，负载因子0.75下链表达到8的概率极低（约0.00000006），是防退化保护机制
- **没有说退化阈值是6**：红黑树退化回链表阈值是6而非8，防止频繁树化/反树化抖动

### ✅ 更完善的回答
**底层结构**：数组 + 链表 + 红黑树（JDK 8 引入）

**转换条件**：链表长度 > 8 **且** 数组长度 ≥ 64 时树化；只满足链表长度条件但数组较短，优先扩容而非树化。

**为什么阈值是8**：根据泊松分布，默认负载因子0.75下链表达到8的概率约0.00000006，极低。正常情况几乎不触发树化，只有 hash 碰撞极严重时才树化，是防退化保护机制。

**为什么不是更小**：红黑树节点内存占用约为链表节点2倍，维护有额外开销。链表短时开销可接受，链表足够长时红黑树 O(log n) 优势才能覆盖额外成本。

**退化阈值是6**：而非8，留2的缓冲防止长度在8附近频繁树化/反树化抖动。

## Q34：HashMap 扩容机制与 2 的幂次方

### 原题
> HashMap 扩容机制是怎样的？为什么容量一定是 2 的幂次方？

### 我的回答
初始容量16，超过0.75（即12个）触发扩容，创建容量×2的新数组，迁移时用 hash & oldSize 判断新位置（0=原位置，非0=原位置+oldSize），采用尾插法。2的幂是为了计算hash值方便。

### ✅ 评价
核心机制正确，扩容迁移的位运算判断也答对了，说明理解过源码。

### ✅ 更完善的回答
**扩容流程**：初始容量16，负载因子0.75，元素数>12触发扩容，新容量=旧容量×2，遍历迁移元素。

**迁移位运算**：判断 `hash & oldCapacity`（注意是oldCapacity而非oldCapacity-1）：0→位置不变，1→位置=旧位置+oldCapacity，避免重新计算hash。

**为什么必须是2的幂**：下标计算用 `hash & (capacity-1)`，2的幂时 capacity-1 二进制全为1，等价于 `hash % capacity` 但位运算更快，且全1掩码保证hash每一位都参与运算，**分布更均匀碰撞更少**。

**JDK 7 vs 8**：JDK 7 头插法，并发扩容可能形成循环链表死循环；JDK 8 改尾插法避免此问题。并发场景应使用 ConcurrentHashMap。
