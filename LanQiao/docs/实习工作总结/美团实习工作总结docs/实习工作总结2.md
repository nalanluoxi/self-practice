# 简历工作内容（重整版）

> 基于实际代码梳理，整合为两大项目线：Sitemap 新链接发现 + HTML 数据合成链路。
> 每项以"痛点 → 方案 → 结果"的面试叙述结构组织。

---

## 项目一：Sitemap 新链接发现系统

> **背景**：LLM 训练语料爬取依赖一个持续扩充的链接库（LinkBase），其 URL 来源有两路：一路从已抓取网页中提取外链，另一路通过 Sitemap 协议主动发现。本系统负责后者——依据 robots.txt 协议，从全球站点的 `robots.txt` 中解析出 Sitemap 声明地址，递归下载并解析 `sitemap.xml`（含 Sitemap Index 多级嵌套），从中提取大量结构化 URL 写入 LinkBase，为下游抓取任务补充丰富的新链接来源。整套链路基于 Mafka 消息队列驱动，独立维护。

---

### 工作点 1：多线程并发架构重构

**痛点**：原架构在 Mafka 回调线程中同步执行 download 业务逻辑，单线程串行消费，处理速率仅 1.6~2.5 万条/小时，消息持续积压。

**方案**：
- 将消费模型从**单线程同步**重构为**回调线程 + 独立业务线程池**的异步并行架构
- `@PostConstruct` 初始化 `ThreadPoolExecutor`（线程数 = `sitemap_thread_num`），使用 `SynchronousQueue`（零容量队列）作为任务队列
- Mafka 回调线程（`SitemapRequestConsumer.receive`）完成前置过滤后调用 `addRequestToThreadPool()`，业务 download 逻辑全部在独立线程池中并发执行，彻底解耦消息拉取与业务处理
- 线程池满时外层 `synchronized + while` 自旋等待（而非无限堆积任务），配合超时重投 MQ 防止消息丢失（`MAX_WAIT_TIME` / `MAX_RETRY_COUNT` 控制）
- 线程数通过 MDP 配置中心（`sitemap_thread_num`）动态下发，`@MdpConfigListener` 热更新线程池 `core/max size`，支持不停机调整
- 协调业务侧 Mafka **分区数从 200 扩容至 400**，消除分区粒度消费瓶颈

**结果**：集群小时处理量从 2.5 万提升至 **96 万**；日新链接发现量从 2~3 亿提升至 **10~14 亿（峰值 75 亿）**；集群 QPS 提升 **16 倍**。

---

### 工作点 2：三级纵深限流体系建设

**痛点**：无限流时大站 URL 数量远超小站，挤兑小站导致饥饿；无效请求（黑名单/去重命中）大量消耗限流配额，有效站点反而被限死。

**方案**：
- 构建**三级纵深限流**，粒度从粗到细，三层均基于 Rhino `OneLimiter`：
  - **集群层**：限流入口 `sitemap_cluster_qps_limit`，跨机器统一管控总 QPS 上限（`SitemapService.isClusterQpsLimited()`）
  - **单机层**：限流入口 `sitemap_limit_single_node`，单机兜底防止本机过载（`SitemapService.isSingleNodeQpsLimited()`）
  - **站点层**：限流入口 `sitemap_limit`，传入 `uuid=assignedDomain`（`EffectiveTldFinder.getAssignedDomain()` 提取顶级域），Rhino 按 uuid 维度独立计数，实现**站点级精确限频**（`SitemapService.isSiteQpsLimited()`）
- **前置拦截链**（先于限流执行，避免浪费配额）：
  1. 作弊站点正则过滤（`FilterUtils.isRegularFilterDomain()`）
  2. 黑名单域名 + URL 后缀过滤（`FilterUtils.isValid()`）
  3. 二级黑名单 + prefix 前缀过滤（`PreprocessUtil.isOnBlacklList()`）
  4. Redis KV 去重（`llm_sitemap_url` category）
- 被限流请求调用 `sitemapPublishService.sendRequest()` 重投 MQ，不丢消息

**结果**： **全天均匀产出**；大站挤兑小站问题基本结局

---

### 工作点 3：自定义本地自适应限流器

**痛点**：三层 Rhino 限流中，集群层与单机层为比例过滤，大站流量依然占比高；站点层 Rhino 阈值固定，无法感知线程池实时负载，线程池无法打满，并发能力浪费。

**方案**：
- `LimiteUtils` 中实现 `CounterRateLimiter`：以 `ConcurrentSkipListMap<Long, Long>` 作为时间戳桶，`headMap(startStamp).clear()` 滑动窗口清过期计数，`synchronized rateLimited()` 判断窗口内总计数是否超 `LIMITE_COUNT`
- 每个顶级域独享一个 `CounterRateLimiter` 实例，以域名 `hashCode` 为 key 存入 `ConcurrentHashMap`；守护线程定期清理长期不活跃的桶（`lastAccessTime > MAX_LIVE_TIME`）
- `SitemapRequestConsumer.setup()` 启动**后台守护线程**（每秒采样），读取 `EXECUTOR.getActiveCount()` 与 `corePoolSize`，调用 `LimiteUtils.updateAdaptiveLimitQuota()`：
  - 连续 3 次 `activeCount < 80% corePoolSize` → `LIMITE_COUNT++`（放宽单站配额）
  - 连续 3 次 `activeCount >= 80% corePoolSize` → `LIMITE_COUNT--`（收紧单站配额）
  - 上限由 `sitemap_limite_count_max` 约束，支持 MDP 热更新；下限 1

**结果**：英文留存量 2000 万 → **1.2 亿**；1000 万站点发现任务处理时长缩短至 **3~4 小时**；峰值集群 QPS **1417+**。

---

### 工作点 4：GZIP 压缩 Sitemap 解析

**痛点**：约 4% 的 sitemap 流量（日均 400 万+）为 `.gz` 格式，原链路直接丢弃，大量新链接漏发现。

**方案**：
- `CompressedUtil.isValid()` 通过 URL 路径扩展名嗅探（`url.getPath().endsWith(".gz")`，排除 `tar.gz`）自动识别压缩 sitemap
- `CompressedUtil.decompressGzip()` 用 `GZIPInputStream` 包装原始字节流，1024 byte 分块读取写入 `ByteArrayOutputStream`，解压后 UTF-8 解码字符串直接交给原有 XML 解析器，最小化改动面

**结果**：日新链发现量峰值从 3.79 亿提升至 **52.6 亿（提升 14 倍）**。

---

### 工作点 5：DSL 规则引擎治理垃圾/作弊站点

**痛点**：垃圾站点 URL 持续混入处理管道，规则更新依赖代码发布，响应周期长。

**方案**：
- `@MdpConfig("sitemap_regular_filter_list")` 接收配置中心下发的正则字符串集合；`@PostConstruct` 遍历编译为 `HashSet<Pattern>` 缓存（避免每次匹配重复编译）
- `@MdpConfigListener("sitemap_regular_filter_list")` 监听配置变更，`updateRegularList()` 重新编译缓存，**秒级生效，无需重启**
- 拦截逻辑前置于 Redis 去重和限流之前，最低成本步骤最先执行

**结果**：日均拦截 **4~5 亿**；规则生效延时从分钟级压缩至**秒级**；有效拦截 90% 垃圾站点；抽样高质量站点率 4.1% → **11.9%**。

---

### 工作点 6：过期消息时效性过滤

**痛点**：历史积压消息重新消费时，已过时的调度批次 URL 被无意义处理，浪费资源并污染结果。

**方案**：
- `SitemapRequest.ext` 字段携带 `dispatchTs`（调度时间戳）和 `batchId`
- 消费时解析 `ext`，计算 `lagMs = System.currentTimeMillis() - dispatchTs`，超过 `staleThresholdHours`（MDP 可配，默认 48h）直接丢弃并打 CAT 漏斗打点 `sitemap.funnel.stale`

## 项目二：HTML 数据合成链路（截图抓取服务）

> **背景**：为训练 Coding 模型"看图写代码"能力，需要大规模采集真实网页的视觉快照与完整源码作为训练对齐数据——即给定网页截图，模型需还原对应 HTML/CSS/JS 代码。本系统独立主导从零搭建，负责批量抓取含交互按钮、动态组件的真实网页，产出截图（多视口/多 DPR）+ HTML 快照 + 完整静态资源包（JS/CSS/字体/图片），写入 S3 并通过结果 MQ 通知下游，为 Coding 模型提供高质量的图文对齐训练数据。技术栈：Playwright + Mafka + S3 + Java 多线程。整体链路：MQ 消费 → 前置过滤 → 线程池调度 → Playwright 渲染抓取 → 资源补全 → S3 上传 → 结果 MQ 发送。

---

**项目整体设计**：

- **消费层**（`ScreenshotRequestConsumer`）：Mafka 消费者，黑名单过滤 + URL 合法性校验后，将请求投入独立 `ThreadPoolExecutor`（`SynchronousQueue` + 自旋背压），与 Sitemap 线程池**完全隔离**，互不影响
- **调度层**（`ScreenshotService`）：业务编排，代理选取（按域名路由海外/国内代理线路）→ 生成 S3 路径前缀 → 提交 `ScreenshotPlaywrightService` 异步执行 → 收集结果 → 发送结果 MQ
- **执行层**（`ScreenshotPlaywrightService`）：双层线程池（`DOWNLOAD_TASK_POOL` + `SUPPLEMENT_POOL`）隔离主抓取与资源补全；`ThreadLocal<PlaywrightDownLoader>` 每线程独享 Browser 实例，实例存活 5 min 后自动重建防内存泄漏；按代理线路绑定不同 Chrome UA（UA_137 海外普通 / UA_136 海外高级 / UA_130 国内）


---

**攻克的核心难题**：

**① 两次 navigate 资源浪费 + 内存峰值高**
v1 Phase1（资源采集）与 Phase2（截图）各起一次 `navigate`，重复加载整页浪费 50% 网络请求；`onResponse` 字节全量持有内存直到处理完。
→ 合并为一次 `navigate(WaitUntilState.LOAD)` + 单 `BrowserContext`；`onResponse` 取字节后立即上传 S3 置 null 释放，内存峰值大幅降低；新增 `SUPPLEMENT_POOL` 与 `DOWNLOAD_TASK_POOL` 完全隔离，防止内部提交死锁。

**② 字体缺失导致离线 HTML 渲染乱码**
Chrome 懒加载机制下未渲染区域的字体不触发请求，`onResponse` 无法捕获 `@font-face` 中的备选字体。
→ `supplementFontsFromCss()` 用 `helger/ph-css` 解析所有 CSS 中 `@font-face { src: url(...) }` 声明，主动补充下载；以 `collectedFontUrls` Set 去重，避免与 `onResponse` 已捕获的字体重复下载。

**③ 懒加载图片大量缺失**
`IntersectionObserver` 图片只有进入视口才触发请求，页面不滚动则仅首屏图片被 `onResponse` 捕获。
→ Phase1 加入分步滚动：逐视口 `window.scrollTo` + 300ms 等待触发全量懒加载；`supplementImagesFromHtml()` 用 Jsoup 解析 `srcset` 所有尺寸变体 + `data-src`，与 `collectedImageUrls` 取差集兜底仍遗漏的图片。

**④ JS/CSS 被 onResponse 遗漏**
部分资源因浏览器缓存（304）或跨域限制 `onResponse` 未捕获响应体。
→ `supplementScriptsAndStylesFromHtml()` 解析 HTML 中 `<script src>` / `<link rel=stylesheet>`，与 `collectedJsCssUrls` 取差集主动补充。

**⑤ styled-components 动态样式序列化丢失**
styled-components 通过 `el.sheet.insertRule()` 写 CSSOM 不写 textContent，`page.content()` 序列化仅取 DOM，动态注入样式全部丢失。
→ 注入 JS 将 `data-styled` style 标签的 `cssRules` 逐条写回 `el.textContent`，再序列化，确保动态样式落入离线 HTML。

**⑥ 下游 S3 ListObjects 成并发瓶颈**
v1 结果 MQ 仅携带 S3 目录前缀，下游须 `ListObjects` 扫描文件列表，高并发下触碰 S3 QPS 限制。
→ `CopyOnWriteArrayList<String> uploadedKeys` 在抓取过程中收集每个文件完整路径，任务结束后序列化为 JSON 数组写入消息，下游直接 `GetObject` 消除扫描依赖。

**结果**：字体缺失基本解决；CSS 缺失基本解决；图片可用率约 70%；下游 S3 扫描瓶颈消除；内存峰值显著降低。

## 一句话精简版（适合简历条目）

1. **线程池并发重构**：Mafka 回调线程与业务线程池解耦，`SynchronousQueue` 自旋背压防 OOM，MDP 热更新线程数；分区 200→400；集群 QPS 提升 16x，日新链 2~3 亿 → 峰值 75 亿。

2. **三级精准限流**：集群层 + 单机层（Rhino OneLimiter）+ 站点层（`ConcurrentSkipListMap` 滑动窗口 `CounterRateLimiter`）三级防护；无效流量前置拦截（正则/黑名单/Redis 去重）；大站挤兑根治，全天流量均匀。

3. **自适应限流器**：守护线程每秒采样线程池 `activeCount`，连续 3 次低于 80% 水位放宽配额，连续 3 次高于收紧；英文留存 2000w → 1.2 亿，峰值 QPS 1417。

4. **GZIP 解析补齐**：URL 后缀嗅探 `.gz`，`GZIPInputStream` 流式解压接原有 XML 解析器；日产出 3.79 亿 → 52.6 亿（14x）。

5. **规则引擎拦截**：正则 `Pattern.compile` 预编译缓存 + `@MdpConfigListener` 热更新，秒级生效；日拦截 4~5 亿，质量提升 4.1% → 11.9%。

6. **截图抓取 v1**：Playwright `ThreadLocal` 实例管理 + `SynchronousQueue` 独立线程池隔离 + S3 流式上传，按代理线路绑定不同 UA，490 台机器 1000 条/分钟。

7. **截图抓取 2.0**：Phase1+2 合并（减少 50% 网络请求）；边抓边上传置 null（内存峰值大幅降低）；6 路资源完整性改造（字体 `@font-face` 解析/图片 `srcset`+懒加载/JS+CSS 兜底/styled-components CSS 修复）；MQ s3DirKey 改 JSON 路径数组，解除下游 ListObjects 瓶颈。
