## 一、实习项目一：多线程并发重构与消息队列扩容

**`ThreadPoolExecutor` 七大参数**：核心参数（corePoolSize / maximumPoolSize / keepAliveTime / workQueue）决定线程池行为。本项目将业务处理从单线程迁移到线程池，需要精确配置参数以匹配目标 QPS。

**MDP 配置中心动态热更新线程池参数**：线程数通过 `@MdpConfig("sitemap_thread_num")` 注入，并用 `@MdpConfigListener` 监听变更，实时调用 `setCorePoolSize / setMaximumPoolSize` 动态修改，无需重启。当前代码未基于 CPU 核数公式推算，而是依赖线上观察手动配置。面试可延伸说明 Little's Law（`corePoolSize = QPS × RT`）是理论调优基准，实际生产中往往结合线上监控数据（线程池 activeCount / 队列水位）动态调整。

**Mafka 回调线程 + 业务线程池异步解耦**：Mafka 框架回调 `receive()` 方法后，前置过滤完成即将任务提交到 `ThreadPoolExecutor`，回调线程立刻返回，业务线程池并发执行 `download`，消息拉取与业务处理完全解耦。这是生产者-消费者模型的实际落地，面试可说明"为什么不让 Mafka 回调线程直接执行业务"——因为会导致 Mafka 阻塞，无法拉取新消息，消费吞吐退化为串行。

**`SynchronousQueue` vs `LinkedBlockingQueue`**：本项目线程池队列选用 `SynchronousQueue`（零容量，必须有空闲线程立即接手，否则触发拒绝策略），而非 `LinkedBlockingQueue`（有界/无界缓冲队列）。实际代码中线程池满时采用外层 `synchronized` + `while` 自旋等待，直到有线程空闲才提交，避免了无界队列无限堆积引发 OOM。面试高频：`SynchronousQueue` 有什么特点？答：没有存储能力，每次 put 必须等待对应的 take，适合线程数固定、不希望任务排队堆积的场景。

**Mafka 回调模型与 Offset 提交**：Mafka 框架通过 `@MdpMafkaMsgReceive` 注解回调 `receive()` 方法，处理完成后返回 `ConsumeStatus.CONSUME_SUCCESS`，框架自动提交 offset，At-Least-Once 语义。当前实现中业务线程池的 `download()` 完成后回调线程才返回，offset 提交由框架串行保证，不存在乱序问题。面试可追问：如果想进一步提升吞吐，让回调线程提交任务后立即返回（不等 download 完成），则需要引入 BitSet 滑动窗口自主管理 offset。

**滑动窗口 + BitSet（待实现优化方向）**：`java.util.BitSet` 用于 O(1) 标记任务完成状态。若实现真正的"提交即返回"异步消费，需要滑动窗口跟踪窗口内各任务完成情况，仅当窗口左边界连续置位时推进 offset 提交，避免乱序提交导致消息重复消费。这是当前代码的演进方向，面试可主动提出作为改进点。

**Kafka 分区与并行度**：Kafka 同一 ConsumerGroup 内分区数决定最大并行消费线程数，分区扩容（200→400）是提升消费吞吐的基础手段，面试常考点。

**线程安全与内存可见性**：多线程共享 BitSet 和 Offset 计数器，需要 `synchronized` 或 `AtomicLong` 保证操作原子性，`volatile` 保证可见性。

## 二、实习项目二：Sitemap 发现环路三级限流体系

**Rhino OneLimiter（美团内部限流框架）**：集群层和单机层实际使用美团内部 Rhino OneLimiter 框架，通过配置 `sitemap_cluster_qps_limit` 和 `sitemap_limit_single_node` 两个限流入口，由框架在 MDP 配置中心动态管理 QPS 阈值，无需代码发布。面试可延伸到外部同类方案：Sentinel（滑动窗口 + 令牌桶）、Resilience4j（RateLimiter）。

**自定义滑动窗口计数器（站点层）**：站点层使用 `ConcurrentSkipListMap<Long, Long>` 实现滑动时间窗口：key 为时间戳，value 为该毫秒内的计数；每次判断前清除窗口外（`headMap(startStamp).clear()`）的过期数据，再 `sum` 窗口内总计数与阈值比较。`ConcurrentSkipListMap` 天然有序，支持高效 range 查询，是实现滑动窗口的合适选择。面试可对比 Redis ZSET 实现方案（跨节点共享 vs 单机内存）。

**Redis KV 去重（非 Bloom Filter）**：当前 URL 去重使用 Tair（Redis 兼容）的普通 KV 存储，key 为 sitemap URL，命中则认为已抓取并丢弃。相比 Bloom Filter，KV 去重无误判，但内存占用更大（每个 URL 约 50-100 字节）。面试可主动提出 Bloom Filter 优化方向：亿级 URL 下 Bloom Filter 空间节省 10x+，代价是允许极低误判率（可接受漏抓少量重复链接）。

> ⚠️ 与简历原描述差异：集群/单机层为 Rhino OneLimiter 而非 Redis+Lua；站点层为自定义 ConcurrentSkipListMap 滑动窗口而非 Guava RateLimiter；URL 去重为 Redis KV 而非 Bloom Filter。

**责任链模式**：拦截链（黑名单 → 正则 → Bloom Filter）是责任链模式的直接应用，每个 Handler 处理自己关心的情况并决定是否传递。面试中可结合 Servlet Filter 链、Spring Security 过滤器链举例说明。

**线程池健康度监控**：通过 `ThreadPoolExecutor.getActiveCount()` 和 `getQueue().size()` 采样健康度，实现自适应限流阈值调整，是线程池监控的实践应用。

**OOM 防护**：通过限流控制入队速率，配合线程池有界 BlockingQueue，防止任务堆积撑爆 JVM 堆内存。

## 三、实习项目三：GZIP 压缩 Sitemap 解析能力补齐

**Java IO 装饰器模式**：`GZIPInputStream(new BufferedInputStream(rawStream))` 是 Java IO 流装饰器模式的典型应用，多个 InputStream 层层包装，每层增加新能力，互不耦合。

**流式处理 vs 全量加载**：流式解压（边读边处理）避免将大文件全量展开到内存，是规避 JVM 堆内存 OOM 的最佳实践。对应面试题：大文件处理为什么用流而不是 readAllBytes？

**URL 路径扩展名嗅探（当前实现）**：通过 `url.getPath().toLowerCase().endsWith(".gz")` 判断是否为 GZIP 压缩文件，同时排除 `tar.gz`（多层压缩，当前不处理）。这是最轻量的实现，无需发起 HTTP 请求即可判断，代价是对扩展名不规范的 `.gz` 文件存在漏识别。

**HTTP Content-Type 双重嗅探（待实现）**：优先信任 HTTP 响应头 `Content-Type: application/gzip`，回退时检查 URL 扩展名，是更健壮的内容类型识别方案。当前代码尚未实现，属于可优化点，面试中可主动提出。

**JVM 堆内存管理**：避免大对象直接进入老年代（大 `.gz` 文件展开后可能触发 Full GC），流式处理使每次在堆上存在的数据量可控，减少 GC 压力。

## 四、实习项目四：站点频度调度策略建设（三维打分模型）

**Hive + Spark 离线计算**：Spark RDD/DataFrame 的宽窄依赖、Shuffle 机制、分区数调优是大数据八股的核心。宽表 JOIN 需要注意数据倾斜（少数域名 URL 量极大），常用广播 JOIN 或 Salting 解决。

**Spark UDF**：用户自定义函数（UDF）将 Java/Scala 逻辑注册到 Spark SQL，实现复杂打分计算，是 Spark SQL 扩展的标准手段。

**闭环反馈系统设计**：调度结果实时回写打分系统形成闭环，是分布式系统中自适应调度的设计思路，体现系统设计能力。

**策略模式**：差异化调度间隔（高分缩短 / 低分延长）本质上是策略模式，不同分段对应不同调度策略，易于扩展新策略。

**分布式定时任务**：调度系统的核心问题是任务分片与故障转移，面试可延伸到 XXL-Job / Quartz 的分布式实现原理。

## 五、实习项目五：DSL 规则引擎治理垃圾/作弊站点

**`volatile` 关键字**：`volatile` 保证修改对其他线程立即可见（内存屏障 + 禁止重排），但不保证复合操作原子性。本项目用 `volatile` 修饰 Pattern 引用，写操作为整体引用替换（非 RMW 操作），因此 `volatile` 单独即可保证线程安全。面试高频：`volatile` 能替代 `synchronized` 吗？答：只在写操作为单一赋值（非复合）时可以。

**原子引用替换**：整体替换 `volatile` 引用是 Java 并发中"不可变对象 + 引用替换"模式的应用，比锁粒度更细，性能更好。类比 `AtomicReference.compareAndSet()`。

**配置中心热更新**：`volatile` + 后台刷新线程定期拉取配置，是配置热更新的简洁实现。面试可延伸到 Nacos/Apollo 配置动态刷新原理（长轮询 / 推送 + Spring `@RefreshScope`）。

**正则表达式与 NFA/DFA**：Java `Pattern.compile()` 将正则编译为 NFA（非确定有限自动机），编译开销不可忽视，缓存 Pattern 对象复用是性能优化的标准做法（类似 PreparedStatement 缓存）。

**责任链模式**：拦截逻辑（黑名单 → DSL 规则 → 限流 → 去重）按成本从低到高排列，前置低成本过滤，减少后续步骤无效开销，是责任链模式与性能优化的结合应用。

**DSL 设计与解释器模式**：AND/OR/NOT 组合规则是**解释器模式（Interpreter Pattern）**的典型场景，将规则表达式解析为 AST，递归求值。面试可延伸到 Spring EL 表达式、Drools 规则引擎。

**Redis Bloom Filter 应用**：去重逻辑中使用 Bloom Filter 是 Redis 在工程中的高频应用，面试必问：为什么不用 `SET`？答：亿级 URL 用 SET 存储内存爆炸（每个 URL 约 50 字节），Bloom Filter 空间压缩到 1/10 以下，代价是允许极低误判率。

## 六、实习项目六：网页截图抓取全链路服务建设

**线程池隔离**：不同业务使用独立线程池，防止慢任务（截图 CPU 密集）占满共享线程池影响核心链路（IO 密集型消费）。这是线程池隔离的标准应用场景，对应 Hystrix/Sentinel 的线程隔离策略。

**CPU 密集型 vs IO 密集型线程池配置**：截图属于 CPU 密集型（Playwright 渲染），线程数建议 `CPU核数 + 1`；消费链路属于 IO 密集型，线程数可设为 `CPU核数 × (1 + IO等待时间/CPU时间)`。

**流式上传 S3**：Java IO 流写入 S3（通过 `InputStream` 直接 pipe 到 S3 SDK），不将图片全量加载到堆内存，减少 GC 压力和 OOM 风险。原理与项目三 GZIP 流式解压相同——大数据处理优先流式。

**JVM OOM 防护**：大图片（全页面截图可达数 MB）若全量加载到 JVM 堆，配合高并发截图任务极易触发 Full GC 甚至 OOM。流式传输 + 独立线程池 + 有界队列是三重防护。

**Playwright 原理**：基于 CDP（Chrome DevTools Protocol）控制 Chromium 进程，支持完整 JS 渲染，可获取动态 SPA 页面截图，优于静态 HTML 截图工具（如 HtmlUnit）。

## 七、个人项目：智析 RAG

**`CompletableFuture` 异步编排**：`CompletableFuture.allOf()` 等待两路检索（全局向量 + 意图定向）并行完成后合并结果，是 Java 异步编排的标准用法。面试常问：`CompletableFuture` vs `Future` 的区别？答：前者支持链式回调、异常处理、组合操作，后者只能阻塞 `get()`。

**三态熔断器（Circuit Breaker）**：`CLOSED → OPEN → HALF_OPEN` 三态转换，失败率超阈值开启熔断，半开时放行探测请求，成功则关闭熔断。是分布式高可用的核心模式，对应 Resilience4j / Sentinel 的实现原理。

**SSE（Server-Sent Events）**：基于 HTTP 长连接的单向推送协议，LLM 流式输出的标准传输方式。首包探测（Probe）的意义在于：SSE 一旦开始写入 HTTP 响应体就无法回退，必须在首包确认模型可用后才能开始真正推送。

**向量数据库**：pgvector 在 PostgreSQL 上扩展向量相似度搜索（cosine / L2），是 RAG 系统的存储核心。面试可延伸到 ANN 算法（HNSW / IVF）的原理与精度-速度权衡。

**意图分类与检索收敛**：LLM 分类 + 意图树三级收敛，是 RAG 系统中解决"大海捞针"问题的关键设计，本质上是通过语义理解缩小检索空间。

**PostgreSQL 持久化 + 摘要压缩**：超过 10 轮后调用 LLM 压缩摘要，是解决 LLM Context Window 限制（Token 超限）的工程方案，面试可延伸到 Sliding Window Memory 与 Summary Memory 的对比。

**Spring IoC / AOP**：Spring AI 的 `ChatClient` / `EmbeddingClient` 通过 IoC 注入，各阶段降级容错通过 AOP 切面统一处理，是 Spring 框架在 AI 应用中的典型落地。

**RAG 链路降级**：各阶段独立捕获异常并降级（如向量检索失败退化为全文搜索），是分布式容错设计的体现，类比 Hystrix Fallback 机制。
