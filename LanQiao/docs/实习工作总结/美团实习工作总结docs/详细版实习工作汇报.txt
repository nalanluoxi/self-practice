一、业务背景与整体架构
--------------------------------------------------------------------------------

【团队定位】
LongCat大模型数据团队，核心目标是为大模型训练构建高质量预训练语料库。
通过抓取互联网网页中的优质文本内容，经过解析、清洗、筛选后用于模型预训练。

【主要链路模块】
整个数据流水线包含以下核心模块：
  1. 新链接发现（Link Discovery）- 从已抓取页面中提取新URL
  2. 调度（Schedule）- 按优先级和配额调度待抓取链接
  3. 抓取（Crawl）- 发起HTTP请求获取网页内容
  4. Sitemap站点新链发现 - 独立于主链路的闭环发现系统
  5. 网页截图抓取 - 面向多模态大模型训练的截图服务

【抓取服务架构】
- 输入输出：均通过Mafka消息队列接收和发送消息，经历过15亿+量级的验证
- 服务形态：无状态服务，接受URL后发起HTTP请求，过程中访问MySQL、Lion、Squirrel等组件获取配置
- 性能保障：MySQL数据预先加载到内存缓存，支持十万级别QPS

二、Sitemap站点新链发现环路 — 核心工作内容
================================================================================

Sitemap环路是独立于主抓取链路的一条闭环链接发现系统。主要流程为：
Pipeline方提供高质量站点domain → 投递robots.txt链接到Mafka → Sitemap集群消费并
抓取robots页面 → 解析提取sitemap链接 → 再次投递Mafka → 抓取sitemap页面 → 解析
提取其中URL链接 → 链接入库 + sitemap链接回投起点Mafka形成闭环。

该环路是实习期间最主要的工作领域，以下按时间线详述各阶段工作。

1. 流量打散逻辑与精准限流体系建设（2025.11.10）
--------------------------------------------------------------------------------

【问题场景】
原系统缺乏有效的流量控制与打散机制，导致Sitemap发现环路处于"无序竞争"状态。
大站点利用其海量的sitemap链接占据了Mafka消息队列的绝大部分带宽，产生严重的
数据倾斜，直接挤兑了小站点的挖掘资源，造成小站任务长时间积压、挖掘时效性极差。
调度分配原先集中于凌晨3点与下午3点两个峰值时段，其他时段产出极低。

【解决方案】
从0到1构建三级限流防护网，在SitemapRequestConsumer的消息处理链路中逐层过滤：

  第一层 - 集群层限流（Cluster-level）：
    通过 sitemapService.isClusterQpsLimited() 接入内部Rhino OneLimiter
    （配置入口：sitemap_cluster_qps_limit），在集群维度统一管控总请求速率，
    保护下游Redis等共享基础设施不被冲垮。

  第二层 - 单机层限流（Single-node）：
    通过 sitemapService.isSingleNodeQpsLimited()（配置入口：
    sitemap_limit_single_node）对单实例流量进行兜底限制，防止单节点过载。
    采用单机均摊策略：集群阈值 / 机器数 = 每台机器的限额。

  第三层 - Redis精确层限流（Site-level）：
    通过 sitemapService.isSiteQpsLimited(request) 以
    EffectiveTldFinder.getAssignedDomain() 提取顶级域作为uuid，实现站点级
    精确限频（配置入口：sitemap_limit）。通过Redis+Lua脚本实现令牌桶算法，
    控制每个站点每秒最多可抓取的数量。

【关键优化 - 拦截前置】
在限流判断之前，依次执行以下拦截逻辑，确保有限限流配额不被无效请求消耗：
  ① 黑名单过滤（blackDomainSet）：直接丢弃已知垃圾域名
  ② URL格式校验（isValidUrl）：MalformedURLException检查
  ③ URL后缀黑名单过滤（urlBlackListSuffixes）
  ④ Redis去重检查：12小时时效性去重

【技术细节 - 限频vs限流的区别】
  - 限流：侧重保护服务稳定性，防止流量激增导致崩溃，全局维度
  - 限频：执行业务策略，防滥用/防爬，通常针对用户/IP/站点等特定维度
  - 本场景使用的是"集群限频"，限制每个站点的请求频率

【成果】
  - 解决了大站挤兑小站的顽疾，实现流量公平调度
  - 调度分配从集中峰值优化为全天均匀产出
  - 集群QPS稳定在6-8左右（此时尚未引入线程池优化）

2. 系统并发性能优化 - 多线程重构与集群扩容（2025.11.17）
--------------------------------------------------------------------------------

【问题场景】
初始系统采用单线程消费模式（Mafka receive()方法同步处理全部逻辑），且单次任务
同步处理耗时较长（约15s/条），导致集群QPS低于10。在面对百万级站点发送量时，
系统吞吐量严重触顶，无法支持大规模的Sitemap发现需求。每分钟集群仅能抓取
400-1500条消息。

【解决方案 - 并发架构重写】

  线程池设计：
    使用 SynchronousQueue 作为线程池队列（无缓冲，直接传递任务给空闲线程），
    配合 ThreadPoolExecutor 创建固定大小的线程池。线程数通过Lion MDP配置
    sitemap_thread_num 动态注入，支持运行期热变更。

    核心参数：
      - corePoolSize = maxPoolSize = threadNum（固定大小线程池）
      - workQueue = SynchronousQueue<>（同步队列，无容量缓冲）
      - handler = AbortPolicy（拒绝策略）
      - 自定义ThreadFactory：线程命名 "sitemap-crawler-pool-{n}-thread"

  架构解耦：
    receive() 方法仅负责 Mafka 消息的反序列化与前置过滤（轻量操作），
    通过 addRequestToThreadPool() 将实际的 sitemap 下载耗时操作异步提交给
    线程池执行，实现了消息拉取与业务处理的完全解耦。

  线程池满时的背压机制：
    当线程池所有线程都在忙碌时（activeCount >= corePoolSize），采用
    synchronized + 自旋等待策略：
      - 每次 sleep(1000ms) 检查线程池状态
      - 最长等待 MAX_WAIT_TIME（36秒）
      - 超时后通过 sitemapPublishService.sendRequest() 将消息重新投递回MQ
    这种设计保证了：(1)消息不丢失 (2)不会因无限阻塞拖死消费者线程

  线程池热更新机制：
    通过 @MdpConfigListener("sitemap_thread_num") 监听配置变更，
    动态调整 corePoolSize 和 maximumPoolSize，无需重启服务即可扩缩容。
    调整顺序：先改大的值再改小的值，避免中间状态异常。

  资源弹性扩展：
    完成 Mafka 集群从 200 分区至 400 分区的翻倍扩容，消除了传输链路的物理瓶颈。

【为什么选择调整限流阈值而不是动态调整线程池大小？】
  - 调整线程池大小是实时的、频繁的、代价高、抖动大、难以预测
  - 频繁创建销毁线程失去了线程池重复利用线程的优势
  - 调整限流阈值是周期性的（每分钟一次）、平缓的、代价更低、易于控制
  - Java不支持设置单线程内存阈值（线程内存是系统级资源，不在JVM管理范围）

【成果】
  - 小时抓取量从 2.5w 跃升至 96w+
  - 峰值 QPS 达到 400（提升16倍）
  - 日均新链发现量从 2-3 亿提升至 10-14 亿（最高产出达 75 亿）
  - 集群每分钟抓取量从 400-1500 提升至 2.4w

3. 动态自适应本地限流优化（2025.11.27）
--------------------------------------------------------------------------------

【问题场景】
在初步建立三级限流后，存在以下问题：
  ① 前两层（集群层+单机层）仍是比例过滤，大站流量占比依然较高
  ② 固定阈值的限流无法感知下游处理能力（线程池负载）的实时变化
     → 存在系统资源浪费或过载的风险
  ③ 线程池无法打满，无法充分发挥线程池的并发能力

【解决方案 - "线程池健康度-限流阈值"动态联动模型】

  核心组件 - CounterRateLimiter（基于时间窗口的本地限流器）：
    使用 ConcurrentSkipListMap<Long, AtomicInteger> 实现滑动窗口计数，
    以毫秒精度记录每个时间片的请求数量，支持精确的速率控制。

  自适应反馈机制：
    在 setup() 方法中启动后台探测线程（Daemon线程），每秒采样：
      - activeCount：当前活跃线程数
      - corePoolSize：核心线程数
    调用 LimiteUtils.updateAdaptiveLimitQuota() 方法，将采样结果写入
    长度为 3 的历史队列（环形缓冲区）。

  联动决策逻辑：
    当连续 3 次采样 均低于 80% 水位阈值 → 自动扩大限流配额（LIMITE_COUNT++）
    当连续 3 次采样 均超过 80% 水位阈值 → 自动收缩限流配额（LIMITE_COUNT--）
    配额边界由配置项 sitemap_limite_count_max 约束

  设计优势：
    - 分钟级自适应调频，响应及时且不过于敏感
    - 与线程池负载真实联动，避免人工调参的滞后性
    - 平滑过渡，不会出现断崖式流量变化

【成果】
  - 线程池并发效率显著提升，峰值集群 QPS 达到 1417+
  - Sitemap环节对英文留存贡献显著：留存量从 2000w 提升至 1.2 亿
  - 针对 1000w 站点的全量发现任务，处理时长缩短至 3-4 小时

4. 压缩包资源解析能力补齐（2025.12.17）
--------------------------------------------------------------------------------

【问题场景】
原处理链路中存在功能盲区：所有以压缩包格式（.gz）存放的Sitemap信息被系统
直接视为无效并丢弃，导致大量高质量的新链资源流失。通过日志统计发现压缩包
流量占比约4%（当日进入线程池流量10000w中，压缩包占400w）。

【解决方案】

  识别逻辑：
    在 addRequestToThreadPool() 的线程池提交逻辑中，任务进入线程池后调用
    CompressedUtil.isValid(request) 对URL后缀进行判断：
    - 识别 .gz 结尾的资源
    - 排除 .tar.gz 等复合格式（case极少，收益不明显）

  解压实现：
    在 SitemapDownloader 内部调用 CompressedUtil.getCompressedData()：

    具体流程：
    ① 将抓取到的压缩字节数组放入 ByteArrayInputStream（输入流）
    ② 通过 Java 自带的 GZIPInputStream 包裹输入流，自动识别GZIP头部解压
    ③ 创建 ByteArrayOutputStream 和 1KB 大小的缓冲区
    ④ 不断从 GZIPInputStream 读取解压数据写入输出流
    ⑤ 最后将输出流按 UTF-8 编码转化为字符串，完成解压

    解压后的 XML 文本交由 SiteMapParser 正常解析，完整保留原有的 Redis 去重、
    限流、CAT 监控等处理链路。

【为什么不支持更多压缩格式？】
  通过日志打点统计，环路中压缩包类型主要是 .gz 格式，其他格式每小时仅 1-2 条
  （低于10条），单独添加收益不明显。当初考虑使用策略模式+工厂方法提高扩展性，
  但其他格式测试样例过少，暂未添加。

【成果】
  - 日均处理压缩包流量达 400w+
  - 压缩包资源贡献约 4.08% ~ 16.23% 的新链
  - 全面推全后，新链发现量从 3.79 亿激增至 52.6 亿（14倍增长）

5. 智能投递策略重构 - 频度调度（2026.02.04 + 第二期优化）
--------------------------------------------------------------------------------

【问题场景 - 第一期】
早期方案每天固定调度全量 robots.txt 进行挖掘（每日一轮）。随着 robots 数量增加：
  - 高频更新站点（如新闻类）调度不足 → 新链遗漏
  - 低频更新站点浪费资源 → 无效抓取
需要根据各站点 sitemap 的更新频率进行差异化调度。

【解决方案 - 第一期】

  打分与分级：
    根据 sitemap 新链接产出效果对 sitemap URL 进行打分，分为三个等级：
    - grade=1（高频优质站点）：设置 Redis 去重过期时间为 3 小时
    - grade=2（中频站点）：设置 Redis 去重过期时间为 5 小时
    - 低频/无等级：使用默认配置值（较长过期时间）

  实现方式：
    在 SitemapService.downLoadSitemap() 中通过 resolveExpireTimeByGrade()
    方法，从请求的 ext 字段中解析 grade 值，关联 Redis 过期时间。
    SitemapPublishService 投递时透传 ext（含 batchId、dispatchTs、grade）。

  多轮投递：
    制定多个定时任务，通过传递不同 grade 参数实现一天多轮差异化投递。

【遇到的坑】
上线数日后发现链接投递效果不佳，经过排查发现：
  - 打分机制过于严苛
  - 发送链接要求过于严格 → 导致发送量大幅减少 → 严重降低新链产出量
  后续经过调整：放宽评分阈值 + 扩充原始站点集合，产出恢复正常。

【第二期优化 - 多维度评分体系】

  问题：早期频度调度策略维度单一，仅依赖新链接产出分，未综合考量站点规模
       与留存质量，调度决策不够精准。

  优化方案 - 三维打分模型：
    ① 新链接分：以新链接产出量作为得分维度
    ② 规模分：从模糊留存表中获取留存量 × 抓取数计算留存率
    ③ 最终分 = 三个维度加权综合计算

  闭环反馈：
    下游调度结果反馈至打分系统，形成持续优化链路。
    抓取侧根据投递中的 grade 值动态设置 Redis 去重记录的过期时间：
    - 高频站点短 TTL（更快允许重复抓取）
    - 低频站点长 TTL（避免无效重复抓取）

【成果】
  - 实现了高频站点加速、低频站点降载的精细化调度
  - 资源利用率显著提升，避免低效站点浪费抓取配额

【量化收益验证（2026.05 数据）】

  频度调度第二期优化上线后，通过 DI 表（llm_data_di_sitemap_frequency_delivery）
  进行收益数据分析，核心指标如下：

  整体产量跃升：
    - 上线前基线：sitemap 日新链产出 10~70 亿/天
    - 上线后当前：sitemap 日新链产出 **100~200 亿/天**（峰值 **200 亿/天**）
    - 提升幅度：约 **10 倍**

  多批次命中覆盖（20260510~0515 连续6日观测）：
    - 日均约 **413 万** sitemap 触发多批次命中（hit_batch_cnt > 1）
    - 峰值达 **493 万**（2026-05-14）
    - 命中批次>1 的 sitemap 累计 **2,480 万**（6日总和）

  URL 增量贡献（多批次命中的额外产出）：
    - 20260510：264w sitemap → 贡献 **552 万** URL
    - 20260511：436w sitemap → 贡献 **1,033 万** URL（突破千万级）
    - 20260514：493w sitemap → 贡献 **1,140 万** URL（单日峰值）
    - 已知样本日均额外贡献约 **908 万** URL/天

  Redis 打点来源分布：
    - 模糊去重主路径：约 **600 亿/天**
    - 频度调度 1~4 级别贡献：约 **400 亿/天**
    - 频度调度占总打点量的约 **40%**

  sitemap 对模糊留存贡献量（20260418~0424 周期）：约 **85 亿**

  打分模型细节（第二期优化）：
    - compositeScore = 0.5 × newUrlScore + 0.5 × fuzzyScore
    - fuzzyScore = 0.5 × rateScore(留存率) + 0.5 × scaleScore(规模)
    - 5 级等级体系：HIGH(6次/天) / MIDDLE(4次/天) / LOW(2次/天) / DISUSE(1次/天) / PENDING(不投递)
    - 平滑降级保护：每次最多降 1 级（防止单次异常误淘汰优质站点）

  近期进展（2026.06）：
    - 从中文历史留存数据中挖掘 **4000 万** 中文站点进行 robots 投递
    - 已完成中文站点 sitemap 抓取扩量

  （数据来源：学城文档 2761541894 / 2757591191 / 2762421623 / 2764067552）

6. 策略拦截与作弊站点治理（2026.03.19）
--------------------------------------------------------------------------------

【问题场景】
对抓取链接结果进行人工评估后发现，大量垃圾/作弊站点混入抓取链路：
  - 作弊站：通过生成大量垃圾页面骗取抓取资源
  - 垃圾站：内容质量极低，无实际价值
这些站点严重影响新链发现的整体质量。

【解决方案 - DSL规则引擎】

  正则预编译缓存：
    在 SitemapRequestConsumer 的 @PostConstruct 初始化阶段，读取 Lion MDP
    配置 sitemap_regular_filter_list 中的所有正则表达式，预先编译为 Pattern
    对象，缓存至 regularPatternList（HashSet<Pattern>）。
    预编译避免了每次请求都重新编译正则的性能开销。

  配置热更新：
    通过 @MdpConfigListener 监听 MDP 配置变更事件，当规则列表发生变化时
    自动重新编译正则并更新缓存。无需重启服务即可生效，新规则秒级上线。

  匹配拦截：
    消息处理时在 preFilterProcess() 中调用 SitemapUtil.isRegularFilterDomain()
    对 domain 和 URL 进行批量正则匹配。将拦截逻辑置于 Redis 去重和限流判断
    之前（最前置位置），避免作弊站点消耗任何有效资源（Redis查询、限流配额等）。

  URL指纹切割：
    除了域名级别的正则匹配，还通过URL指纹切割技术识别作弊链接的特征模式，
    进一步提高拦截精准度。

【成果】
  - 有效拦截 90%+ 的垃圾/作弊站点
  - 规则支持快速迭代，新作弊模式发现后分钟即可上线拦截规则
  - 新链发现链接质量显著提升

7. Sitemap环路监控体系建设
--------------------------------------------------------------------------------

【问题场景】
缺乏对每批次抓取数据的精细化监控，无法及时发现：
  - 消息积压
  - 高失败率
  - 大量无效站点
  - 各批次产出不均衡等问题

初期尝试接入内部 Raptor 日志监控平台，但因监控指标粒度过细、平台有 type 数量
上限要求，方案不可行。

【解决方案 - Redis统计方案】

  统计粒度：以小时为最小粒度

  维度设计：batchId + batchHour（批次ID + 小时）

  核心方法：在 SitemapService 的关键节点调用 redisService.recordTraffic()：
    - downLoadRobotsTxt()：记录 robots 抓取成功/失败数量
    - parseSitemapAndSend()：记录 sitemap 解析与新链发现数量

  监控指标Key设计（CAT漏斗打点配合）：
    - sitemap_funnel_robots_suc：robots成功抓取数
    - sitemap_funnel_url_found：发现的URL数量
    - sitemap_funnel_sitemapIndex_found：发现的sitemap索引数量
    - sitemap_funnel.* 系列：全链路漏斗各阶段数据

【成果】
  - 实现了对全链路漏斗的实时可见
  - 能及时发现积压、高失败率、无效站点过多等异常
  - 为后续无效站点治理提供了数据基础


--------------------------------------------------------------------------------
8. 无效站点治理
--------------------------------------------------------------------------------

【问题场景】
监控体系完善后发现：
  ① 每天有 1500w 历史积压消息持续占用处理资源
  ② 批次中发现大量无效站点：
     - 抓取结果为默认界面（空内容/模板页）：占 27%-34%
     - 抓取失败（超时/连接拒绝等）：占 11%-17%
     - robots中无sitemap链接：占 25%-27%
  这些无效流量严重消耗线程池资源，降低有效站点的处理效率。

【解决方案】

  历史积压清理：
    在 SitemapRequestConsumer.preFilterProcess() 中扩充 ext 字段解析，
    提取 dispatchTs 时间戳与可配置的 staleThresholdHours 比对，
    对超过时效窗口的历史积压消息直接丢弃（标记为 sitemap.funnel.stale），
    彻底消除历史积压对当前批次的干扰。

  失败原因细分与持久化：
    在 SitemapService.saveFailRobotsTxt() 中对失败原因进行细分：
    - download_fail：下载失败
    - abnormal_content：异常内容（默认页面/模板页）
    - cf_blocked_1005/1020：Cloudflare拦截
    - captcha_blocked：验证码拦截
    将失败原因持久化到 robots_txt 表的 ext 字段，为无效站点识别提供数据基础。

  过期式封禁（非永久封禁）：
    对于无效站点的过滤采用"过期时间"策略而非永久封禁：
    - 设置合理的过期时间窗口
    - 避免一次临时失败导致站点被彻底屏蔽
    - 在拦截效果与站点覆盖率之间取得平衡
    - 站点恢复后可自然重新进入处理流程

【成果】
  - 每日消除 1500w 历史积压消息的处理开销
  - 无效站点在进入线程池前即被拦截，节省大量线程池资源
  - 有效站点处理效率显著提升

--------------------------------------------------------------------------------
9. 抓取引擎架构升级（Selenium -> Playwright）
--------------------------------------------------------------------------------

【问题场景】
原有 Selenium 引擎架构存在以下问题：
  ① 维护成本极高：需人工维护复杂的线程调度、心跳探活及异步轮询机制
  ② 逻辑冗长：大量代码用于管理浏览器生命周期，业务代码占比低
  ③ 并发能力受限：资源分配不均，缺乏高效并发管理，单机吞吐量瓶颈明显
  ④ JS渲染支持局限：对现代化Web技术的兼容性不足
  ⑤ 等待逻辑不稳定：Selenium的隐式/显式等待在面对复杂页面时不可靠

【选型依据】
团队其他同学进行了多进程抓取实测对比：
  - 分别使用 Selenium 和 Playwright 进行多进程网页抓取对比测试
  - Playwright 在避免不稳定等待、自动化API设计、现代浏览器兼容性方面更优
  - 最终选定 Playwright 作为新一代抓取引擎

【解决方案】

  Browser Context 技术：
    引入 Playwright 的 Browser Context（浏览器上下文）概念，实现轻量化的
    多租户模拟。每个 Context 共享同一个浏览器实例但拥有独立的 Cookie、
    Cache、Session 等状态，资源复用率远高于 Selenium 的独立浏览器实例模式。

  自定义线程池管理：
    配合自定义线程池实现任务的有序调度，彻底去除原 Selenium 架构下繁琐的
    探活与轮询逻辑，实现了抓取流程的同步解耦（submit→execute→完成，无需回调）。

【成果】
  - 代码量大幅精简，维护成本显著降低
  - 对最新版本 Chrome 完美兼容
  - 系统在高并发场景下的资源复用率与抓取效能大幅提升

10. 服务器基础设施治理
--------------------------------------------------------------------------------

【问题场景】
Playwright 在生产环境部署时面临底层系统库版本过低的兼容性挑战：
  - glibc 版本过低：不支持高版本 Chrome/Chromium 的某些系统调用
  - gcc 版本过低：C++标准库缺少必要的特性支持
  导致：本地测试成功但线上服务器无法运行

尝试过的方案：
  - Playwright 依赖降级 → 导致功能缺失，不可行
  - 手动逐台升级 → 效率低下，不可规模化

【解决方案】
  ① 完成对服务器 glibc 及 gcc 核心库的深度版本升级
  ② 将升级流程沉淀为标准化自动化脚本（Shell脚本）
  ③ 实现全量服务器的平滑迁移与批量化升级

【成果】
  - 彻底解决了高版本浏览器的运行依赖问题
  - 后续扩容新服务器只需执行标准化脚本即可
  - 大幅降低了环境治理的运维成本

--------------------------------------------------------------------------------
11. 截图抓取全链路服务（2026.03.24）
--------------------------------------------------------------------------------

【业务背景】
面向多模态大模型训练需求，业务方（CC团队）筛选出一批高质量URL，需要进行
网页截图抓取。截图结果用于训练大模型的"看图写代码"能力——根据网页截图
生成对应的前端代码。

【技术方案 - 独立服务设计】

  架构决策：完全独立于 Sitemap 环路
    - 独立的 Mafka Consumer：ScreenshotRequestConsumer
    - 独立的线程池：ScreenshotRequestConsumer.EXECUTOR
    - 独立的监控指标：screenshot.* 前缀
    原因：截图任务耗时长（JS渲染+截图）、资源需求不同，混用会互相影响

  消费链路（preFilterProcess）：
    ① 反序列化：JackSonUtils.fromJson(msg, ScreenshotRequest.class)
    ② 空值校验：request/url/domain/host 为空时直接丢弃
    ③ Domain/Host 补全：从 URL 中提取（new URL(url).getHost()）
    ④ URL合法性校验：isValidUrl（MalformedURLException检查）
    ⑤ 黑名单过滤：FilterUtils.isInBlacklist(blackDomainSet, domain, host)
    ⑥ Redis 去重：（当前已注释掉，按需开启，12小时TTL）
    ⑦ 投入独立线程池：addRequestToThreadPool()

  线程池设计（参照 SitemapRequestConsumer 结构）：
    - SynchronousQueue<> 同步队列（无缓冲）
    - 固定大小线程池（corePoolSize = maxPoolSize = threadNum）
    - 线程命名："screenshot-crawler-pool-{n}-thread"
    - Lion MDP 配置 screenshot_thread_num 动态注入
    - 支持热更新：@MdpConfigListener("screenshot_thread_num")
    - 满载策略：synchronized + 自旋等待（sleep 1s）

  CAT 监控上报：
    启动 Daemon 监控线程（screenshot-pool-monitor），每秒采集：
    - screenshot.threadpool.activeCount：活跃线程数
    - screenshot.threadpool.coreCount：核心线程数
    上报至 CAT 监控平台，实现线程池状态的实时可视化。

  截图执行（ScreenshotService.submit()）：
    - 基于 Playwright 引擎打开浏览器访问 URL
    - 等待页面完全加载（JS渲染完成）
    - 执行全页面截图
    - 上传截图至 S3 存储系统
    - 记录截图结果与元数据

【遇到的问题与解决】

  中文站点乱码问题：
    现象：中文网页截图中文字显示为方块/乱码
    原因：服务器操作系统缺少中文字体文件
    解决：在服务器上安装中文字体包
      - wqy-zenhei（文泉驿正黑）
      - noto-cjk（Noto CJK字体）
    彻底解决中文页面截图显示异常问题。

  单机性能限制：
    由于 JS 渲染消耗大量 CPU/内存资源，单机每分钟仅能处理 1-2 条 URL。
    超过此阈值会导致机器负载过高甚至 OOM。
    因此通过横向扩容（490台机器）来提升整体吞吐能力。

【成果】
  - 集群 490 台机器整体吞吐约 1000 条/分钟
  - 产出数据直接用于训练大模型「看图写代码」多模态能力
  - 线程池支持配置热更新，可随时动态扩缩容
  - 内置黑名单过滤、URL合法性校验等多重质量保障机制
  - CAT 监控全覆盖，线程池状态实时可见

【第19项】监控指标按天查询异常排查（CAT平台配额限制）
时间：2026年4月17日
类别：监控排查 / CAT平台 / 问题解决
----------------------------------------------------------------------------------

【问题描述】
监控打点在以小时粒度查询时正常，但切换到天粒度后无法显示数据。
怀疑是系统Bug或配置问题。

【根因分析】（与杨宇航同学协作排查）
  该服务机器规模较大（2000+台），导致 Meta 数量超过周聚合报表800个的
  配额限制。周聚合报表采取"先到先占位"原则，排在后面的Meta数据被系统移除。
  因此天粒度查询（查的是预聚合周报表）无法显示超出的数据。

  小时粒度查询正常的原因：查询的是实时Meta报表，不受800个配额限制。

【解决方案】
  替代方案：在小时粒度视图下点击指标的"Graph"，手动选择"最近7天"
  时间范围来模拟天级趋势查看。
  细则查看：使用"group by name"功能按机器名分组查看。
  限制：7天前的数据因小时数据存储周期限制无法回溯。

【经验总结】
  大规模集群（2000+节点）的监控建设需要考虑平台配额限制，
  超过800个Meta时需采用聚合/采样/downsampling等策略规避。
