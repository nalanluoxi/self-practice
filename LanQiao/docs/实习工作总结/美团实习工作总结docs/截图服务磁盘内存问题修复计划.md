# 截图服务磁盘与内存问题修复计划

## 一、问题背景

线上截图抓取服务（ScreenshotRequestConsumer）上线后出现两个告警：
- 磁盘利用率间歇性飙升至 100%（正常 2-3%）
- 可用内存占比持续下降至 5% 以下

## 二、根因分析

### 问题1：磁盘利用率间歇性100%

**根因**：`PlaywrightDownLoader.java` 第98行存在参数 `--disable-dev-shm-usage`

该参数原本用于 Docker 容器环境（/dev/shm 默认只有64MB），作用是禁用共享内存、改用磁盘 /tmp。
但线上服务器 /dev/shm 有 3.9G 且完全空闲，该参数反而造成：

```
page.screenshot() → Chrome 渲染缓冲 → 写 /tmp（磁盘）→ 突发大块写入 → 磁盘100%
截图完成          → 临时文件删除   → 磁盘恢复2-3%
```

**间歇性特征**完全由此解释：每次 screenshot() 调用对应一次飙升。

---

### 问题2：可用内存持续下降

**根因1：同一URL被 navigate 两次（已通过合并Phase1+Phase2修复）**

原代码：
- Phase1：创建 Context1（无viewport）→ navigate → 收集HTML/JS/CSS → close
- Phase2：创建 Context2（有viewport）→ **再次 navigate 同一URL** → 截图 → close

两个 Context 缓存隔离，Phase2 无法复用 Phase1 的缓存，导致：
- 网络请求翻倍
- Chrome 磁盘缓存写入翻倍
- 两个 Page 对象同时存活，内存峰值叠加

> ✅ 已修复：合并为一个 mergedContext，只 navigate 一次

**根因2：所有大对象同时堆在内存等待S3上传**

单次任务内存峰值拆解：
```
htmlBytes              ≈ 几十KB ~ 几MB
assetBytes（全量JS/CSS）≈ 10-50MB（热门页面更多）
每个viewport：
  screenshotBytes      ≈ 1-3MB（PNG压缩后）
  annotatedBytes       ≈ 1-3MB
  BufferedImage解码    ≈ 5.6MB（1400×1000×4字节）
  BufferedImage副本    ≈ 5.6MB
  baos                 ≈ 1-3MB

单viewport内存峰值     ≈ 18-20MB
N个viewport + assetBytes ≈ 100-200MB/条URL
```

所有数据在 `crawlScreenshot()` 返回后统一上传S3，上传期间（串行网络IO）全部无法GC。

> ✅ 已部分修复：ScreenshotService.submit() 中 S3 上传完成后立即 setNull

**根因3：Chrome 进程内存未计入**

每个线程持有一个 ThreadLocal PlaywrightDownLoader = 一个 Chrome 进程：
- Chrome 进程本身占 200-500MB（JVM堆外，操作系统级别）
- 5分钟重建实例时，新旧进程短暂同时存活，内存双倍峰值

---

### 问题3：400分区只有200台机器有CAT打点

`screenshot_thread_num=1`，490台机器 = 490个消费者。
400个分区只能分配给400台机器，剩余90台分不到分区。
但实际只有200台有打点，疑似**实际生效分区数只有200**，需确认。

---

## 三、修复计划

### 修复1：删除 `--disable-dev-shm-usage`【解决磁盘间歇性100%】

- **文件**：`llm-crawler-server/.../downloader/PlaywrightDownLoader.java`
- **改动**：删除第98行 `"--disable-dev-shm-usage",`
- **效果**：screenshot() 渲染缓冲从写 /tmp 改回写 /dev/shm（内存），磁盘完全不感知
- **风险**：/dev/shm 有 3.9G 空闲，无风险

---

### 修复2：禁用 Chrome 磁盘缓存【减少磁盘缓存持续累积】

- **文件**：`llm-crawler-server/.../downloader/PlaywrightDownLoader.java`
- **改动**：在 Chrome 启动参数中新增：
  ```
  "--disk-cache-size=0"
  "--media-cache-size=0"
  ```
- **效果**：Chrome 不再将 JS/CSS 缓存到磁盘，爬虫场景下缓存命中率接近0，禁用无损失
- **风险**：无

---

### 修复3：viewport 截图完成后立即上传S3并释放内存【解决内存持续下降】

- **文件**：`llm-crawler-server/.../service/ScreenshotPlaywrightService.java`
- **改动**：`crawlScreenshot()` 方法新增 `Consumer<ViewportResult>` 回调参数，每截完一个viewport立即触发回调上传S3，上传完立即释放该viewport的 screenshotBytes/annotatedBytes
- **同步改动**：`ScreenshotService.java` 中传入回调实现，在回调内调用 S3 上传逻辑
- **效果**：
  - 内存中同时只保留1个viewport的数据（而非N个viewport全部攒完再上传）
  - 内存峰值从"所有viewport之和"降为"单个viewport大小"
- **风险**：需要注意回调异常处理，确保上传失败不影响后续viewport处理

---

### 修复4：assetBytes 逐个上传立即释放【进一步降低内存峰值】

- **文件**：`llm-crawler-server/.../service/ScreenshotPlaywrightService.java`
- **改动**：Phase1 中处理 collectedResponses 时，每处理一个 Response 立即上传S3并从 assetBytes 移除，不再攒完整 Map
- **效果**：assetBytes 内存占用从"全量JS/CSS"降为"单个资源大小"
- **风险**：改动较大，需要注入S3Service，建议单独测试

---

### 确认项：400分区实际生效数量

- **操作**：在任意broker机器执行：
  ```bash
  kafka-consumer-groups.sh --bootstrap-server <broker地址> \
    --describe --group <screenshot消费者组名>
  ```
- **目的**：确认实际分配到消费者的分区数，判断是否需要重新触发 Rebalance

| 优先级 | 修复项 | 预期效果 | 风险 |
|--------|--------|---------|------|
| P0 | 修复1：删 --disable-dev-shm-usage | 磁盘间歇性100%立即消失 | 无 |

**建议发布顺序**：
1. 第一次发布：修复1 + 修复2（改动最小，立即止血）
2. 观察内存情况，若仍偏低则进行修复3
3. 修复4作为后续优化迭代
