# 工作总结 3.0

---

## 模块一：Sitemap 新链接发现系统

### 业务背景

LLM 训练语料爬取依赖一个持续扩充的链接库（LinkBase），URL 来源有两路：一路从已抓取网页中提取外链，另一路通过 Sitemap 协议主动发现新链接。本模块负责后者——依据 robots.txt 协议，从全球站点解析 Sitemap 声明地址，递归下载并解析 sitemap.xml（含多级嵌套 Sitemap Index），从中提取结构化 URL 写入 LinkBase，为下游抓取任务持续补充高质量新链接来源。整套链路基于 Mafka 消息队列驱动，独立维护。

---

### 核心工作内容总览（STAR 法则）

- **【情景 Situation】** 系统接手时日新链接产出量仅 400 万~2000 万，波动较大；系统为单线程串行抓取，消息持续积压，吞吐严重不足；垃圾站点大量混入处理管道，原有拦截仅基于 domain 粒度过粗，大量作弊站点无法被有效识别；约 4% 的 `.gz` 格式 sitemap 因缺乏解压能力被全量丢弃；全量站点每天无差异投递，高频更新站点错过最新链接，低频站点浪费资源。

- **【任务 Task】** 对系统进行全面治理与升级：提升吞吐、构建多层限流、提升链接质量、补全 GZIP 处理能力、降低运维成本，并通过频度调度实现对站点的差异化精细调度。

- **【行动 Action】** 推进六项系统性改进：① 多线程并发架构重构；② 三级纵深限流体系建设；③ 自研本地自适应限流器；④ GZIP 压缩 Sitemap 解析补全；⑤ DSL 规则引擎治理垃圾站点；⑥ 频度调度迭代（v1 差异化 TTL → v2 三维打分模型 + 多轮投递闭环）。

- **【结果 Result】** 集群小时处理量从 2.5 万提升至 96 万（↑16x）；日新链接发现量从 400 万~2000 万稳定提升至 200 亿（整体提升逾千倍，频度调度阶段单独贡献 ~10x 跃升）；高质量站点占比从 4.1% 提升至 11.9%；规则响应从分钟级压缩至秒级；频度调度日均额外贡献 URL 约 908 万，日均多批次命中 sitemap ~413 万，Redis 打点规模达千亿级。

### 工作点详细展开

---

#### 工作点 1：多线程并发架构重构

**【情景 Situation】**

原架构在 Mafka 回调线程中同步执行全部 download 业务逻辑，单线程串行消费，处理速率仅 1.6~2.5 万条/小时。由于回调线程被 IO 阻塞（HTTP 下载 sitemap），消息队列持续积压，无法满足链接发现规模诉求。

**【任务 Task】**

在不影响消息可靠性的前提下，将消费架构改造为高并发异步模型，消除串行瓶颈，大幅提升系统吞吐量。

**【行动 Action】**

- **思考链路**：串行瓶颈 → 需要异步解耦回调线程与业务执行 → 引入线程池，但线程池满时如何防止消息丢失？→ 用 `SynchronousQueue` 零容量队列 + `synchronized + while` 自旋等待，线程池打满时暂停消费并超时重投 MQ，形成背压闭环。
- **线程池初始化**：`@PostConstruct` 初始化 `ThreadPoolExecutor`，核心线程数通过 MDP 配置中心动态下发，`@MdpConfigListener` 监听配置变更实现不停机热更新。
- **背压设计**：`SynchronousQueue` 零容量队列，`submit` 失败时外层 `synchronized + while` 自旋等待，超时后将请求重投 MQ，确保消息不丢失。
- **分区扩容**：业务侧协调 Mafka 分区数从 200 扩容至 400，消除消息队列侧的分区瓶颈。

**技术要点**：`ThreadPoolExecutor`、`SynchronousQueue`、`@PostConstruct`、`@MdpConfigListener`、Mafka 分区扩容

**难点**：线程池打满时既不能阻塞 Mafka 回调线程（会导致 rebalance），也不能直接丢弃消息。最终方案是自旋 + 超时重投 MQ，兼顾消费连续性与消息可靠性。

**【结果 Result】**

集群小时处理量从 2.5 万提升至 96 万；日新链接发现量从 2~3 亿提升至 10~14 亿（峰值 75 亿）；集群 QPS 提升 16 倍。

#### 工作点 2：三级纵深限流体系建设

**【情景 Situation】**

系统无限流保护时，大站 URL 数量远超小站，形成「大站挤兑小站」现象：优质小站有效处理率极低。同时黑名单/去重命中的无效请求也大量消耗限流配额，造成配额浪费。

**【任务 Task】**

构建多粒度限流体系，保障大站与小站的处理公平性，同时通过前置过滤减少限流配额浪费。

**【行动 Action】**

- **思考链路**：单一限流无法区分大站小站 → 需要在不同粒度分别管控 → 集群级（总吞吐上限）+ 单机级（单节点上限）+ 站点级（per-domain 独立计数）三层叠加。
- **三层限流**：基于 Rhino OneLimiter，分别配置 `sitemap_cluster_qps_limit`（集群层）、`sitemap_limit_single_node`（单机层）、`sitemap_limit`（站点层，以 `assignedDomain` 为 uuid 独立计数）。
- **前置拦截链**：限流之前依次执行：作弊站点正则过滤 → 黑名单域名/URL 后缀过滤 → 二级黑名单 prefix 过滤 → Redis KV 去重，最大限度避免浪费限流配额。
- **重投保障**：被限流请求通过 `sitemapPublishService.sendRequest()` 重投 MQ，确保不丢消息。

**技术要点**：Rhino OneLimiter、Redis KV 去重、多级黑名单过滤链、MQ 重投

**难点**：站点层限流以 `assignedDomain` 为 uuid 独立计数，需要在高并发下保证各域名计数器互不干扰，同时配额参数需支持动态调整。

**【结果 Result】**

全天均匀产出，大站挤兑小站问题基本解决；无效请求对限流配额的消耗大幅降低。

#### 工作点 3：自研本地自适应限流器

**【情景 Situation】**

集群与单机两层限流为比例过滤，大站流量占比依然偏高；固定阈值无法感知线程池实时负载——线程池利用率不足时，并发能力持续被浪费；线程池打满时，大站依然占用过多配额，小站仍被挤压。

**【任务 Task】**

在现有三级限流之上，自研一个能感知线程池负载并动态调整单站配额的本地自适应限流器。

**【行动 Action】**

- **思考链路**：固定配额无法应对负载波动 → 需要根据线程池利用率动态调整 → 用后台采样线程定期读取 `activeCount / corePoolSize`，根据利用率高低收放单站配额上限。
- **滑动窗口计数器**：`CounterRateLimiter` 以 `ConcurrentSkipListMap<Long, Long>` 实现滑动窗口，每个顶级域独享一个限流器实例，存入 `ConcurrentHashMap`，守护线程定期清理不活跃桶防内存泄漏。
- **自适应调节**：`SitemapRequestConsumer.setup()` 启动后台采样线程，每秒读取 `EXECUTOR.getActiveCount()` 与 `corePoolSize`，连续 3 次低于 80% 则放宽配额（`LIMITE_COUNT++`），连续 3 次超过 80% 则收紧（`LIMITE_COUNT--`），上限由 MDP 热更新控制。

**技术要点**：`ConcurrentSkipListMap` 滑动窗口、`ConcurrentHashMap` 按域名隔离、守护线程内存清理、MDP 热更新

**难点**：`ConcurrentSkipListMap` 做时间分桶的边界问题——桶的时间精度与窗口对齐；以及采样线程与业务线程对 `LIMITE_COUNT` 的并发修改需要保证可见性（`volatile`）。

**【结果 Result】**

英文留存量从 2000 万增长至 1.2 亿；1000 万站点发现任务处理时长缩短至 3~4 小时；峰值集群 QPS 达 1417+。

#### 工作点 4：GZIP 压缩 Sitemap 解析

**【情景 Situation】**

约 4% 的 sitemap 流量（日均 400 万+）为 `.gz` 格式，原链路因缺乏解压能力，遇到此类格式时直接丢弃，导致大量新链接漏发现。

**【任务 Task】**

以最小改动面为原则，补充 GZIP 格式 sitemap 的识别与解压能力，复用现有 XML 解析逻辑。

**【行动 Action】**

- **思考链路**：已有 XML 解析能力，只需在入口处加一层解压适配 → 识别 `.gz` 扩展名 → 用 `GZIPInputStream` 包装字节流 → 解码后交给原有 XML 解析器，改动最小化。
- **格式识别**：`isValid()` 通过 URL 路径扩展名嗅探自动识别（排除 `tar.gz` 避免误判）。
- **解压实现**：`decompressGzip()` 以 `GZIPInputStream` 包装原始字节流，分块读取并 UTF-8 解码，结果直接传入已有 XML 解析器。

**技术要点**：`GZIPInputStream`、URL 扩展名嗅探、最小改动复用已有解析链路

**难点**：`GZIPInputStream.read()` 返回 `int`，-1 表示流结束（不是 null），需正确处理读取终止条件，避免解压截断或死循环。

**【结果 Result】**

日新链接发现量峰值从 3.79 亿提升至 52.6 亿，提升约 14 倍。

#### 工作点 5：DSL 规则引擎治理垃圾/作弊站点

**【情景 Situation】**

垃圾站点 URL 持续混入处理管道，消耗大量计算资源与限流配额。而原有规则更新需要走代码发布流程，响应周期以天计，无法快速应对新出现的垃圾站点类型。

**【任务 Task】**

构建动态规则引擎，实现秒级规则热更新，将垃圾站点拦截前置到限流和 Redis 去重之前，以最低成本优先拦截。

**【行动 Action】**

- **思考链路**：规则变更不能依赖发布 → 需要配置化 → 用 MDP 配置中心存储正则集合 → `@PostConstruct` 预编译缓存 → `@MdpConfigListener` 监听变更后重新编译，秒级生效。
- **预编译缓存**：`@MdpConfig` 接收正则字符串集合，`@PostConstruct` 预编译为 `HashSet<Pattern>` 避免每次匹配重复编译，降低 CPU 开销。
- **热更新**：`@MdpConfigListener` 监听配置变更后重新编译 Pattern 集合并替换缓存，无需重启服务。
- **前置拦截**：拦截逻辑置于 Redis 去重和限流之前，确保垃圾请求在消耗任何资源之前被过滤掉。

**技术要点**：MDP 配置中心、`@MdpConfigListener`、`Pattern` 预编译、`HashSet<Pattern>` 缓存

**难点**：`Pattern` 未重写 `equals/hashCode`，不能直接用 `HashSet<Pattern>` 做去重（每个 Pattern 实例独立），需要以正则字符串为 key 进行去重后再编译成 Pattern 集合。

**【结果 Result】**

日均拦截 4~5 亿条请求；规则生效延时从分钟级压缩至秒级；有效拦截 90% 垃圾站点；抽样高质量站点率从 4.1% 提升至 11.9%。

#### 工作点 6：频度调度——从差异化 TTL 到三维打分模型的完整迭代

**【情景 Situation】**

早期方案每天通过 `RobotsMsgSendingJob`（每日 Spark 任务）对全量 robots.txt 无差异地固定调度一次。随着站点库规模扩大，该策略暴露出两个对立的问题：高频更新站点（如新闻类、电商类）一天只调度一次，错过大量最新链接；低频更新站点（如企业官网、博客）每天都被无意义重复调度，浪费大量资源。链路缺乏对站点更新频率的感知与区分能力，全量无差异投递既浪费资源又错过高价值新链。

**【任务 Task】**

设计并落地频度调度体系，实现高频站点多次调度、低频站点控制频率的差异化精细调度策略；通过两个版本的迭代，从最小可行方案逐步演进为三维打分 + 多轮投递 + 闭环反馈的完整体系，最终将日抓取量提升一个数量级。

**【行动 Action】**

**— v1 阶段：天级差异化调度，踩坑发现问题（2026.02）—**

- **核心思路**：以天为调度粒度，根据前一天站点是否有新链接产出进行打分，高分站点每天投递一次 sitemap、低分站点隔天投递、无产出站点不投递，利用多天累计结果动态调整调度频次；此阶段尚未引入 Redis TTL 差异化，仅通过投递频次来区分站点优先级。
- **实现**：`SitemapPublishService` 在消息 `ext` 字段携带 `batchId`、`dispatchTs`、`grade`，消费侧解析 grade 字段路由到对应的调度分支；打分维度单一，仅依赖 `newUrlScore`（前一天新链接产出量）。
- **踩坑**：上线数日后发现实际发送量远少于预期，新链产出量大幅下降。排查后定位根本原因：初版打分阈值设置过于严苛，绝大多数站点被归入低频甚至 PENDING 等级，高等级站点集合过小，实质上并未起到有效扩量作用；同时单一 `newUrlScore` 维度无法全面衡量站点价值——产出新链较少但留存率极高的优质站点会被错误地打低分。
- **v1 的意义**：验证了天级差异化调度的基础框架（ext 字段透传 + 调度频次联动），通过踩坑精准定位了两个核心问题：阈值策略过严 + 打分维度单一；同时天级粒度本身也是瓶颈——高频站点一天最多被调度一次，无法进一步提升产出，为 v2 升级到小时级多轮投递提供了方向。

**— v2 阶段：小时级多轮投递 + 三维打分 + TTL 差异化 + 闭环反馈（2026.04~05）—**

- **问题拆解**：v1 有两个本质问题：① 打分维度单一，站点价值评估不准；② 调度粒度为天级，高频站潜力未被充分发挥。v2 需同时解决：引入留存率（`rateScore`）和站点规模（`scaleScore`）构建三维打分模型；将投递粒度从天级升级为小时级（grade 1 每天 6 次），并首次引入 Redis TTL 差异化使 TTL 与投递间隔精确配合，避免去重拦截失效。

- **三维打分模型**（`UpdateFrequencyTableJob`，Spark 离线任务，T+1 每日更新）：
  ```
  compositeScore = 0.5 × newUrlScore + 0.5 × fuzzyScore
  fuzzyScore     = 0.5 × rateScore   + 0.5 × scaleScore
  ```
  - `newUrlScore`：来自 `sitemap_link_bloomfilter_daily_new_url`（Bloom 去重新链接表），衡量昨日新链接产出效果
  - `rateScore`：来自 `llm_crawler_domain_save_info`（域名留存统计表），衡量链接留存率（留存量/抓取数）
  - `scaleScore`：同表，站点规模经 log 压缩归一化，防止超大站点独占高分

- **等级映射与多轮投递**（`FrequencyDeliverySitemapJob`，按 grade 多轮定时）：
  ```
  compositeScore ≥ 0.75 → grade 1 HIGH   → 每天 6 次（00/04/08/12/16/20h）
  compositeScore ≥ 0.50 → grade 2 MIDDLE → 每天 4 次（00/06/12/18h）
  compositeScore ≥ 0.25 → grade 3 LOW    → 每天 2 次（00/12h）
  rate ≥ 0.01           → grade 4 DISUSE → 每天 1 次（00h）
  else                  → grade 5 PENDING → 不投递
  ```

- **工程化关键设计**：
  - **降级保护**：每次最多降 1 级，防止单日数据波动（如周末流量低谷）导致等级快速跌落，保护调度稳定性
  - **冷启动回退**：无历史数据的站点默认 `fuzzyScore = 0.35`（grade 3 附近），不直接降为最低级，保证新站点有机会进入调度
  - **EffectiveTldFinder**：用 `crawlercommons.getAssignedDomain()` 提取真实 assigned domain 作为打分 key，避免子域名（如 `news.bbc.com` 和 `www.bbc.com`）割裂同一站点的数据
  - **TTL 与投递间隔配合**：grade 1 每 4h 投递一次，对应 TTL 设为 3h；TTL 必须小于投递间隔，否则同一 sitemap 在 TTL 未过期时再次被投递，仍被去重过滤，多轮投递失去意义
  - **ext 透传链路**：`FrequencyDeliverySitemapJob` 写入 `ext.grade` → `SitemapRequestConsumer` 解析 → `SitemapService.resolveExpireTimeByGrade()` 设置 Redis TTL，全链路无损透传

- **完整闭环反馈链路**：
  ```
  ① UpdateFrequencyTableJob（T+1 离线，每日）
     输入：抓取结果表 + Bloom 新链接表 + 域名留存表 + 黑名单
     输出：DI 表（每日快照）+ DF 表（T+1 累积）
  ② FrequencyDeliverySitemapJob → 读 DF 表 → 按 grade 多轮投递 MQ
  ③ SitemapRequestConsumer → 解析 grade → TTL 适配 → 抓取
  ④ 抓取结果流回打分输入表 → 下一轮 T+1 重新评分（形成闭环）
  ```

**技术要点**：Mafka ext 字段透传、Redis TTL 动态设置、Spark 离线打分（`UpdateFrequencyTableJob`）、Bloom 过滤器去重、`EffectiveTldFinder.getAssignedDomain()`、DI/DF 表设计、多轮定时投递、降级保护算法

**难点**：
- **v1 的策略陷阱**：打分阈值如何设定才能在「覆盖足够多高价值站点」与「不引入过多低质站点」之间取得平衡——v1 因阈值过严踩坑，这是频度调度最难的部分，不是技术问题而是策略调参问题；同时天级粒度决定了高频站每天最多只能被处理一次，v2 升级到小时级多轮投递后，TTL 必须精确配合投递间隔（TTL < 投递间隔），否则 Redis 去重尚未过期就再次投递，多轮投递完全失效
- **rate_score 字段的双重计算陷阱**：DI 表中 `rate_score` 存储的是已乘权重的值（`0.5 × rateScore`），而非原始档位值；读取时不能再乘一次，否则权重翻倍导致评分虚高
- **domain key 一致性**：`real_domain`（数据表字段）与 `EffectiveTldFinder.getAssignedDomain()` 提取结果可能不一致；不一致时静默回退 `fuzzyScore = 0.35`，保证健壮性

**【结果 Result】**

连续 6 天（2026-05-10 ~ 2026-05-15）实测：
- 日均多批次命中 sitemap **~413 万**，峰值 **493 万**（2026-05-14）

## 模块二：HTML 数据合成链路（截图抓取服务）

### 业务背景

为训练 Coding 模型「看图写代码」能力，需要大规模采集真实网页的视觉快照与完整源码作为训练对齐数据——给定网页截图，模型需还原对应 HTML/CSS/JS 代码。本模块独立主导从零设计并落地，负责批量抓取含交互按钮、动态组件的真实网页，产出截图（多视口/多 DPR）+ HTML 快照 + 完整静态资源包（JS/CSS/字体/图片），写入 S3 并通过结果 MQ 通知下游。技术栈：Playwright + Mafka + S3 + Java 多线程。

---

### 核心工作内容总览（STAR 法则）

- **【情景 Situation】** 无现有系统可复用，需从零设计；同时面临三大核心挑战：高并发下 Playwright Browser 实例内存泄漏、离线 HTML 资源完整性（字体/图片/JS/CSS 大量缺失）、线程池内部任务互相阻塞死锁风险；另有线上部署环境依赖缺失、中文字体渲染乱码等工程问题。

- **【任务 Task】** 从零设计并落地完整的截图抓取服务，确保高并发稳定运行、离线 HTML 资源尽可能完整、产出数据可供模型训练使用。

- **【行动 Action】** 构建三层解耦架构（消费层/调度层/执行层）；ThreadLocal Browser 实例复用与定时重建防内存泄漏；双线程池隔离抓取与资源补全防死锁；逐一攻克四类资源完整性难题；解决线上部署环境问题与中文渲染问题。

- **【结果 Result】** 字体与 CSS 缺失问题基本解决；图片可用率约 70%；内存峰值显著降低；下游 S3 扫描瓶颈消除；为模型训练提供了可规模化生产的高质量数据来源。

### 工作点详细展开

---

#### 工作点 1：整体系统架构设计

**【情景 Situation】**

从零搭建，无现有参考，需要同时满足：高并发（多线程并行抓取）、稳定性（Browser 实例不泄漏）、资源完整性（离线 HTML 可离线渲染）三个目标。

**【任务 Task】**

设计合理的分层架构，将消息消费、业务调度、Playwright 执行三类关注点解耦，便于独立扩展和问题定位。

**【行动 Action】**

- **思考链路**：三类职责混在一起难以维护和扩展 → 分层解耦 → 消费层只管消息可靠性，调度层只管业务编排，执行层只管 Playwright 细节。
- **消费层（ScreenshotRequestConsumer）**：Mafka 消费者，黑名单过滤 + URL 合法性校验后，将请求投入独立 `ThreadPoolExecutor`（`SynchronousQueue` + 自旋背压），与 Sitemap 线程池完全隔离互不影响。
- **调度层（ScreenshotService）**：业务编排——代理选取（按域名路由海外/国内代理线路）→ 生成 S3 路径前缀 → 提交 `ScreenshotPlaywrightService` 异步执行 → 收集结果 → 发送结果 MQ。
- **执行层（ScreenshotPlaywrightService）**：双层线程池（`DOWNLOAD_TASK_POOL` + `SUPPLEMENT_POOL`）隔离主抓取与资源补全；`ThreadLocal<PlaywrightDownLoader>` 每线程独享 Browser 实例，实例存活 5 min 后自动重建防内存泄漏；按代理线路绑定不同 Chrome UA。

**技术要点**：三层解耦、`ThreadLocal<PlaywrightDownLoader>`、双线程池隔离、代理路由

**难点**：`ThreadLocal` Browser 实例需要在线程复用场景下定时重建——直接用 `ThreadLocal.remove()` 不够，需要主动调用 `browser.close()` 释放 Chromium 进程，否则造成进程泄漏。

**【结果 Result】**

架构清晰，三层职责单一，内存峰值显著降低，下游 S3 扫描瓶颈消除。

---

#### 工作点 2：线上部署环境问题

**【情景 Situation】**

本地开发环境下 Playwright 抓取完全正常，但部署到线上机器后出现异常。查看线上日志，发现系统缺少 Playwright 运行所需的底层 C 语言依赖库（glibc 版本过低），导致 Chromium 无法启动。

**【任务 Task】**

解决线上 Playwright 运行环境依赖问题，确保服务可稳定部署。

**【行动 Action】**

- **思考链路**：线上与本地环境差异 → 查日志定位缺失依赖 → 优先尝试低风险方案（降低浏览器/Node 版本），失败后才升级 glibc（对服务器影响较大）。
- **排查过程**：首先尝试降低 Playwright 版本、降低 Node.js 版本，均失败；分析错误信息确认根因是 glibc 版本不足；最终通过升级 glibc + 安装对应版本 npm/Node.js 工具 + 安装 Playwright 浏览器依赖，成功运行。
- **沉淀**：将整套安装流程总结为可复用的环境部署脚本，后续新机器一键执行。

**技术要点**：Playwright 环境依赖、glibc 升级、部署脚本化

**难点**：升级 glibc 对服务器系统级依赖影响面广，需要评估风险后谨慎操作，不能在生产机器上随意执行。

**【结果 Result】**

成功在线上机器稳定运行 Playwright；沉淀出可复用部署脚本，降低后续新机器部署成本。

#### 工作点 3：中文字体渲染乱码

**【情景 Situation】**

本地抓取中文站点截图正常，但线上机器截图中所有中文均显示为方块（口口）。

**【任务 Task】**

排查并解决线上中文渲染乱码问题。

**【行动 Action】**

- **思考链路**：本地正常线上异常 → 环境差异 → 字体问题 → 线上机器缺少中文字体包导致 Chromium 无法渲染中文。
- **解决方案**：在线上机器安装中文字体包（如文泉驿、Noto CJK 等），重启服务后中文渲染恢复正常。

**技术要点**：Linux 字体包管理、Chromium 字体渲染依赖

**【结果 Result】**

中文站点截图渲染恢复正常，不再出现乱码方块。

#### 工作点 4：四类资源完整性难题攻克

**【情景 Situation】**

离线 HTML 需要在无网络环境下可渲染，但 Playwright 的 `onResponse` 回调存在多种漏捕获场景，导致字体、图片、JS/CSS、动态样式大量缺失。

**【任务 Task】**

逐一识别并攻克四类资源缺失场景，提升离线 HTML 资源完整性。

**【行动 Action】**

**① 字体缺失（Chrome 懒加载）**

- **思考链路**：`onResponse` 只能捕获实际发生的请求 → Chrome 懒加载下未渲染区域的字体不触发请求 → 需要主动从 CSS 中解析 `@font-face` 声明并补充下载。
- **方案**：`supplementFontsFromCss()` 用 helger/ph-css 解析所有 CSS 中 `@font-face { src: url(...) }` 声明，主动补充下载；以 `collectedFontUrls` Set 去重，避免与 `onResponse` 已捕获的字体重复下载。

**② 懒加载图片缺失（IntersectionObserver）**

- **思考链路**：`IntersectionObserver` 只在图片进入视口时触发请求 → 页面不滚动只有首屏图片被捕获 → 需要模拟滚动触发全量懒加载。
- **方案**：Phase1 加入分步滚动——逐视口 `window.scrollTo` + 300ms 等待触发全量懒加载；`supplementImagesFromHtml()` 用 Jsoup 解析 `srcset` 所有尺寸变体 + `data-src`，与 `collectedImageUrls` 取差集兜底仍遗漏的图片。

**③ JS/CSS 被 onResponse 遗漏（304 缓存/跨域）**

- **思考链路**：浏览器缓存命中（304）或跨域限制导致 `onResponse` 未捕获响应体 → 需要从 HTML 中解析所有引用并主动补充。
- **方案**：`supplementScriptsAndStylesFromHtml()` 解析 HTML 中 `<script src>` / `<link rel=stylesheet>`，与 `collectedJsCssUrls` 取差集主动补充下载。

**④ styled-components 动态样式丢失**

- **思考链路**：`styled-components` 通过 `el.sheet.insertRule()` 写 CSSOM 而不写 `textContent` → `page.content()` 序列化仅取 DOM，动态注入样式全部丢失 → 需要在序列化前将 CSSOM 回写到 DOM。
- **方案**：注入 JS 将 `data-styled` style 标签的 `cssRules` 逐条写回 `el.textContent`，再序列化，确保动态样式落入离线 HTML。

**技术要点**：helger/ph-css 解析 @font-face、Jsoup 解析 HTML、`window.scrollTo` 模拟滚动、CSSOM 序列化回写、差集兜底策略

**难点**：各类资源的补全需要与 `onResponse` 已收集的资源做差集，避免重复下载；`onResponse` 的字节流需要立即上传 S3 后置 null 释放，防止内存峰值过高。

**【结果 Result】**

字体缺失基本解决；CSS 缺失基本解决；图片可用率约 70%；内存峰值显著降低；下游 S3 扫描瓶颈消除。
