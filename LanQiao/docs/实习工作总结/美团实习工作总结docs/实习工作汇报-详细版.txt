实习工作汇报 — 详细版
所属团队：计算机平台 / Friday 数据组
业务背景：为 LongCat 大模型训练构建预训练语料库，建立网页抓取-解析-清洗全流程体系，通过抓取网页优质文本内容，解析清洗后用于预训练语料。主要模块：新链接发现、调度、抓取、sitemap 站点新链发现。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
一、流量智能调度优化（三级限流体系建设）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

【背景与问题】
原系统缺乏有效的流量控制与打散机制，Sitemap 发现环路处于"无序竞争"状态。大站点利用海量 sitemap 链接占据 Mafka 消息队列的绝大部分带宽，产生严重数据倾斜，直接挤兑小站点的挖掘资源，导致小站任务长时间积压、挖掘时效性极差。调度分配集中于凌晨 3 点与下午 3 点两个时间段，产出极不均匀。

【实现方案】
从 0 到 1 构建三级限流防护网：
  - 集群层（单机均摊限流）：在集群维度配置总限流阈值，动态均摊到每台机器，防止服务扩缩容时总流量跟随缩放，保护下游 Redis 吞吐压力。
  - 单机层（本地比例过滤）：在每台机器独立按站点比例过滤，适配大部分场景，性能好，无外部依赖。
  - Redis 精确层（集群限频）：通过 Redis 实现集群维度的站点级精确限频，控制每个站点每秒最多抓取数量，解决机器间流量不均衡问题。
  - 前置拦截：将黑名单过滤、去重流量等无效流量拦截逻辑前置，避免无效流量空耗限流配额，确保有限限流通道全部用于有效站点。

【效果】
调度产出从原先集中于凌晨 3 点与下午 3 点，优化后实现均匀产出，解决了大站挤兑小站的顽疾，实现流量的公平调度。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
二、环路架构与并发能力提升（多线程重构与集群扩容）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

【背景与问题】
初始系统采用单线程消费模式，单次任务同步处理耗时约 15s，导致集群 QPS 低于 10。面对百万级站点发送量时，系统吞吐量严重触顶，无法支持大规模 Sitemap 发现需求。

【实现方案】
  - 并发架构重写：在业务侧重构线程池管理模型，实现 Mafka 消息拉取与业务逻辑处理的异步解耦，消费线程只负责接收消息并投递到业务线程池，业务线程池负责实际 HTTP 抓取与解析。
  - 资源弹性扩展：完成 Mafka 集群从 200 分区到 400 分区的翻倍扩容，消除传输链路的物理瓶颈。
  - 线程池阻塞机制：当线程池已满时，主线程阻塞等待而非丢弃消息，保证消息不丢失的同时通过背压机制自然限速。

【效果】
小时抓取量从 2.5w 跃升至 96w，峰值 QPS 达到 400。日均新链发现量从 2–3 亿提升至 10–14 亿（最高产出达 75 亿）。集群 QPS 较原来提升 16 倍（原 QPS 6–25，优化后 400+）。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
三、动态自适应本地限流机制
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

【背景与问题】
初步建立三级限流后，前两层过滤仍是比例过滤，大站流量占比依然较高。固定阈值的限流无法感知下游处理能力（线程池负载）的实时变化，存在系统资源浪费或过载风险；同时线程池无法打满，无法充分发挥并发优势。

【实现方案】
  - 引入基于时间窗口（分钟级）的本地限流机制，作为第二层站点级流量打散。
  - 建立"线程池健康度–限流阈值"动态联动模型：系统每分钟采集线程池活跃线程数与核心线程数的比值（健康度），根据执行效率自动调整各站点的放行阈值。
  - 为什么调整限流阈值而非线程池大小：调整线程池大小是实时的、频繁的，代价高、抖动大、难以预测，且会失去线程重复利用的优势；而调整限流阈值是周期性的（每分钟一次），平缓、代价低、易于控制。

【效果】
线程池利用率显著提升，峰值集群 QPS 达 1417+，英文新链留存量从 2000w 提升至 1.2 亿。针对 1000w 站点的全量发现任务，处理时长缩短至 3–4 小时。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
四、压缩包处理能力拓展
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

【背景与问题】
原处理链路存在功能盲区，所有以 .gz 压缩格式存放的 Sitemap 信息被系统直接视为无效并丢弃，导致大量高质量新链资源流失。通过日志打点统计，发现压缩包类型占进入线程池流量的 4.08%，但其他压缩格式每小时不足 10 条，收益较低。

【实现方案】
  - 开发 .gz 压缩包解压解析逻辑：将抓取下来的压缩字节数组放入 ByteArrayInputStream，用 Java 自带 GZIPInputStream 包裹，自动识别 gzip 头部进行解压；创建输出流 + 1KB 缓冲区循环读取解压数据，最终按 UTF-8 编码转化为字符串。
  - 方案扩展性考量：考虑过使用策略模式+工厂方法支持多种压缩格式，但其他类型 case 过少（每小时低于 10 条），为避免过度设计仅实现 .gz 格式。

【效果】
日均处理压缩包流量达 400w+，压缩包资源贡献约 4.08%–16.23% 的新链。全面推全后，新链发现量从 3.79 亿激增至 52.6 亿，实现 14 倍产出增长。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
五、智能投递策略重构（频度调度）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

【背景与问题】
早期方案是每天调度所有 robots 链接去挖掘，随着 robots 数量增加，静态调度造成资源浪费：高频更新站点未及时挖掘，低频更新站点占用大量资源。

【实现方案】
  - 基于 sitemap 新链接产出效果对 sitemap 链接打分，构建三维评分体系：新链接产出量（新链接分）、模糊留存表中的留存量与抓取数计算的留存率（留存分）、规模分，三个分数加权合并为最终分数。
  - 根据最终分数动态调整调度频次：高频优质站点提高调度频度，低频低质站点降低调度频次。
  - 制定多个定时任务，支持一天多轮投递；抓取侧根据投递中的 grade 动态设置 Redis 去重过滤记录保存时间。
  - 上线后发现打分机制过于严苛，发送链接要求过严导致发送量骤降，经排查调整打分逻辑并扩充原始站点集合后恢复正常。

【效果】
高频站点加速抓取，低效站点降载，显著提升整体发现效率与资源利用率，robots 投递策略放宽频度调度间隔，节约资源。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
六、策略拦截打压（DSL 规则引擎建设）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

【背景与问题】
通过对抓取链接结果的人工评估，发现大量垃圾站点、作弊站点存在，严重影响新链发现质量，需要一套灵活可热更新的拦截机制。

【实现方案】
  - 搭建 DSL 规则引擎，支持通过配置正则表达式对 domain 站点进行匹配拦截，正则表达式预先编译缓存，支持热更新快速迭代。
  - 结合 URL 指纹切割技术，识别垃圾链接模式（如参数爆炸、路径随机等），在进入线程池前进行拦截。
  - 对无效站点设置一定的过期时间，不以一次失败或无效完全封禁站点，避免误杀。

【效果】
有效拦截 90% 垃圾站点，显著提升新链发现链接质量。

七、JS 抓取引擎升级（Selenium → Playwright）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

【背景与问题】
原有 Selenium 引擎架构下，需人工维护复杂的线程调度、心跳探活及异步轮询机制，维护成本极高且逻辑冗长。资源分配不均、缺乏高效并发管理，系统单机吞吐量存在明显瓶颈。经其他同学多进程抓取实测对比，Playwright 在稳定性上更优，可避免不稳定的等待。

【实现方案】
  - 成功集成 Playwright 引擎并重构底层并发模型，引入 Browser Context（浏览器上下文）技术实现轻量化多租户模拟，每个请求独占一个 Context，互相隔离。
  - 自定义线程池管理机制，实现任务有序调度，彻底去除繁琐的探活与轮询逻辑，抓取流程同步解耦。
  - 服务器基础设施治理：Playwright 生产部署时面临 glibc、gcc 版本过低的兼容性问题（本地成功线上无法运行）。完成 glibc 及 gcc 核心库深度升级，将升级流程沉淀为标准化自动化脚本，实现全量服务器批量化升级。

【效果】
大幅提升系统在高并发场景下的资源复用率与抓取效能，对最新版本 Chrome 完美兼容，显著提升动态页面抓取稳定性。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
八、网页截图抓取服务建设
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

【背景与问题】
多模态业务方需要对 CC 数据集筛选出的一批 URL 进行截图抓取，用于训练大模型"看图写代码"能力：根据抓取的网页截图，交给大模型训练，使其能参照截图编写前端代码。需要一套独立于现有抓取架构的截图专属服务。

【实现方案】
  - 消息消费层（ScreenshotRequestConsumer）：通过 Mafka 消费截图任务消息，反序列化后经多重过滤流程（URL 合法性校验、黑名单过滤），最终投入截图专属线程池。
  - 线程池设计：独立于 Sitemap 环路线程池，完全隔离，避免互相抢占资源。使用 SynchronousQueue（无缓冲队列）+ AbortPolicy，线程池满时主线程阻塞等待（synchronized 循环检测），不重投 MQ，防止消息积压。
  - 动态配置：线程池核心线程数通过 MdpConfig 配置中心热更新（screenshot_thread_num），支持运行时动态扩缩容，且正确处理 corePoolSize 与 maximumPoolSize 的调整顺序（扩容先调 max 再调 core，缩容先调 core 再调 max）。
  - 监控体系：独立守护线程每秒采集线程池 activeCount / coreCount，上报 CAT 监控平台，实现实时可观测。
  - 截图服务层（ScreenshotService）：基于 Playwright 引擎打开浏览器页面，渲染完成后截图，截图文件以 S3 文件夹名+时间戳命名，支持同一天同一条 URL 多次抓取不冲突，截图结果上传 S3 存储系统。
  - 质量保障：内置黑名单域名过滤（blackDomainSet）、URL 格式合法性校验，解决中文站点乱码问题（为服务器安装中文字体包）。

【关键技术细节】
  - SynchronousQueue 的选择：不需要任务缓冲队列，因为 JS 渲染是 CPU/内存密集型操作，积压太多任务会撑垮机器；无缓冲队列 + 主线程阻塞的方式实现天然背压。
  - 时间戳文件命名：S3 文件夹名+时间戳，支持同一天同一条 URL 抓取多次，避免文件名冲突覆盖历史数据。
  - 乱码问题排查：中文站点截图出现乱码，排查发现是服务器未安装中文字体包，导致浏览器渲染中文时显示乱码，通过安装字体包解决。

【效果】
集群 490 台机器整体吞吐约 1000 条/分钟（单机每分钟处理 1–2 条，受限于机器 JS 渲染性能），产出截图数据直接用于多模态大模型「看图写代码」能力训练。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
九、sitemap 环路监控体系建设
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

【背景与问题】
初期使用内部 Raptor 日志监控平台，但由于监控细节粒度过于详细，监控平台存在 type 上限要求，方案不可行。缺乏精细化监控导致堆积问题、失败率高、无效站点多等问题无法及时发现。

【实现方案】
  - 采用 Redis 统计方案，以小时为粒度进行数据统计，精确统计每个批次的抓取量、链接发现数量。
  - 监控指标包括：每批次入线程池量、压缩包处理量、链接发现量、失败率、无效站点占比等。

【效果】
及时发现 1500w 历史积压问题，并发现部分批次中大量无效站点（默认页面 27%–34%、抓取失败 11%–17%、无 sitemap 链接 25%–27%），推动后续无效站点治理落地。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
十、无效站点治理
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

【背景与问题】
监控体系完善后，发现每天有 1500w 历史积压，部分批次中存在大量无效站点，包括：抓取结果为默认界面（27%–34%）、抓取失败（11%–17%）、抓取到 robots 但无 sitemap 链接（25%–27%）。

【实现方案】
  - 对无效站点进行分类记录，在进入线程池前进行拦截，避免无效 URL 占用资源。
  - 设置一定的过期时间，不以一次失败或无效完全封禁站点，避免误杀正常站点（部分站点可能是临时不可用）。

【效果】
有效减少无效站点对系统资源的占用，改善线程池利用率与新链发现质量。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
附：核心技术栈与架构特点
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  - 消息队列：Mafka（内部 Kafka 封装），支持分区扩容、集群限流
  - 缓存/限流：Redis（集群精确限频、去重、监控统计），TTL 控制时效性
  - 浏览器自动化：Playwright（Browser Context 隔离、Chrome 兼容）
  - 监控：CAT 监控平台（事务、Metric 上报）
  - 配置中心：MdpConfig / Lion / Squirrel（热更新配置）
  - 存储：S3（截图文件存储）、Hive（链接数据落表）
  - 并发模型：ThreadPoolExecutor + SynchronousQueue + 自适应限流 + 主线程阻塞背压
