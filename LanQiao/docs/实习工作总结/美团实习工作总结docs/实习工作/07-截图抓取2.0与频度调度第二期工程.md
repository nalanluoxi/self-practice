> 本文档记录两个较晚期、工程量较大的迭代模块，是实习后期的核心交付物。

## 一、截图抓取 2.0 —— HTML 数据合成升级（dev/html-page-js-download）

### 1.1 背景与目标

截图抓取 v1 已完成核心链路搭建（Playwright 渲染 + S3 上传）。随着下游多模态大模型训练需求深化，对网页 **HTML 数据的完整性**（字体、图片、CSS、JS 全量收集）和**离线重现能力**提出更高要求。`dev/html-page-js-download` 分支是对整个截图链路的全面重构升级。

### 1.2 核心架构变化

| 维度 | v1 旧版 | v2 新版（dev/html-page-js-download） |
|:--|:--|:--|
| Phase 结构 | Phase1 + Phase2 各自独立 Context，**2 次 navigate** | 合并为 1 个 Context，**只 navigate 1 次**，网络请求减少 50% |
| S3 上传时机 | 抓取完毕后**统一批量上传** | **边抓边上传**：每个文件截完/抓完立即上传并置 null |
| 内存模型 | `ScreenshotCrawlResult` 持有 `assetBytes`（Map）+ 截图字节 | 移除所有字节缓存，只保留 `htmlBytes` + `viewportResults`（只含坐标/elements JSON） |
| 线程池 | 单层线程池（外层 EXECUTOR 同步执行 crawlScreenshot） | **两层隔离**：外层消费池 + 内层 `DOWNLOAD_TASK_POOL`（SynchronousQueue + AbortPolicy）|
| proxy null 处理 | 直接返回 FAIL | fallback 到默认代理 `10.217.129.223:9090`，继续执行 |
| 实例存活时间 | 5 分钟（300000ms） | **1 分钟（60000ms）**，减少实例老化导致的抓取失败 |
| MQ 消息 s3DirKey | 目录前缀字符串 | **JSON 数组字符串**（所有上传文件完整路径列表） |

### 1.3 资源完整性提升（6 项改造）

#### 改造 1：字体文件补充下载

**问题根因**：
- `onResponse` 过滤条件只有 javascript/css/image，font content-type（`font/woff2`、`application/x-font-ttf` 等）被跳过
- Chrome 字体懒加载机制：只有元素可见且实际使用该字体才触发网络请求

**解决方案**：
- `onResponse` 新增 font 类型收集（`contentType.contains("font")` 或 `resourceType().equals("font")`）
- CSS 后处理兜底：对已下载的 CSS 解析 `@font-face { url() }` 正则，主动 HTTP 下载缺失字体（`supplementFontsFromCss()`）

**效果**：字体缺失问题基本解决（2026.06 周报确认）。

---

#### 改造 2：图片懒加载触发（分步滚动 + LOAD 策略）

**问题根因**：
- navigate 后只等 3s 且不滚动，`IntersectionObserver` 判断视口外图片"不在视口内"，不发请求
- 等待策略为 `DOMCONTENTLOADED`（只代表 HTML 解析完），图片请求尚未发出

**解决方案**：
- 等待策略改为 `WaitUntilState.LOAD`（等待所有资源加载完成）
- Phase1 加分步滚动：每次滚动一个视口高度，等待 300ms，确保 `IntersectionObserver` 经过每个区域；滚动完成后回到顶部，与 Phase2 截图起点兼容
- 为何用分步滚动而非直接跳底部：一步跳底会跳过中间区域，懒加载图片不会触发；分步滚动连续经过每个区域，覆盖更完整

---

#### 改造 3：HTML 解析补充图片（srcset 变体兜底）

**问题根因**：浏览器在任何 viewport 下只请求**最匹配宽度的那一个 srcset 变体**，其余变体永远没有网络请求，`onResponse` 无法捕获。

```html
<!-- 例：viewport=1280px 只请求 img-p-1080，其余 3 个变体缺失 -->
<img srcset="img-p-500.avif 500w, img-p-800.avif 800w, img-p-1080.avif 1080w, img-p-1600.avif 1600w">
```

**解决方案**（`supplementImagesFromHtml()`）：
```
第一步：onResponse 捕获浏览器实际请求的图片（受 viewport 限制）
第二步：Jsoup 解析 HTML，收集所有图片 URL
        → img[src]、img[srcset]、img[data-src]、img[data-srcset]
        → picture source[srcset]
        → srcset 解析：按 "," 分割，取每项第一个空格前的 URL，解析相对路径
第三步：取差集 → HTML 里有但 onResponse 未捕获的
第四步：对缺失 URL 主动 HTTP 下载 → 上传 S3 → 追加 resources.tsv
```

改造 2（分步滚动）与改造 3（HTML 解析）互补：分步滚动触发 `onResponse`（性能最优），HTML 解析兜底补全遗漏（覆盖最全）。

---

#### 改造 4：JS/CSS 兜底补充（supplementScriptsAndStylesFromHtml）

**逻辑**：解析 HTML 中 `<link rel="stylesheet">` 和 `<script src>` 标签，取与 `onResponse` 已收集集合的差集，主动 HTTP 下载上传。

---

#### 改造 5：resources.tsv 全量记录（含失败资源）

**原逻辑**：只有 body 非空的资源才写入 TSV，失败（404/403/304）资源无记录，无法观测失败情况。

**新逻辑**：
```
body 非空 → 正常上传 S3，写入 TSV（localName=文件名, status=200）
body 为空 → 不上传，写入 TSV（localName=null, status=实际状态码）
```

TSV 格式不变：`url\tlocalName\ttype\tstatus`，失败行 localName 为字符串 `"null"`。

---

#### 改造 6：MQ 消息 s3DirKey 改为完整路径列表

**原问题**：`s3DirKey` 只存目录前缀（如 `screenshot/20260526/xxx/`），下游需调用 S3 `ListObjects` 扫描整个目录才能得知有哪些文件，`ListObjects` 是串行 IO，严重限制下游并发。

**解决方案**：不新增 MQ 字段，`s3DirKey` 改为所有上传文件完整路径的 **JSON 数组字符串**：
```json
["screenshot/20260526/xxx/index.html",
 "screenshot/20260526/xxx/resources.tsv",
 "screenshot/20260526/xxx/assets/font-awesome.woff2",
 "screenshot/20260526/xxx/viewport_0/screenshot.png"]
```
下游将 `s3DirKey` 反序列化为 `List<String>`，直接按路径 `GetObject`，无需 `ListObjects` 扫描目录。

## 二、频度调度第二期工程化落地

### 2.1 背景

`频度调度 v2`（`UpdateFrequencyTableJob` 三维打分模型）是**策略设计阶段**，在 2026.04 完成了核心评分逻辑的 Spark 开发。

**第二期工程化**是将该策略**完整落地到生产环境**的工程建设工作，包括：
- `UpdateFrequencyTableJob` v2 正式上线（替换 v1 打分逻辑）
- `FrequencyDeliverySitemapJob` 多轮定时任务配置（按 grade 分多批次投递）
- 评分阈值调优与扩充站点集合（修复 v1 因打分过严导致发送量少的问题）
- 收益数据观测与验证（6 天连续实测确认效果）

### 2.2 工程化核心工作

#### 2.2.1 UpdateFrequencyTableJob v2 上线

**打分逻辑**（相较 v1 关键变化）：
```
compositeScore = 0.5 × newUrlScore + 0.5 × fuzzyScore
fuzzyScore     = 0.5 × rateScore   + 0.5 × scaleScore
```

**数据来源扩展**：
- `newUrlScore`：来自 `sitemap_link_bloomfilter_daily_new_url`（Bloom 去重后的每日新链接表）
- `rateScore`：来自 `llm_crawler_domain_save_info`（域名留存统计表，T+1 更新）
- `scaleScore`：同上，留存数量经 log 压缩归一化

**EffectiveTldFinder 处理**：用 `crawlercommons.getAssignedDomain()` 提取真实域名 key。若 `real_domain` 与提取域名不一致，静默回退 `fuzzyScore = 0.35`（无数据默认值）。

**DI 表字段说明**：`rate_score` 字段存储的是已乘权重的值（`0.5 × rateScore`），而非原始档位值。

#### 2.2.2 多轮定时任务配置

`FrequencyDeliverySitemapJob` 通过传递不同 `grades` 参数实现一天多轮投递：

| grade | 投递次数/天 | 参考时间点 |
|:--:|:--:|:--|
| 1 (HIGH) | 6 次 | 00/04/08/12/16/20 |
| 2 (MIDDLE) | 4 次 | 00/06/12/18 |
| 3 (LOW) | 2 次 | 00/12 |
| 4 (DISUSE) | 1 次 | 00 |

每次任务执行：
```java
// FrequencyDeliverySitemapJob 核心逻辑
String sql = "SELECT ... FROM llm_data_df_sitemap_frequency_delivery WHERE dt = maxDt AND grade IN (gradesParam)";
// 消息格式
{
  "reqId": "dispatchTs_hostHash",
  "url": "sitemapUrl",
  "type": "sitemap",
  "ext": {"batchId": "batch-freq-list", "dispatchTs": "...", "grade": "1"}
}
producer.sendDelayMessage(msg, 6000); // 6s 延迟投递
```

#### 2.2.3 评分阈值调优

**v1 问题回顾**：上线后发现打分机制过于严苛，实际发送量远少于预期，新链产出量大幅下降。

**v2 工程化调整**：
1. 放宽评分阈值（compositeScore 分档边界微调，增加 grade 3/4 的站点覆盖）
2. 扩充原始站点集合（`llm_host_robots_url` 表扩量，纳入更多有历史数据的站点）
3. 无数据站点默认 `fuzzyScore = 0.35`（不再直接降为最低级）
4. 降级保护：每次最多降 1 级（防止单日数据波动导致等级快速跌落）

#### 2.2.4 SitemapService 抓取侧适配

`SitemapService.downLoadSitemap()` 中 `resolveExpireTimeByGrade()` 按 grade 设置 Redis 去重 TTL：
```java
grade=1 → TTL 3h   // 高频站点，3h 后可重新抓取
grade=2 → TTL 5h   // 中频站点，5h 后可重新抓取
grade=3/4 → 默认   // 低频站点，使用全局默认过期时间
```

ext 字段透传链路：
```
FrequencyDeliverySitemapJob 投递 → SitemapRequestConsumer 消费
  → ext.dispatchTs 时效性检测（超 48h 丢弃）
  → ext.grade 传入 SitemapService
  → resolveExpireTimeByGrade() 设置 Redis TTL
```

### 2.3 闭环反馈链路（完整）

```
① UpdateFrequencyTableJob（T+1 离线，每日）
   输入：search_api_result_dt（抓取结果）
         INNER JOIN sitemap_link_bloomfilter_daily_new_url（新链接）
         LEFT JOIN llm_crawler_domain_save_info（域名留存）
         broadcast join spider_site_info（黑名单）
   输出：
   ├─ DI 表（llm_data_di_sitemap_frequency_delivery，每日快照）
   └─ DF 表（llm_data_df_sitemap_frequency_delivery，T+1 累积）

② FrequencyDeliverySitemapJob（按 grade 多轮定时）
   读 DF 表 → 按 grade 过滤 → 发 MQ（llm_sitemap_url）

③ SitemapRequestConsumer → SitemapService.downLoadSitemap()
   读 ext.grade → resolveExpireTimeByGrade() → 设置 Redis TTL

④ 抓取结果流回 search_api_result_dt → 下一轮 UpdateFrequencyTableJob 评分
```

### 2.4 收益验证数据（2026-05-10 ~ 2026-05-15，连续 6 天）

| 指标 | 数据 |
|:--|:--:|
| 日均多批次命中 sitemap | **~413 万**（峰值 493 万） |
| 日均额外贡献 URL | **~908 万**（峰值 1,139 万） |
| 整体日抓取量提升 | 10~70 亿 → **100~200 亿（~10x）** |
| hit_batch_cnt=2 主力占比 | **~78%** |
| Redis 打点：频度调度 1~4 级 | 约 **400 亿/天** |
| Redis 打点：模糊去重 | 约 **600 亿/天** |

### 2.5 与频度调度 v1 的区别总结

| 维度 | v1（2026.02） | v2 第二期工程（2026.04~05） |
