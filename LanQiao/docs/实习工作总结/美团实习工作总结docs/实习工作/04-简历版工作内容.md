## 一、通用项目描述（推荐版）

### 项目一：多线程并发重构与消息队列扩容

**痛点**：原架构单线程同步消费 Mafka，受限于串行处理，消费速率仅 1.6~2.5 万条/小时，消息严重积压。

**方案**：
- 将消费架构从单线程同步模型重构为 **Mafka 回调线程 + 独立业务线程池**的异步并行模型：回调线程完成前置过滤后立即提交任务到 `ThreadPoolExecutor`，业务线程池并发执行 download 逻辑，彻底解耦消息拉取与业务处理
- 线程池使用 `SynchronousQueue`（零容量队列），线程池满时外层自旋等待而非无限堆积，避免队列膨胀引发 OOM
- 线程数通过 **MDP 配置中心**（`sitemap_thread_num`）动态下发，支持不停机热更新
- 协调业务侧将 Mafka **分区数从 200 扩容到 400**，消除分区粒度的消费瓶颈

**结果**：集群小时处理量从 2.5 万跃升至 **96 万**；日新链接产出量从 2~3 亿提升至 **10~14 亿（峰值 75 亿）**；集群 QPS 提升 **16 倍**。

---

### 项目二：Sitemap 发现环路三级精准限流体系

**痛点**：大站 URL 数量远超小站，无限流时大站挤兑小站导致饥饿问题；无效 URL（黑名单/去重）大量消耗有限限流配额，有效站点反而被饿死。

**方案**：
- 构建**三级纵深限流体系**，均基于 Rhino OneLimiter，粒度从粗到细：
  - **集群层**：接入 Rhino OneLimiter（`sitemap_cluster_qps_limit`），集群维度统一管控总 QPS 上限
  - **单机层**：Rhino OneLimiter（`sitemap_limit_single_node`），单机兜底防过载
  - **站点层**：Rhino OneLimiter（`sitemap_limit`），以 `EffectiveTldFinder.getAssignedDomain()` 提取顶级域作为 uuid 传入 Rhino，实现**站点级精确限频**，大站消耗配额后受限、小站始终有配额
- **前置拦截链**：黑名单域名过滤 → URL 后缀黑名单 → 正则规则集过滤（预编译 Pattern 缓存复用）→ Redis KV 去重；无效流量拦截前置于限流入口之前，确保有效配额不被黑名单/重复请求消耗

**结果**：调度分配从集中于凌晨 3 点和下午 3 点 → **全天均匀产出**；大站挤兑小站问题根治；**零 OOM**。

---

### 项目三：自定义本地自适应限流器（线程池健康度联动）

**痛点**：三级限流建立后，前两层（集群+单机）为比例过滤，大站流量占比依然较高；固定阈值无法感知线程池实时负载，线程池无法打满，并发能力大量浪费。

**方案**：
- 在 `LimiteUtils` 中实现基于**时间窗口滑动计数**的自定义本地限流器（`CounterRateLimiter`，`ConcurrentSkipListMap` 实现，每个站点独立计数桶）
- `setup()` 方法启动**后台守护线程**，每秒采样线程池 `activeCount / corePoolSize`，结果写入长度为 3 的历史队列
- **动态联动逻辑**（`LimiteUtils.updateAdaptiveLimitQuota()`）：
  - 连续 3 次 `activeCount < 80% corePoolSize` → `LIMITE_COUNT++`（放宽单站配额）
  - 连续 3 次 `activeCount > 80% corePoolSize` → `LIMITE_COUNT--`（收紧单站配额）
  - 上限由 `sitemap_limite_count_max` 约束，支持 MDP 热更新
- 为何调整限流阈值而非动态扩缩线程池：线程池大小调整实时频繁、代价高、抖动大；限流阈值调整周期性（每秒）、平缓，代价低，易于控制

**结果**：英文留存量 2000 万 → **1.2 亿**；1000 万站点发现任务处理时长缩短至 **3~4 小时**；峰值集群 QPS **1417+**。

### 项目五：GZIP 压缩 Sitemap 解析能力补齐

**痛点**：约 4% 的 Sitemap 流量（日均 400 万+）为 `.gz` 格式，原链路对压缩格式无感知，直接丢弃。

**方案**：
- 用 `GZIPInputStream` 包装原始字节流进行**流式解压**，分块读取（1024 byte buffer）后写入 `ByteArrayOutputStream`，解压后直接对接原有 XML 解析器，最小化改动面
- 通过 **URL 路径扩展名嗅探**（`url.getPath().endsWith(".gz")`，排除 `tar.gz`）自动路由到对应解压解析器

**结果**：日新链发现量峰值从 1000w~3000w 上升至 **3.79 亿 → 52.6 亿（提升 14 倍）**。

---

### 项目六：站点频度调度策略建设（三维打分模型）

**痛点**：全量站点固定周期调度，高更新频率站点抓取不及时，低频站点被反复无效抓取，资源分配粗放。

**方案**：
- 设计**三维打分模型**：`compositeScore = 0.5×newUrlScore + 0.5×(0.5×rateScore + 0.5×scaleScore)`
  - `newUrlScore`：昨日新链接产出（Bloom 去重表）
  - `rateScore`：域名留存率（留存量/抓取数）
  - `scaleScore`：站点规模（log 压缩）
- **Hive + Spark** 离线批量计算打分，写回 DF/DI 表；调度结果实时回写打分系统，形成**闭环反馈**
- 高分站点缩短调度间隔（grade=1：每天 6 次），低分站点延长间隔（grade=4：每天 1 次）
- 降级保护：每次最多降 1 级，防止数据波动导致等级快速跌落

**结果**：日抓取量从 10~70 亿 → **100~200 亿**（约 **10x**）；频度调度日均额外贡献 URL **约 908 万**，峰值 **1,139 万**。

---

### 项目七：DSL 规则引擎治理垃圾/作弊站点

**痛点**：垃圾站点 URL 持续混入处理管道，规则更新依赖代码发布，周期长、成本高。

**方案**：
- 接入 MDP 配置中心，规则配置动态下发；`@PostConstruct` 预编译正则 Pattern 对象缓存至 `HashSet<Pattern>`
- `@MdpConfigListener` 监听配置变更，实现正则缓存**热更新，秒级生效**，无需重启
- 拦截逻辑前置于 Redis 去重和限流之前，最低成本步骤最先执行

**结果**：日均拦截 **4~5 亿**；规则生效延时从分钟级压缩至**秒级**；有效拦截 **90%** 垃圾站点；抽样高质量站点率 4.1% → **11.9%**。

---

### 项目八：网页截图抓取全链路服务建设（多模态）

**痛点**：多模态大模型训练需要大规模高质量网页截图，截图任务 CPU/内存开销大。

**方案**：
- 引入 **Playwright** 引擎实现全页面 JS 动态渲染截图，覆盖 SPA/动态页面
- 截图任务使用**独立线程池**（两层隔离），与主链路彻底隔离
- `onResponse` 全量收集 JS/CSS/图片/字体资源；补充 `supplementFontsFromCss()` / `supplementImagesFromHtml()` / `supplementScriptsAndStylesFromHtml()` 三路兜底
- 截图结果**流式上传 S3**，边生成边上传，规避大体积图片 OOM 风险
- 解决中文站点乱码问题（安装 noto-cjk 等中文字体包）

**结果**：已完成核心链路搭建；集群 490 台机器，每分钟处理约 1000 条 URL。

---

### 项目九：频度调度第二期工程化落地

**痛点**：三维打分模型策略已设计完成，但 v1 因打分过严发送量极少，需完整工程化落地并调优。

**方案**：
- `UpdateFrequencyTableJob` v2 正式上线，三维打分（newUrlScore + rateScore + scaleScore）替换 v1 单维打分
- 配置 `FrequencyDeliverySitemapJob` **多轮定时任务**：grade1 每天 6 次，grade2 4 次，grade3 2 次，grade4 1 次，形成差异化多轮投递
- 放宽评分阈值 + 扩充原始站点集合；无数据站点默认 `fuzzyScore=0.35`（避免直接降级）；降级保护：每次最多降 1 级
- 连续 6 天实测验证收益，确认闭环反馈链路（抓取结果 → T+1 评分 → 投递 → 抓取）稳定运行

**结果**：日抓取量从 10~70 亿提升至 **100~200 亿（~10x）**；日均多批次命中 **~413 万**；日均额外贡献 URL **~908 万**；有效链接占比 9.4% → **11.9%**。

---

### 项目十：截图抓取 2.0 —— HTML 数据合成升级（dev/html-page-js-download）

**痛点**：v1 内存峰值高（资产字节全量持内存）、Phase1+2 两次 navigate 浪费网络；下游多模态训练对字体/图片/CSS 完整性要求更高。

**方案**：
- **架构重构**：Phase1+Phase2 合并为 1 次 navigate（减少 50% 网络请求）；**边抓边上传 S3 并置 null**，移除内存字节缓存，内存峰值大幅降低；新增内层 `DOWNLOAD_TASK_POOL`（两层线程池隔离）
- **字体完整性**：`onResponse` 新增 font 类型收集 + `supplementFontsFromCss()` 解析 `@font-face` 主动下载 Chrome 懒加载不触发的字体
- **图片完整性**：等待策略改为 `LOAD` + Phase1 分步滚动触发 `IntersectionObserver`；`supplementImagesFromHtml()` 用 Jsoup 解析 HTML 补充 srcset 所有尺寸变体 + data-src 懒加载兜底
- **MQ 消息升级**：`s3DirKey` 从目录前缀改为所有上传文件的 **JSON 路径数组**，下游直接 `GetObject` 而无需 `ListObjects` 扫描，解除下游并发瓶颈
- **可观测性**：resources.tsv 全量记录（含失败资源，localName=null）；新增 CAT 资源粒度打点（`screenshot.resource.download.*`）

**结果**：字体缺失基本解决；CSS 缺失基本解决；图片可用率约 70%；下游 S3 扫描瓶颈消除。

## 二、一句话精简版（适合简历条目）

1. **Sitemap 并发重构**：将单线程同步消费重构为异步线程池模型，Mafka 扩容 200→400 分区，集群 QPS 提升 16 倍，日新链发现量从 2~3 亿 → 峰值 75 亿。

2. **三级精准限流**：从 0 构建集群层（Rhino）+单机层（Rhino）+站点层（ConcurrentSkipListMap 滑动窗口）三级防护，无效流量前置拦截，大站挤兑问题根治，全天流量均匀产出。

3. **自定义自适应限流器**：基于 ConcurrentSkipListMap 实现站点级滑动窗口计数器，守护线程每秒采样线程池 activeCount，连续 3 次低于 80% 水位自动放宽配额，连续 3 次高于自动收紧，英文留存 2000w → 1.2 亿，峰值 QPS 1417。

4. **GZIP 解析补齐**：流式解压 .gz 格式 Sitemap，日均处理 400w+，推动日产出 3.79 亿 → 52.6 亿（14x）。

5. **频度调度三维打分**：基于新链率/留存率/站点规模构建 compositeScore 评分体系，5 级差异化调度，闭环反馈，日抓取量提升 ~10x（10~70 亿 → 100~200 亿）。

6. **规则引擎拦截**：正则预编译+热更新机制，有效拦截 90% 垃圾站点，日拦截 4~5 亿，质量提升（1+2 率 4.1% → 11.9%）。

7. **截图抓取 v1**：Playwright 多视口截图 + S3 流式上传，三路资源兜底补全，服务器 glibc/gcc 升级，支撑多模态大模型训练数据生产。

8. **频度调度第二期**：UpdateFrequencyTableJob v2 工程上线，多轮定时投递（grade1 每天 6 次），放宽阈值扩充集合，日抓取量 ~10x（100~200 亿），日均命中 ~413 万，额外贡献 URL ~908 万。

9. **截图抓取 2.0**：Phase1+2 合并（减少 50% 网络请求），边抓边上传（内存峰值大幅降低），6 项资源完整性改造（字体/srcset 图片/懒加载/JS+CSS 兜底），MQ s3DirKey 改 JSON 路径数组解除下游 ListObjects 瓶颈。
