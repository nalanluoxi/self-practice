一、团队与业务背景
================================================================================

【团队定位】
LongCat大模型数据团队，核心目标是为大模型训练构建高质量预训练语料库。
通过抓取互联网网页中的优质文本内容，经过解析、清洗、筛选后用于模型预训练。
后续扩展至多模态方向，为"看图写代码"等能力提供网页截图训练数据。

【主要链路模块】
整个数据流水线包含以下核心模块：

  1. 抓取模块（Crawl）
     - 概要：抓取服务项目部署的核心内容，主题流程是抓取。接受URL，
       发送HTTP请求，结果处理后落表。同时包含sitemap管理、站点管理、
       信息更新等功能。
     - 输入输出：均通过Mafka接受和发送消息，经历过15亿+量级的验证，
       20亿量级出现堆积时可通过扩分区解决，风险低。
     - 逻辑：无状态服务。接受URL后发起HTTP请求，过程中访问MySQL、Lion、
       Squirrel等组件获取配置。MySQL数据预先加载到内存缓存，支持十万级别QPS。

  2. 链接发现（Link Discovery）
     - 概要：对抓取结果（where content is not null）进行链接发现，
       发现的所有链接落到Hive表（包括不同域名的后链）。
     - 风险：当前8-10亿抓取量，近7天产出时间约3小时，22号发生过OOM。

  3. 链接筛选 + 归一化 + 链接入库
     - 根据链接发现内容进行筛选（同域名、白名单次级域名扩散等），
       归一化处理后写入HBase链接库。

  4. Cache调度
     - 从HBase链接库提取链接，按quota*10进行limit限制写入cache表作为缓存。
     - 风险：依赖URL状态码回填任务，启动较慢；产出不稳定，需二级cache兜底。

  5. 调度（Schedule）
     - 从归一化结果表按quota表进行调度站点，按优先级和数量排序后limit筛选，
       写入明日待抓取Hive表。
     - 风险：强依赖归一化结果表，该表某天不产出则第二天无数据可抓。

  6. Sitemap站点新链发现（独立闭环）
     - 起点：消息队列（可人为以特定JSON格式发送到topic，普遍是Spark任务定期发送）
     - 独立于主链路的链接发现环路，为主要抓取链路补充更多URL资源。

  7. 网页截图抓取（多模态）
     - 面向多模态大模型训练的截图服务，基于Playwright渲染截图后存S3。

【带宽评估】
  - 内网带宽：评估过且经历过15亿洗礼，风险暂无
  - 公网出口带宽：国内专线已评估，风险暂无
  - 海外网络：可能有风险，逐步扩量观察；代理商承诺能抗10GB带宽

二、Sitemap站点新链发现环路 — 全链路详解
================================================================================

【环路概要】
Sitemap环路是一条独立于主抓取链路的闭环链接发现系统：
  Pipeline方提供高质量站点domain → 投递robots.txt链接到Mafka →
  Sitemap集群消费并抓取robots页面 → 解析提取sitemap链接 → 再次投递Mafka →
  抓取sitemap页面 → 解析提取其中URL链接 → 链接入库 + sitemap链接回投起点Mafka形成闭环

【抓取服务消费逻辑（完整处理链路）】

  Step 1 - 重复链接丢弃前置：
    先判断URL是否已经抓取过，有效期12小时（时效性配置15分钟）
    使用Redis String类型存储，设置过期时间

  Step 2 - 自适应流量打散：
    根据站点进行站点限频，同时根据下游线程池状态动态调整放行阈值

  Step 3 - 集群限频：
    控制每个站点每秒最多可以抓取的数量
    由于其依赖Redis，流量轮转过大时QPS过大会导致Redis崩溃
    因此需要在Redis精确限流前加一层集群限流保护

  Step 4 - 投递线程池进行HTTP抓取：
    与上游自适应流量打散动态联动，线程池阻塞则缩小放行阈值

  Step 5 - 压缩包匹配：
    发现是压缩包类型数据（.gz）后，对原始数据进行GZIP解压处理

  Step 6 - 内容解析：
    URL链接发送到Hive表，后续跟每日链接发现链接一同进入linkbase（linkcache）
    Sitemap链接发送到起点Mafka形成闭环

【Robots协议说明】
robots协议也称爬虫协议/爬虫规则，指网站可建立一个robots.txt文件来告诉
搜索引擎哪些页面可以抓取、哪些不能抓取。搜索引擎通过读取robots.txt来识别
页面是否允许被抓取。但robots协议不是防火墙，没有强制执行力，搜索引擎完全可以
忽视它去抓取网页快照。如果想单独定义搜索引擎的漫游器访问子目录时的行为，
可以将自定义设置合并到根目录下的robots.txt，或者使用robots元数据（Metadata）。

【第1项】流量打散逻辑与精准限流体系建设
时间：2025.11.10
类别：Sitemap环路 / 限流策略 / 架构设计
----------------------------------------------------------------------------------

【问题场景】
原系统缺乏有效的流量控制与打散机制，导致Sitemap发现环路处于"无序竞争"状态。
大站点利用其海量的sitemap链接占据了Mafka消息队列的绝大部分带宽，产生严重的
数据倾斜，直接挤兑了小站点的挖掘资源，造成小站任务长时间积压、挖掘时效性极差。
调度分配原先集中于凌晨3点与下午3点两个峰值时段，其他时段产出极低。

【解决方案 - 三级限流防护网】

  ★ 第一层：集群层限流（Cluster-level QPS Limit）
    实现方式：sitemapService.isClusterQpsLimited()
    配置入口：sitemap_cluster_qps_limit
    技术实现：接入内部Rhino OneLimiter组件
    作用：在集群维度统一管控总请求速率，保护下游Redis等共享基础设施不被冲垮

  ★ 第二层：单机层限流（Single-node QPS Limit）
    实现方式：sitemapService.isSingleNodeQpsLimited()
    配置入口：sitemap_limit_single_node
    技术实现：单机均摊策略（集群阈值/机器数=每台机器限额）
    作用：防止单节点过载，随服务扩缩容自动调整

  ★ 第三层：Redis精确层限流（Site-level Rate Limit）
    实现方式：sitemapService.isSiteQpsLimited(request)
    配置入口：sitemap_limit
    技术实现：EffectiveTldFinder.getAssignedDomain()提取顶级域作为uuid，
              通过Redis+Lua脚本实现令牌桶算法
    作用：控制每个站点每秒最多可抓取的数量，精确到站点维度

【关键优化 - 拦截前置】
在限流判断之前依次执行以下拦截逻辑：
  ① 黑名单过滤（blackDomainSet）：直接丢弃已知垃圾域名
  ② URL格式校验（isValidUrl）：MalformedURLException检查
  ③ URL后缀黑名单过滤（urlBlackListSuffixes）
  ④ Redis去重检查：12小时时效性去重
目的：确保有限限流配额不被黑名单/重复请求消耗

【技术知识点 - 限流vs限频的区别】
  ┌──────────┬──────────────────────────┬──────────────────────────┐
  │          │ 限流（Rate Limiting）      │ 限频（Rate Frequency）    │
  ├──────────┼──────────────────────────┼──────────────────────────┤
  │ 目的      │ 保护服务稳定性             │ 执行业务策略              │
  │ 场景      │ 防止流量激增导致崩溃        │ 防滥用/防爬/商业策略限制   │
  │ 维度      │ 全局接口/服务节点/DB连接   │ 用户ID/IP/手机号/站点     │
  │ 触发动作   │ 直接丢弃请求               │ 拦截返回提示信息           │
  │ 算法      │ 令牌桶/漏桶/滑动窗口       │ 令牌桶/漏桶/滑动窗口       │
  └──────────┴──────────────────────────┴──────────────────────────┘

  本场景使用的是"集群限频"，限制每个站点的请求频率。

【技术知识点 - 集群限流的三种模式】
  (1) 单机限流：每台机器独立计数，适用于大部分场景，性能好无外部依赖
  (2) 集群限流-单机均摊：集群配置阈值动态均摊到每台机器，防止扩容导致下游被压垮
  (3) 集群限流-统一计数：通过Netty或Redis集群统一计数，解决流量不均衡问题

【成果】
  ✅ 解决了大站挤兑小站的顽疾，实现流量公平调度
  ✅ 调度分配从集中峰值优化为全天均匀产出
  ✅ 集群QPS稳定在6-8左右（此时尚未引入线程池优化）

【第2项】系统并发性能优化 - 多线程重构与集群扩容
时间：2025.11.17
类别：Sitemap环路 / 并发编程 / 性能优化
----------------------------------------------------------------------------------

【问题场景】
初始系统采用单线程消费模式（Mafka receive()方法同步处理全部逻辑），单次任务
同步处理耗时约15s，导致集群QPS低于10。面对百万级站点发送量时，系统吞吐量严重触顶。
每分钟集群仅能抓取400-1500条消息。

【解决方案 - 并发架构重写】

  ★ 线程池核心设计：
    队列类型：SynchronousQueue<>（同步队列，无容量缓冲，直接传递给空闲线程）
    线程池类型：ThreadPoolExecutor（固定大小：corePoolSize = maxPoolSize）
    配置来源：Lion MDP配置 sitemap_thread_num 动态注入
    拒绝策略：AbortPolicy
    线程工厂：自定义ThreadFactory，线程命名 "sitemap-crawler-pool-{n}-thread"

  ★ 架构解耦设计：
    receive() 方法仅负责：
      - Mafka消息的反序列化（轻量操作）
      - 前置过滤（黑名单/校验/去重/限流）
    addRequestToThreadPool() 负责：
      - 将实际的sitemap下载耗时操作异步提交给线程池执行
    效果：消息拉取与业务处理的完全解耦

  ★ 背压机制（线程池满时处理）：
    当 activeCount >= corePoolSize 时：
      synchronized(EXECUTOR) {
        while (活跃线程 >= 核心线程数) {
          Thread.sleep(1000ms);  // 自旋等待
        }
        EXECUTOR.execute(task);   // 提交任务
      }
    最长等待36秒，超时后重新投递MQ保证消息不丢失

  ★ 线程池热更新机制：
    @MdpConfigListener("sitemap_thread_num")
    public void updateThreadNum(ConfigEvent event) {
      // 动态调整corePoolSize和maximumPoolSize
      // 先改大的值再改小的值，避免中间状态异常
    }

  ★ 资源弹性扩展：
    Mafka集群从200分区扩容至400分区（翻倍），消除传输链路物理瓶颈

【为什么选择调整限流阈值而不是动态调整线程池大小？】
  调整线程池大小的弊端：
    - 实时的、频繁的操作，代价高、抖动大、难以预测
    - 相当于每来一个任务就创建一个线程，用完就丢弃
    - 失去了线程池重复利用线程的优势
  调整限流阈值的优势：
    - 周期性操作（每分钟检查一次），平缓、代价低、抖动小、易于控制

【Java线程能否设置每个线程的内存阈值？】
  不能。Java不支持设置单线程内存阈值控制。
  线程内存是系统级别的资源，不在JVM管理范围内。
  替代方案：
    - 设置JVM堆内存限制控制总内存
    - 使用ThreadLocalMemory设置本地存储
    - 自定义ThreadFactory或拦截器监控内存

【成果】
  ✅ 小时抓取量从 2.5w 跃升至 96w+
  ✅ 峰值 QPS 达到 400（提升16倍）
  ✅ 日均新链发现量从 2-3 亿提升至 10-14 亿（最高产出达 75 亿）
  ✅ 集群每分钟抓取量从 400-1500 提升至 2.4w

【第3项】动态自适应本地限流优化
时间：2025.11.27
类别：Sitemap环路 / 自适应算法 / 性能调优
----------------------------------------------------------------------------------

【问题场景】
初步建立三级限流后仍存在以下问题：
  ① 前两层（集群+单机）仍是比例过滤，大站流量占比依然较高
  ② 固定阈值无法感知下游线程池负载的实时变化 → 资源浪费或过载风险
  ③ 线程池无法打满 → 并发能力未充分发挥

【解决方案 - "线程池健康度-限流阈值"动态联动模型】

  ★ 核心组件：CounterRateLimiter
    基于时间窗口的本地限流器
    数据结构：ConcurrentSkipListMap<Long, AtomicInteger>
    以毫秒精度记录每个时间片的请求数量
    支持精确的速率控制（滑动窗口算法）

  ★ 自适应反馈机制实现：
    后台Daemon线程（setup()中启动），每秒执行：
      1. 采样线程池状态：
         - activeCount（当前活跃线程数）
         - corePoolSize（核心线程数上限）
      2. 计算健康度：activeCount / corePoolSize 是否超过80%水位
      3. 写入历史队列（长度为3的环形缓冲区）
      4. 调用 LimiteUtils.updateAdaptiveLimitQuota()

  ★ 联动决策逻辑：
    if 连续3次采样 < 80%水位 → LIMITE_COUNT++（扩大配额，放行更多请求）
    if 连续3次采样 > 80%水位 → LIMITE_COUNT--（收缩配额，减少放行）
    配额边界由 sitemap_limite_count_max 约束

  ★ 设计优势：
    - 分钟级自适应调频，响应及时但不过于敏感
    - 与线程池负载真实联动，避免人工调参滞后性
    - 平滑过渡，不会出现断崖式流量变化
    - 周期性调整（每分钟），代价低且易于控制

【成果】
  ✅ 线程池并发效率显著提升
  ✅ 峰值集群 QPS 达到 1417+
  ✅ 英文新链留存量从 2000w 提升至 1.2 亿
  ✅ 1000w站点的全量发现任务处理时长缩短至 3-4 小时

【第4项】压缩包资源解析能力补齐
时间：2025.12.17
类别：Sitemap环路 / 数据处理 / 功能拓展
----------------------------------------------------------------------------------

【问题场景】
原处理链路中存在功能盲区：所有.gz格式的Sitemap被直接视为无效并丢弃。
通过日志统计发现压缩包流量占比约4%（日流量10000w中压缩包占400w），
大量高质量新链资源因此流失。

【解决方案】

  ★ 识别逻辑：
    CompressedUtil.isValid(request)
    - 识别 .gz 结尾的URL
    - 排除 .tar.gz 等复合格式（case极少）

  ★ 解压实现（CompressedUtil.getCompressedData）：
    具体流程：
    ① 抓取到的压缩字节数组 → ByteArrayInputStream（输入流）
    ② GZIPInputStream 包裹输入流（自动识别GZIP头部并解压）
    ③ 创建 ByteArrayOutputStream + 1KB 缓冲区
    ④ 循环从 GZIPInputStream 读取 → 写入 ByteArrayOutputStream
    ⑤ ByteArrayOutputStream → UTF-8字符串（完成解压）

  ★ 解压后处理：
    解压后的XML文本交由 SiteMapParser 正常解析
    完整保留 Redis 去重、限流、CAT 监控等原有处理链路

【为什么不支持更多压缩格式？】
  日志统计显示环路中压缩包主要是 .gz 格式
  其他格式每小时仅 1-2 条（<10条），单独添加收益不明显
  曾考虑使用策略模式+工厂方法提高扩展性，但因测试样例过少暂未添加

【成果】
  ✅ 日均处理压缩包流量达 400w+
  ✅ 压缩包贡献约 4.08% ~ 16.23% 的新链
  ✅ 新链发现量从 3.79 亿激增至 52.6 亿（14倍增长）

【第5项】智能投递策略重构 - 频度调度（第一期 + 第二期优化）
时间：2026.02.04起
类别：Sitemap环路 / 策略算法 / 调度优化
----------------------------------------------------------------------------------

【问题场景 - 第一期】
早期方案每天固定调度全量robots.txt（每日一轮）。随着robots数量增加：
  - 高频更新站点（新闻类等）→ 调度不足 → 新链遗漏
  - 低频更新站点 → 浪费抓取资源
需要根据各站点sitemap的更新频率进行差异化调度。

【解决方案 - 第一期】

  ★ 打分分级体系：
    根据sitemap新链接产出效果打分，分为三个等级：
    - grade=1（高频优质站点）：Redis去重TTL = 3小时
    - grade=2（中频站点）：Redis去重TTL = 5小时
    - 无等级/低频：使用默认较长TTL

  ★ 实现方式：
    SitemapService.downLoadSitemap() 中 resolveExpireTimeByGrade()
    从请求ext字段解析grade值 → 关联Redis过期时间
    SitemapPublishService投递时透传ext（含batchId、dispatchTs、grade）

  ★ 多轮投递：
    多个定时任务通过不同grade参数实现一天多轮差异化投递

  ⚠️ 遇到的坑：
    上线数日后投递效果不佳，排查发现：
    - 打分机制过于严苛
    - 发送链接要求过严 → 发送量大减 → 新链产出骤降
    解决：放宽评分阈值 + 扩充原始站点集合

【第二期优化 - 多维度评分体系】

  问题：早期仅依赖新链接产出分，未考量站点规模与留存质量

  ★ 三维打分模型：
    ① 新链接分：新链接产出量
    ② 规模分：模糊留存表中获取留存量和抓取数 → 计算留存率
    ③ 最终分 = 三个维度加权综合

  ★ 闭环反馈：
    下游调度结果反馈至打分系统 → 持续优化
    抓取侧根据grade动态设Redis TTL：
    - 高频站点短TTL（更快允许重复抓取）

五、网页截图抓取服务建设（多模态方向）

----------------------------------------------------------------------------------
【第11项】截图抓取全链路服务
时间：2026.03.24起
类别：多模态 / 服务建设 / Playwright / 全链路设计
----------------------------------------------------------------------------------

【业务背景】
面向多模态大模型训练需求：
  - 业务方（CC团队）筛选一批高质量URL
  - 需要进行网页截图抓取
  - 截图用于训练"看图写代码"能力
  - 大模型参照截图生成前端代码

【架构决策 - 完全独立于Sitemap环路】
  为什么独立？
    - 截图任务耗时长（JS渲染+截图）
    - 资源需求不同（CPU/内存密集型）
    - 混用会互相影响
  独立的内容：
    - 独立Consumer：ScreenshotRequestConsumer
    - 独立线程池：ScreenshotRequestConsumer.EXECUTOR
    - 独立监控指标：screenshot.* 前缀
    - 独立Mafka Topic

【消息消费完整链路（preFilterProcess）】

  ① 反序列化：
     JackSonUtils.fromJson(msg, ScreenshotRequest.class)

  ② 空值校验：
     request/url/domain/host 为空 → 直接丢弃 + CAT打点

  ③ Domain/Host 补全：
     从URL中提取：new URL(url).getHost()

  ④ URL合法性校验：
     isValidUrl（MalformedURLException检查）

  ⑤ 黑名单过滤：
     FilterUtils.isInBlacklist(blackDomainSet, domain, host)
     blackDomainSet 通过 @MdpConfig("screenshot_black_domain_list") 注入

  ⑥ Redis去重：（当前已注释，按需开启，12h TTL）
     redisService.isScreenshotCrawled(url)

  ⑦ 投入独立线程池：
     addRequestToThreadPool(request) → screenshotService.submit(request, true)

【线程池设计（参照SitemapRequestConsumer结构）】

  核心参数：
    - workQueue: SynchronousQueue<>（同步队列，无缓冲）
    - corePoolSize = maxPoolSize = threadNum（固定大小）
    - threadNum 来源：@MdpConfig("screenshot_thread_num")
    - handler: AbortPolicy
    - 线程命名："screenshot-crawler-pool-{n}-thread"

  热更新：
    @MdpConfigListener("screenshot_thread_num")
    public void updateThreadNum(ConfigEvent event) {
      // 动态调整corePoolSize和maximumPoolSize
    }

  满载背压：
    synchronized(EXECUTOR) {
      while (activeCount >= corePoolSize) { Thread.sleep(1000ms); }
      EXECUTOR.execute(task);
    }

  优雅关闭：
    Runtime.getRuntime().addShutdownHook(new Thread(() -> EXECUTOR.shutdown()));

【CAT监控上报】

  Daemon监控线程（screenshot-pool-monitor）：
  - 每秒采集一次
  - 上报指标：
    * screenshot.threadpool.activeCount：活跃线程数
    * screenshot.threadpool.coreCount：核心线程数
  - 上报至CAT监控平台，实时可视化

【截图执行流程（ScreenshotService.submit）】
  1. Playwright打开浏览器访问URL
  2. 等待页面完全加载（JS渲染完成）
  3. 执行全页面截图
  4. 上传截图至S3存储系统
  5. 记录截图结果与元数据

【遇到的问题与解决】

  ⚠️ 中文站点乱码：
    现象：中文网页截图中文字显示为方块/乱码
    原因：服务器缺少中文字体文件
    解决：安装中文字体包
      - wqy-zenhei（文泉驿正黑）
      - noto-cjk（Noto CJK字体）
    结果：彻底解决中文页面截图异常

  ⚠️ 单机性能限制：
    JS渲染消耗大量CPU/内存
    单机每分钟仅处理1-2条URL
    超过此阈值会导致机器负载过高甚至OOM
    解决：横向扩容至490台机器

【成果】
  ✅ 集群490台机器整体吞吐约1000条/分钟
  ✅ 产出数据用于训练「看图写代码」多模态能力
  ✅ 线程池支持Lion MDP配置热更新
  ✅ CAT监控全覆盖，线程池状态实时可见
  ✅ 内置黑名单过滤、URL合法性校验等多重质量保障

六、技术知识点汇总
================================================================================

【1. 分布式场景下线程池可能存在的问题】
  (1) 资源竞争与死锁：多节点线程池竞争共享资源
  (2) 负载不均衡：Hash到某线程的任务卡住会阻塞该线程所有后续任务（木桶效应）
  (3) 通信开销：跨节点线程通信带来网络延迟
  (4) 故障处理与容错：节点故障可能导致任务丢失
  (5) 数据一致性问题：分布式事务处理复杂
  (6) 监控与管理复杂：分布式线程池状态监控困难

【2. Thread-per-Key 分区线程池设计】
  开N个只有1个线程的线程池，通过Hash分发任务到对应线程池执行
  优点：绝对保序 + 天然反压
  风险：木桶效应阻塞扩散 + CPU利用率不均匀（数据倾斜）+ 线程上下文切换开销

【3. Kafka有序消费保证方案】
  生产端：相同Routing Key → 同一Partition + 幂等性 + acks=all
  消费端方案A：单线程消费（绝对有序但吞吐低）
  消费端方案B：内存队列(BlockingQueue) + 线程池（二次Hash分发到同一线程）
  异常处理：死信队列(DLQ)，不能跳过否则业务逻辑出错

【4. 系统性能瓶颈排查方法论】
  第一阶段-全貌观察：top/htop → 确认受限资源（CPU/内存/磁盘/网络）
  第二阶段-深度剖析：火焰图(Flame Graph) + Arthas(trace/thread/watch)
  第三阶段-链路与资源：慢查询日志 + iostat + jstack(BLOCKED/WAITING)
  第四阶段-全链路压测：JMeter/Locust寻找性能拐点

【5. 内存泄漏排查路径】
  确认泄漏(jstat -gcutil阶梯式上升) → 导出Heap Dump(jmap/MemoryError自动导出)
  → MAT分析(Leak Suspects/Dominator Tree/GC Roots)
  → 常见场景：静态集合/ThreadLocal未remove/未关闭资源/内部类引用
  → 动态追踪：Arthas dashboard/profiler

【6. 提高系统吞吐量的方法】
  ① 提高线程池线程数（有上限，超限后CPU忙于切换）
  ② 排查内部瓶颈（成功率/单消息处理耗时/带宽影响）
  ③ 检查下游依赖能力（Redis/MySQL/Kafka的QPS上限）
  ④ 无状态服务横向扩容
  ⑤ 有状态服务保证状态机流转正常
  ⑥ 读写分离集群横向扩容读机器

【7. AI幻觉处理方案】
  架构层：引入RAG（检索增强生成）
  提示词层：设定"不知道"出口 + 思维链(CoT) + 少样本提示(Few-shot)
  数据层：RLHF对齐 + SFT指令微调
  验证层：Self-Correction + N-Shot投票 + 引用来源检查
  业务层：Human-in-the-loop + 置信度评分拦截

【8. 高并发日志系统设计要点】
  冷热数据分离 + 数据多重备份 + 写入缓冲批处理 + 分片分区策略
