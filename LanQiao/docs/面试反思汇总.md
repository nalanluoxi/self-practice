## 二、各场面试回顾

### 1. 抖音 推荐架构 一面（2026-02-27）

**主要考点：**
- 美团实习项目深挖：Kafka消费模型、线程池架构、并发设计
- JVM：堆/栈区别、对象创建的硬件存储位置、逃逸分析
- 操作系统：CPU缓存（L1/L2/L3）、虚拟内存与物理内存、页表
- Kafka幂等性实现
- 算法题：两个线程并发操作同一个List（生产者写1-9，消费者加1）

**答得好的地方：**
- JVM分区（堆、栈、方法区、程序计数器）描述基本清晰
- CPU三级缓存独享/共享关系答对（L1/L2独享，L3共享）
- 虚拟内存→页表→物理地址映射答出来了
- 限流改造架构（Kafka单线程→线程池）逻辑描述清晰

**答得不好的地方：**
- ❌ Kafka消费模型没讲清楚：面试官追问"拉取线程和消费线程如何交互"，一直绕圈未能精准回答
- ❌ 算法题：代码出现死循环，主线程未等子线程完成就打印；Condition信号量用了但没正确配套 await，面试官指出主线程没有 join/wait
- ❌ 被问"为什么不直接扩线程数而要用线程池"，思维转不过来，被面试官引导才明白
- ❌ 对象在"堆还是栈"的硬件层面理解薄弱，被面试官追问到底层内存/总线时答不上

**反思小结：**
> 项目讲解容易陷入细节叙述，缺乏高层架构视角；并发题对线程协作机制掌握不牢，wait/notify/join 使用要专项练习。

### 2. 懂车帝 后端 一面（2026-03-03）

**主要考点：**
- 美团项目全面回顾（压缩包回捞、频度调度、流量打散）
- Redis数据结构（string/list/set/zset/hash）
- ZSet底层为何用跳表而非红黑树
- Redis渐进式rehash流程
- MySQL事务隔离级别（读未提交/读已提交/可重复读/串行化）
- MySQL三大日志（redo log/undo log/binlog）
- TCP vs UDP区别、TCP面向字节流
- IO多路复用模型（select/poll/epoll）
- 算法题：零钱兑换（经典DP）

**答得好的地方：**
- Redis ZSet底层（跳表+哈希表）讲出来了
- Redis渐进式rehash两张哈希表迁移流程描述清楚
- MySQL四种隔离级别及MVCC + ReadView 讲解清晰
- redo/undo/binlog三个日志基本到位
- TCP面向字节流 + HTTP队头阻塞问题答出来
- DP零钱兑换思路正确并运行通过

**答得不好的地方：**
- ❌ Redis数据结构漏报 ZSet，只说了 string/set/list，被追问才想起来
- ❌ ZSet用跳表原因只说"快"，没展开：跳表范围查询友好、节点插入不需要旋转、实现简单
- ❌ IO多路复用（select/poll/epoll）三种模型区别基本没答上，只知道epoll和redis有关联
- ❌ 分布式锁只说了 SET NX，没提 expire 原子性、Lua脚本、可重入等细节
- ❌ 项目表达过于啰嗦（面试官直接点出"介绍有点啰嗦"）

**反思小结：**
> 基础知识点有漏洞，尤其是IO模型是高频考点必须补齐；项目介绍要提炼出 STAR 结构，控制在2分钟内。

### 5. 抖音 广告 一面（2026-03-31）

**主要考点：**
- 线程池参数配置（核心线程数、最大线程数、队列大小）
- IO密集型线程数评估
- 压测经验
- Linux命令（大文件排序，sort/awk）
- 大文件Top-N问题（1T文件，内存8G，找第二列最大前100行）
- MySQL脏读/幻读/不可重复读 + MVCC解决方案
- MySQL B+树 vs 红黑树 vs B树
- Redis五种数据类型及ZSet应用场景（排行榜）
- 缓存雪崩/穿透/击穿

**答得好的地方：**
- MySQL MVCC + ReadView + 幻读分析讲得很好（面试官夸"果然背得很好"）
- B+树优势（只叶子存数据、双向链表支持范围查询、层高低IO少）答到位
- 缓存雪崩（随机TTL）、穿透（布隆过滤器+空值缓存）答出来
- 大文件Top-100：流式读取+小根堆（优先队列）思路正确

**答得不好的地方：**
- ❌ Linux命令排序完全答不上（sort -t ' ' -k2 -rn file | head -100）
- ❌ 线程池参数：没说出最优IO密集型计算公式（CPU核数 × 2 + 1）
- ❌ 压测经验为零（没有做过正式压测评估线程数参数）
- ❌ 算法题（最长有效括号）没完全跑通，思路有但实现有bug

**反思小结：**
> Linux命令是实用技能，必须掌握 sort/awk/grep/jq 组合；算法题要多练medium难度字符串/DP题；压测、性能调优是工程能力短板。

### 10. 迅雷 后端 一面（2026-06-15）

**主要考点：**
- 项目深挖：线程池拒绝策略选型理由（SynchronousQueue + 抛异常 vs CallerRunsPolicy vs 无界队列）
- 线程池设计：信号量方案 vs 加锁检查方案的对比权衡
- 网络IO瓶颈分析：线程数与带宽的关系、如何评估最优线程数
- 系统性能调优：压测思路（单机压测 → 逐步放量 → 观察CPU/内存 → 留安全余量）
- GZip压缩流处理：流式解压、文件头元数据位置
- 频度调度策略：两版方案对比（单维产出量 → 三维打分）
- RAG系统深挖：向量库构建（MD5去重、异步入库、定时重试兜底）、知识库与意图树的绑定关系
- 算法题：有序单链表去重

**答得好的地方：**
- 线程池拒绝策略三选一的分析非常完整，清晰说明了为何不选 CallerRunsPolicy（主线程执行期间下游线程空闲浪费）和无界队列（OOM风险），并给出了选用"抛异常+MQ重试兜底"的完整理由
- 信号量 vs 加锁检查的权衡分析有深度，说出了信号量引入的额外复杂度和"初始满载时才有收益、后续收益不明显"的结论
- 系统瓶颈定位（网络IO等待是主要耗时，CPU/内存消耗较少）方向正确
- 压测评估线程数的思路清晰（单机→逐步调大→观察内存CPU→留余量→灰度推全）
- RAG向量库入库细节（MD5去重、异步入库、定时兜底任务）答得完整
- 算法题（有序链表去重）思路正确，双指针跳过重复节点的方案清晰

**答得不好的地方：**
- ❌ **GZip元数据位置**：被问到"流式解压时文件头/文件尾的元数据放在哪里，是否需要先读取元数据再解压"，回答"没有相关策略"——实际上GZip头部包含魔术字节（1f 8b）、压缩方法、文件名等元数据，且Java的GZIPInputStream可以自动处理，应该说出来
- ❌ **线程数与网络IO的量化关系**：面试官追问"如何通过线程数最大化发挥网络IO能力"，只答了"不断调大线程池观察指标"，没有给出公式（IO密集型线程数 = CPU核数 / (1 - 阻塞系数)，或实测带宽/单次请求数据量 × 平均响应时间）
- ❌ **内存占用层级**：被追问"抓取一个网页时在系统层面内存占用是什么样"，理解为"应用层对象大小"，没答到操作系统层面（内核缓冲区、Socket缓冲区、进程堆内存、文件描述符等）
- ❌ **IDEA运行环境出问题**：算法题写完后因本地IDEA配置问题无法运行，影响了演示效果（面试官表示无所谓，但这是硬伤）

**反思小结：**
> 本场整体发挥是所有面试中较好的一场，拒绝策略分析、信号量权衡、压测思路都给出了有深度的回答。主要短板在于对底层系统细节（网络IO量化、OS内存模型）和GZip格式细节认知不足。IDEA本地环境要保持随时可运行的状态。

## 五、后续重点强化计划

### 优先级 P0（每场都会问，必须烂熟）

1. **Kafka核心原理**：partition/consumer group/rebalance/offset/ISR/ack三种模式
2. **Kafka消息可靠消费完整链路**：先持久化（写Redis/DB）→ 再提交offset → 定时补偿扫描 → 幂等去重；进程崩溃场景的兜底逻辑（银河驿站被追问10分钟的教训）
3. **项目业务价值链**：为每个优化准备完整的"技术指标→中间指标→业务收益"话术
4. **多线程并发编程**：wait/notify/Condition/CountDownLatch/Semaphore，每种写一遍demo
5. **SynchronousQueue 背压控制答法**（小红书被追问5次，P0新增）：不要用排除法（不选有界/无界）而要正面说——SynchronousQueue 不缓冲，直接透出"线程池满"信号，配合外层 while 循环停止拉 MQ 消息，实现端到端背压；有缓冲队列会掩盖满信号，导致 while 误判继续拉消息 OOM。
6. **wait/notify 时机规则**（小红书算法题暴露）：**生产完 → notifyAll（唤醒消费者）**；**消费完 → notifyAll（唤醒生产者）**；**等待中 while(条件){wait()} 内部绝不 notify**；判断用 while 不用 if（防虚假唤醒）。
7. **🔴 CAP理论（腾讯1面最严重失分）**：C（Consistency一致性→所有节点同一时刻数据一致）、A（Availability可用性→每次请求都有非错误响应）、P（Partition Tolerance分区容错性→通信中断仍正常服务）。三者最多同时实现两个（CA/CP/AP）。BASE：BA基本可用→S软状态→E最终一致性。**必须脱口而出，这是分布式系统"第一课"**
8. **🔴 一致性哈希（腾讯1面直接说忘记了）**：解决节点扩缩容时最小化数据迁移问题。取模哈希缺点→一致性哈希原理（2^32虚拟圆环→顺时针找节点→增减节点只影响相邻节点）→虚拟节点解决数据倾斜。**结合美团Redis集群讲**
9. **🔴 进程间通信IPC（腾讯1面答管道被纠正）**：效率排名：共享内存 > 消息队列 > 管道(FIFO) > Socket > 信号。共享内存最快（直接读写同一物理内存，无需内核态切换），需信号量同步。
10. **分布式锁高可用方案（腾讯1面主从丢失未答出）**：Redlock原理（N/2+1独立节点半数加锁）；实际生产降级（过期时间×2 + 数据库乐观锁兜底 + 业务层幂等）。

## 七、面试答错基础知识纠正（完整答案+延伸）

> 本栏收集面试中回答错误或不完整的基础知识，给出完整正确回答和相关延伸考点，用于考前快速复习。

### 1. HTTP 报文结构（QQ音乐面答错 🔴）

**❌ 错误：** 把 HTTP 请求头说成包含"ACK/SYN 标志位、IP、端口"——应用层和传输层混淆。

**✅ 正确回答：**

| 组成 | 内容 | 示例 |
|------|------|------|
| **请求行** | 方法 + URL + 协议版本 | `GET /index.html HTTP/1.1` |
| **请求头** | key:value 键值对 | `Host: www.qq.com` `Content-Type: application/json` |
| **空行** | CRLF（\\r\\n） | 分隔 header 和 body |
| **请求体** | POST/PUT 传输的数据 | JSON/XML/表单数据 |

响应报文将**请求行**换成**状态行**：`HTTP/1.1 200 OK`

**🔗 延伸考点：**
- **HTTP 方法**：GET（幂等）、POST（非幂等）、PUT（幂等，全量替换）、PATCH（部分更新）、DELETE（幂等）
- **HTTP 状态码**：1xx（信息）、2xx（成功）、3xx（重定向）、4xx（客户端错误）、5xx（服务端错误）
- **HTTP/1.1 vs HTTP/2**：HTTP/2 多路复用（一个 TCP 连接并发多个请求）、头部压缩（HPACK）、服务端推送
- **HTTP 无状态**：每个请求独立，Session/Cookie/Token 实现状态管理

### 2. TCP TIME_WAIT 状态（QQ音乐面答错 🔴）

**❌ 错误：** 说成"服务端第二次挥手时进入 TIME_WAIT" + "服务端数据没传完等待"。

**✅ 正确回答：**

TIME_WAIT 在 **主动关闭方**（通常是客户端），收到服务端 FIN 后发送 ACK 进入，等待 **2MSL（约 60 秒）** 后关闭。

**四次挥手完整流程：**
```
主动方                         被动方
  │  ─── FIN seq=x ───────→  │
  │  ←── ACK ack=x+1 ─────  │  (被动方还有数据可发)
  │  ←── FIN seq=y ───────  │  (被动方数据发完)
  │  ─── ACK ack=y+1 ────→  │  → 主动方进入 TIME_WAIT(2MSL)
```

**TIME_WAIT 两个作用：**
1. **防延迟报文干扰**：上一个连接延迟到达的数据包，不会污染使用相同四元组的新连接
2. **保最后一个 ACK 可达**：如果服务端没收 ACK 会重发 FIN，TIME_WAIT 期间客户端可以重发 ACK

**🔗 延伸考点：**
- **大量 TIME_WAIT 怎么处理？** 高并发短连接场景（如爬虫），可开启 `net.ipv4.tcp_tw_reuse`（复用 TIME_WAIT 连接）或 `SO_LINGER` 设置立即关闭
- **CLOSE_WAIT** 发生在被动关闭方（服务端收到 FIN 后等待自己业务代码调用 close()）——如果服务端代码有 bug 没调用 close()，会导致大量 CLOSE_WAIT
- **2MSL 为什么是 60 秒？** MSL（Maximum Segment Lifetime）在 Linux 默认 30 秒，2MSL = 60 秒

### 3. TCP 三次握手完整四目的（QQ音乐面答不完整 ⚠️）

**❌ 原来回答：** 只说了"确认双方收发能力"和"防历史连接"。

**✅ 完整回答（四个目的，缺一不可）：**

| # | 目的 | 说明 |
|---|------|------|
| ① | **确认收发能力** | SYN→SYN+ACK→ACK，双方都确认对方能发能收 |
| ② | **防历史连接** | 收到旧 SYN 时，客户端通过序号比较发现，发 RST 断开——两次握手做不到 |
| ③ | **同步初始序列号** | 双方交换 ISN（seq=x / seq=y），之后用序列号排序、去重、重传 |
| ④ | **最少往返次数** | 服务端 SYN+ACK 合并发，只需 1.5 个 RTT；如果四次握手需要 2 个 RTT |

**为什么两次握手不行？**
- 如果只有两次：服务端收到 SYN 就分配资源建立连接
- 此时如果客户端端的旧 SYN 延迟到达——服务端建立连接 → 客户端发 RST 断开 → 服务端白白浪费资源
- **三次握手让服务端等到 ACK 才确认连接**，旧 SYN 不会导致资源浪费

**🔗 延伸考点：**
- **SYN Flood 攻击**：攻击者发送大量 SYN 不回复 ACK → 服务端半连接队列打满，正常连接进不来
- **防御**：SYN Cookie（不分配资源，用序号编码信息）、增大 tcp_max_syn_backlog、缩短 SYN 超时
- **同时打开（Simultaneous Open）**：两端同时发 SYN，建立一条连接（少见，需四步交互）

### 4. K 个一组翻转链表（LeetCode 25）（QQ音乐面写不出 ❌）

**❌ 错误：** 思路正确但 30 分钟写不出完整代码。

**✅ 完整解法（递归，最简洁）：**

```java
public ListNode reverseKGroup(ListNode head, int k) {
    // 1. 检查剩余节点是否够 k 个
    ListNode cur = head;
    int count = 0;
    while (cur != null && count < k) {
        cur = cur.next;
        count++;
    }
    if (count < k) return head;  // 不够 k 个，不翻转，直接返回
    
    // 2. 翻转当前组前 k 个节点（标准的链表反转）
    ListNode prev = null, curr = head;
    for (int i = 0; i < k; i++) {
        ListNode next = curr.next;  // 保存下一个
        curr.next = prev;            // 指向前驱
        prev = curr;                 // prev 后移
        curr = next;                 // curr 后移
    }
    
    // 3. head 现在变成当前组的尾节点，递归翻转下一组
    head.next = reverseKGroup(curr, k);
    
    // 4. prev 是当前组翻转后的新头
    return prev;
}
```

**迭代法（空间 O(1)）：**
```java
public ListNode reverseKGroup(ListNode head, int k) {
    ListNode dummy = new ListNode(0);
    dummy.next = head;
    ListNode prev = dummy, end = dummy;
    
    while (end.next != null) {
        // 找到第 k 个节点
        for (int i = 0; i < k && end != null; i++) end = end.next;
        if (end == null) break;
        
        ListNode start = prev.next;
        ListNode nextGroup = end.next;
        end.next = null;  // 断开
        
        prev.next = reverse(start);   // 翻转并接入
        start.next = nextGroup;       // start 变成尾节点，指向下一组
        
        prev = start;   // 移动 prev 到下一组的前驱
        end = start;    // 移动 end 到下一组的前驱
    }
    return dummy.next;
}

private ListNode reverse(ListNode head) {
    ListNode prev = null, curr = head;
    while (curr != null) {
        ListNode next = curr.next;
        curr.next = prev;
        prev = curr;
        curr = next;
    }
    return prev;
}
```

**时间复杂度：** O(N)，每个节点遍历常数次
**空间复杂度：** 递归 O(N/k)，迭代 O(1)

**🔗 延伸考点：**
- **反转链表（LeetCode 206）**：基本功，必须 3 分钟内写出
- **反转链表 II（LeetCode 92）**：指定区间反转
- **两两交换链表节点（LeetCode 24）**：K=2 的特殊情况

### 5. 性能瓶颈分析方法论（QQ音乐面答不出 ❌）

**❌ 错误：** 猜测"CPU 打满 80%"，被面试官反问"等待需要耗 CPU 吗"后无法自圆其说。

**✅ 完整方法论：**

**第一步：区分 IO 密集型 vs CPU 密集型**

| 类型 | 特征 | 典型操作 | 线程状态 | 优化方向 |
|------|------|---------|---------|---------|
| IO 密集型 | 大量等待 | HTTP下载、DB查询、磁盘读写 | WAITING/BLOCKED 多 | 增加线程数（公式：核数/(1-阻塞比)） |
| CPU 密集型 | 持续运算 | 数据解析、正则匹配、加解密 | RUNNABLE 多 | 线程数≈核数，优化算法 |

**第二步：生产排查工具链**
```bash
top               # 看整体 CPU/内存
top -H -p <pid>   # 看进程内各线程 CPU 分布
vmstat 1          # 看上下文切换(cs)、CPU 占用(us/sy/id)
jstack <pid>      # dump 线程栈，看 WAITING vs RUNNABLE 比例
jstat -gcutil     # 看 GC 频率和耗时（GC 也可能高 CPU）
```

**第三步：分析逻辑**
- 大量线程 **WAITING** → IO 瓶颈（可增加线程数）
- 大量线程 **RUNNABLE** → CPU 瓶颈（需优化代码逻辑或扩核）
- **高上下文切换（cs）**+ 不高 CPU → 线程数过多
- **GC 频繁** → 内存配置不当或内存泄漏

**🔗 延伸考点：**
- **IO 密集型线程数公式**：`N = CPU核数 / (1 - 阻塞系数)`，阻塞系数 = 等待时间/(等待+处理)
- **上下文切换开销**：每次切换约几微秒，每秒万级切换会导致明显性能下降
- **CPU 飙高排查三板斧**：`top -H` 找高 CPU 线程 → `jstack` 看线程栈 → 定位到具体代码行

### 6. synchronized vs Semaphore 选型（快手/QQ音乐面深度不足 ⚠️）

**❌ 原来回答：** "信号量代码复杂度高、synchronized 不需要手动释放"——没有触及核心差异。

**✅ 深度分析：**

| 维度 | synchronized | Semaphore |
|------|-------------|-----------|
| **获取方式** | 阻塞等待，一直等到锁释放 | **tryAcquire() 非阻塞**，拿不到立即返回 false |
| **锁粒度** | 整个代码块串行化 | 允许多个线程**并行检查**，只有实际提交时才串行 |
| **释放** | 自动释放（退出 synchronized 块） | 需手动 try-finally release（标准模式） |
| **适用场景** | 低并发、少量回调线程 | 高并发、大量线程同时检查线程池状态 |
| **背压效果** | 线程阻塞在锁上，回调线程没机会拉消息 | tryAcquire 失败直接跳过，回调线程继续正常工作 |

**核心差异一句话：** synchronized 强制"检查+提交"整个过程串行化——所有回调线程抢同一把锁；Semaphore 允许多个回调线程**并行做检查**，只有实际提交时才串行，**高并发下锁争用远低于 synchronized**。

**🔗 延伸考点：**
- **Semaphore 标准模式**：`try { semaphore.acquire(); ... } finally { semaphore.release(); }`——finally 保证不泄漏
- **限流场景选型**：Semaphore 更适合限流（明确信号量上限），synchronized 更适合保护临界区
- **LongAdder vs AtomicLong**：高并发计数场景，LongAdder 分段减少 CAS 冲突

### 7. IO 多路复用（select/poll/epoll）（懂车帝/腾讯/多场答不上 ❌🔴 P0）

**❌ 错误：** 多场面试答不上，只知道"epoll和Redis有关联"。

**✅ 完整回答：**

| 特性 | select | poll | epoll |
|------|--------|------|-------|
| 数据结构 | 位图 FD_SET | pollfd 链表 | **红黑树 + 就绪链表** |
| fd 上限 | 1024（FD_SETSIZE） | **无上限** | 无上限 |
| 注册方式 | 每次调用全量传入（用户↔内核 2次拷贝） | 每次调用全量传入（2次拷贝） | **epoll_ctl 一次注册，长期生效** |
| 事件获取 | O(N) 扫描全部 fd | O(N) 扫描全部 fd | **O(1) 取就绪链表** |
| 触发模式 | 仅水平触发（LT） | 仅水平触发（LT） | **LT + ET（边缘触发）** |

**epoll 核心优势：**

**🔗 延伸考点：**
- **ET 编程模式**：必须设置非阻塞IO，while 循环读直到 EAGAIN
- **应用场景**：Nginx（ET）、Redis（LT，单线程事件循环）、Netty（ET + 非阻塞IO）
- **零拷贝**：sendfile（内核直接发）、mmap（内核缓冲区映射用户空间）
- **C10K/C100K 问题**：epoll 是解决高并发连接的基石

```java
// ❌ 错误：分开两步（非原子）
```

```
Redlock 方案：
① 向 N/2+1 个独立 Redis 节点申请加锁（N=奇数，如5个）
② 每个节点超时设 ~50ms，防止单节点卡死
③ 超过半数（≥3/5）成功 → 检查总耗时 elapsed < TTL
④ 否则释放所有已加锁节点，随机延迟后重试
```

| 层级 | 方案 | 问题 |

| 第一层 | Redis 分布式锁 | 主从异步复制丢了就丢了 |
| 第二层 | 数据库乐观锁 version | `UPDATE t SET version=version+1 WHERE id=? AND version=?` |

### 9. CAP 理论（腾讯1面全场最严重失分 ❌🔴🔴 P0）

**❌ 错误：** 三个字母一个没说对，答成了"投票机制/选举策略"。

**✅ 完整回答：**

| 字母 | 含义 | 说明 |
|------|------|------|
| **C** | **Consistency 一致性** | 所有节点同一时刻看到的数据一致 |
| **A** | **Availability 可用性** | 每次请求都能获得非错误响应（可不保证最新） |
| **P** | **Partition Tolerance 分区容错性** | 节点间通信中断时系统仍正常服务 |

**P 是必选项！** 网络分区（Partition）是分布式系统的**必然事件**——机房断网、交换机故障、光纤被挖断，只是概率问题不是有无问题。所以实际分布式系统只能在 **CP** 和 **AP** 之间选，CA 在分布式场景下不存在。

**三个组合的详细解释：**

**CA（一致+可用，不处理分区）：**
- 代表是**单机 MySQL**——只有一个节点，不会发生网络分区。此时可以同时保证一致性和可用性。
- 但一旦变成**分布式多节点**（主从/集群），网络分区就不可避免。分区发生时，如果追求CA，系统只能**停服**——因为它既不能放弃一致性（不能允许主从数据不同步），也不能放弃可用性（必须返回正确数据），两者冲突时只能停摆。
- 所以 CA 本质上不是分布式系统，是**单机系统**。CAP定理讨论的是分布式场景，CA只是理论上的组合。

**CP（一致+分区容错，牺牲可用性）：**
- **ZooKeeper / etcd**：集群通过**过半选举**（Paxos/Raft）保证强一致性
- 分区发生时：**多数派（大于半数）**的节点可以继续服务；**少数派**的节点无法收到多数确认，写请求会**直接返回错误**——这就是"牺牲可用性"（A）。
- 例：ZK 3节点，挂1个剩2个 → 多数派依然过半，可正常服务。但如果挂2个剩1个 → 少数派不足半数，所有写请求被拒绝。
- 所以 ZooKeeper 保证的是：**任何时候读取到的数据都是一致的**（C），但分区时部分节点可能不可用（A被牺牲）。

**AP（可用+分区容错，牺牲强一致性）：**
- **Redis Cluster / Eureka / DNS**：分区发生时，**两边各自独立服务**
- Redis Cluster：分区后，大分区继续提供服务，小分区的请求被重定向；两边数据可能短暂不一致，但网络恢复后最终收敛（最终一致性）
- Eureka：分区后，每个节点都认为自己是健康的，继续返回注册信息——即使信息可能不准确（已宕机的服务还在注册表里），但客户端**总能获得响应**（A保障了）
- 所以 AP 系统的代价是：**数据可能读到旧值或不一致**（C被牺牲），但保证**每次请求都有响应**（A）。

**BASE 理论（对 AP 的延伸）：**
- **BA**（Basically Available）：基本可用，允许降级
- **S**（Soft State）：软状态，允许中间状态
- **E**（Eventual Consistency）：最终一致性

**🔗 延伸考点：**
- **Eureka（AP）vs ZooKeeper（CP）**：Eureka 优先可用性（注册中心挂了不影响已有服务通信），ZooKeeper 优先一致性（选主期间不可用）

### 分布式事务全解（XA / AT / TCC / Saga）及与 CAP 的关系

> 这是一个高频/深度的延伸考点，腾讯1面 CAP 答不上后如果面试官追问分布式事务会更严重。需要把各种分布式事务方案的核心原理和 CAP 取舍逻辑理清楚。

#### 核心矛盾：CAP 决定了分布式事务的设计空间

分布式事务的本质是：**在分布式系统（P 是必然事件）中，如何保证多个节点的数据一致（C）**。而 P 必然存在，所以必须在 C 和 A 之间做取舍——这就产生了不同的分布式事务方案，分为两大流派：

| 流派 | 追求的 CAP 组合 | 代表方案 | 特点 |
|------|---------------|---------|------|
| **强一致派** | **CP**（分区时牺牲可用性） | XA / 2PC | 数据强一致，但性能差、阻塞 |
| **最终一致派** | **AP+最终一致**（分区时优先可用） | AT / TCC / Saga | 高性能、高可用，通过补偿达到最终一致 |

---

#### ① XA 协议（强一致，对应 CP）

**全称：** eXtended Architecture，数据库层面的分布式事务标准。

**原理（2PC 两阶段提交）：**

```
阶段一（准备阶段）：
协调者 → 所有参与者：prepare？
参与者 → 协调者：OK（锁定资源，写 undo/redo log，但未提交）

阶段二（提交阶段）：
协调者 检查所有参与者的回复：
  ├─ 全票通过 → 协调者 → 所有参与者：commit（正式提交） ✅
  └─ 有失败或超时 → 协调者 → 所有参与者：rollback（回滚） ❌
```

**与 CAP 的关系：** 追求 **CP**（分区时牺牲可用性）。

| CAP 维度 | XA/2PC 的表现 |
|----------|--------------|
| C（一致性） | ✅ 强一致——要么全部成功要么全部回滚 |
| A（可用性） | ❌ **协调者单点故障**：协调者挂了，参与者阻塞等待，锁资源不释放，系统不可用<br>❌ **同步阻塞**：阶段一锁定资源，其他事务无法操作 |
| P（分区容错） | ⚠️ 分区时协调者和参与者失联，参与者一直等待协调者指令，资源被锁死 |

**代表：** MySQL XA、Atomikos、Narayana

**适用场景：** 银行转账、金融对账（强一致优先，可以接受低吞吐）

**缺点：**
- **同步阻塞**：所有参与者锁资源，等协调者决策
- **单点故障**：协调者挂了，参与者永远不知道是 commit 还是 rollback
- **数据不一致**：阶段二协调者发了 commit 但部分参与者没收到 → 部分提交成功部分没提交

---

#### ② Seata AT 模式（自动补偿，对应 AP+最终一致）

**全称：** Automatic Transaction，Seata 框架的自动补偿方案。

**原理（拦截 SQL + 反向 SQL 补偿）：**

```
一阶段（执行+记录）：
① 业务执行 SQL（UPDATE account SET money=money-100 WHERE id=1）
② Seata 自动拦截，生成 前置镜像（before image）和 后置镜像（after image）
③ 写入 undo_log 表
④ 提交本地事务，释放本地锁

二阶段（提交或回滚）：
  ├─ 全局成功 → 异步删除 undo_log ✅（不需要额外操作）
  └─ 全局失败 → 读取 undo_log，用 前置镜像 生成反向 SQL 自动回滚 ❌
```

**与 CAP 的关系：** 追求 **AP + 最终一致**。

| CAP 维度 | AT 的表现 |
|----------|----------|
| C（一致性） | ⚠️ **最终一致**——一阶段提交了本地事务，如果后续回滚需要补偿 |
| A（可用性） | ✅ **非阻塞**——一阶段执行完就释放锁，不需要等待全局决策 |
| P（分区容错） | ✅ 分区时各自执行本地事务，网络恢复后补偿回滚 |

**适用场景：** 大多数微服务场景（订单+库存+积分），可以接受短暂不一致

**缺点：**
- 需要 Seata Server 作为全局事务协调者（额外依赖）
- 生成镜像有性能开销
- 补偿可能有中间状态（用户看到数据先增加，后回滚减少）

---

#### ③ TCC（Try-Confirm/Cancel，业务侵入，对应 AP+最终一致）

**全称：** Try-Confirm-Cancel，业务层面手动实现的三阶段模型。

**原理（业务逻辑控制，不依赖 DB 锁）：**

```
Try（预留资源）：       冻结库存 1 件（库存表 reserve=1, available=available-1）
Confirm（确认执行）：    扣减冻结（reserve=reserve-1，实际扣减）
Cancel（取消回滚）：     释放冻结（reserve=reserve-1, available=available+1）

例：下单场景
Try：    创建订单状态=待支付 + 冻结库存 + 冻结金额
Confirm：订单状态改已支付 + 扣减冻结库存 + 扣减冻结金额（真正扣款）
Cancel： 订单状态改已取消 + 释放冻结库存 + 释放冻结金额
```

**与 CAP 的关系：** 追求 **AP + 最终一致**。

| CAP 维度 | TCC 的表现 |
|----------|-----------|
| C（一致性） | ⚠️ **最终一致**——三个阶段都是独立本地事务 |
| A（可用性） | ✅ **不阻塞**——Try 阶段后就释放资源，高性能 |
| P（分区容错） | ✅ 各阶段独立本地事务，分区时不影响已预留的资源 |

**对比 AT 的核心差异：**

| 维度 | AT（Seata） | TCC |
|------|-----------|-----|
| **实现方式** | 自动拦截 SQL，生成镜像 | **业务手动实现三阶段方法** |
| **业务侵入** | 低（自动拦截） | **高**（每个服务都要写 Try/Confirm/Cancel） |
| **粒度** | SQL 行级 | **业务级**（可控制预留多少、怎么预留） |
| **性能** | 有镜像开销 | 高（精确控制） |
| **适用场景** | 简单增删改 | **复杂业务**（跨资源、跨服务） |

**适用场景：** 库存预留、账户扣款、订单状态流转（需要精确控制资源预留量的场景）

**缺点：**
- 业务侵入性强（每个方法都得写三阶段逻辑）
- Cancel 方法必须保证幂等（可能被多次调用）

---

#### ④ Saga（长事务拆分 + 补偿，对应 AP+最终一致）

**原理：** 将长事务拆成 N 个本地事务，每个本地事务对应一个补偿操作。

```
正常流程（T1 → T2 → T3 → T4）：
  创建订单 → 扣减库存 → 扣减余额 → 发货

异常回滚（T1 → T2 → T3 失败 → 补偿C3 → 补偿C2 → 补偿C1）：
  创建订单 → 扣减库存 → 扣减余额失败 → 恢复余额 → 恢复库存 → 取消订单
```

**两种实现方式：**

| 方式 | 说明 | 适用 |
|------|------|------|
| **编排（Orchestration）** | 一个协调者负责告诉每个参与者做什么 | 流程复杂、需要统一管控 |
| ** choreography（ choreography）** | 每个服务执行完发 MQ 事件，下一个服务监听后执行 | 流程简单、松耦合 |

**与 CAP 的关系：** 追求 **AP + 最终一致**。

| CAP 维度 | Saga 的表现 |
|----------|------------|
| C（一致性） | ⚠️ **最终一致**——中间状态对外可见（用户能看到"已扣款但未发货"） |
| A（可用性） | ✅ **不阻塞**——每个本地事务执行完就提交 |
| P（分区容错） | ✅ 基于 MQ 异步通信，天然容忍分区 |

**适用场景：** 长链路、多步骤的业务流程（旅行预订、下单发货）

**缺点：**
- **缺少隔离性（缺乏ACID的I）**：一个 Saga 事务的中间结果对其它事务可见
- 补偿逻辑复杂，且补偿操作必须幂等

---

#### 四者对比总结

| 方案 | CAP 倾向 | 一致性 | 可用性 | 性能 | 业务侵入 | 典型场景 |
|------|---------|--------|--------|------|---------|---------|
| **XA（2PC）** | CP | 强一致 | ❌ 阻塞 | 低 | 低 | 金融转账 |
| **AT（Seata）** | AP+最终一致 | 最终一致 | ✅ | 中 | 低 | 通用微服务 |
| **TCC** | AP+最终一致 | 最终一致 | ✅ | 高 | **高** | 库存预留 |
| **Saga** | AP+最终一致 | 最终一致 | ✅ | 高 | 中 | 长链路业务 |

**面试回答框架**（被问到"分布式事务你了解哪些"）：

> *"分布式事务的本质是在 P（分区容错）必然存在的分布式系统中解决 C（一致性）问题。根据 CAP 取舍分为两类：*
>
> *① **强一致派**用 XA/2PC——数据强一致但性能差，有同步阻塞和协调者单点问题，适合金融场景。*
> *② **最终一致派**又分三种：Seata AT 自动拦截 SQL 做补偿回滚（侵入低）；TCC 业务手动实现 Try/Confirm/Cancel（性能高但侵入强）；Saga 把长事务拆成多个本地事务 + 补偿（适合长链路）。*

### 10. MySQL 事务实现原理（MVCC + Redo Log + Undo Log）

**面试官可问：** "MySQL 事务是怎么实现的？"

**标准回答（三种机制协同）：**

| 机制 | 解决的问题 | 原理 |
|------|-----------|------|
| **Redo Log（重做日志）** | **持久性 D** | WAL 机制：事务提交前先写 redo log（顺序IO），崩溃恢复时重放已提交但未写入磁盘的事务 |
| **Undo Log（回滚日志）** | **原子性 A + MVCC** | 记录修改前的旧值，回滚时用 undo log 恢复；MVCC 通过 undo log 构建历史版本链 |
| **锁 + MVCC** | **隔离性 I** | 行锁/间隙锁防止并发冲突；MVCC 实现 RC/RR 级别的一致性读 |

**MVCC 具体实现：**
```
每行记录有两个隐藏列：
  trx_id：最后修改该行的事务 ID
  roll_pointer：指向 Undo Log 中上一个版本

事务开始时创建 ReadView（4个核心字段）：
  m_ids：当前活跃事务 ID 列表
  min_trx_id：最小活跃事务 ID
  max_trx_id：最大已分配 ID + 1
  creator_trx_id：本事务 ID

可见性判断：
  trx_id == creator_trx_id → 自己改的 → 可见 ✅
  trx_id < min_trx_id     → 已提交的老事务 → 可见 ✅
  trx_id >= max_trx_id    → 未来事务 → 不可见 ❌
  trx_id 在 m_ids 中      → 活跃未提交 → 不可见 ❌
  trx_id 不在 m_ids 中    → 已提交 → 可见 ✅
```

**RC vs RR 的 ReadView 区别：**
- **RC（读已提交）**：每条 **语句**都创建新的 ReadView（所以两次查询可能看到不同结果 = 不可重复读）
- **RR（可重复读）**：事务 **开始时**创建 ReadView，事务期间一直复用（所以多次查询结果一致）

**Redo Log 的 WAL 机制：**
```
事务提交流程：
① 写 redo log（prepare 状态）→ 刷盘（顺序IO）
② 写 binlog → 刷盘
③ 写 redo log（commit 状态）→ 刷盘
```
两阶段提交保证 redo log 和 binlog 一致。

**🔗 延伸：**
- **WAL（Write-Ahead Logging）**：先写日志再写数据，日志是顺序IO远快于数据随机IO
- **Checkpoint**：定期将脏页刷盘，缩短崩溃恢复时间
- **长事务风险**：undo log 膨胀导致回滚段过大，影响历史版本链长度

### 11. 百万数据大分页查询优化

**面试官问：** "比如说要查第 100 万行到第 100 万零 100 行这 100 条数据，你会怎么查？"

**❌ 错误回答：** 只说"分段查询"，没给出具体方案。

**✅ 四种方案（从优到劣）：**

**方案一：游标分页（推荐，适合实时滚动）**
```sql
-- 记住上一页最后一条的 id，性能最优
SELECT * FROM t WHERE id > 1000000 ORDER BY id LIMIT 100;
-- 优点：不走偏移量，索引直接定位
-- 缺点：只能连续翻页，不能跳页
```

**方案二：子查询延迟关联（适合跳页）**
```sql
-- ❌ 传统写法：查出前 1000100 行后丢弃 1000000 行
SELECT * FROM t ORDER BY id LIMIT 1000000, 100;

-- ✅ 子查询优化：先走覆盖索引取主键，再关联
SELECT * FROM t 
INNER JOIN (SELECT id FROM t ORDER BY id LIMIT 1000000, 100) AS tmp 
ON t.id = tmp.id;
-- 子查询只查主键（覆盖索引，快），再回表取整行
```

**方案三：范围查询（适合按 ID 段分页）**
```sql
SELECT * FROM t WHERE id BETWEEN 1000000 AND 1000100;
-- 走主键索引，最快
-- 要求：ID 连续无空洞
```

**方案四：业务层限制**
- "用户看到第 100 页就不让再翻了"——百度/谷歌都这么干
- 改用"加载更多"而不是传统分页器

**核心原理：** `LIMIT 1000000, 100` 为什么慢？MySQL 会**先查 1000100 行再丢弃前 1000000 行**——偏移量越大越慢。游标/子查询都是为了避免这种"查出再丢"的浪费。

### 12. 索引下推（ICP）

**面试官问：** "联合索引 (A,B,C)，WHERE A=? AND C=? ，C 怎么过滤的？"

**✅ 标准回答：**
> *"在 MySQL 5.6 之前，存储引擎通过索引定位到 A 匹配的行后，回表取整行，交给 Server 层过滤 C 条件。*
> *MySQL 5.6+ 引入**索引下推（ICP）**：如果 C 条件涉及的字段也在索引中，存储引擎在索引遍历时**直接比较 C 条件**，只有满足条件的才回表。减少了回表次数。*
>
> *具体到这个 SQL：WHERE A=? AND C=?
> - A 走索引精确查找（最左前缀命中）
> - B 缺失 → C **不能走索引精确匹配**，但 ICP 让 C 在索引遍历时就被检查
> - `EXPLAIN` 的 Extra 列会显示 `Using index condition`
>
> *打个比方——没有 ICP：你从书架上取出所有 A 类书，搬回座位，一本本看书的 C 属性。有 ICP：你站在书架前，只抽 A 类中 C 属性也满足的书。"*

### 13. RPC 框架

**RPC 调用流程：**

### 15. 一致性哈希（腾讯1面直接说忘记了 ❌🔴 P0）

**❌ 错误：** 直接说"有些忘记了"。

**✅ 完整回答：**

**解决什么问题：** 分布式缓存/存储节点扩缩容时最小化数据迁移。

**传统取模 hash(key) % N 的问题：**
- 节点从 N->N+1，几乎所有 key 重新映射
- 大量缓存同时失效 → **缓存雪崩** → 后端 DB 被打爆

**一致性哈希原理：**
```
①  哈希环：0 ~ 2³²-1 构成虚拟环
②  虚拟节点：每个物理节点创建 150~200 个虚拟节点，散列在环上（解决数据倾斜）
③  路由：key 计算 hash，顺时针找到第一个虚拟节点 → 映射到物理节点
④  扩缩容：只影响相邻节点的 key，其他节点零迁移
```

**虚拟节点的作用：**
- 物理节点少时（如3个），3个点在环上可能扎堆 → 数据倾斜
- 每个物理节点映射 150 个点 → 450 个点均匀散列

**🔗 延伸考点：**
- **Redis Cluster**：不用一致性哈希，用 16384 个 hash slot（确定性分片）
- **一致性哈希 vs hash slot**：一致性哈希去中心化弹性扩缩但概率均匀；hash slot 精确控制但需元数据管理
- **一致性哈希的应用**：Memcached 分布式缓存、负载均衡（Nginx upstream hash）

### 11. 进程间通信 IPC——效率排名（腾讯1面答管道 ❌🔴 P0）

**❌ 错误：** 答"管道"，被面试官纠正为"共享内存"。

**✅ 完整回答：**

**效率排名：共享内存 > 消息队列 > 管道(FIFO) > Socket > 信号**

| 方式 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **共享内存** 🥇 | 两进程直接读写同一物理内存 | **最快**，无需用户态/内核态切换 | 需信号量同步读写 |
| **消息队列** 🥈 | 内核维护消息链表 | 比管道灵活，支持消息类型 | 每次读写需内核态切换 |
| **管道(FIFO)** 🥉 | 半双工字节流 | 实现简单 | 匿名管道只能父子进程 |
| **Socket** | 网络通信 | 跨机器最灵活 | 速度最慢 |
| **信号量/信号** | 传递状态 | 适合同步控制 | 不能传大量数据 |

**为什么共享内存最快？** 两个进程的虚拟地址映射到同一物理页，读写直接操作物理内存，不经过内核。

**🔗 延伸考点：**
- **管道 vs 命名管道**：匿名管道 `pipe()` 只能父子进程；命名管道 `FIFO` 任意进程通过文件路径访问
- **Java 中 IPC 实现**：共享内存（MappedByteBuffer）、Socket、RPC（Dubbo/gRPC）

### 12. 多态底层实现（腾讯1面重写/重载混淆 ❌ P1）

**❌ 错误：** 一开始答"继承+接口"；被追问后重写和重载概念搞混，改了几次口才说清楚。

**✅ 完整回答：**

**编译时多态 = 方法重载（Overload）：**
- 编译时根据参数类型/数量确定调用哪个方法
- **静态绑定**：编译期确定方法地址，用 invokespecial/invokestatic 指令
- final/private/static 方法也是编译时确定

**运行时多态 = 方法重写（Override）：**
- 编译看引用类型，运行看实际对象类型
- **动态绑定**：JVM 用 **invokevirtual** 指令 → 找**虚方法表（vtable）** → 根据实际对象类型定位方法入口

```java
Parent p = new Child();
p.method();  // 编译时看 Parent（检查 method 是否存在）
             // 运行时看 Child（调用 Child 的 method）
```

**虚方法表（vtable）原理：**
```
类加载时，JVM 为每个类创建虚方法表（数组），存放方法实际入口地址
子类重写方法 → vtable 中对应位置指向子类实现
子类未重写 → 指向父类实现
调用时：对象头 → 类元数据 → vtable → O(1) 定位方法
```

**🔗 延伸考点：**
- **static 方法**：属于类，不是多态（静态绑定）
- **private 方法**：隐式 final，不是多态
- **接口方法**：JDK8 之前用 invokedynamic / 接口方法表

### 13. 双亲委派 + 热升级（快手AI/基建两场答不好 ❌ P1）

**❌ 错误：** 知道"要用自定义 ClassLoader"，但讲不清如何打破双亲委派、如何卸载旧类。

**✅ 完整回答：**

**双亲委派机制：**
```
加载一个类时：
① 先委托父类加载器去加载
② 父类加载不了，自己才加载
顺序：自定义 → Application → Extension → Bootstrap

好处：
- 避免重复加载（父类已加载则不重复）
- 核心类安全（java.lang.String 由 Bootstrap 加载，不会被篡改）
```

**如何打破双亲委派？**
```java
public class MyClassLoader extends ClassLoader {
    @Override
    public Class<?> loadClass(String name) {
        // 不先委派父类，自己先尝试加载
        byte[] classData = loadClassFromFile(name);
        if (classData != null) {
            return defineClass(name, classData, 0, classData.length);
        }
        // 自己加载不了才委派父类
        return super.loadClass(name);
    }
}
```

**Tomcat 打破双亲委派：**
- 每个 WebApp 有独立 WebAppClassLoader
- 优先加载自己 WEB-INF/lib 下的类（不委派父类）
- 不同 WebApp 的类隔离，同名类不冲突

**热部署原理：**
```
① 新版本类文件放新目录
② 创建新 ClassLoader 加载新版本
③ 旧类由旧 ClassLoader 卸载（无引用后 GC 回收）
④ Spring Boot DevTools 就是这么做的
```

**🔗 延伸考点：**
- **OSGi**：每个模块独立 ClassLoader，模块间通过 Export-Package 共享
- **Tomcat 类加载顺序**：Bootstrap → System → WEB-INF/classes → WEB-INF/lib → 应用类
- **ClassLoader 泄漏**：框架缓存了旧 ClassLoader 的类引用 → 热部署导致 Metaspace OOM

### 14. Kafka 消费模型（抖音/快手/腾讯/银河驿站多场 ❌ P0）

**❌ 错误：** 拉取线程和消费线程的交互讲不清楚；partition/consumer group/offset 关系模糊。

**✅ 完整回答：**

**Kafka 消费核心模型：**
```
Topic →
  ├─ Partition 0 ── Consumer A（组内唯一消费者）
  ├─ Partition 1 ── Consumer B
  ├─ Partition 2 ── Consumer C
  └─ Partition 3 ── Consumer D（组内多余消费者会空闲）

核心原则：
1. 一个 partition 只能被同一 group 内的一个 consumer 消费
2. consumer 数量超过 partition 数 → 多余的 consumer 空闲
3. rebalance 触发：consumer 加入/退出/崩溃，partition 数量变化
```

**拉取线程 vs 消费线程（生产实践）：**
```
[Kafka Consumer 拉取线程]  →  拉取消息放到阻塞队列  →  [业务线程池消费]
          ↓                              ↓
    手动提交 offset                处理完成后才提交
```
- 拉取线程只负责 poll，不处理业务逻辑
- 消费线程池异步处理，处理完通知拉取线程提交 offset
- **先写 Redis 再提交 offset**：防止进程崩溃导致消息丢失

**ISR（In-Sync Replicas）：**
```
Leader 维护 ISR 列表（与 Leader 保持同步的 Follower）
ack=0：发完即返回（可能丢）
ack=1：Leader 写入就返回（默认）
ack=-1：ISR 全部同步才返回（最安全，但慢）
```

**🔗 延伸考点：**
- **再均衡（Rebalance）**：`ConsumerRebalanceListener` 可以注册回调，在 rebalance 前提交 offset
- **静止伙伴协议（Static Group Membership）**：Kafka 2.3+ 支持，避免频繁 rebalance
- **幂等生产者**：`enable.idempotence=true`，保证消息不重复

### 15. G1 GC vs CMS（飞轮科技面精度不足 ❌ P1）

**❌ 错误：** 说 G1"引入了分带回收算法"——实际 G1 本身就是分代收集器，不是"引入"。

**✅ 完整回答：**

| 维度 | CMS | G1（JDK9+ 默认） |
|------|-----|------------------|
| 回收算法 | **标记-清除** | **标记-整理**（最终）、复制（年轻代） |
| 内存布局 | 连续新生代/老年代 | **Region**（1~32MB，最多2048个） |
| 停顿时间 | 不可预测 | `-XX:MaxGCPauseMillis` **可预测停顿**（默认200ms） |
| 碎片问题 | ❌ 标记-清除产生碎片→Full GC | ✅ 标记-整理：无碎片 |
| 并发阶段 | 并发标记+并发清除 | 并发标记+并发清理（混合GC） |
| 大对象 | 直接进入老年代 | **Humongous Region** 存大对象 |

**为什么 G1 取代 CMS？**
1. **CMS 内存碎片化**：标记-清除持续产生碎片，大对象分配可能触发 Full GC
2. **CMS 停顿不可控**：老年代越大停顿越长；G1 的 `-XX:MaxGCPauseMillis` 可设定目标停顿
3. **G1 Region 独立回收**：不需要扫描全堆，只回收收益高的 Region（优先回收垃圾最多的 Region）

**G1 GC 阶段：**
```
① 年轻代 GC（STW，但 Region 少则快）
② 并发标记（与用户线程并行）
③ 混合回收（Mixed GC）：回收老年代+年轻代
④ Full GC（降级为串行，应避免）
```

**🔗 延伸考点：**
- **CMS 并发失败（Concurrent Mode Failure）**：并发标记期间对象太多 → 降级为串行 Full GC
- **G1 调优参数**：`-XX:MaxGCPauseMillis=100` `-XX:G1HeapRegionSize=4M` `-XX:G1NewSizePercent`
- **ZGC（JDK11+）**：和 G1 比，ZGC 停顿 <10ms 但吞吐略低

### 16. MVCC ReadView 四字段（懂车帝✅→飞轮科技❌精度不足 ⚠️ P1）

**❌ 错误：** 知道"四个字段"但没准确说出名字（回答用了多次"我记得"）。

**✅ 标准答法（肌肉记忆）：**

```sql
-- ReadView 四个核心字段
m_ids           -- 当前活跃事务 ID 列表（有序数组）
min_trx_id      -- m_ids 中最小的事务 ID
max_trx_id      -- 当前已分配的最大事务 ID + 1
creator_trx_id  -- 创建这个 ReadView 的事务自己的 ID
```

**可见性判断规则（重要）：**
```
比较每行数据的 trx_id（最后修改该行的事务 ID）：

① trx_id == creator_trx_id → 自己修改的 → 可见 ✅
② trx_id < min_trx_id     → 已提交的旧事务 → 可见 ✅
③ trx_id >= max_trx_id    → 未来事务（还未创建）→ 不可见 ❌
④ min_trx_id <= trx_id < max_trx_id：
   - trx_id 在 m_ids 中 → 活跃的未提交事务 → 不可见 ❌
   - trx_id 不在 m_ids 中 → 已提交 → 可见 ✅
```

**🔗 延伸考点：**
- **RC vs RR 的 ReadView 区别**：RC 级别每条语句都创建新 ReadView；RR 级别事务开始时创建，事务期间复用
- **当前读 vs 快照读**：SELECT = 快照读（ReadView）；SELECT FOR UPDATE / UPDATE / DELETE = 当前读（lock in share mode）

### 17. HashMap 2 的幂次方原理（飞轮科技面精度不足 ❌ P1）

**❌ 错误：** 只说"扩容和位运算"，没说出 `hash & (n-1)` 替代取模。

**✅ 标准答法：**

**为什么容量是 2 的幂？三个原因：**

**① 位运算替代取模（性能）：**
```java
// ❌ 取模运算（慢）
int index = hash % n;

// ✅ 位运算（快，前提：n 是 2 的幂）
int index = hash & (n - 1);
// 例：n=16 (10000), n-1=15 (01111), hash & 15 = 取 hash 低4位
```

**② 扩容时元素迁移规律：**
```java
// 旧容量 n，新容量 2n
// 元素要么在旧位置，要么在 旧位置 + n
// 判断：看 hash 的 第 log2(n) 位是 0 还是 1
//   0 → 留在旧位置；1 → 迁移到 旧位置+n
```
不需重新计算每个 key 的 hash，只需判断新增的 bit 位。

**③ 均匀分布：**
- 2 的幂意味着 `n-1` 二进制全为 1（如 16-1=1111）
- `hash & 1111` 会均匀取低4位，减少碰撞

**🔗 延伸考点：**
- **加载因子 0.75**：泊松分布算出的平衡值——时间（减少碰撞）和空间（减少扩容）的 trade-off
- **树化阈值 8**：链表长度 >8 转红黑树；退化阈值 6（留余量避免震荡）；泊松分布证明 8 的概率极低
- **JDK7 头插法 vs JDK8 尾插法**：头插（resize 时死循环）→尾插（避免死循环）

### 18. TCP 拥塞控制——丢包检测方式（腾讯1面只说"丢包减半" ❌ P1）

**❌ 错误：** 只说"丢包减半"，没说出两种丢包检测方式的区别。

**✅ 完整回答：**

**TCP 拥塞控制四部曲：**
```
慢启动（Slow Start）→ 拥塞避免 → 快速重传 → 快速恢复
```

**两种丢包检测方式：**

| 检测方式 | 触发条件 | 响应 | 效果 |
|---------|---------|------|------|
| **超时重传（RTO）** | 发送包后计时器到期未收到 ACK | cwnd 重置为 1，**重新慢启动** | 严重（带宽锐减） |
| **快速重传（Fast Retransmit）** | 收到 **3 个重复 ACK** | cwnd 减半，**进入快速恢复** | 较温和（带宽减半后线性恢复） |

**快速重传+快速恢复流程：**
```bash
① 发送方收到 3 个重复 ACK → 立即重传丢失报文（不等超时）
② cwnd 减半 + ssthresh = cwnd
③ 进入快速恢复：每收到一个重复 ACK，cwnd += 1（等待丢失包 ACK）
④ 收到丢失包的 ACK → cwnd = ssthresh，进入拥塞避免
```

**🔗 延伸考点：**
- **RTO 计算**：`RTO = SRTT + 4 * RTTVAR`（加权移动平均）
- **SACK（Selective ACK）**：告诉发送方哪些包丢了、哪些收到了，避免重传已收到的包
- **BBR（Google）**：基于带宽和 RTT 建模，不把丢包作为拥塞信号，在高带宽高延迟场景优于 CUBIC

### 19. TCP 粘包完整解法（腾讯1面答不完整 ⚠️ P1）

**❌ 错误：** 只说了"头部标记长度"。

**✅ 完整回答：**

**粘包原因：** TCP 是面向字节流的，没有消息边界。多次发送的数据可能粘在一起。

**三种解法：**

| 解法 | 原理 | 适用场景 | 示例 |
|------|------|---------|------|
| **固定长度** | 每个包固定 N 字节，不够补 0 | 协议简单，定长字段 | 二进制协议，每个消息 1024 字节 |
| **分隔符** | 消息末尾加特殊分隔符 | 文本协议 | **HTTP/1.1 的 chunked**：以 \\r\\n 分隔 |
| **长度前缀** | 先传 4 字节 int 标记 body 长度，再传 body | 通用二进制协议 | **主流方式**：4字节int + body数据 |

**HTTP 的粘包处理：**
```
HTTP/1.1：Content-Length（定长body） + chunked transfer encoding（分块传输）
HTTP/2：  Frame 帧（自带 StreamID + Length），一个 TCP 连接多路复用
```

**🔗 延伸考点：**
- **Netty 粘包解码器**：FixedLengthFrameDecoder / DelimiterBasedFrameDecoder / LengthFieldBasedFrameDecoder
- **为什么粘包不是 bug？** 是 TCP 优化（Nagle 算法合并小包），应用层自己处理消息边界

### 20. IO 密集型线程数公式（抖音广告/迅雷面答不出 ❌ P1）

**❌ 错误：** 只说"不断调大线程池观察指标"，没给出公式。

**✅ 完整回答：**

```java
// IO 密集型线程数公式：
// N = CPU核数 / (1 - 阻塞系数)

// 阻塞系数 = IO等待时间 / (IO等待时间 + CPU处理时间)
// 例：HTTP下载等待 10s，CPU 解析 0.1s
// 阻塞系数 = 10 / (10 + 0.1) ≈ 0.99
// N = 16核 / (1 - 0.99) = 1600 线程

// 简化版本（通用经验值）：
// IO 密集型：线程数 = CPU核数 × 2 + 1  （不是精确的，只是个简便估算）
```

**实测方法（比公式更可靠）：**
```
① 从单机小线程数开始（如 20）
② 逐步增加线程数，观察吞吐量变化
③ 找到"吞吐量不再线性增长"的拐点
④ 在这个值上留 20% 余量
⑤ 同时监控 CPU、内存、带宽是否成为新瓶颈
```

**🔗 延伸考点：**
- **带宽是隐藏瓶颈**：多线程并发下载共享同一网卡，带宽打满后加线程不再提速
- **上下文切换成本**：线程超过 CPU 核数后，每个线程获得的时间片减少，切换成本增加

**GZip 文件结构：**

### 25. 可观测性 / 监控响应标准化（多场追问 ⚠️ P2）

**4 个核心维度 + 对应工具：**
```
① 业务监控：QPS、成功率、响应时间（P99/P95/P50）
② 资源监控：CPU/内存/磁盘/网络 IO
③ 组件监控：MQ 消费 Lag、Redis 命中率/内存、DB 慢查询
④ 链路追踪：一次请求跨多个服务的全链路追踪
```

**MQ 消费链路监控（最常用）：**
```
Consumer Lag（消费落后量） → 预警阈值（如 >10000）
线程池活跃度 → 拒绝率 → 是否需要扩容
下载成功率 → 耗时分布（P50/P95）
自动告警 → 积压后自动扩分区/扩消费者
```

**线上问题排查标准流程（P0）：**
```
① 确认影响范围：是全部还是部分？上游还是下游？
② 先止血（回滚/降级/重启）→ 再找根因
③ 定位方法：监控 → 日志 → 线程栈 → DB 慢查询
④ 根因修复 + 改进方案 + 复盘
```

**🔗 延伸考点：**
- **监控三件套**：Prometheus（采集）+ Grafana（展示）+ AlertManager（告警）
- **链路追踪**：OpenTelemetry（统一标准）/ Jaeger / SkyWalking
