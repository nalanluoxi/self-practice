## 二、失误与薄弱点分析

### 2.1 进程崩溃导致消息丢失场景，迟迟没有找到核心解法

**面试官连续追问：** 进程整个崩溃（不是线程崩溃），消息已提交 offset 但线程池还没处理完，怎么保证不丢？

**候选人的问题：**
- 第一反应是"查日志/内存快照"，方向偏向排障而非预防
- 换了多个方案兜圈子（事务消息、新队列、定时扫描），迟迟没有直接答到核心点
- 核心解法其实面试官已经一步步引导到了，但候选人每次接近了又绕开

**核心解法（面试官引导出的）：**
```
方案：先写 Redis，再提交 offset（两步操作，顺序关键）

流程：
1. 消费者拉取消息
2. 写入 Redis：key=URL，value=消息内容，TTL=处理超时上限（如 5 分钟）
3. 提交 Kafka offset（此时才算"已消费"）
4. 投递线程池处理
5. 处理成功后：从 Redis 删除该 key
6. 定时任务：扫描 Redis 中 TTL 快到期但还未删除的 key → 重新投递 MQ 消费

崩溃场景分析：
- 第2步前崩溃（还未写 Redis）→ offset 未提交 → 重启后 MQ 重发 → 安全 ✅
- 第2步写完、第3步提交前崩溃 → Redis 有记录 → 定时任务补偿 ✅
- 第3步提交后、第4步投递前崩溃 → Redis 有记录 → 定时任务补偿 ✅
- 第5步处理完成、删除 Redis 前崩溃 → Redis 残留 → 定时任务重投（幂等去重兜底）✅

关键点：
- Redis 写在 offset 提交之前，保证"有记录才提交"
- 幂等性由原有的 Redis URL 去重（12h）保证，不会真正重复处理
```

**风险（候选人答对了一个）：**
```
- Redis 过期时间设短了 → 链接处理慢（>TTL）→ 记录提前消失 → 丢失
  解法：TTL = max(预期处理时间) × 3，留足余量

- Redis 内存打满触发 maxmemory 淘汰策略 → key 被驱逐
  解法：监控 Redis 内存水位，设置 allkeys-lru 策略下 TTL 过期优先
```

### 2.2 被追问"只写 Redis 再提交有无消息丢失风险"时停顿太久，遗漏 Redis 驱逐场景

**面试官问：** 用 Redis 先记录再提交，还会有别的消息丢失问题吗？

**候选人的问题：**
- 只答了"TTL 设短了链接处理慢导致 key 过期"，是正确的
- 停顿超过 30 秒才说出，节奏慢
- 遗漏了面试官最后总结的 Redis 内存打满 / key 被驱逐场景

**完整风险清单：**
```
1. TTL 设置过短：处理时间超过 TTL → key 提前消失 → 定时任务感知不到 → 丢失
2. Redis 内存打满：触发 maxmemory-policy 淘汰 → key 被驱逐 → 丢失
3. Redis 本身宕机（未持久化）：记录丢失 → 定时任务无法补偿 → 丢失
   解法：Redis 开启 AOF 持久化，或使用主从/哨兵保证高可用
4. 定时任务自身故障：扫描任务停了，积压 key 无法重投
   解法：定时任务健康检查 + 告警
```

### 2.3 算法题细节不清晰（LeetCode 第 3 题 — 无重复字符的最长子串）

**面试官问题：** LeetCode 第 3 题（无重复字符的最长子串）+ 代码风格问题

**候选人的问题：**
- 代码可以运行，但 `Set` 前面少了一个空格，被面试官当作代码风格问题指出
- 说明代码风格习惯不够严谨，格式问题在 review 时容易被扣分

**正确写法（滑动窗口）：**
```java
public int lengthOfLongestSubstring(String s) {
    Set<Character> window = new HashSet<>();
    int left = 0, maxLen = 0;

    for (int right = 0; right < s.length(); right++) {
        char c = s.charAt(right);
        while (window.contains(c)) {
            window.remove(s.charAt(left));
            left++;
        }
        window.add(c);
        maxLen = Math.max(maxLen, right - left + 1);
    }
    return maxLen;
}
```

**代码风格要点：**
```
- 类型声明后空格：Set<Character> window（不是Set<Character>window）
- 变量命名清晰：left/right 比 i/j 更具可读性
- 边界条件：空字符串 "" → 返回 0（上述代码已覆盖）
- 时间复杂度：O(n)，空间复杂度：O(min(m,n))，m 为字符集大小
```

### 2.4 MQ 积压问题场景下的应对思路不够系统

**面试官问：** 如果改成"完整处理完再提交 offset"，MQ 积压会很高，怎么处理？

**候选人的问题：**
- 只说了"投递到新队列做回捞"，方向偏向事后补救
- 没有说到直接降低积压的手段（加消费者、扩分区、降低处理耗时）

**更完整的回答：**
```
积压高的应对策略（分层处理）：

1. 扩容消费能力（治标）
   - 扩分区数（如从 100 → 400），允许更多消费者并发消费
   - 横向扩容消费者机器数量

2. 降低单条处理耗时（治本）
   - 批量提交（每消费 N 条提交一次 offset）减少提交开销
   - 下载超时时间收紧（从 15s 降为 8s），快失败快重试

3. 削峰（针对流量尖峰）
   - 消费者限速（令牌桶），尖峰时主动降速，避免下游被打垮
   - 非核心数据降优先级，高质量站点优先消费

4. 积压告警
   - 监控 consumer lag（消费延迟），超阈值触发告警 + 自动扩容
```
