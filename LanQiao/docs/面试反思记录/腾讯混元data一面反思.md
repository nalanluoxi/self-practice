### 2.2 配置中心动态感知原理——答了"用什么"没说"怎么实现的"

**面试官问：** 规则引擎的配置改变后，你的服务是如何感知并重新加载的？从原理层面说。

**候选人的问题：**
> 「代码中它有一个注解，它就是这个方法，它就会感应到这个配套的话。」——只说了用法，没有说原理。

**面试官引导：** 「你没有现成平台，要自己实现这个能力，怎么做？」

**候选人给出的方案：** Nacos + 定时轮询（每1分钟检查配置变更）——方向对，但没有说出更优的方案。

**更完整的原理回答：**
```
配置变更感知的两种实现：

方案1：轮询（Pull 模式）
  定时任务每隔 N 秒调用配置中心 API，比较版本号/MD5
  缺点：时效性差（最大延迟 = 轮询间隔）

方案2：长轮询（Long Polling，Nacos/Apollo 实际采用的方案）
  客户端发起 HTTP 请求，服务端 hold 住请求（如 30s）
  若在超时前配置变更，立即响应；超时无变更则返回空，客户端重新发起
  优点：近实时（秒级），对服务端无轮询压力
  Nacos 原理：客户端 HTTP 长轮询，服务端用 Netty 异步持有请求，变更时 push

方案3：推送（Push 模式）
  配置中心通过 WebSocket/SSE 主动推送变更给客户端
  优点：实时，缺点：连接管理复杂

实际代码层：
  Spring Cloud Config + @RefreshScope 注解 → 收到 /actuator/refresh 后重新加载 Bean
  Nacos + @NacosValue(autoRefreshed=true) → 监听器自动触发 setValue
```

### 2.3 Spring AOP 和 IoC 混淆

**面试官问：** Spring AOP 是怎么实现的？

**候选人表现：**
> 「这个好像是依赖注入，它会首先在 XML 文件中配置对象...」——把 AOP 和 IoC/DI 完全说混了，面试官指出「你讲的是 IoC 的实现」

**AOP vs IoC 必须清晰区分：**
```
IoC（控制反转）：对象的创建由 Spring 容器控制，而非程序员 new
  DI（依赖注入）：容器将依赖的 Bean 注入到需要的地方
  → 通过 XML 配置 / @Component + @Autowired 实现

AOP（面向切面编程）：在不修改业务代码的前提下，动态织入横切逻辑
  核心概念：
    切点（Pointcut）：在哪些方法上增强（表达式：execution(* com.xxx.*.*(..))）
    通知（Advice）：前置/@Before、后置/@After、环绕/@Around、异常/@AfterThrowing
    切面（Aspect）：切点 + 通知的组合（@Aspect 注解的类）

AOP 实现原理（必须掌握）：
  JDK 动态代理：目标类实现了接口，生成接口的代理实现类（Proxy.newProxyInstance）
  CGLIB：目标类没有接口，生成目标类的子类（继承），方法被重写后加入切面逻辑

  Spring Boot 默认：有接口用 JDK 代理，无接口用 CGLIB
  Spring Boot 2.x 后默认强制使用 CGLIB（proxyTargetClass=true）

典型应用：@Transactional（事务）、@Cacheable（缓存）、@Log（操作日志）
```

### 2.4 多级缓存一致性——删除操作的顺序说反了

**面试官问：** 删除操作时，如何保证多级缓存（本地缓存 Caffeine + Redis + DB）的一致性？

**候选人回答：**
> 「首先去删除数据库中的数据，之后呢再同步到 redis 中」

**这个顺序有问题！先删 DB 再删 Redis，会有以下问题：**
```
错误顺序：先删 DB → 删 Redis
问题：线程A删 DB，线程B读到旧 Redis 缓存，缓存未删时读到脏数据

正确策略（Cache Aside 模式）：
  写操作：先更新 DB，再删除 Redis 缓存
    → 即使删除失败，缓存有 TTL，最终一致
    → 或引入重试机制 / binlog+Canal 异步删除

本地缓存（Caffeine）：
  设置短 TTL（如 5-10s）自动过期，可接受短暂不一致（正确思路 ✅）
  如需强一致：更新 DB 时同时通过本地事件或 MQ 广播失效所有实例的本地缓存

面试官期望的回答：
  先更新 DB → 删 Redis（失败重试 or Canal）→ 本地缓存靠 TTL 自然失效
  这是「最终一致性」的标准实现
```
