## 二、失误与薄弱点分析

### 2.1 向量数据库技术栈不清晰，回答露怯

**面试官追问：** 向量数据库底层跑的是啥？你往里写数据是怎么写的？

**候选人的问题：**
- 只说了"Supabase 上的一个在线向量数据库"，对底层用的是什么（pgvector / Pinecone / Qdrant 等）说不清楚
- 被追问底层时直接"记不太清了"
- 对 SDK 调用方式描述也比较模糊

**更好的回答：**
```
Supabase 内置的向量存储底层是 pgvector（PostgreSQL 扩展）。

写入流程：
1. 文档经 Embedding 模型（如 text-embedding-ada-002 或 Ollama 本地模型）转为向量
2. 通过 Spring AI 提供的 VectorStore 抽象层，调用 Supabase 的 REST API 或 pgvector 客户端
3. 向量连同原始文本、chunkId、knowledgeBaseId 一起存入 vector_store 表

查询流程：
1. 用户问题先做 Embedding，得到查询向量
2. 调用 pgvector 的 <-> 运算符（余弦距离 / L2 距离）做最近邻搜索
3. 返回 Top-K 文档块，传入 LLM 作为上下文

如果让我重新选型，本地开发用 PgVector（轻量易部署），生产环境可以选 Milvus（高并发、分布式）。
```

### 2.2 Embedding 模型选型依据回答空洞

**面试官追问：** 你选择某个具体模型的时候，依据是什么？

**候选人的问题：**
- 停顿很久，最终只说了"当时没有考虑过"
- 补救说的"按专业方向选"停留在理论层面，没有回答实际做了什么

**更好的回答：**
```
选模型时主要考量三个维度：

1. 任务类型匹配
   - 意图分类/短路路由：轻量模型（Qwen2.5-1.5B / 3B），延迟低、成本低
   - RAG 最终回答：参数量大的模型（Qwen2.5-72B / Deepseek），理解深度更好
   - Embedding：中文语义匹配能力，选 bge-large-zh 或 text-embedding-v3

2. 中文能力评估
   - 中文 RAG 场景优先选千问系列（阿里），中文理解和长文本表现稳定
   - 不选纯英文模型（如 Llama 3）做中文意图识别，准确率下降明显

3. 部署成本
   - 本地 Ollama：选 3B-7B 量级，适合 MacBook/普通服务器
   - 云端 API：按 Token 计费，适合高质量回答场景

实际项目中我用的是 Ollama 运行的千问小模型做意图分类，
DashScope（通义）的 text-embedding-v3 做向量化，最终回答用 Qwen2.5-72B。
```

### 2.3 系统设计题（通用 Agent 知识管理系统）回答结构散乱

**面试官问：** 设计一个 C 端个人助理（类似豆包）的知识管理系统，怎么做？

**候选人的问题：**
- 思路有但缺乏系统性，模块之间没有明确的层次关系
- 先说了知识库管理、工具调用、AI 网关，但没有说数据流
- "复用"部分（对话历史中有价值信息沉淀为知识）回答方向正确但细节薄弱
- 没有提到多租户隔离、知识更新等工程问题

**更好的回答框架：**
```
通用 Agent 知识管理系统（C 端个人助理）

一、整体分层架构
  ┌──────────────────────────────────────────┐
  │  用户层：Web / App / 语音入口             │
  ├──────────────────────────────────────────┤
  │  AI 网关：鉴权 + 限流 + 安全过滤（注入/   │
  │           隐私脱敏）+ 模型路由             │
  ├──────────────────────────────────────────┤
  │  Agent 编排层：意图识别 → 工具选择 →       │
  │              知识检索 → 回答生成           │
  ├──────────────────────────────────────────┤
  │  知识层：个人知识库 + 公共知识库（双轨）   │
  ├──────────────────────────────────────────┤
  │  工具层：日历/邮件/文档/搜索等工具 MCP     │
  └──────────────────────────────────────────┘

二、知识管理核心设计
  - 知识来源：用户上传文档 + 对话中自动沉淀 + 工具查询结果
  - 知识入库：文档解析（Tika）→ 分块（512 token + 50 重叠）→ Embedding → 向量库
  - 多租户隔离：每个用户独立 namespace，知识库物理/逻辑隔离
  - 对话沉淀：
    * 闲聊：摘要压缩，保留"曾于某日闲聊"
    * 有价值查询（会议/任务/决策）：完整保留 + 打标签 + 写入个人知识库
    * 定期自动整理：按主题聚类，生成"个人知识图谱"

三、安全与合规
  - 输入检测：Prompt 注入检测、敏感词过滤
  - 输出脱敏：身份证/手机号/银行卡号正则替换
  - 权限隔离：用户 A 的知识库不能被用户 B 检索

四、复用机制（重点）
  - 知识打标：对话中产生的有效信息自动标记（事件/偏好/决策）
  - 主动提醒：检测到与历史知识相关的新提问时，主动关联推送
  - 知识更新：同主题知识冲突时，保留新版本 + 标记旧版本过期
```

### 2.4 项目难点回答时停顿过长、结构模糊

**面试官问：** 你觉得这个项目最大的难点是什么？

**候选人的问题：**
- 停顿约 15 秒才开始回答
- 回答选的是"频度调度策略迭代升级"，方向正确，但陈述从头讲起，没有先点出"难"在哪

**改进：先说难点本质，再说解法**
```
改进结构（先亮难点，再说过程）：

「最大难点是：如何用量化指标客观衡量一个站点的"更新价值"，
  以此驱动差异化抓取频次，而不是凭经验拍脑袋。」

难点1：没有现成的更新频率信号
  → 解法：与调度侧协商，利用留存表（每天投递 vs 实际留存）
         反算留存率，作为更新活跃度代理指标

难点2：留存率对大小站点不公平
  → 解法：引入规模评分（总投递量），与留存率加权合成综合分
         公式：综合分 = 0.5×留存率 + 0.5×(0.5×规模分+0.5×新链率)

难点3：频次调整要避免抖动
  → 解法：降级最多 1 级 / 次，升级不限速，防止站点频繁跳档
```
