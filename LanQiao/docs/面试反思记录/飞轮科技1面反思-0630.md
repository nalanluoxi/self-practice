## 三、答得不好的地方（❌）

### 面试表现层面

1. ❌ **自我介绍无量化数据**：只说"学了 Java 技术栈+美团实习"，没有说任何一条核心成果数据（日新链提升 2000万→3-4亿、GZIP 解析 3.79亿→52.6亿等）。面试官听完没有追问亮点直接开始问细节，说明没有抓住注意力。

2. ❌ **「Hive」发音/表达不当**：面试官听成了"Hill"并反问"Hill 是什么数据库"，候选人答"内部的一个数据库"——Hive 是大数据数仓不是数据库，面试官对大数据不敏感（他熟悉的是 OLAP/ClickHouse/Doris），但候选人也没有把 Hive 的数仓概念讲清楚。

3. ❌ **G1 GC 原理表述有误**：说 G1"引入了分带回收算法"——G1 本身是分代收集器（一直有 Eden/Survivor/Old），不是"引入"。面试官问的是"CMS→G1 为什么改默认"，回答过于简略，没说到 G1 可预测停顿时间（`-XX:MaxGCPauseMillis`）和 CMS 的碎片化问题。

4. ❌ **MVCC 回答零散模糊**：虽然框架对了（版本链+ReadView），但 ReadView 的关键字段没准确说出（m_ids/low_limit_id/up_limit_id/creator_trx_id），回答时用了很多"我记得是"、"我记得有四个字段"这类不确定表述。

5. ❌ **HashMap 2 的幂次方回答不精确**：只说"扩容和位运算"，没有说出核心——`hash & (n-1)` 替代 `hash % n` 位运算优化。面试官顺着追问 75% 负载因子（这个问题回答了），但对 2 的幂次本质原因只说了半句。

6. ❌ **系统改进设计深度不够**：提到 Topic 拆分和规则引擎 AI 化，但说完了就停了，没有深入展开。面试官追问"可观测性"时回答不够具体，只说"有相关指标"，没有说到具体监控项（消费 lag、处理耗时、成功率等）。

7. ❌ **Kafka 误说**：自我介绍和回答中把 Kafka 发音为"卡夫卡"，虽然面试官没指出，但专业度不够。

### 面试策略层面

8. ❌ **可观测性问题被问得非常少**：面试官问"可观测性这块"，只用一句"有相关指标"带过。应主动展示：消费 lag 监控、线程池活跃度、下载成功率、积压告警阈值等——这在简历上是大厂实习生的工程能力体现。

## 五、改进方向

1. **自我介绍带量化**：必须加入"日新链从2000万提升至3-4亿"等核心指标
2. **HashMap 2的幂次方标准答法**：`hash & (n-1)` 替代取模 → 位运算更快 → 扩容时元素要么在原位置要么在 `原位置+oldCap` → 不需要重新hash
3. **G1→CMS 为啥改**：① **停顿可预测**（`-XX:MaxGCPauseMillis`，Region 独立回收）② **CMS 碎片化**（标记-清除产生碎片，大对象连续空间不足时 Full GC）③ G1 **大对象直接进 Humongous Region**
4. **Hive≠数据库**：Hive 是基于 Hadoop 的数仓工具（将 SQL 转为 MR/Spark 任务），不是关系型数据库
5. **MVCC ReadView 四字段标准答法**：`m_ids`（活跃事务 ID 列表）、`min_trx_id`（最小活跃事务 ID）、`max_trx_id`（最大已分配事务 ID+1）、`creator_trx_id`（本事务 ID）
6. **可观测性回答标准化**：消费 lag + 线程池活跃度 + 下载成功率 + 处理耗时分布 + 积压自动告警
7. **发音注意**：Kafka（标准发音 /ˈkæf.kə/），Hive (/haɪv/)
