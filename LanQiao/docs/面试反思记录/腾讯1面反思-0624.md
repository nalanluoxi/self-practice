## 二、失误与薄弱点分析

### 2.1 ❌🔴 CAP 理论——三个字母一个没说对（**全场最严重失分**）

**面试官问：** 「分布式系统一致性的那几个理论清楚吗？像 CAP 还有 BASE。」

**候选人表现：**
> 直接开始说"投票机制、大多数节点认为可靠才写入、选举策略"——面试官打断说"那是具体实现，CAP是一个理论，讲的是一致性系统的三个问题"

**候选人卡壳：** 「一个是可靠性和吞吐能力，还有一个是什么来着……记不太清了」

**CAP 正确答法必须脱口而出：**
```
CAP 是分布式系统的三个基本属性：
  C（Consistency 一致性）：所有节点在同一时刻看到的数据是一致的
  A（Availability 可用性）：每次请求都能获得非错误的响应（但不保证数据是最新的）
  P（Partition Tolerance 分区容错性）：系统间通信中断时，系统仍能正常对外服务

核心定理：分布式系统中 C、A、P 三者最多同时实现两个（CA/CP/AP）
  CA（放弃分区容错性）：传统单机数据库（MySQL 主从不跨机房）
  CP（放弃可用性）：Zookeeper（选举期间不可用）、etcd
  AP（放弃强一致性）：Eureka、DNS、CDN（最终一致性）

BASE 理论是对 AP 的延伸：
  BA（Basically Available 基本可用）——允许降级
  S（Soft State 软状态）——中间状态可接受
  E（Eventually Consistent 最终一致性）——一段时间后数据一致
```

**为什么本场最严重：**
- 候选人全程实习项目涉及分布式系统（Kafka + MQ + Redis集群），CAP理论是分布式最基础的"第一课"
- 面试官问之前还以为候选人"分布式方面有了解"，结果C/A/P三个字母一个都没说对
- 而且面试官已经指出"CAP是理论"后，候选人仍然往"投票机制/选举策略"方向上跑——说明理论知识和工程实践没有建立起关联

### 2.2 ❌🔴 一致性哈希——直接说"忘记了"

**面试官问：** 「一致性哈希有没有清楚，它是要解决什么问题？」

**候选人：** 「这个可能有些忘记了，这部分东西有段时间没有看。」

**正确答法（标准话术）：**
```
一致性哈希要解决的问题：分布式缓存/存储系统中，节点扩缩容时最小化数据迁移。

问题背景：
  传统取模哈希（hash(key) % N）在节点增减时，几乎所有 key 都要重新映射
  → 大量缓存失效 → 数据库被打穿（缓存雪崩）

一致性哈希原理：
  1. 将哈希值空间组织成 0~2^32-1 的虚拟圆环
  2. 服务器节点（IP/名称）hash 后落在这个环上
  3. 数据 key hash 后，顺时针找到第一个节点存放

优点：
  节点增减时，只有相邻节点的数据需要迁移
  例如：新增一个节点，只需将部分数据从原节点移动到新节点
        减少一个节点，该节点数据迁移到顺时针下一个节点

虚拟节点优化：
  物理节点少时，环上分布不均 → 数据倾斜
  每个物理节点映射多个虚拟节点（如 150~200 个）→ 分布均匀
```

**实际业务关联：** 美团的 Redis 集群如果增删节点，Redis Cluster 自身的 slot 迁移机制就是一致性哈希工程化的一个变种。

### 2.3 ❌🔴 进程间通信效率——答"管道"，应为"共享内存"

**面试官问：** 「进程之间通信哪种比较快？」

**候选人：** 「管道。」

**面试官引导：** 「管道的话传输数据量不大，而且只允许父子进程之间传递。」

**候选人：** 犹豫后答不出。

**面试官给出答案：** 「一般是共享内存，两个进程直接访问同一块内存区域。」

**管道 vs 共享内存 vs 其他 IPC 方式：**
```
效率排名：共享内存 > 消息队列 > 管道(FIFO) > Socket > 信号

各方式对比：
  1. 共享内存（最快）：两个进程直接读写同一块物理内存，无需内核态/用户态切换
     shmget/shmat → 直接指针操作
     缺点：需要同步机制（信号量互斥）
  
  2. 消息队列：内核维护消息链表，按类型读取
     比管道灵活（双向、可指定类型），但每次读写需要内核态切换
  
  3. 管道（pipe/FIFO）：半双工，字节流
     匿名管道：父子进程
     命名管道（FIFO）：任意进程（文件系统中可见）
  
  4. Socket：最灵活，可跨机器
  
  5. 信号量/信号：传递信号量/状态，不能传递大量数据
```

**本场核心规律：** 所有"分布式"相关问题全部答不好（CAP、一致性哈希、分布式锁主从同步），说明**分布式基础知识是系统性短板，不是某个知识点的漏洞。**

### 2.4 ❌ 多态概念——重写(override)和重载(overload)混淆

**面试官问：** 「Java 多态的底层实现是什么？」

**候选人初答：** 「多态和继承还有接口有关系……子类继承父类重写父类方法……实现接口……」

**面试官追问：** 「重写具体说一下。」

**候选人改口：** 「继承好像就是方法重写（指 override），重载是同一个方法名参数不同……不对不对……继承、方法重写，啊不是……」
→ 明显乱了，改了几次口才说清楚

**面试官追问本质区别：** 「编译时多态和运行时多态？」

**候选人：** 「底层层面的我记得一个是编译时就已经知道调用哪个方法，一个是在运行时才知道。」

**完整答法：**
```
多态 = 同一个行为具有不同的表现形式，核心是"父类引用指向子类对象"

编译时多态 = 方法重载（Overload）：
  同一个类中，方法名相同、参数列表不同
  编译时根据参数类型/数量确定调用哪个方法
  本质是静态绑定

运行时多态 = 方法重写（Override）：
  子类重写父类方法
  编译时看引用类型（父类），运行时看实际对象类型（子类）
  本质是动态绑定 → 虚方法表（vtable）

底层实现（JVM）：
  invokevirtual 指令
  方法区维护虚方法表（vtable），表结构 = [对象实际类型, 方法指针]
  调用时：从对象头找类元信息 → 查 vtable → 定位到实际方法入口
  final/private/static 方法编译时确定地址（invokespecial/invokestatic）
```

### 2.5 ❌ 算法题 IPv4 校验——边界条件漏了字符判断

**面试官指出两个问题：**
1. 最后一个分支 `>1` 进不去单个数字（如 "1"、"2"）
2. 字符串包含非数值字符（如 "12a"）时没有判断——代码会抛 NumberFormatException

**候选人承认：** 「对这部分没有考虑到，当时没有考虑全。」

**IPv4 校验完整逻辑示例：**
```java
// 每段校验
if (segment.length() > 1 && segment.charAt(0) == '0') return false; // 前导零
for (char c : segment.toCharArray()) {
    if (!Character.isDigit(c)) return false;  // 非数字字符
}
int val = Integer.parseInt(segment);
if (val < 0 || val > 255) return false;
```

### 2.7 ⚠️ TCP 拥塞控制——只说"重试机制"，没有快速重传/超时重传

**面试官追问：** 「怎么检测丢包？发送数据有没有可能出现阻塞？」

**候选人：** 说了慢启动→线性增长→丢包减半的流程，但丢包检测方式没说清楚。

**补充：**
```
TCP 检测丢包的两种方式：
1. 超时重传（RTO）：
  发送一个包后启动计时器，在 RTO 时间内未收到 ACK → 认为丢包，重传
  RTO 动态计算（基于 RTT 采样），超时后会重新慢启动（阈值减半）

2. 快速重传（Fast Retransmit）：
  接收方收到乱序包时，立即回复重复的 ACK（seq=期望收到的序号）
  发送方收到 3 个重复 ACK → 立即重传，不等待超时
  快速重传后进入快速恢复（Fast Recovery），阈值减半但拥塞窗口不降为 1

拥塞控制四部曲：
  慢启动（Slow Start）→ 拥塞避免（Congestion Avoidance）→ 快速重传（FR）→ 快速恢复（FR）
```

### 2.8 ⚠️ 分布式锁主从同步丢失——对 Redlock 不了解

**面试官追问：** 「单机 Redis 挂了，主从同步还没来得及同步，新主晋升后锁丢了怎么办？」

**候选人：** 答了类似 Kafka 的 ISR 同步机制——写入主节点后需等待同步到从节点才返回。

**面试官认可但指出：** 「但是同步是有时延的，会成为瓶颈。」

**更优方案（至少提到以下之一）：**
```
1. Redlock（Redis 官方分布式锁算法）：
   向 N/2+1 个独立 Redis 节点申请加锁
   超过半数加锁成功 + 在锁有效时间内完成 → 加锁成功
   不依赖单个 Redis 主从复制

2. Redisson 看门狗机制已有自动续期（候选人提到了看门狗，但是没和主从丢失关联）

3. 实际生产中降级方案：
   - 锁过期时间设为业务最大执行时间 × 2
   - 结合数据库乐观锁兜底
   - 业务层幂等设计（MQ 去重）
```

### 2.9 ⚠️ TCP 粘包——说了解法但不完整

候选人只说了"头部标记长度"，没有说 Content-Length 和 chunked encoding 两种具体实现。

**完整答法：**
```
TCP 粘包解决方案：
1. 固定长度：每个报文固定大小（如 1024 字节），不足补齐 → 浪费带宽
2. 特殊分隔符：如 HTTP 头用 \r\n\r\n → 需要转义处理
3. 长度前缀（最常用）：头部 N 个字节标记 body 长度
   HTTP/1.1：Content-Length 头部
   二进制协议：4 字节 int 表示 body 长度 + body 数据
4. HTTP/2 解决：引入 Frame 帧概念，每个 Frame 自带 StreamID + Length
```
