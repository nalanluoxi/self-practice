## 二、失误与薄弱点分析

### 2.1 线程池类型选择——没有说明同步队列的风险

**面试官问：** 线程池选了什么队列？为什么？

**候选人问题：**
> 「创建一个线程池，然后是一个同步队列的」——SynchronousQueue 不是有界队列，任务无法缓冲，会直接创建新线程直到 maxPoolSize，之后才拒绝。IO 密集型爬虫选 LinkedBlockingQueue（有界）更合理。

**更好的回答：**
```
爬虫是 IO 密集型，任务高峰期很多，选择：
  队列：LinkedBlockingQueue(capacity)，有界缓冲，平衡并发和内存
  核心/最大线程数：IO 密集型 ≈ CPU * 2~4（大量时间等网络）
  拒绝策略：CallerRunsPolicy（让调用线程自己执行，实现背压，防止 OOM）

SynchronousQueue 适合任务传递场景（Executors.newCachedThreadPool），
不适合高并发爬虫（任务积压会导致线程数暴增）
```

### 2.2 MySQL 联合索引——回表细节不清晰

**面试官追问：** 联合索引 `(a,b,c)`，查 `SELECT a,c WHERE a=? ORDER BY b` 会不会回表？

**候选人问题：** 对回表触发条件表述模糊，没有说清「覆盖索引」和「回表」的判断逻辑。

**判断逻辑：**
```
回表 = 需要查的列不在索引里，必须通过主键再查聚簇索引

SELECT a,c WHERE a=? → 需要 c，(a,b,c) 已包含 c，不回表（覆盖索引）
SELECT * WHERE a=? → 需要所有列，索引不包含所有列，回表
SELECT a,d WHERE a=? → d 不在索引里，回表

ORDER BY b 利用了联合索引有序性，避免额外排序（filesort）
```

### 2.3 Redis 分布式锁——解锁操作说得不够原子

**面试官问：** Redis 分布式锁如何防止误删别人的锁？

**候选人的问题：** 只说了「判断 value 是自己的再删除」，没有说明判断+删除需要原子操作（非原子会有竞态）。

**正确回答：**
```
加锁：SET lockKey uuid NX PX timeout
  - NX: 不存在才设置（原子抢锁）
  - PX: 设置过期时间防死锁
  - value 存 uuid（唯一标识锁持有者）

解锁：Lua 脚本保证原子性
  if redis.call("get", KEYS[1]) == ARGV[1] then
      return redis.call("del", KEYS[1])
  else
      return 0
  end
  - 判断 value==uuid 和 del 必须在同一 Lua 脚本，否则中间被其他线程抢占

锁续期（可选）：watchdog 定时续期，或使用 Redisson
```

### 2.4 Java 线程状态——漏掉 TIMED_WAITING

**面试官问：** Java 线程有哪些状态？

**候选人的问题：** 回答了 NEW/RUNNABLE/BLOCKED/WAITING/TERMINATED，没有区分 WAITING 和 TIMED_WAITING，面试官追问时有些混乱。

**完整6种状态：**
```
NEW          new Thread() 未 start()
RUNNABLE     start() 后，包括运行中和等待 CPU 调度
BLOCKED      synchronized 等待获取锁
WAITING      Object.wait() / Thread.join() / LockSupport.park()，无限等待
TIMED_WAITING Object.wait(timeout) / Thread.sleep(ms) / join(ms)，有超时
TERMINATED   run() 结束

面试高频：
BLOCKED vs WAITING 的区别：
  BLOCKED = 等 synchronized 锁（锁释放后自动变回 RUNNABLE）
  WAITING = 主动放弃 CPU 等待通知（需要 notify/interrupt 才能唤醒）

sleep() vs wait() 的区别：
  sleep() 不释放锁，时间到自动恢复
  wait() 释放锁，需要 notify() 唤醒
```
