## 二、失误与薄弱点分析

### 2.1 线程池参数配置——没有理论支撑

**面试官问：** 线程池核心线程数怎么设置的？

**候选人的问题：**
- 只说了「从 10 调到 30 是经验值」，没有说出 IO 密集型 vs CPU 密集型的区别
- 没有提到调参的观测指标（线程池活跃数/队列积压）

**更好的回答：**
```
爬虫是 IO 密集型场景（大量时间在等网络响应），核心线程数公式：
  核心线程数 = CPU核数 × (1 + IO等待时间/CPU计算时间)
实际做法：初始设较大值（如 CPU×4~8），配合监控（活跃线程数/队列积压），
动态调整到吞吐量饱和、响应时间可接受的平衡点。
队列选有界队列（避免 OOM），拒绝策略用 CallerRunsPolicy（背压生产者）。
```

### 2.2 Linux 命令——完全没有尝试

**面试官问：** 用 Linux 命令对文件某列排序并取 Top 100，怎么写？

**候选人表现：** 「不太记得了」——直接放弃，是明显失分项。

**正确命令：**
```bash
sort -k2 -n -r 文件名 | head -100
# -k2   按第2列排序
# -n    数值排序
# -r    降序
# head  取前N行

# 若需要统计词频后排序：
awk '{print $1}' file | sort | uniq -c | sort -rn | head -100
```

### 2.4 缓存三大问题——命名和定义混淆

**候选人的问题：** 三个概念在叙述中有混淆，出现了「缓存宽度」这样的词。

**三者必须清晰区分：**
```
缓存穿透：查询根本不存在的数据，每次都打到 DB
  解决：布隆过滤器拦截（不存在=一定不存在）；或缓存空值（TTL短）

缓存击穿：某个热点 key 过期瞬间，大量请求同时打到 DB
  解决：互斥锁（只允许一个线程重建缓存）；逻辑过期（后台异步更新）

缓存雪崩：大批 key 同时过期，或 Redis 宕机，大量请求打到 DB
  解决：过期时间加随机值；多级缓存；熔断限流；Redis 集群
```

### 2.5 算法题——最长有效括号 DP（有 Bug）

**候选人的问题：** DP 方向正确，但漏掉了 `dp[j-1]` 的拼接，导致多个样例没跑通。

**正确 DP 思路（关键细节）：**
```java
public int longestValidParentheses(String s) {
    int n = s.length(), max = 0;
    int[] dp = new int[n];
    for (int i = 1; i < n; i++) {
        if (s.charAt(i) == ')') {
            if (s.charAt(i-1) == '(') {
                // case1: ...()
                dp[i] = (i >= 2 ? dp[i-2] : 0) + 2;
            } else if (dp[i-1] > 0) {
                // case2: ...))，找到配对的左括号位置
                int j = i - dp[i-1] - 1;
                if (j >= 0 && s.charAt(j) == '(') {
                    dp[i] = dp[i-1] + 2 + (j > 0 ? dp[j-1] : 0); // 易漏：dp[j-1]
                }
            }
        }
        max = Math.max(max, dp[i]);
    }
    return max;
}
// 最容易遗漏的是：找到配对左括号后，还需要加上 dp[j-1]（j左侧的有效括号长度）
```
