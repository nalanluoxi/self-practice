## 二、失误与薄弱点分析

### 2.1 SynchronousQueue 选型理由没讲清楚——被反复追问 5+ 次

**面试官连续追问：** 为什么选零缓冲同步队列？有缓冲队列不是更好吗？

**候选人的问题：**
- 反复说"无界队列会 OOM，有界队列迟早打满，都会走淘汰策略"
- 面试官听完后说"你这不是矛盾吗？" / "你说了但我没听懂"
- 候选人始终没有说出 **SynchronousQueue 的核心价值：背压控制**
- 候选人最后才绕回到 while 循环背压，但表达已经混乱

**面试官的预期回答（最终引导出来的）：**
```
选 SynchronousQueue 的核心原因：

不需要缓冲，因为背压由 while 循环完成：
- 线程池有空闲 → 立即投递执行
- 线程池全忙 → while sleep(1s) 等待 → 不去 MQ 拉消息

整个背压链：
  MQ 积压（拉不了） ← while 阻塞 ← 线程池满 ← SynchronousQueue 直传

选有缓冲队列的问题：
- 有缓冲队列会掩盖线程池满的信号，while 循环检测不到真实状态
- 会导致消息无限积压在 JVM 内部，最终 OOM
- 而 SynchronousQueue 直接透出"线程满"的信号，让 while 循环感知并停止拉消息
```

**下次遇到此问的答法模板：**
> "选 SynchronousQueue 是为了配合外层 while 循环实现背压控制。SynchronousQueue 不缓冲，当线程池满时提交会立即触发拒绝，while 循环感知到后停止拉消息，实现 MQ 端自然积压。如果换成有界队列，线程池满了任务还是先进队列缓冲，while 循环检测的是活跃线程数，这时候 while 会误判线程池'未满'而继续拉消息，导致 JVM 内部积压 OOM。"

### 2.2 生产者消费者算法题：满时 notify 逻辑有冗余，面试官质疑

**面试官问：** 第 33 行（缓冲区满时也调用了 notifyAll），有必要吗？

**候选人的问题：**
- 解释了"担心消费者进入了 await 没被唤醒"
- 面试官质疑后，候选人说"注释掉也可以的"
- 说明候选人对 wait/notify 的**调用时机**没有内化清楚

**正确理解：**
```java
// 生产者逻辑
synchronized (lock) {
    while (queue.size() == CAPACITY) {
        lock.wait();          // 满了，等待消费者消费
    }
    queue.offer(item);
    lock.notifyAll();         // 通知消费者来消费 ✅ 必要
    // lock.notifyAll() 在 while(满) 里面 ❌ 不必要
    // 原因：此时还没生产，通知消费者没意义，消费者醒来发现队列还是满的会继续 wait
}

// 消费者逻辑
synchronized (lock) {
    while (queue.isEmpty()) {
        lock.wait();          // 空了，等待生产者生产
    }
    queue.poll();
    lock.notifyAll();         // 通知生产者来生产 ✅ 必要
}
```

**核心规则：**
```
生产完 → notifyAll()（唤醒消费者）
消费完 → notifyAll()（唤醒生产者）
等待中（wait 内部）→ 不需要 notifyAll
```

**标准写法（多生产者多消费者）：**
```java
public class BoundedBuffer<T> {
    private final Queue<T> queue = new LinkedList<>();
    private final int capacity;
    private final Object lock = new Object();

    public BoundedBuffer(int capacity) {
        this.capacity = capacity;
    }

    public void produce(T item) throws InterruptedException {
        synchronized (lock) {
            while (queue.size() == capacity) {
                lock.wait();
            }
            queue.offer(item);
            lock.notifyAll(); // 唤醒消费者
        }
    }

    public T consume() throws InterruptedException {
        synchronized (lock) {
            while (queue.isEmpty()) {
                lock.wait();
            }
            T item = queue.poll();
            lock.notifyAll(); // 唤醒生产者
            return item;
        }
    }
}
```

**关键点：**
- 判断条件用 `while` 不用 `if`（防止虚假唤醒）
- `notifyAll` 优于 `notify`（多消费者/生产者场景，避免只唤醒同类线程）
- 满时在 `while(满)` 里加额外 notify 是多余的，反而会干扰逻辑

### 2.3 RAG 项目介绍：面试官追问意图分类细节，有一次停顿较长

**面试官问：** 什么情况下会识别到需要用 RAG？

**候选人的问题：**
- 给出的解释是"情感倾诉/闲聊 → 短路，其他 → 检索"，太笼统
- 没有说出意图树三级结构（领域 → 类目 → 话题）
- 没有说出置信度阈值（0.85）和 fallback 到 unknown 的机制

**完整回答：**
```
意图分类逻辑（IntentClassifier）：

1. 将意图树（三级层次：领域→类目→话题）整理成 Prompt 上下文
2. 调用轻量模型，让 LLM 返回整数 nodeId
3. nodeId = -1 → 闲聊短路，用小模型直接回答
4. nodeId = 其他 → 从意图树中找到对应节点，进行定向检索
5. 置信度 < 0.85 → fallback 到 unknown，走全局向量检索兜底
```

## 五、需要补课的知识点

- [ ] **SynchronousQueue 背压控制**：核心价值=透出"线程满"信号，配合 while 循环实现 MQ 端背压，而有缓冲队列会掩盖这个信号

- [ ] **对话记忆技术细节**：区分 DbBasedChatMemory（PostgreSQL，无 Redis）和假设中的 Redis 热缓存，介绍时不要混淆

## 六、下次遇到类似追问的应对策略

**当被反复追问同一问题时：**
