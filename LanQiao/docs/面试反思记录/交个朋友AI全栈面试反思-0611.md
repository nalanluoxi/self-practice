## 二、多模态抓取场景设计题

### 问题
**面试官问：** 如果要抓取TikTok/Instagram的短视频、评论、点赞等多模态数据，你会怎么做？

### 回答中的不足
1. **思考时间过长（超过30秒）**，且未说明在思考什么，显得反应慢
2. **方案不完整，只覆盖了「爬取执行层」**，没有从全链路角度回答：链接发现→爬取执行→数据存储→清洗处理
3. **对「多模态」的处理没有针对性**：视频≠普通网页，需要讨论：
   - 视频流的下载策略（分片下载、CDN直连 vs 页面解析）
   - 评论翻页/无限滚动的JS渲染处理
   - 视频元数据与媒体文件分离存储
4. **Playwright方案说得不够准**：只说「Playwright应该支持视频抓取」，显得不确定，实际上Playwright本身不直接下载视频流，需要拦截Network请求或配合yt-dlp

### 更完整的回答思路

```
【全链路视角回答框架】

1. 链接发现层
   - TikTok/Instagram 无公开Sitemap，需要通过：
     · 热榜/标签页面解析（Playwright渲染后提取视频URL）
     · API逆向（官方APP的内部API接口）
     · 爬取评论区用户主页形成图谱扩散

2. 执行层（Playwright + 反爬）
   - Playwright用于渲染动态页面、处理无限滚动、获取评论数据
   - 视频文件本身：拦截 Network 请求中的 .m3u8 / .mp4 CDN直链，用下载器另行下载
   - 这两类数据（结构化评论 vs 媒体文件）需要分开处理

3. 存储层
   - 视频媒体文件 → 对象存储（S3/OSS），按 video_id 命名
   - 评论/点赞等结构化数据 → MySQL/MongoDB
   - 视频元数据（时长、分辨率、标签）→ 关系型DB

4. 数据标识
   - 用 video_id 作为主键把三类数据关联起来

5. 规模考虑
   - 视频文件很大，需要异步下载队列 + 限速，不能和网页爬取混在同一线程池
   - 评论翻页可能需要分批次调度，分开任务队列
```

## 三、反爬对抗策略

### 回答质量：较好，但有一个术语错误

**说得好的地方：**
- IP代理池 + 按地区区分国内/国外代理 ✅
- UA池 + 配合代理IP设置对应地区的时区/语言 ✅
- 多浏览器（Chrome + Firefox）轮换 ✅
- 关闭 headless 模式（这里说的"force关闭无图浏览器配置"就是 `headless: false`）✅

**术语表达不准确的地方：**
> 「可以在这配中会设置这一个 force 的话，它会默认把这个无图浏览器的配置去关闭」

- 「无图浏览器」这个说法不规范，准确术语是 **headless 模式**
- 应该说：「Playwright 默认以 headless 模式运行，可以设置 `headless: false` 来模拟真实浏览器，绕过部分反爬检测」

**可以补充但没提到的点：**
- **浏览器指纹伪装**：Canvas 指纹、WebGL 指纹（stealth 插件）
- **行为模拟**：随机鼠标移动、随机滚动、随机延迟，模拟人类行为
- **Cookie池**：维护已登录的 Cookie，绕过需要登录才能访问的内容
- **验证码处理**：接入第三方打码平台，或训练 OCR 模型

## 四、Agent 场景限流设计

### 回答质量：框架正确，但缺少关键细节

**说得对的：**
- 三层限流：总体QPS → 用户等级 → 模型调用层 ✅
- 引入负载均衡降级（打满时切换小模型）✅
- 动态限流：通过信号量 + 线程池水位监测动态调整 ✅

**明显不足：**

1. **没有提到限流算法本身**：面试官说到「三级限流」时，应该主动提到你在美团用的是什么算法（令牌桶/漏桶/滑动窗口），把美团经验和这道题关联起来
2. **动态限流的具体实现没说清楚**：
   - 提到了「信号量」和「线程池水位」，但两个方案混着讲，逻辑不清晰
   - 面试官给了明确场景（凌晨 vs 高峰期），应该给出具体方案：**基于时间规则的预设策略 + 实时水位的动态微调**
3. **没有提到 Redis 在限流中的作用**：分布式限流必然要用 Redis，你有美团项目经验，这里漏掉了

### 更完整的回答

```
【Agent 场景限流设计】

第一层：全局QPS限流（令牌桶，Redis + Lua 脚本保证原子性）
  - 防止流量洪峰打垮系统

第二层：用户级限流（滑动窗口，Redis ZSET，按用户ID隔离）
  - VIP用户：更高的RPM（Requests Per Minute）
  - 普通用户：较低的RPM，超出后返回排队提示
  - 与模型版本绑定：VIP可调GPT-4级，普通用户只能调轻量模型

第三层：模型调用层限流（线程池隔离 + 信号量）
  - 每个模型有独立的线程池，防止一个模型超时拖垮全局
  - 信号量控制并发上限，超出后快速失败或降级

【动态限流】
方案：预设时间规则 + 实时水位微调
  - 预设规则：在配置中心（Apollo/Nacos）配置各时段的基准阈值
    · 低谷期（0:00-8:00）：阈值放宽50%
    · 高峰期（9:00-22:00）：使用基准值
  - 实时微调：定时任务（每15s）采集线程池利用率 + 响应延迟
    · 连续3次采集利用率 > 80%：当前阈值 * 0.8（降速）
    · 连续3次采集利用率 < 30%：当前阈值 * 1.2（放量），不超过上限
```

## 五、RAG 流水线与 Agent 工具调用

### 回答质量：有深度，结构清晰，是本次面试较好的部分

**可以补充的点：**

- Memory 机制（多轮对话上下文管理）
- 工具调用幻觉防控（结合下一问）

### 工具调用幻觉防控

**回答的问题：**
> 只说了「设定工具的入参出参格式」，停留在 Spring AI 框架配置层面，没有给出系统性的工程化方案

**更完整的回答：**

```
【工具调用幻觉防控三板斧】

1. Prompt 层约束
   - 工具描述要精确：名字、用途、参数类型、返回格式写清楚
   - 加入负向描述：「此工具不用于XX场景」
   - 要求模型在调用前输出CoT（思维链），解释为何选择该工具

2. 参数校验层（入口卡口）
   - 工具被调用前，拦截器校验参数是否符合 JSON Schema
   - 类型不匹配/必填项缺失 → 返回错误信息让模型重试，而非抛异常崩溃

3. 结果验证层（出口卡口）
   - 工具执行后，用轻量模型对结果做「相关性校验」
   - 如果工具返回结果与用户问题语义不相关，判定为幻觉调用，触发重试或降级
   - 设置最大重试次数（如3次），防止死循环
```

## 六、Agent Harness 理解

### 回答质量：意思对，但概念模糊，术语不准

**说的内容：** 把 Agent Harness 类比成团队协作——一个 leader 分配任务给多个子 agent 执行。

**问题：**
- **「Harness」不等于「Multi-Agent」**，面试官问的可能是测试框架/评估框架（Harness = 约束/测试套件），但也可能是 Agent 编排框架
- 回答时用了大量类比，缺少具体的技术词汇（Orchestrator、Sub-agent、Tool Call Chain 等）
- 没有结合自己的 Spring AI 项目经验来说

**更好的回答策略：**
先确认面试官的意图：「您说的 Agent Harness 是指 Agent 的编排框架，还是 Agent 的测试评估框架？」然后再作答，避免答非所问。

**如果是编排框架（Orchestration）：**
```
Agent Harness 可以理解为 Agent 的运行时容器和编排框架，它负责：
1. 任务分解（Planner）：把复杂任务拆解成子任务序列
2. 工具注册与路由：管理可调用的工具列表，把 Agent 的意图映射到具体工具
3. 状态管理：维护多步任务的中间状态，支持断点续跑
4. 错误重试和降级：工具调用失败时的兜底策略
典型框架：LangGraph、LlamaIndex Workflow、Spring AI 的 Agent 模块
```
