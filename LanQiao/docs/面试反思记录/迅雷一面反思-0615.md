## 二、失误与薄弱点分析

### 2.1 GZip 元数据位置答错

**面试官问：** GZip 格式里，元数据（Magic Number、压缩方法等）存在哪里？

**候选人的问题：**
- 答成了"在文件尾部"，实际上 Magic Number 在文件头部

**正确回答：**
```
GZip 文件结构（RFC 1952）：
┌─────────────────────────────────────────┐
│ 头部（Header）                           │
│   Magic Number：1F 8B（固定2字节）        │
│   压缩方法：08（DEFLATE）                 │
│   标志位（FLG）：是否含文件名/注释等       │
│   修改时间（MTIME）：4字节               │
│   额外标志（XFL）、OS 字段               │
├─────────────────────────────────────────┤
│ 压缩数据块（DEFLATE 格式）               │
├─────────────────────────────────────────┤
│ 尾部（Trailer）                          │
│   CRC32：4字节校验值                     │
│   ISIZE：原始数据大小（低32位）           │
└─────────────────────────────────────────┘

关键点：
- 元数据（Magic Number、压缩方法）在【文件头部】
- Java GZIPInputStream 会自动解析头部并校验 Magic Number
- 1F 8B 是识别 GZip 格式的标志，不是需要手动处理的字段
```

### 2.2 IO 密集型线程数的量化公式不熟

**面试官问：** IO 密集型任务的线程数怎么定？有没有量化公式？

**候选人的问题：**
- 只说了"CPU 核数 × 2"的经验值，没有给出理论公式
- 没有提到阻塞比例（Blocking Ratio）的概念

**正确回答：**
```
量化公式（Little's Law 推导）：

最优线程数 = CPU 核数 / (1 - 阻塞比例)

其中：
  阻塞比例 = 阻塞等待时间 / (阻塞等待时间 + CPU 计算时间)

举例：
  - 纯 CPU 任务：阻塞比例 ≈ 0，线程数 = CPU 核数
  - 纯 IO 任务（阻塞 90%）：线程数 = CPU 核数 / (1 - 0.9) = CPU 核数 × 10
  - HTTP 请求（阻塞 80%）：线程数 = CPU 核数 / 0.2 = CPU 核数 × 5

实践补充：
  - 公式给的是理论上限，实际还受内存、连接池大小限制
  - 最终值应结合压测拐点确定：固定核心线程数，逐步加压，
    观察 TPS 不再提升或 P99 响应时间开始劣化的拐点即为最优区间
  - 爬虫场景（HTTP IO 密集）经验值：CPU 核数 × 4~8
```

### 2.3 HTTP 请求的 OS 底层内存模型描述不清晰

**面试官问：** 一次 HTTP 响应从网卡到 Java 堆，数据在操作系统层面经过了哪些拷贝？

**候选人的问题：**
- 只说了"内核缓冲区 → 用户空间"，没有描述完整路径和拷贝次数
- 没有提到 DMA、socket 缓冲区等概念

**正确回答：**
```
HTTP 响应数据流转路径（传统 BIO 场景，2次拷贝）：

网卡 → [DMA 拷贝] → 内核 Socket 接收缓冲区（sk_buff）
     → [CPU 拷贝] → 用户空间 JVM 堆（byte[]）

详细步骤：
1. 网卡收到数据包，通过 DMA（直接内存访问）将数据写入
   内核 Socket 接收缓冲区（不占用 CPU）
2. 应用调用 read()/InputStream.read() 系统调用，触发
   内核态 → 用户态切换
3. CPU 将内核 Socket 缓冲区的数据拷贝到 JVM 堆上的 byte[]
4. GZIPInputStream 等包装流在用户态对数据进行解压

零拷贝优化（sendfile / mmap）：
- sendfile：内核直接将文件数据传输到 Socket，绕过用户空间
- mmap：内核缓冲区直接映射到用户空间地址，节省一次拷贝
- Java NIO DirectByteBuffer：分配堆外内存，避免一次额外拷贝

爬虫场景影响：
- 大量并发 HTTP 连接 → Socket 缓冲区占用大量内核内存
- GZip 响应需在用户态解压 → 额外的堆内存压力
- 合理设置 Socket 超时 + 连接数上限，防止 Socket 缓冲区积压
```

### 2.4 链表去重算法无法在 IDEA 中运行

**题目：** 给定有序链表，删除重复元素，只保留出现一次的节点（LeetCode 82，不保留重复元素）

**候选人的问题：**
- 口述逻辑正确，但 IDEA 环境问题导致代码无法运行验证
- 边界 case（头节点重复、连续多个相同值）未完整考虑

**正确写法：**
```java
public ListNode deleteDuplicates(ListNode head) {
    // 哑节点处理头节点可能被删除的情况
    ListNode dummy = new ListNode(0);
    dummy.next = head;
    ListNode prev = dummy;

    while (prev.next != null) {
        ListNode cur = prev.next;
        // 检测是否有重复（cur 与下一个值相同）
        if (cur.next != null && cur.val == cur.next.val) {
            int dupVal = cur.val;
            // 跳过所有值等于 dupVal 的节点
            while (prev.next != null && prev.next.val == dupVal) {
                prev.next = prev.next.next;
            }
            // prev 不移动，继续检查新的 prev.next
        } else {
            prev = prev.next;
        }
    }
    return dummy.next;
}
```

**关键思路：**
```
- 哑节点（dummy）：解决头节点被删除的边界问题
- prev 指针始终指向已确认保留的最后一个节点
- 发现重复时：记录重复值 dupVal，循环跳过所有相同值节点
- 未发现重复时：prev 向后移动一步
- 时间复杂度：O(n)，空间复杂度：O(1)

变种：LeetCode 83（保留一个重复元素）
  cur.next = cur.next.next  // 直接跳过下一个重复节点即可
```
