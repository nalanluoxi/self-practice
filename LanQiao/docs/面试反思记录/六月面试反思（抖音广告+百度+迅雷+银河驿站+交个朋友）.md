## 四、银河驿站 一面 · 2026-06-15（招聘AI应用）

### 基本信息
- 公司/岗位：银河驿站，Java后端（招聘求职AI应用）
- 面试日期：2026年6月15日，16:00
- 考察重点：Kafka深度（offset提交/消息丢失/分区扩容）、Redis去重、算法题（LeetCode 3最长无重复子串）

### 问题回答分析

| 问题 | 候选人回答质量 | 问题点 | 参考回答要点 |
|------|-------------|--------|------------|
| Kafka offset何时提交 | ⚠️一般 | 说了手动commit，但没说清楚时机（处理完后提交） | 标准：处理完业务逻辑后再调用commitSync()/commitAsync()，保证at-least-once；不能处理前提交（会丢消息）；不能批量处理后再一起提交（中途崩溃会重复消费） |
| 进程崩溃后如何保证消息不丢 | ❌差 | 思路卡顿，没能说出"先写Redis再提交offset"的标准模式，需要面试官引导很久 | **P0级标准答案**：①处理消息→②幂等写入Redis（或DB）→③commit offset；崩溃重启后会重消费，但因为有幂等保证不会双写。反过来不能先commit再写业务，否则崩溃后消息丢失 |
| Redis如何做消息去重 | ✅好 | 说了Redis Set存储已处理messageId，有效期TTL | 正确，可补充：key设计 consumed:{topic}:{partition}:{offset}，TTL建议24h（消息最大可能重试周期） |
| Kafka消费者分区扩容后如何重新分配 | ⚠️一般 | 知道rebalance，但没说清楚分区分配策略 | 扩容触发rebalance：Range策略（按范围顺序分配）/ RoundRobin策略（轮询） / Sticky策略（尽量保持原有分配，减少移动）；分区扩容后只能新增分配给新消费者，不会改变已有分区的分配 |
| 算法题（最长无重复子串LeetCode 3） | ✅好 | 滑动窗口，双指针+HashMap，解题思路和实现基本正确 | 正确，标准解法：left/right双指针 + HashMap记录字符最后出现位置 |

### 亮点表现
- 算法题LeetCode 3解法完整，展示了滑动窗口的掌握
- Redis去重方案有实战落地思考

### 核心薄弱点
- **Kafka消息可靠性链路**：这是最大薄弱点！"先写业务再commit offset"这个顺序被引导了很久才说出来，说明没有真正内化
- **Kafka分区扩容分配策略**：三种分配器（Range/RoundRobin/Sticky）不熟

### 面试官考察意图
- 深度考察Kafka→招聘AI应用有大量Kafka使用，招聘事件流、简历处理队列等
- 专门追问进程崩溃场景→考察候选人对消息中间件的"边界情况"思考

### 改进建议
1. **Kafka消息可靠性必背三步**：① 消费消息 → ② 业务处理（幂等写DB/Redis） → ③ 手动commit offset；顺序不能错
2. **三种分区分配策略**：Range（可能不均）/ RoundRobin（均衡）/ Sticky（减少rebalance）
3. **幂等消费设计**：业务key去重（如订单ID）/ Redis SET NX / DB unique constraint，三种方案要能脱口而出

### 给下一场面试的建议
1. **Kafka问题必答完整版**：生产者ack=-1 + 消费者手动commit + 幂等消费，缺一不可
2. **每道技术问题加一句业务价值**：让面试官感受到你不只是技术执行者
3. **算法题每周30题**：重点刷：字符串（滑动窗口）、链表（双指针）、树（DFS/BFS）、DP（状态转移）
4. **小红书/抖音这类数据平台岗位**：会重点考察大数据处理、分布式存储，提前准备Kafka/Flink相关场景
