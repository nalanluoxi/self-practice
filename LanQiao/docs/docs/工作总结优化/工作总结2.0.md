项目一：Sitemap 新链接发现系统

LLM 训练语料爬取依赖一个持续扩充的链接库（LinkBase），其 URL 来源有两路：一路从已抓取网页中提取外链，另一路通过 Sitemap 协议主动发现。本系统负责后者——依据 robots.txt 协议，从全球站点的 `robots.txt` 中解析出 Sitemap 声明地址，递归下载并解析 `sitemap.xml`（含 Sitemap Index 多级嵌套），从中提取大量结构化 URL 写入 LinkBase，为下游抓取任务补充丰富的新链接来源。整套链路基于 Mafka 消息队列驱动，独立维护。

【项目总结】面对 LLM 训练语料爬取对海量新链接的持续需求，负责对 Sitemap 新链接发现系统进行全面治理与升级。系统接手时日发现量仅 2~3 亿，消息持续积压，垃圾站点混入严重，.gz 格式 sitemap 全量丢弃。为此，推进了六项系统性改进：将串行消费架构重构为异步并行线程池模型，构建三级纵深限流体系，自研自适应限流器感知线程池负载，补充 GZIP 压缩 sitemap 解析能力，引入 DSL 规则引擎治理垃圾站点，并增加过期消息时效性过滤。最终将集群小时处理量提升2.5 万→96 万，日新链接发现量峰值突破 200亿，高质量站点占比从 4.1% 提升至 11.9%，系统稳定性与链接质量均大幅改善。

工作点 1：多线程并发架构重构

原架构在 Mafka 回调线程中同步执行 download 业务逻辑，单线程串行消费导致处理速率仅 1.6~2.5 万条/小时，消息持续积压，无法满足链接发现规模诉求。为解决吞吐瓶颈，将消费模型重构为回调线程 + 独立业务线程池的异步并行架构：以 `@PostConstruct` 初始化 `ThreadPoolExecutor`，使用 `SynchronousQueue` 零容量队列实现背压，线程池满时外层 `synchronized + while` 自旋等待并配合超时重投 MQ 防止消息丢失；线程数通过 MDP 配置中心动态下发，`@MdpConfigListener` 支持不停机热更新；同步协调业务侧 Mafka 分区数从 200 扩容至 400 消除分区瓶颈。最终集群小时处理量从 2.5 万提升至 96 万，日新链接发现量从 2~3 亿提升至 10~14 亿（峰值 75 亿），集群 QPS 提升 16 倍。

工作点 2：三级纵深限流体系建设

系统无限流保护时，大站 URL 数量远超小站形成挤兑，加之黑名单/去重命中的无效请求大量消耗限流配额，导致优质小站有效处理率极低。为此构建三级纵深限流体系：基于 Rhino OneLimiter 分别在集群层（`sitemap_cluster_qps_limit`）、单机层（`sitemap_limit_single_node`）、站点层（`sitemap_limit`，以 `assignedDomain` 为 uuid 独立计数）三个粒度实施管控；同时在限流前置入拦截链，依次执行作弊站点正则过滤、黑名单域名/URL 后缀过滤、二级黑名单 prefix 过滤、Redis KV 去重，最大限度避免浪费限流配额；被限流请求通过 `sitemapPublishService.sendRequest()` 重投 MQ 确保不丢消息。最终实现全天均匀产出，大站挤兑小站问题基本解决。

工作点 3：自定义本地自适应限流器

集群与单机两层限流为比例过滤，大站流量占比依然偏高；同时固定阈值无法感知线程池实时负载，线程池利用率不足导致并发能力持续浪费。为此在 `LimiteUtils` 中自研 `CounterRateLimiter`：以 `ConcurrentSkipListMap<Long, Long>` 实现滑动窗口计数，每个顶级域独享一个限流器实例存入 `ConcurrentHashMap`，守护线程定期清理不活跃桶防止内存泄漏；`SitemapRequestConsumer.setup()` 启动后台采样线程，每秒读取 `EXECUTOR.getActiveCount()` 与 `corePoolSize`，连续 3 次低于 80% 则放宽单站配额（`LIMITE_COUNT++`），连续 3 次超过 80% 则收紧（`LIMITE_COUNT--`），上限由 MDP 热更新控制。最终英文留存量从 2000 万增长至 1.2 亿，1000 万站点发现任务处理时长缩短至 3~4 小时，峰值集群 QPS 达 1417+。

工作点 4：GZIP 压缩 Sitemap 解析

约 4% 的 sitemap 流量（日均 400 万+）为 `.gz` 格式，原链路因缺乏解压能力直接丢弃，导致大量新链接漏发现。为此在 `CompressedUtil` 中补充 GZIP 识别与解压能力：`isValid()` 通过 URL 路径扩展名嗅探自动识别压缩 sitemap（排除 `tar.gz`），`decompressGzip()` 以 `GZIPInputStream` 包装原始字节流分块读取并 UTF-8 解码后直接交给原有 XML 解析器，最小化改动面。最终日新链接发现量峰值从 3.79 亿提升至 52.6 亿，提升约 14 倍。

工作点 5：DSL 规则引擎治理垃圾/作弊站点

垃圾站点 URL 持续混入处理管道，而规则更新依赖代码发布，响应周期长，导致有效资源被大量消耗。为此基于 MDP 配置中心构建动态规则引擎：`@MdpConfig` 接收正则字符串集合，`@PostConstruct` 预编译缓存为 `HashSet<Pattern>` 避免重复编译；`@MdpConfigListener` 监听配置变更后秒级重新编译生效，无需重启；拦截逻辑前置于 Redis 去重和限流之前，以最低成本优先拦截。最终日均拦截 4~5 亿条请求，规则生效延时从分钟级压缩至秒级，有效拦截 90% 垃圾站点，抽样高质量站点率从 4.1% 提升至 11.9%。

工作点 6：过期消息时效性过滤

历史积压消息重新消费时，已过时的调度批次 URL 被无意义处理，既浪费计算资源又污染发现结果。为此在 `SitemapRequest.ext` 字段中携带 `dispatchTs` 和 `batchId`，消费时解析 ext 计算消息延迟 `lagMs`，超过可配阈值（默认 48h，MDP 热更新）的消息直接丢弃并打 CAT 漏斗打点 `sitemap.funnel.stale`，实现低成本的时效性兜底过滤。

项目二：HTML 数据合成链路（截图抓取服务）

为训练 Coding 模型"看图写代码"能力，需要大规模采集真实网页的视觉快照与完整源码作为训练对齐数据——即给定网页截图，模型需还原对应 HTML/CSS/JS 代码。本系统独立主导从零搭建，负责批量抓取含交互按钮、动态组件的真实网页，产出截图（多视口/多 DPR）+ HTML 快照 + 完整静态资源包（JS/CSS/字体/图片），写入 S3 并通过结果 MQ 通知下游，为 Coding 模型提供高质量的图文对齐训练数据。技术栈：Playwright + Mafka + S3 + Java 多线程。整体链路：MQ 消费 → 前置过滤 → 线程池调度 → Playwright 渲染抓取 → 资源补全 → S3 上传 → 结果 MQ 发送。

【项目总结】面对 Coding 模型训练对大规模高质量图文对齐数据的迫切需求，独立主导从零设计并落地 HTML 数据合成链路。系统需同时解决高并发稳定抓取、离线 HTML 资源完整性、内存峰值控制三大核心挑战。通过构建三层解耦架构（消费层/调度层/执行层）、ThreadLocal Browser 实例复用与定时重建、双线程池隔离抓取与补全，并逐一攻克字体懒加载缺失、图片 IntersectionObserver 触发缺失、JS/CSS onResponse 遗漏、styled-components 动态样式丢失四类资源完整性难题。最终实现字体与 CSS 缺失问题基本解决，图片可用率约 70%，内存峰值显著降低，下游 S3 扫描瓶颈消除，为模型训练提供了可规模化生产的高质量数据来源。

项目整体设计：

消费层（ScreenshotRequestConsumer）：Mafka 消费者，黑名单过滤 + URL 合法性校验后，将请求投入独立 ThreadPoolExecutor（SynchronousQueue + 自旋背压），与 Sitemap 线程池完全隔离，互不影响

调度层（ScreenshotService）：业务编排，代理选取（按域名路由海外/国内代理线路）→ 生成 S3 路径前缀 → 提交 ScreenshotPlaywrightService 异步执行 → 收集结果 → 发送结果 MQ

执行层（ScreenshotPlaywrightService）：双层线程池（DOWNLOAD_TASK_POOL + SUPPLEMENT_POOL）隔离主抓取与资源补全；ThreadLocal<PlaywrightDownLoader> 每线程独享 Browser 实例，实例存活 5 min 后自动重建防内存泄漏；按代理线路绑定不同 Chrome UA（UA_137 海外普通 / UA_136 海外高级 / UA_130 国内）

① 内存峰值高

onResponse 取字节后立即上传 S3 置 null 释放，内存峰值大幅降低；新增 SUPPLEMENT_POOL 与 DOWNLOAD_TASK_POOL 完全隔离，防止内部提交死锁。

② 字体缺失导致离线 HTML 渲染乱码

Chrome 懒加载机制下未渲染区域的字体不触发请求，onResponse 无法捕获 @font-face 中的备选字体。

→ supplementFontsFromCss() 用 helger/ph-css 解析所有 CSS 中 @font-face { src: url(...) } 声明，主动补充下载；以 collectedFontUrls Set 去重，避免与 onResponse 已捕获的字体重复下载。

③ 懒加载图片大量缺失

IntersectionObserver 图片只有进入视口才触发请求，页面不滚动则仅首屏图片被 onResponse 捕获。

→ Phase1 加入分步滚动：逐视口 window.scrollTo + 300ms 等待触发全量懒加载；supplementImagesFromHtml() 用 Jsoup 解析 srcset 所有尺寸变体 + data-src，与 collectedImageUrls 取差集兜底仍遗漏的图片。

④ JS/CSS 被 onResponse 遗漏

部分资源因浏览器缓存（304）或跨域限制 onResponse 未捕获响应体。

→ supplementScriptsAndStylesFromHtml() 解析 HTML 中 <script src> / <link rel=stylesheet>，与 collectedJsCssUrls 取差集主动补充。

⑤ styled-components 动态样式序列化丢失

styled-components 通过 el.sheet.insertRule() 写 CSSOM 不写 textContent，page.content() 序列化仅取 DOM，动态注入样式全部丢失。

→ 注入 JS 将 data-styled style 标签的 cssRules 逐条写回 el.textContent，再序列化，确保动态样式落入离线 HTML。

结果：字体缺失基本解决；CSS 缺失基本解决；图片可用率约 70%；下游 S3 扫描瓶颈消除；内存峰值显著降低。
