# 截图抓取模块开发规划

> 文档创建时间：2026-05-11
> 状态：规划中

---

## 一、背景与目标

基于 `test-project` 中 `ExtractClickableElementsV3` 已验证的 Playwright 截图 + 可交互元素提取能力，参照 `llm-spider-crawler` 中 `SitemapRequestConsumer` 的消费框架，在 `llm-crawler-server` 模块内新建一个 **截图抓取模块（Screenshot Crawler Module）**。

核心能力：
- 从 Mafka 消息队列消费 URL 任务
- 使用 Playwright 无头浏览器完成页面截图和可交互元素提取
- 将截图、HTML、元素 JSON 上传 S3 长期存储
- 抓取结果发送 Mafka，由 Spark 任务同步到 Hive 表持久化
- Python 定时任务以 URL 为输入调用打分模型，将页面质量分数回写到 Hive 表字段

---

## 二、整体数据流

```
                      ┌─────────────────────────────────────────┐
                      │           抓取主链路（Java）              │
                      └─────────────────────────────────────────┘

Mafka (URL任务)
      │
      ▼
ScreenshotRequestConsumer
  ├─ 前置过滤（黑名单 / Redis去重 / 限流）
  └─ ThreadPoolExecutor
            │
            ▼
     ScreenshotService
  ├─ 阶段一：HTML 资源抓取
  └─ 阶段二：截图 + 元素提取
            │
     ┌──────┴──────────┐
     ▼                 ▼
  S3 存储           Mafka (结果MQ)
  (PNG/HTML/            │
   elements.json)       ▼
                   Spark 同步任务
                        │
                        ▼
                   Hive 表（持久化）
                   page_quality_score = NULL（待打分）

                      ┌─────────────────────────────────────────┐
                      │        URL 打分链路（Python，异步）        │
                      └─────────────────────────────────────────┘

                   Hive 表（score=NULL 的记录）
                        │  仅读取 url 字段
                        ▼
                   Python 定时任务
                   ├─ 批量读取待打分 URL
                   ├─ 调用打分模型（输入：URL）
                   └─ 回写 page_quality_score 字段
                        │
                        ▼
                   Hive 表（score 已填写，下游按阈值决策）
```

## 三、开发步骤

### Phase 1 — 抓取核心（Java）

**Step 1：引入 Playwright 依赖**

在 `llm-crawler-server/pom.xml` 添加：

```xml
<dependency>
    <groupId>com.microsoft.playwright</groupId>
    <artifactId>playwright</artifactId>
    <version>1.44.0</version>
</dependency>
```

> 注意：V3 使用了 Text Block（Java 15+）和 Pattern Matching（Java 16+），需提前确认 MDP 容器 JDK 版本。若版本不满足，需将相关语法降级改写。

---

**Step 2：定义数据模型**

| 类 | 说明 |
|----|------|
| `ScreenshotRequest` | 参照 `SitemapRequest`，含 `url`、`domain`、`priority`、`ext`、`retryTimes` |
| `ScreenshotResultMessage` | 发往结果 MQ 的消息体（见下方字段说明） |
| `ClickableElement` | 从 test-project 迁移，描述单个可交互元素 |
| `HtmlCrawlResult` | 阶段一返回值，含 httpCode、success、resourceCount 等 |

`ScreenshotResultMessage` 核心字段：

```
url          原始 URL
domain       域名
http_code    HTTP 状态码
status       SUCCESS / FAIL / SKIP
s3_dir_key   S3 目录前缀（该 URL 所有文件均在此目录下）
batch_id     批次 ID
error_reason 失败原因（失败时填写）
```

---

**Step 3：新建 `ScreenshotPlaywrightService`，不复用 `PlaywrightService`**

**为什么不直接复用 `PlaywrightService`？**

`PlaywrightService` 的 Browser 实例通过 ThreadLocal 绑定在线程上，截图任务若提交到同一线程池，会复用 Sitemap 任务的 Browser 实例，两类任务的 Page 在同一个 Browser 里并发执行，互相干扰，影响 Sitemap 抓取稳定性。

**方案：仿照 `PlaywrightService` 的模式，新建 `ScreenshotPlaywrightService`**，两套完全隔离：

```
PlaywrightService（已有，Sitemap 用）        ScreenshotPlaywrightService（新增，截图用）
────────────────────────────────────        ──────────────────────────────────────────
SPIDER_TASK_POOL（4个线程池）               SCREENSHOT_TASK_POOL（1个独立线程池）
PLAYWRIGHT_INSTANCES_137/136/130/FF         SCREENSHOT_INSTANCES（1个 ThreadLocal）
crawlPage()                                 crawlScreenshot()
instanceMap（static，Browser生命周期）      复用同一个 static instanceMap + 清理线程
```

`ScreenshotPlaywrightService` 精简实现，只保留截图场景需要的部分：
- **独立线程池** `SCREENSHOT_TASK_POOL`，线程数由 MdpConfig `screenshot_thread_num` 控制，支持热更新，与 Sitemap 线程池完全隔离
- **独立 ThreadLocal** `SCREENSHOT_INSTANCES`，每个截图线程绑定独立的 `PlaywrightDownLoader` 实例（Chromium，不需要 Firefox）
- **复用** `PlaywrightDownLoader` 类本身（Browser 封装、UA、`close()`）、`PlaywrightService.instanceMap`（Browser 生命周期管理）、`PlaywrightService.runClearThread`（清理线程，static 共享，不重复启动）
- **复用** `PlaywrightService` 的代理选择逻辑（`proxySetService.getJsNoCacheProxy()`），注入到截图的 `BrowserContext`

**`crawlScreenshot()` 方法**，核心逻辑来自 V3：

```
输入：url、proxyItem、timeout、viewportWidth、viewportHeight、deviceScaleFactor
输出：ScreenshotCrawlResult（含 httpCode、status、htmlBytes、resourcesMap、
                             screenshotBytes、annotatedBytes、elementsJson）

内部流程：
  获取当前线程的 PlaywrightDownLoader（ThreadLocal，Browser 已就绪）
  阶段一：新建 Context + Page → navigate → onResponse 收集 JS/CSS/图片 → 获取 HTML
  阶段二：新建 Context + Page → navigate → scrollTo → screenshot → JS 注入提取元素 → drawAnnotated
  两个阶段复用同一个 Browser 实例（ThreadLocal 管理，无需重复创建）
```

**改造点（对比 V3）**：
- 去除所有本地磁盘写入（`Files.write`），改为内存 `byte[]` / `Map<String, byte[]>` 返回，由 `ScreenshotService` 调用 `S3Service` 上传
- 移除 `detectPageAnomaly` 逻辑（已确认无效，整体取消）
- 移除 `BrowserHolder` / `getOrCreateBrowser`，由 `ScreenshotPlaywrightService` 的 ThreadLocal 管理

---

**Step 4：新建 `ScreenshotService`**

编排完整流程：

```
1. 调用 ScreenshotPlaywrightService.crawlScreenshot() → 得到 ScreenshotCrawlResult
2. 调用 S3Service.upload() 将各类文件上传到 s3_dir_key 目录下
3. 构建 ScreenshotResultMessage 发送结果 MQ
```

复用 `SitemapService` 已有能力：
- 内存阈值检查（`exceedMaxInProcessMem`）

---

**Step 5：新建 `ScreenshotRequestConsumer`**

完全参照 `SitemapRequestConsumer` 结构：

| 功能 | 实现方式 |
|------|---------|
| MQ 消费 | `@MdpMafkaMsgReceive` |
| 消息反序列化 | `JackSonUtils.fromJson` |
| 过期消息丢弃 | 解析 `ext.dispatchTs`，超过阈值小时数丢弃 |
| URL 格式校验 | `new URL(request.getUrl())` |
| 黑名单过滤 | MdpConfig `screenshot_black_domain_list` |
| Redis 去重 | Key: `llm_screenshot_url:{url}`，TTL 7 天 |
| 限流 | 复用 `LimiteUtils` + QPS 限流逻辑 |
| 线程池 | `ThreadPoolExecutor` + `SynchronousQueue`，满时重投 MQ |
| 重试上限 | `retryTimes >= 2` 时放弃 |
| 线程数动态调整 | MdpConfig `screenshot_thread_num` + `@MdpConfigListener` |

### Phase 2 — 数据同步（Spark）

**Step 6：Hive 表设计**

```sql
CREATE TABLE llm_screenshot_result (
    url                 STRING    COMMENT '原始 URL',
    domain              STRING    COMMENT '域名',
    http_code           INT       COMMENT 'HTTP 状态码',
    status              STRING    COMMENT 'SUCCESS / FAIL / SKIP',
    s3_dir_key          STRING    COMMENT 'S3 目录前缀，该 URL 所有文件均在此目录下',
    batch_id            STRING    COMMENT '批次 ID',
    error_reason        STRING    COMMENT '失败原因',
    page_quality_score  DOUBLE    COMMENT '页面质量分数（NULL=待打分，0~1，越高越优质）',
    score_time          STRING    COMMENT '打分时间'
)
PARTITIONED BY (dt STRING COMMENT '日期分区 yyyyMMdd')
STORED AS ORC;
```

> **字段设计说明**：
>
> **为什么用一个 `s3_dir_key` 而非多个路径字段？**
> 每个 URL 在 S3 下对应一个完整目录，结构固定（见 Step 8），内含 `index.html`、`assets/`、`viewport_0/screenshot.png` 等多个文件。用目录前缀一个字段即可寻址所有内容，增减文件类型也无需改表结构，更易维护。
>
> **为什么不存 `element_count`、`viewport_w/h`、`crawl_duration_ms`、`crawl_time`、`score_time`？**
> - `element_count`、`viewport_w/h`：这些是抓取过程的运行时参数，已完整记录在 S3 目录的 `viewport_0/clickable_elements.json` 中，Hive 表不需要冗余存储
> - `crawl_duration_ms`：抓取耗时属于监控指标，应由 CAT 上报和看板展示，不属于业务数据，无需落表
> - `crawl_time`、`score_time`：时间信息通过 Hive 分区字段 `dt` 已覆盖日粒度查询需求；若需精确时间可从 S3 文件的 LastModified 获取，不必在 Hive 冗余一列
>
> **死链处理**：`status=FAIL` + http_code 4xx/5xx 的记录，Spark 写入时 `page_quality_score` 直接置 0，无需打分模型介入。
>
> **下游使用**：分数阈值由下游使用方自行定义，本模块不硬编码。

---

**Step 7：Spark 同步任务**

新建 Spark Streaming 或定时批量任务（参照 `llm-spider-jobs` 模式）：

- 消费结果 MQ（与 `FrequencyDeliverySitemapJob` 类似的消费方式）
- 数据清洗：去重（同一 URL 保留最新一条）、字段校验
- 按 `dt` 分区写入 Hive 表 `llm_screenshot_result`
- `page_quality_score` 字段：死链（`status=FAIL` + http_code 4xx/5xx）写入 0，其余写入 NULL（待打分）
- `s3_dir_key` 直接从 MQ 消息中透传，Spark 不做 S3 操作

---

**Step 8：S3 目录结构规范**

每个 URL 对应 S3 下一个独立目录，目录名（`dir_name`）由算法生成，规则如下：

```
dir_name = urlToSafeName(url) 截取前 60 字符 + "_" + MD5(url) 前 8 位

示例：
  URL:      https://1library.net/document/q0permlz/...
  dir_name: 1library_net_document_q0permlz_..._a3f2b1c4
```

S3 完整目录前缀（即 `s3_dir_key`）：

```
screenshot/{yyyyMMdd}/{dir_name}/
```

该目录下的固定文件结构（与 V3 本地输出保持一致）：

```
screenshot/{yyyyMMdd}/{dir_name}/
├── index.html                          ← 页面原始 HTML
├── resources.tsv                       ← 子资源清单（url/type/status）
├── assets/                             ← 页面子资源
│   ├── *.js
│   ├── *.css
│   └── *.png / *.jpg / ...
└── viewport_0/                         ← 第一个视口（numViewports=1 时只有 viewport_0）
    ├── screenshot.png                  ← 原始截图
    ├── annotated_screenshot.png        ← 标注了可交互元素框的截图
    └── clickable_elements.json         ← 可交互元素列表（含 bbox、tag、text 等）
```

> Hive 表只存 `s3_dir_key`（即 `screenshot/{yyyyMMdd}/{dir_name}/`），下游通过拼接固定文件名即可访问任意文件，无需在表中单独记录每个文件路径。

### Phase 3 — URL 打分（Python）

**Step 9：Python 定时任务设计**

```
任务名：screenshot_quality_scorer
触发方式：定时调度（建议每天运行一次，处理前一天新增数据）

执行流程：
1. 查询 Hive：SELECT url, dt FROM llm_screenshot_result
             WHERE dt = '${yesterday}'
               AND page_quality_score IS NULL
               AND status = 'SUCCESS'

2. 批量调用打分模型：
   - 输入：URL 列表（不需要截图或 HTML，模型仅依赖 URL）
   - 输出：每条 URL 对应的质量分数（0~1 的浮点数）
   - 建议每批 100~500 条，控制单次请求量

3. 回写 Hive：
   UPDATE page_quality_score = {score}
          score_time         = '{now}'
   WHERE url = '{url}' AND dt = '{dt}'

4. 统计本次打分结果（分数分布、覆盖率），输出日志
```

**死链不入打分模型**：`status=FAIL` 且 `http_code` 为 4xx/5xx 的记录已在 Spark 写入时置为 0，Python 任务查询时 `score IS NULL` 条件自动跳过。

**注意**：分数的含义和阈值由下游使用方（如数据消费团队）自行定义，本任务只负责打分和回写，不做筛选或过滤决策。

## 六、风险与应对

| 风险 | 影响 | 应对措施 |
|------|------|---------|
| Playwright 与 MDP 容器化环境冲突 | 高 | 提前验证 headless Chrome 系统依赖（`--no-sandbox`）；必要时在 Dockerfile 中补充 chromium 依赖 |
| Browser 进程内存占用高 | 高 | 每个线程独立一个 Browser；空闲 2 分钟自动回收；`screenshot_thread_num` 控制并发上限 |
| Java 版本不兼容（Text Block / Pattern Matching） | 中 | 提前确认 MDP 容器 JDK 版本，不满足则改写为兼容语法 |
| 测试阶段 URL 质量差，死链率高 | 中 | 以"有效 URL 成功率"为核心指标；死链通过 http_code 识别，不污染成功率统计 |
| 结果 MQ 发送失败导致 Hive 数据缺失 | 中 | MQ 发送失败记录到 CAT；可补充本地落盘兜底或重试机制 |
| 打分模型调用量大导致成本或限流问题 | 中 | 死链提前过滤不入模型；批量调用控制每批大小；按需限速，避免触发模型 API 限流 |
| S3 上传带宽瓶颈 | 低 | `deviceScaleFactor` 降为 1 减小截图体积；或按需压缩 |
