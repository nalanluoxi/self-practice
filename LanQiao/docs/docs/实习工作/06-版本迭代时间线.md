## 详细迭代记录

### 阶段一：基础能力建设（2025.08）

#### V0-1：JS 抓取引擎架构升级

**时间**：2025.08
**背景**：原 Selenium 引擎维护成本高（探活+轮询逻辑复杂），并发能力受限，对现代 JS 渲染支持局限。经过多进程抓取实测对比，Playwright 更优。
**关键技术决策**：
- 选型 Playwright（vs Selenium）：避免不稳定等待，Browser Context 轻量化多租户
- 自定义线程池管理机制替代原有 Selenium 线程调度

**产出**：
- 新架构去除探活/轮询逻辑，抓取流程同步解耦
- 对最新版 Chrome 完美兼容，高并发下资源复用率提升

---

#### V0-2：服务器基础设施治理

**时间**：2025.08
**背景**：Playwright 部署时底层库（glibc、gcc）版本过低，本地测试通过但线上无法运行，尝试"依赖降级"方案无果。
**技术方案**：
- 完成 glibc 及 gcc 核心库深度升级
- 升级流程沉淀为标准化自动化脚本，实现全量服务器批量化升级

**产出**：彻底解决高版本浏览器运行依赖问题，后续环境扩容运维成本大幅降低。

---

### 阶段二：Sitemap 环路性能建设（2025.11 ~ 2025.12）

#### V1：三级精准限流体系（2025.11.10）

**触发**：Sitemap 发现环路"无序竞争"，大站挤兑小站，小站任务长期积压。
**关键决策**：
- 三级纵深：集群层（Rhino）→ 单机层（Rhino）→ Redis 精确层（Lua 令牌桶）
- 无效流量前置拦截（黑名单/去重先于限流），避免配额被无效请求消耗
- 技术选型：Redis Lua 脚本（原子性）实现站点级令牌桶

**里程碑**：首次实现流量均匀分配，大站挤兑问题解决。

---

#### V2：多线程重构 + Mafka 扩容（2025.11.17）

**触发**：三级限流后吞吐量依然很低（QPS 6~8），需要提高并发处理能力。
**关键决策**：
- `SynchronousQueue` 而非 `LinkedBlockingQueue`：保持背压能力，防止任务无限积压 OOM
- 线程池满时 `synchronized + 自旋等待`，超时后重投 MQ（At-Least-Once 语义）
- Mafka 扩容 200→400 分区（与业务侧协调）

**里程碑**：
- 集群 QPS：<10 → 400（**16x**）
- 小时产出：2.5w → 96w（**38.4x**）
- 日新链：2~3 亿 → 10~14 亿（峰值 75 亿）

---

#### V3：动态自适应本地限流（2025.11.27）

**触发**：多线程改造后线程池无法打满，仍有部分大站占用过多配额，线程池利用率不足。
**关键决策**：
- 为何不调整线程池大小而调整限流阈值？
  - 线程池大小调整：实时、频繁、代价高、抖动大
  - 限流阈值调整：周期性（每秒）、平缓、代价低、易于控制
- 80% 水位而非 100%：预留弹性空间防止过载

**里程碑**：
- 英文留存：2000 万 → 1.2 亿
- 峰值 QPS：**1417+**

---

#### V4：GZIP 压缩包解析（2025.12.17）

**触发**：日志打点发现约 4% 流量为 `.gz` 格式但被直接丢弃。
**关键决策**：
- 流式解压（非全量展开）：避免大文件 OOM
- 仅支持 `.gz`（不支持 `.7z/.bz2/.zip`）：其他格式每小时不超过 10 条，收益不显著
- 预留策略模式+工厂方法扩展口，保持可扩展性

**里程碑**：新链发现量 3.79 亿 → **52.6 亿（14x）**

---

### 阶段三：频度调度体系建设（2026.01 ~ 2026.05）

#### 频度 V1：基于等级的 Redis TTL（2026.02.04）

**触发**：全量调度 robots.txt 资源浪费，高频站点调度不足。
**技术方案**：grade=1→TTL 3h，grade=2→TTL 5h，低频→默认值。
**问题**：上线后打分机制过于严苛，发送量少，新链产出大幅下降。
**修复**：放宽评分阈值 + 扩充原始站点集合。

---

#### 质量治理：策略拦截（2026.03.19）

**触发**：人工质检发现大量作弊/垃圾站点（首次质检 2026.03.03）。
**关键技术**：预编译正则 + @MdpConfigListener 热更新 + 前置拦截。
**里程碑**：1+2 高质量站点率 4.1% → **11.9%**；日拦截 4~5 亿。

---

#### 频度 V2：三维打分模型（2026.04）

**触发**：V1 维度单一，仅靠新链产出分无法准确评估站点价值。
**核心改进**：
- 新增 rateScore（留存率）+ scaleScore（站点规模）两个维度
- 降级保护（每次最多降 1 级）
- 多个定时任务实现一天多轮投递（grade1：6次/天）
- 闭环反馈：抓取结果 → 评分 → 投递 → 抓取结果（T+1 更新）

**里程碑**：日抓取量 10x 提升（100~200 亿/天）；日均额外贡献 URL ~908 万。

#### 截图 V2：资源完整性提升（2026.05 ~ 2026.06）

**背景**：下游发现截图资源不完整（字体/图片/CSS 缺失）。
**核心修复**：
- `supplementFontsFromCss()`：ph-css 解析 @font-face，主动下载字体
- `supplementImagesFromHtml()`：Jsoup 解析差集图片，并行下载
- `supplementScriptsAndStylesFromHtml()`：JS/CSS 兜底
- CSS CSSOM 内存回写（JS 注入）

**里程碑（2026.06 周报）**：字体缺失基本解决；CSS 缺失基本解决；图片可用率约 70%。

#### 频度调度第二期：工程化上线与调优

**触发**：v2 策略（三维打分模型）Spark 代码已完成，需完整工程化落地到生产环境。

**核心工作**：

**关键决策**：

### 阶段六：截图抓取 2.0 / HTML 数据合成（2026.05~06）

**触发**：下游多模态训练对网页 HTML 数据完整性（字体/图片/CSS/JS 全量收集）和离线重现能力提出更高要求；同时 v1 内存峰值过高、Phase1+2 两次 navigate 资源浪费。

**分支**：`dev/html-page-js-download`

**核心重构**：
- Phase1+Phase2 合并为 1 次 navigate，减少 50% 网络请求
- 边抓边上传 S3，移除内存字节缓存，内存峰值大幅降低
- 新增内层 `DOWNLOAD_TASK_POOL`（两层线程池隔离）

**资源完整性 6 项改造**：
1. `onResponse` 新增 font 收集 + `supplementFontsFromCss()` CSS 后处理兜底
2. 等待策略改为 `LOAD` + Phase1 分步滚动触发懒加载图片
3. `supplementImagesFromHtml()` 解析 HTML 补充 srcset 所有变体 + data-src 兜底
4. `supplementScriptsAndStylesFromHtml()` JS/CSS 兜底补充
5. `resources.tsv` 全量记录（含 404/304 失败资源，localName=null）
6. `s3DirKey` 改为 JSON 数组字符串（完整路径列表，解决下游 ListObjects 串行瓶颈）

**新增能力**：Phase2 灰度开关（`screenshot_phase2_enabled`）、CAT 资源粒度打点。

**里程碑**：字体缺失基本解决；CSS 缺失基本解决；图片可用率约 70%（持续优化）。

## 关键技术决策总结

| 决策点 | 选择 | 理由 |
|:--|:--|:--|
| 限流库 | Rhino OneLimiter（非 Guava） | 美团内部标准组件，支持集群维度统一计数 |
| 站点限流 | ConcurrentSkipListMap 滑动窗口（非 Bloom Filter） | 计数精确，支持动态调整阈值 |
| 线程池队列 | SynchronousQueue（非 LinkedBlockingQueue） | 保持背压，防止任务无限积压 |
| 解压策略 | 仅支持 .gz（不扩展其他格式） | 其他格式日流量 <10 条，收益不足以支撑开发成本 |
| 限流调控 | 调整限流阈值（非动态扩缩线程池） | 周期性、平缓，避免频繁线程创建销毁 |
| 失败站点处理 | 过期时间封禁（非永久封禁） | 避免一次失败导致站点永久屏蔽，平衡拦截与覆盖率 |
| 监控方案 | Redis 统计（非 Raptor 日志平台） | Raptor 有 type 数量上限，Redis 方案更灵活 |
