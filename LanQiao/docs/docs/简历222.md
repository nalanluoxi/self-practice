### 多线程并发重构与消息队列扩容

**痛点**：原单线程同步消费模式导致消息积压严重，消费速率瓶颈在 2.5 万条/小时，与下游处理能力严重不匹配。

**思考链路**：单线程消费 → I/O 等待期 CPU 空转 → 吞吐受限于单线程串行延迟；Mafka（Kafka 内部实现）分区数决定并行度上限 → 扩分区 + 并行消费者才能线性提升吞吐。但多线程消费引入 Offset 顺序提交问题，需保障 At-Least-Once 语义下的消息不丢失。

**技术方案**：
- 将消息拉取与业务处理彻底解耦，引入**异步线程池架构**：拉取线程负责 poll，业务线程池并行处理，提交 Offset 时基于 **滑动窗口 + 位图标记** 确保已处理消息区间连续提交，避免乱序提交造成数据丢失；
- 同步完成 Mafka 集群从 **200 分区 → 400 分区**翻倍扩容，分区数增加直接提升消费并行度；
- 线程池参数（核心线程数 / 队列容量 / 拒绝策略）基于消息处理 RT 和目标 QPS 反推，避免盲目堆积队列引发 OOM。

### Sitemap 发现环路三级限流体系

**痛点**：大站（百万级 URL）持续挤兑小站，导致小站长期饥饿；同时无效 URL（黑名单、非法格式、Redis 已存在）混入消费管道，浪费线程资源。

**思考链路**：限流本质是**资源隔离**与**公平调度**问题。单一限流粒度无法兼顾全局流量上限与站点间公平性 → 需多级防护：集群全局上限 → 单机节点上限 → 站点粒度隔离。前置过滤则是将"低价值拦截"提前，减少有价值资源的无谓消耗（类比数据库索引前置条件下推）。

**技术方案**：
- **集群层**：基于 Redis + Lua 脚本实现原子滑动窗口计数，控制集群整体 QPS 上限，Lua 保证 INCR + EXPIRE 的原子性，避免并发竞态；
- **单机层**：基于 `Semaphore` 控制单节点并发度，与集群层形成双重保障，防止单机过载；
- **站点层**：每个站点独立令牌桶，大站消耗令牌后受限，小站始终有配额；
- **前置拦截链**：黑名单过滤 → URL 合法性正则校验（预编译 `Pattern` 缓存复用） → Redis `Bloom Filter` 去重，三关拦截后再进入限流判断，避免作弊站点消耗有效令牌；
- 引入**线程池健康度 - 限流阈值动态联动模型**：监听线程池队列水位，队列水位高时自动收紧限流阈值，水位恢复后放宽，实现自适应背压。

**结果**：系统稳定性大幅提升，大站/小站资源分配更公平，峰值压力下零 OOM。

### GZIP 压缩 Sitemap 解析能力补齐

**痛点**：通过日志分析发现约 **4% 的 Sitemap 流量（日均 400 万+）** 为 `.gz` 格式，原链路直接丢弃，造成大量新链漏发现。

**思考链路**：`.gz` 文件本质是 DEFLATE 压缩流，Java 标准库 `GZIPInputStream` 支持流式解压，无需全量加载到内存（避免大文件 OOM）。关键点在于：流式解压 → 流式解析 XML/TXT，保持内存复杂度 O(1)，与原有 `BufferedReader` 处理链路无缝衔接，改动面极小。

**技术方案**：基于 `GZIPInputStream` 包装原始字节流，解压后对接原有 Sitemap 解析器，无需改动下游逻辑。增加 `Content-Type` 和文件扩展名双重嗅探，自动路由到对应解析器。

**结果**：新链发现量峰值从 3.79 亿激增至 **52.6 亿**，提升 **13 倍以上**。
**结果**：日新链发现量峰值从 1000w-3000w上升到5000w-8000w。

### 站点频度调度策略建设（三维打分模型）

**痛点**：全量站点每日固定周期调度，高频更新站点（新闻、电商）更新不及时，低频静态站点（政务、文档）反复无效抓取，资源分配效率低。

**思考链路**：调度本质是**优先级队列**问题：需要对站点进行动态评分，高分站点高频调度。评分维度需覆盖：历史新链发现率（反映站点活跃度）、链接规模（反映站点体量）、历史覆盖率（反映已发现程度）。三维归一化后加权合成，形成闭环反馈：调度 → 抓取 → 结果回写评分 → 下次调度优先级调整。

**技术方案**：
- 建立**三维打分模型**：`新链发现率 × 权重₁ + 站点规模 × 权重₂ + 历史覆盖率缺口 × 权重₃`；
- 下游调度结果（新增 URL 数、覆盖站点数）实时回写打分系统，形成闭环；
- 打分结果持久化至 Hive，通过 Spark 批量计算离线更新，调度器读取最新打分进行优先级排序（类比优先队列 `PriorityQueue` 的动态调整）；
- 高分站点缩短调度间隔、低分站点延长间隔，实现精细化资源调度。

**结果**：日链接产出贡献量达 **900 亿+**，高频站点延迟明显缩短，低频站点无效抓取大幅降低。
**结果**：日链接产出量从8000w左右上升到1.3-1.5亿,频度调度模块贡献新链接300w-500w不等

### DSL 规则引擎治理垃圾/作弊站点

**痛点**：垃圾/作弊站点 URL 混入抓取管道，消耗 Redis 去重资源和限流令牌，且规则需频繁更新，代码发布周期长。

**思考链路**：正则匹配是 CPU 密集操作，`Pattern.compile()` 每次编译成本高；配置热更新需要线程安全替换，`volatile` + 不可变引用交换可保证可见性；拦截点需前置于 Redis 去重和限流之前（越早拦截，节省资源越多，类比数据库谓词下推）。

**技术方案**：
- 接入 MDP 配置中心，监听配置变更事件，规则更新时重新编译并以 `volatile` 引用原子替换 Pattern 缓存，**秒级热生效**；
- 基于 DSL 语法（支持 AND/OR/NOT 组合、域名前缀/后缀/正则多匹配类型）构建规则引擎，业务同学可自助配置，无需发布代码；
- 拦截逻辑前置于 Redis 去重和限流节点，避免作弊站点消耗有效资源。

**结果**：日均拦截量达 **4~5 亿**，规则生效时间从分钟级压缩至**秒级**,人工抽样1+2打分从4.1%高质量站点率上升11.9%

### 网页截图抓取全链路服务建设

**痛点**：面向多模态大模型「看图写代码」训练需求，需大规模采集高质量网页截图，且截图任务 CPU/内存开销大，不能与 Sitemap 主链路竞争资源。

**思考链路**：Playwright 全页面渲染是重 I/O + 重 CPU 混合操作，直接与主链路共享线程池会导致资源争抢，影响 Sitemap 核心流程 SLA。需**独立线程池**隔离，本质是**资源隔离**思想（类比 JVM 不同 GC 区域隔离）。截图结果为大对象，需流式上传 S3，避免堆内存瞬时膨胀引发 GC。

**技术方案**：
- 基于 **Playwright** 引擎实现全页面渲染截图（含 JS 动态内容），配置视口参数模拟不同终端；
- 构建**独立线程池**与 Sitemap 主链路完全隔离，线程池参数（核心线程数、队列深度）根据单机 Playwright 实例内存占用反推，防止 OOM；
- 截图结果**流式上传 S3**，不缓存大对象，减少堆内存压力；

- **Chat / Embedding 双维熔断路由**：为 Chat 与 Embedding 分别实现多模型候选三态熔断器（CLOSED → OPEN → HALF_OPEN），连续失败自动熔断、定时探测恢复；Chat 路由额外引入首包探测，拦截空流响应触发切换，实现 AI 服务零感知故障转移。

- **意图树三级分类缩小检索空间**：构建领域 → 类目 → 话题三级意图树，通过 LLM 对用户查询分类后将检索范围收敛至目标知识库；对闲聊/系统意图短路处理，跳过向量检索直接回复，降低无效调用开销。
