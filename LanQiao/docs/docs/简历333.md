### 项目一：多线程并发重构与消息队列扩容

**痛点**：原架构单线程同步消费 Mafka，受限于单线程串行处理，消费速率仅 1.6-2.5 万条/小时，消息严重积压。

**思路与方案**：

- 将消费架构从单线程同步模型重构为 **Mafka 回调线程 + 独立业务线程池**的异步并行模型：回调线程完成前置过滤后立即提交任务到 `ThreadPoolExecutor`，业务线程池并发执行 `download` 逻辑，彻底解耦消息拉取与业务处理；线程池使用 `SynchronousQueue`（零容量队列），线程池满时外层自旋等待而非无限堆积，避免队列膨胀引发 OOM
- Mafka 框架采用**回调模型**（`@MdpMafkaMsgReceive`），每条消息处理完成后返回 `ConsumeStatus.CONSUME_SUCCESS`，框架自动提交 offset，消费语义为 At-Least-Once；业务线程池处理完成后回调线程才返回，避免了多线程自主提交 offset 的乱序风险
  > ⚠️ **待实现**：可进一步引入滑动窗口 + BitSet 位图标记各任务完成状态，仅当窗口左边界连续置位时推进 offset 提交，实现真正的并发消费下 Offset 顺序提交；当前框架回调模式已规避该问题，但吞吐受限于单次 poll 的串行提交
- 线程池核心线程数通过 **MDP 配置中心**（`sitemap_thread_num`）动态下发，支持不停机热更新，无需重启即可根据线上实际吞吐情况调整并发度
- 协调业务侧将 Mafka **分区数从 200 扩容到 400**，最大化并行消费能力，消除分区粒度的消费瓶颈

**结果**：消息队列每分钟处理消息量峰值从 1.6k–20k 不等上升至约 **1300 万/分钟**；日新链接产出量从 120w–170w 不等提升至 **1000w–3000w**。

### 项目二：Sitemap 发现环路三级限流体系

**痛点**：大站 URL 数量远超小站，无限流时大站挤兑小站导致饥饿问题；无效 URL 大量混入管道，浪费下游解析与存储资源。

**思路与方案**：

- 构建**三级限流体系**，从粗到细逐层收口：
  - **集群层 + 单机层**：接入美团内部 **Rhino OneLimiter** 框架，分别配置 `sitemap_cluster_qps_limit`（集群整体 QPS 上限）和 `sitemap_limit_single_node`（单机上限），通过 MDP 配置中心动态调整阈值，无需发布即可生效
  - **站点层**：基于 `ConcurrentSkipListMap` 实现自定义**滑动窗口计数器**（`CounterRateLimiter`），每个站点独立维护一个计数桶，窗口内超出 `sitemap_limite_count` 则限流，大站消耗令牌后受限、小站始终有配额
- 在限流之前引入**前置拦截链**：黑名单域名过滤（`sitemap_black_domain_list`）→ URL 后缀黑名单（`sitemap_black_list_suffixes`）→ 正则规则集过滤（`regularPatternList`，预编译 Pattern 缓存复用）→ Redis KV 去重（已抓取的 sitemap URL 写入 Tair，命中则直接丢弃）
- 实现**线程池健康度–限流阈值动态联动模型**（`LimiteUtils.updateAdaptiveLimitQuota`）：每秒采样线程池 `activeCount / corePoolSize`，连续 3 次低于 80% 阈值则放宽单站点配额，连续 3 次高于则收紧，实现自适应背压
  > ⚠️ **与简历原描述差异**：集群层/单机层实际为 Rhino OneLimiter（非 Redis+Lua），站点层为自定义滑动窗口计数（非 Guava RateLimiter），URL 去重为 Redis KV（非 Bloom Filter）

**结果**：系统稳定性显著提升，大站/小站资源分配趋于公平，峰值压力下**零 OOM**。

### 项目三：GZIP 压缩 Sitemap 解析能力补齐

**痛点**：约 4% 的 Sitemap 流量（日均 400 万+）为 `.gz` 格式，原链路对压缩格式无感知，直接丢弃，造成大量有效链接静默损失。

**思路与方案**：

- 用 `GZIPInputStream` **包装原始字节流**进行流式解压，分块读取（1024 byte buffer）后写入 `ByteArrayOutputStream`，解压后直接对接原有 XML/TXT 解析器，最小化改动面，避免大文件全量展开至内存引发 OOM
- 通过 **URL 路径扩展名嗅探**（`url.getPath().endsWith(".gz")`，排除 `tar.gz`）自动路由到对应解压解析器，`Content-Type` 嗅探作为后续优化方向
  > ⚠️ **待实现**：当前仅检查 URL 扩展名，尚未实现 HTTP 响应头 `Content-Type: application/gzip` 的双重嗅探，对于后缀不规范但响应头正确的 `.gz` 文件存在漏识别

**结果**：日新链发现量峰值从 1000w–3000w 上升至 **5000w–8000w**。

### 项目四：站点频度调度策略建设（三维打分模型）

**痛点**：全量站点固定周期调度，高更新频率站点抓取不及时，低频站点被反复无效抓取，整体资源分配粗放。

**思路与方案**：

- 设计**三维打分模型**：`compositeScore = 新链发现率 × w1 + 站点规模 × w2 + 历史覆盖率缺口 × w3`，通过多维度特征融合刻画站点"值得调度的程度"，解决单一指标评估失真的问题
- **Hive + Spark** 离线批量计算打分，结果写回调度系统；调度执行结果实时回写打分系统，形成**闭环反馈**，使打分随站点行为动态收敛
- 高分站点缩短调度间隔（强化热点站点覆盖），低分站点延长间隔（降低无效抓取），实现差异化调度
- 打分更新采用 Spark **宽表 JOIN + UDF 计算**，避免大表笛卡尔积，重点优化 Shuffle 分区数与数据倾斜

**结果**：日链接产出量从约 8000w 上升至 **1.3–1.5 亿**；频度调度模块单独贡献新链接 **300w–500w**。

### 项目五：DSL 规则引擎治理垃圾/作弊站点

**痛点**：垃圾站点 URL 持续混入处理管道，规则更新依赖代码发布，周期长、成本高，业务同学无法自助配置。

**思路与方案**：

- 接入 **MDP 配置中心**，实现规则配置的动态下发；使用 `volatile` 修饰 Pattern 引用，结合**原子引用替换**（`volatile` 保证可见性，写操作为整体替换而非部分修改，天然规避复合操作的线程安全问题），实现规则**秒级热生效**，无需重启
- 设计 **DSL 语法**支持 `AND / OR / NOT` 逻辑组合，业务同学通过配置中心自助编写规则，降低研发介入门槛
- 规则引擎采用**责任链模式**，拦截逻辑前置于 Redis 去重和限流，将最低成本的过滤步骤放在最前面，减少后续步骤的无效开销
- Pattern 编译结果**缓存复用**，避免每次请求重复编译正则（正则编译为 NFA/DFA 构建，开销不可忽视）

**结果**：日均拦截量 **4–5 亿**；规则生效时延从分钟级压缩至**秒级**；人工抽样 1+2 打分高质量站点率从 **4.1% 上升至 11.9%**。

### 项目六：网页截图抓取全链路服务建设

**痛点**：多模态大模型训练需要大规模高质量网页截图，截图任务 CPU/内存开销大，若与主链路共享资源会互相干扰。

**思路与方案**：

- 引入 **Playwright** 引擎实现全页面 JS 动态渲染截图，覆盖 SPA/动态页面，确保截图内容的完整性
- 截图任务使用**独立线程池**，与主链路彻底隔离，防止截图任务的 CPU/内存高峰影响核心消费流程（线程池隔离是 JUC 线程池在业务场景中的典型应用）
- 截图结果采用**流式上传 S3**，边生成边上传，避免将大体积图片文件全量加载到 JVM 堆内存，规避 OOM 风险

**结果**：目前处于持续优化阶段，已完成核心链路搭建，覆盖全页面 JS 动态渲染、S3 流式上传等关键功能。

### 智析 RAG —— 基于 Spring AI 的企业级 RAG 对话系统

**技术栈**：Java 17 · Spring Boot 3 · Spring AI · PostgreSQL (pgvector) · Redis · RocketMQ

**核心亮点**：

- **多通道并行检索**：`CompletableFuture` 同时发起全局向量检索与意图定向检索，两路结果合并后经去重与 LLM 重排序，兼顾召回率与精准度
- **意图树三级分类**：领域 → 类目 → 话题，LLM 分类后将检索范围收敛至目标意图节点下的向量空间，提升检索精度
- **Chat / Embedding 双维熔断路由**：三态熔断器（`CLOSED → OPEN → HALF_OPEN`）+ 失败率阈值自动切换备用模型；Chat 通道额外引入**首包探测（Probe）**，缓冲首个 SSE chunk 判断模型是否实际可用，防止脏流写入用户端
- **LLM 重排序**：对候选文档片段与问题的语义相关性打分（0–10 分），取 Top-3 注入 Prompt，减少噪声 chunk 对生成质量的干扰
- **持久化对话记忆与摘要压缩**：PostgreSQL 持久化多轮对话，超过 10 轮后调用 LLM 自动压缩为摘要，解决长上下文 Token 超限问题
- **全流水线降级容错**：各阶段（检索 / 重排 / 生成）独立捕获异常并降级，保证单点故障不影响整体链路可用性
- **支持多格式文档入库**：PDF / Markdown / TXT，ETL 流水线覆盖解析 → 分块 → 向量化 → 存储全流程
