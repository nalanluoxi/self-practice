# llm-spider-crawler 项目交接文档


## 一、项目概览

### 1.1 模块结构

```
llm-spider-crawler/
├── llm-crawler-client/          ← SDK 模块，供上游调用
│   └── request/                 ← CrawlerRequest、SitemapRequest、SitemapType
│   └── response/                ← CrawlerResponse
│   └── rpc/                     ← CrawlerRpcService（RPC 接口定义）
│
└── llm-crawler-server/          ← 服务端主模块
    └── src/main/java/.../crawler/
        ├── consumer/            ← MQ 消费者（4 个）
        ├── service/             ← 核心服务
        ├── screenshot/          ← 截图抓取子模块
        ├── sitemap/             ← Sitemap 子模块
        ├── downloader/          ← 下载器（HTTP/Playwright/Camoufox/Antibot）
        ├── config/              ← 配置类
        ├── controller/          ← HTTP 接口
        ├── dao/                 ← 数据库 Mapper
        ├── model/               ← 数据模型
        ├── util/                ← 工具类
        ├── crane/               ← 定时任务
        └── exception/           ← 自定义异常
```

### 1.2 两条核心抓取链路

| 链路 | 入口 Consumer | 核心 Service | 说明 |
|------|--------------|-------------|------|
| **Sitemap 链路** | `SitemapRequestConsumer` | `SitemapService` | robots.txt → sitemap.xml → page URL 发现 |
| **Screenshot 链路** | `ScreenshotRequestConsumer` | `ScreenshotService` + `ScreenshotPlaywrightService` | HTML + 静态资源 + 截图 + 可交互元素 |

## 二、Sitemap 链路（当前状态）

### 2.1 完整流转图

```
【离线调度层 llm-spider-jobs】
    ├─ RobotsMsgSendingJob → Topic: llm_sitemap_url
    ├─ UpdateFrequencyTableJob (T+1) → DF/DI 表
    └─ FrequencyDeliverySitemapJob → Topic: llm_sitemap_url

【在线消费层 llm-spider-crawler】
    SitemapRequestConsumer.receive()
        → 预处理漏斗（12 道过滤）
        → 线程池（SynchronousQueue）
        → SitemapService.download()
            ├─ robots 分支 → downLoadRobotsTxt() → 写 MySQL → 发 sitemap URL 回环
            └─ sitemap 分支 → downLoadSitemap() → parseSitemapAndSend()
                ├─ SiteMapIndex → 回环发 MQ
                └─ SiteMap → 提取 pageUrl → 发 sitemapResultTopic（结果）
```

### 2.2 Consumer 预处理漏斗（12 道，顺序过滤）

1. JSON 反序列化
2. `ext.dispatchTs` 过期检测（默认 48h，lion: `sitemap_stale_threshold_hours`）
3. URL 格式校验 / 长度校验（max 256）/ 重复字符检测
4. 正则黑名单过滤（`sitemap_regular_filter_list`，@PostConstruct 预编译，@MdpConfigListener 热更新）
5. 域名/后缀黑名单（`FilterUtils.isValid`）
6. 站点级黑名单（`PreprocessUtil.isOnBlackList`）
7. Redis 去重（`llm_sitemap_url:{url}`）
8. 动态 domain QPS 限流（`LimiteUtils`）→ 重投
9. 集群/单节点/站点三级 Rhino 限流 → 重投
10. `isSuspend` 开关
11. 内存阈值检测（`exceedMaxInProcessMem`）
12. 提交线程池，满时阻塞等待，超时重投（最多 10 次）

### 2.3 关键 Lion 配置

| 配置键 | 说明 |
|--------|------|
| `sitemap_thread_num` | 线程池大小，热更新 |
| `sitemap_max_wait_time` | 线程池满最大等待时间（默认 36s） |
| `sitemap_stale_threshold_hours` | 过期消息丢弃阈值（默认 48h） |
| `sitemap_crawl_status_expire_time` | sitemap 去重 Redis 过期时间 |
| `sitemap_common_config.isSuspend` | 暂停消费开关 |
| `sitemap_common_config.crawlSitemap` | 是否解析 sitemap 并发现子链接 |
| `sitemap_common_config.maxInProcessMemInBytes` | 内存上限 |
| `sitemap_black_domain_list` | 域名黑名单 |
| `sitemap_regular_filter_list` | 垃圾站点正则过滤（90% 垃圾站点拦截） |

## 三、Screenshot 链路（当前状态）

### 3.1 整体架构

```
Mafka (URL 任务)
    → ScreenshotRequestConsumer（过滤 + 线程池）
        → ScreenshotService.submit()
            → ScreenshotPlaywrightService.crawlScreenshot()
                Phase1: navigate → onResponse 收集 JS/CSS/图片/字体 → 获取 HTML
                        + supplementFontsFromCss()（CSS 字体兜底）
                        + supplementImagesFromHtml()（HTML 图片兜底）
                        + supplementScriptsAndStylesFromHtml()（JS/CSS 兜底）
                Phase2: 多视口截图 + JS_DOM_EXTRACT → ClickableElement → annotated_screenshot
            → 上传 S3（边抓边上传，不攒内存）
            → 发 MQ（ScreenshotResultMessage，含 uploadedKeys JSON 数组）
```

### 3.2 线程池设计（两层隔离）

| 线程池 | 变量名 | Lion 配置 | 说明 |
|--------|--------|-----------|------|
| 外层消费池 | `ScreenshotRequestConsumer.EXECUTOR` | `screenshot_thread_num` | MQ 消费 → 转发/提交任务 |
| 内层下载池 | `ScreenshotPlaywrightService.DOWNLOAD_TASK_POOL` | `screenshot_download_thread_num` | 实际执行 Playwright 抓取 |
| 补充下载池 | `ScreenshotPlaywrightService.SUPPLEMENT_POOL` | `screenshot_supplement_thread_num` | 图片/字体/CSS/JS 兜底并行下载（与下载池完全隔离防死锁） |

### 3.3 Playwright 实例管理

- **三条线路，各自独立 ThreadLocal**：
  - `INSTANCES_137`：海外普通（OVERSEA_NORMAL），Chrome 137，新加坡时区
  - `INSTANCES_136`：海外高级（OVERSEA_ADVANCED_LINE），Chrome 136，英国时区
  - `INSTANCES_130`：国内普通（MAINLAND_NORMAL），Chrome 130
- **实例存活**：5 分钟后刷新（`PLAYWRIGHT_INSTANCE_SURVIVE_MAX_TIME = 5min`），每次使用时续期
- **清理线程**：每 5 分钟扫描 `instanceMap`，关闭过期实例

### 3.4 资源收集策略

| 阶段 | 方式 | 说明 |
|------|------|------|
| 主收集 | `onResponse` 监听 | navigate 过程中拦截 JS/CSS/图片/字体响应，立即 `body()` |
| 状态码 200 但 body 为空 | `downloadWithProxy` 重试 | 典型场景：304 缓存命中或网络抖动，主动重拉 1 次 |
| 字体兜底 | `supplementFontsFromCss` | ph-css 解析 `@font-face src url()`，主动下载 Chrome 懒加载未触发的字体 |
| 图片兜底 | `supplementImagesFromHtml` | Jsoup 解析 `img[src/srcset/data-src]`、`picture source[srcset]`，取差集并行下载 |
| JS/CSS 兜底 | `supplementScriptsAndStylesFromHtml` | 解析 `<link rel="stylesheet">`、`<script src>` 等，取差集并行下载 |

### 3.5 灰度转发逻辑（目前关闭）

- **Lion 配置**：`screenshot_Sent_isGray`（开关）、`screenshot_Sent_Gray`（灰度比例）、`screenshot_cluster_ip`（转发目标 IP 列表）
- **当前状态**：`screenShotSentisGray = false`，线上已关闭，本机直接执行 `screenshotService.submit()`
- **转发目标接口**：`http://{ip}:8080/screenshot/submitScreenShotAndSend`
- **响应码处理**：`code=1` 成功；`threadpool_full` / `screenshot_qps_limited` 重投 MQ；其他失败不重投
- **代码位置**：`ScreenshotRequestConsumer.forwardToCluster()`（第 316 行）
- **代码注释**：`//TODO 转发逻辑需要测试,目前存在一些问题,目前线上关闭了灰度转发,使用mafka指定消费机器`

### 3.6 S3 目录结构

```
screenshot/{yyyyMMdd}/{urlSafeName}_{md5前8位}/
├── index.html                    ← 页面 HTML
├── resources.tsv                 ← 资源清单（url\tlocalName\ttype\tstatus）
├── assets/                       ← 静态资源
│   ├── *.js / *.css / *.img / *.font
└── viewport_{n}/                 ← 第 n 个视口（phase2 截图）
    ├── screenshot.png
    ├── annotated_screenshot.png  ← 标注可交互元素框
    └── clickable_elements.json
```

### 3.7 Screenshot TODO（待办）

#### 待办3：增加对 iframe 内部文档的支持
- **现状**：`onResponse` 只收集主文档资源；`JS_DOM_EXTRACT` 中 iframe 只记录为可交互元素（role=document），但 iframe 内部 HTML/CSS/JS 资源未下载
- **影响**：含嵌入式 iframe 的页面（如广告、第三方组件、地图）资源不完整，离线重现时 iframe 内容空白
- **方向**：在 Phase1 navigate 后，枚举 `page.frames()`，对每个 `frame` 单独收集资源；或通过 JS 注入提取 iframe 的 `contentDocument`
- **相关代码**：`ScreenshotPlaywrightService.java` 的资源收集段（约 550~730 行）

#### 待办4：CSS/JS 二次回捞策略
- **现状**：已有 `supplementScriptsAndStylesFromHtml()` 做 HTML 解析兜底，但仅限页面初始 HTML 快照时点
- **待补充**：对于 **动态懒加载** 的 JS（`import()`、`IntersectionObserver` 触发）或 CSS（`loadCSS`、`async style`），目前二次回捞覆盖不完全
- **方向**：在 Phase1 滚动触发后再次统计 `collectedJsCssUrls` 差集，或增加 navigate 后额外等待时间
- **相关代码**：`ScreenshotPlaywrightService.supplementScriptsAndStylesFromHtml()`（第 956~1052 行）

#### 待办5：状态码 200 但 body null 的重试逻辑
- **现状**：`onResponse` 收到 status=200 但 `body()` 为空时，已有 `downloadWithProxy` 重试一次（第 677~693 行）
- **待完善**：
  - 重试只针对静态资源，**index.html 为空时没有重试**
  - 仅重试 1 次，失败后只记录日志，不影响主流程
  - 对 html `page.content()` 返回空的情况没有处理（httpCode=-2 的 LOAD 超时场景可能导致 HTML 为空）
- **方向**：对 `html == null` 或 `html.length() < 某阈值` 时补充 `page.content()` 重试；扩展资源重试次数为可配置

#### 待办6：转发逻辑完善（灰度目前关闭）
- **现状**：`forwardToCluster()` 已实现 HTTP 转发 + 重投逻辑，但存在已知问题，目前线上关闭
- **已知问题**：
  - 转发时线程池满导致死锁（外层 Consumer 线程持有锁等待内层 HTTP 请求，而 HTTP 请求返回的处理又需要外层线程）
  - 响应体泛型擦除导致 `ResponseBean<ScreenshotResultMessage>` 反序列化失败
- **方向**：转发 HTTP 请求改为异步（不阻塞 Consumer 线程）；ResponseBean 反序列化改用 TypeReference 泛型擦除兼容方案
- **相关代码**：`ScreenshotRequestConsumer.forwardToCluster()`（第 316~375 行）

#### 待办7：针对下游发现的新异常 case 进行逐步解决收敛
- **现状**：系统已上线，下游（Spark/Hive/Python 打分）陆续反馈各类边界 case，需要逐步跟踪处理
- **已知 case 追踪位置**：`docs/截图抓取质量扫描报告_20260527.md`（最新扫描结果）
- **方向**：建立 case 登记机制，每个新 case 对应一个修复 PR，修复后在报告中标注
