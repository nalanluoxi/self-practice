# 简历版实习工作内容浓缩汇总

**团队**：美团计算机平台 / FRIDAY 组 — LongCat 大模型数据团队
**岗位**：后端开发实习生
**方向**：大模型预训练语料库建设 / 网页抓取系统 / 多模态截图服务

---

**【1】多线程并发重构，吞吐量提升 40 倍**

原系统单线程消费 Mafka，每次任务同步耗时约 15s。引入线程池后难点在于防止任务堆积 OOM 及保证消息不丢失。选用 SynchronousQueue 无缓冲队列，无空闲线程时生产者直接阻塞，天然背压防堆积；回调线程只做反序列化和前置过滤，HTTP 抓取异步提交业务线程池，实现拉取与处理解耦；线程池满时主线程自旋等待而非丢弃消息。同步推动 Mafka 集群从 200 分区扩容至 400 分区消除传输瓶颈。最终小时抓取量从 2.5 万升至 96 万+，日均新链发现量最高达 75 亿。

---

**【2】三级限流 + 动态自适应限流体系建设**

Sitemap 环路无流量控制，大站挤兑小站；固定阈值无法感知线程池实时负载，并发能力浪费。限流侧设计三级递进：集群层 Rhino OneLimiter 保护下游 Redis；单机层均摊策略应对扩缩容；站点层 Redis+Lua 令牌桶精确限频；无效流量前置拦截防止消耗有效配额。自适应侧，调整线程池大小代价高抖动大，改为调整限流阈值——Daemon 线程每秒采样线程池健康度（activeCount/corePoolSize），维护长度 3 的环形缓冲，连续 3 次低于 80% 水位则扩大配额，超过则收缩。最终调度产出从集中双峰优化为全天均匀，峰值集群 QPS 达 1417+，英文新链留存量从 2000 万升至 1.2 亿。

---

**【3】GZIP 压缩包 Sitemap 解析能力补齐**

原链路对 .gz 格式 Sitemap 直接丢弃，日志打点发现压缩包日均 400 万+（占流量约 4%），大量新链流失。利用 Java 原生 GZIPInputStream 自动识别 gzip 头部流式解压：字节数组 → ByteArrayInputStream → GZIPInputStream，1KB 缓冲区循环读取写入输出流，最终转 UTF-8 字符串交由原有 SiteMapParser 解析，完整复用 Redis 去重、限流、CAT 监控等下游节点。其他压缩格式每小时不足 10 条，避免过度设计未引入策略模式。推全后新链发现量从 3.79 亿激增至 52.6 亿，实现 14 倍产出增长。

---

**【4】频度调度 — 多维打分差异化投递策略**

原方案每天固定调度全量 robots 链接，高频站点调度不足导致新链遗漏，低频站点白占资源。设计三维打分模型：新链接分（时效）+ 留存率分（质量）+ 规模分，加权合并为 compositeScore，划分 5 级，平滑降级保护每次最多降 1 级；抓取侧通过 Redis TTL 差异化控制重复抓取间隔，高频短 TTL，低频长 TTL；多定时任务支持一天多轮投递。上线后发现打分阈值过严导致发送量骤降，通过监控定位后放宽阈值并扩充站点集合修复。最终 sitemap 日新链产出从 10~70 亿提升至 100~200 亿（约 10 倍）。

---

**【5】DSL 规则引擎治理垃圾/作弊站点**

人工质检发现大量参数爆炸、路径随机等作弊站点混入链路，严重影响新链质量。难点是规则需支持热更新且正则逐次编译性能差。在 @PostConstruct 阶段将所有正则一次性预编译为 Pattern 对象缓存至 HashSet，避免运行时重复编译；@MdpConfigListener 监听配置变更自动重编译，秒级热更新；结合 URL 指纹切割识别作弊特征，拦截逻辑前置于 Redis 去重和限流之前，保证资源消耗前即完成过滤。最终抽样高质量站点率从 4.1% 提升至 11.9%，链接质量大幅提升，新规则分钟内上线生效。

---

**【6】监控体系建设与无效站点治理**

初期 Raptor 日志监控因 type 数量超上限不可行，导致 1500 万/天历史积压及大量无效站点（默认页 27%~34%、失败 11%~17%、无 sitemap 25%~27%）长期消耗资源无从发现。改用 Redis + CAT，以 batchId+小时为粒度构建全链路漏斗监控。监控上线后定位积压问题，通过 dispatchTs 与 staleThresholdHours 对比丢弃超时历史消息；细分失败原因（下载失败/默认页/CF 拦截/验证码）持久化，进入线程池前拦截；采用过期式封禁而非永久屏蔽，让临时故障站点自然恢复。每日消除 1500 万历史积压开销，线程池有效利用率显著提升。

---

**【7】JS 抓取引擎升级（Selenium → Playwright）**

原 Selenium 引擎需人工维护心跳探活、异步轮询，维护成本高，动态页面等待不稳定。迁移至 Playwright 后利用 BrowserContext 共享浏览器实例但独立隔离 Cookie/Cache/Session，资源复用率大幅提升；自定义线程池替代探活轮询，流程同步解耦。生产部署时发现 glibc/gcc 版本过低导致高版本 Chrome 无法运行，浏览器降级功能缺失，推动全量服务器升级核心基础库，将升级流程沉淀为标准化 Shell 脚本，新服务器扩容一键部署。高并发下资源复用率和抓取效能大幅提升。

---

**【8】网页截图抓取全链路服务建设（多模态方向）**

多模态业务方需对高质量 URL 截图抓取，用于训练大模型「看图写代码」能力。JS 渲染 CPU/内存密集，单机每分钟仅处理 1~2 条，堆积即 OOM，选用 SynchronousQueue + 主线程阻塞背压，不重投 MQ 防二次积压；线程池热更新需注意顺序（扩容先调 max 再调 core，缩容反之）；守护线程每秒上报 CAT 实时可观测；中文乱码排查定位为服务器缺少中文字体包，安装后解决。全链路独立 Consumer/线程池/监控/Topic，与 Sitemap 完全隔离。集群 490 台机器吞吐约 1000 条/分钟，产出数据直接用于多模态大模型训练。
