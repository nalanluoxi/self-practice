# 新旧版本线程池进入次数 & 磁盘打满差异分析

## 一、线程池进入次数差异

### 结论

**不是新版本进入次数变多，而是新版本任务耗时极短（毫秒级），线程释放极快，单位时间内反复快速进入又退出，导致 `succEnter` 事件计数暴增。实际处理的有效 URL 数两个版本相同。**

---

### 旧版本任务耗时（7b469f5）

线程池里执行的是 `screenshotService.submit(request, true)` → 本机完整抓取：

| 步骤 | 耗时 |
|------|------|
| Phase1：新建 Context → navigate → waitForTimeout(2000) → 收集 HTML/JS/CSS | 10~40 秒 |
| Phase2：**再新建第二个 Context → 第二次 navigate → waitForTimeout(3000)** → 多视口截图 | 20~60 秒 |
| S3 上传：`uploadScreenshotResult()` 把 HTML + 所有 assets + 截图一次性上传 | 5~30 秒 |
| **合计** | **35~130 秒/任务** |

> 注意：旧版本 Phase1 和 Phase2 是**两个独立的 BrowserContext，两次 navigate**，同一个 URL 请求了两遍。

5 个线程占满，每个任务 60 秒 → 每分钟最多处理 5 个任务 → `succEnter` 极少。

---

### 新版本任务耗时（12fff64）

线程池里执行的是 `forwardToCluster(request)` → HTTP 转发：

```java
// sendPostRequest 是同步 HttpURLConnection，没有设置 connectTimeout / readTimeout
CrawlerRequestConsumer.sendPostRequest(targetUrl, JackSonUtils.toJson(request));
```

实际存在两种情况：

| 情况 | 原因 | 线程占用时长 |
|------|------|------------|
| 集群机器限流拒绝（`screenshot_limit` OneLimiter）| HTTP 立即返回 error | **< 100ms** |
| 集群机器连接失败 / 网络异常 | 抛出异常退出 | **< 1 秒** |
| 集群机器正常抓取并返回 | 等待远端完整抓取 | 60~120 秒 |

每分钟限流通过 < 450 条，分散到 38 台机器，每台每分钟 < 12 条。集群机器的 `screenshot_limit` 限流阈值若低于这个速率，**大量请求会被立即拒绝**，消费者线程毫秒级返回，5 个线程空转，每分钟可处理几百上千次"快速失败" → `succEnter` 暴增到 1k~2k。

---

### 核心对比

| | 旧版本 | 新版本 |
|---|---|---|
| 线程池任务内容 | 本机 Playwright 完整抓取 + S3 上传 | HTTP 转发（同步等响应）|
| 单次任务耗时 | **35~130 秒** | **< 100ms（快速失败）或 60~120 秒（正常）** |
| 每分钟线程空闲机会 | 极少 | **极多** |
| `succEnter` 事件/分钟 | **< 100** | **1k~2k** |
| 实际有效处理 URL/分钟 | ~10 | ~10（相同）|

## 二、为什么新版本会磁盘打满，旧版本不会

### 旧版本为什么不会磁盘打满

旧版本所有资源都保存在**内存**里，完成后一次性上传 S3，没有任何本地磁盘写入：

- `assetBytes`：`Map<String, byte[]>` 全在 JVM 堆内存
- `screenshotBytes` / `annotatedBytes`：`byte[]` 全在 JVM 堆内存
- S3 上传用的是 `new ByteArrayInputStream(data)`，直接走内存流，**不写临时文件**（只有超过 100MB 才写临时文件，但截图资源远达不到这个量级）

旧版本的 `uploadScreenshotBytes` 实现：
```java
// S3Service.java（旧版本）
s3Client.putObject(bucket, s3Key, new ByteArrayInputStream(data), meta);
// ← 纯内存流，无本地文件写入
```

所以旧版本不产生任何磁盘写入，不会打满磁盘。

---

### 新版本为什么会磁盘打满

新版本的集群机器执行 `screenshotService.submit()` 时，`ScreenshotPlaywrightService` 在每次抓取过程中会写入大量数据，**同时产生了意想不到的磁盘写入**。

#### 根因1：Playwright 的 `setChannel("chrome")` 会使用系统 Chrome 的默认 Profile 目录

`PlaywrightDownLoader.java`：
```java
playwright.chromium().launch(new BrowserType.LaunchOptions()
    .setChannel("chrome")   // ← 使用系统已安装的 Chrome，而非 Playwright 自带的 Chromium
    ...
    // ← 没有指定 --user-data-dir
)
```

**关键区别：**

| 启动方式 | user-data-dir 行为 |
|---|---|
| `playwright.chromium().launch()` 不指定 channel | Playwright 自己生成随机临时目录，关闭时**自动删除** |
| `playwright.chromium().launch().setChannel("chrome")` | 使用系统 Chrome 的**默认 Profile 目录**（`~/.config/google-chrome` 或 `/root/.config/google-chrome`），**不会自动删除** |

因为使用了 `setChannel("chrome")`，Chrome 启动时会写入系统默认 Profile 目录：
- `Cache/` —— HTTP 缓存（HTML / JS / CSS / 图片等）
- `Default/Storage/`
- `Default/Session Storage/`
- `Default/Code Cache/`

每次请求网页，Chrome 都会往这个目录写缓存。这个目录只增不减，最终把磁盘打满。

旧版本在消费者机器上运行时，消费者机器 QPS < 1，磁盘增速慢，所以没有暴露问题。新版本转发后，集群38台机器每台 QPS < 1，但消费者机器同时向38台机器发请求，集群机器实际上在高强度写缓存。

#### 根因2：新版本在抓取过程中写入了大量日志（旧版本没有这条路径）

旧版本的消费者机器不执行抓取，没有 Playwright 相关日志。

新版本集群机器执行 `ScreenshotPlaywrightService`，每次抓取打印大量 `log.info`：
- `screenshot playwright 获取代理server:...`
- `screenshot crawlScreenshot sampled params...`
- `screenshot phase2 url=... pageSize=...`
- 每个 viewport 循环的截图日志
- S3 上传每个文件的日志：`screenshot s3 upload ok, key=..., size=...`

按每次抓取产生约 20~30 行日志，每行约 200 字节，每天集群每台机器处理 ~600 次（< 12 次/分钟 × 60 分钟 × 8 小时）：
```
600 次/天 × 25 行 × 200 字节 = 3MB/天/台
```
这个量级不足以打满磁盘，**日志不是主因**。

#### 根因3（最可能的主因）：`setChannel("chrome")` 的 Chrome 缓存随请求量线性增长且不清理

每抓取一个页面，Chrome 写入的缓存估算：
- HTML + JS + CSS：通常 1~10 MB/页面
- Chrome 默认 Cache 目录无上限，也没有配置 `--disk-cache-size=0` 来禁用

在 QPS < 1 但**连续运行数小时/天**后：
```
10 次/小时 × 5MB/次 × 24小时 = 1.2GB/天
```
磁盘空间可在数天内被打满。

---

### 两个版本的关键差异总结

| 维度 | 旧版本（消费者机器本机执行）| 新版本（集群机器执行）|
|---|---|---|
| Playwright 启动方式 | `setChannel("chrome")` | `setChannel("chrome")` |
| Chrome 缓存写入 | 写入消费者机器，QPS < 1，慢 | 写入集群机器，被大量复用 |
| 资源存储 | 全内存，无本地磁盘写入 | 全内存（已优化），但 Chrome Profile 缓存写磁盘 |
| 磁盘增速 | 极慢，几乎不增 | **持续增长，不清理** |

## 三、修复方案

### 问题1：磁盘打满

**修复：禁用 Chrome 磁盘缓存，或指定随机临时 user-data-dir 并在关闭时删除。**

在 `PlaywrightDownLoader.java` 的 launch args 中增加：
```java
"--disk-cache-size=0",        // 禁用磁盘缓存
"--disable-application-cache", // 禁用 Application Cache
"--media-cache-size=0",        // 禁用媒体缓存
```

或者改为不指定 channel（使用 Playwright 自带 Chromium），让 Playwright 自动管理临时目录：
```java
// 去掉 .setChannel("chrome")，使用 Playwright 内置 Chromium
playwright.chromium().launch(new BrowserType.LaunchOptions()
    .setHeadless(true)
    .setArgs(...)
)
```

---

### 问题2：消息丢失（resendMsg 被注释）

当线程池满或 HTTP 转发失败时，当前新版本直接丢弃消息。需要恢复保底机制：

**方案：恢复 resendMsg，并给 sendPostRequest 加超时**

1. `sendPostRequest` 加 connectTimeout（如 3 秒）和 readTimeout（如 120 秒），防止无限阻塞。
2. 当转发失败（异常、网络错误、限流返回 error）时，重新发送 MQ 消息，最多重试 2 次。
3. 恢复 `MAX_WAIT_TIME` 超时保护：线程池满等待超时后，resend 消息而非无限等待。

**核心修改点在 `forwardToCluster`：**
```java
private void forwardToCluster(ScreenshotRequest request) {
    // 1. 发送 HTTP，加超时
    String result = sendPostRequestWithTimeout(targetUrl, body, 3000, 120000);
    // 2. 失败时 resend MQ
    if (result == null || result contains "error") {
        resendMsg(request);
    }
}
```

---

### 问题3：线程池 `succEnter` 统计虚高

快速失败的请求进入线程池立刻退出，导致 `succEnter` 计数虚高，掩盖真实处理量。

建议分开打点：
- `succEnter`：进入线程池
- `forwardSuccess`：转发成功（HTTP 返回正常响应）
- `forwardFail`：转发失败（异常 / 限流 / 超时）
