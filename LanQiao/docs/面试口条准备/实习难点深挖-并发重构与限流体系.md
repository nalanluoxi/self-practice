# 实习难点深挖：多线程并发重构 + 三级自适应限流体系

> 选题理由：这是整个实习产出里技术含量最高、业务影响最大的单一改造，
> 涉及 JUC 并发模型、背压控制、消息队列、分布式限流多个维度，面试官极易往深了问。

---

## 一、业务背景（Situation — 必须交代清楚）

**Sitemap 新链发现环路是什么**：

美团 LongCat 大模型需要海量网页预训练语料。Sitemap 是网站提供的"站点地图"XML 文件，列出了网站所有 URL。我们的任务就是定期抓取各大网站的 Sitemap，从中提取新 URL，喂给后续的抓取-解析-清洗流水线，最终产出大模型训练数据。

**改造前的系统瓶颈（两个独立问题）**：

| 问题 | 现象 | 根本原因 |
|------|------|---------|
| 消费吞吐极低 | 小时新链发现量只有 2.5 万 | 单线程同步消费 Mafka，一条消息处理完才能处理下一条，单次同步耗时约 15s |
| 大站挤兑小站 | 美团、淘宝等大站 Sitemap 几百 MB，把线程池占满，小站的任务饿死 | 所有站点共享同一个线程池，无任何调度优先级和限频 |

## 二、并发重构：SynchronousQueue 背压模型

### 2.1 改造方案

**原模型**（单线程同步）：
```
Mafka 消费回调 → [解析Sitemap → 发现新链 → 写DB] → 处理完ACK → 下一条
```
每条消息串行处理，IO 等待期间 CPU 闲置，吞吐极低。

**新模型**（回调线程 + 业务线程池 + SynchronousQueue）：
```
Mafka 消费回调线程
    ↓ put(task) — 阻塞，直到有 worker 来取
SynchronousQueue（无缓冲）
    ↓ take(task) — worker 取走
业务线程池（N 个 worker 线程并行处理）
    ↓
[解析Sitemap → 发现新链 → 写DB]
```

### 2.2 为什么选 SynchronousQueue，不选其他队列

这是面试官最爱深挖的点，必须讲清楚每种方案的取舍：

**方案对比**：

| 队列类型 | 缓冲能力 | 背压效果 | 问题 |
|---------|---------|---------|------|
| `LinkedBlockingQueue`（无界） | 无限 | 无背压 | 消息无限堆积，内存 OOM |
| `ArrayBlockingQueue(N)` | 有界 | 满了才阻塞 | 队列未满期间积压不可见，响应慢 |
| `直接 submit + CallerRunsPolicy` | 无 | 满了回调线程自己跑 | 回调线程被占用，影响 Mafka ACK 节奏 |
| **`SynchronousQueue`** ✅ | **无缓冲** | **立即背压** | 每次 put 必须等 take，天然流控 |

**SynchronousQueue 的核心特性**：
- 它是一个**没有存储空间**的队列，每次 `put()` 必须等到有线程来 `take()` 才能返回
- 相当于「人传人」而不是「放到货架上等人来拿」
- 效果：业务线程池满时，`put()` 阻塞，Mafka 回调线程自旋等待，消息不会积压，也不会丢失

**主线程自旋等待的逻辑**：
```
while (pool.getActiveCount() >= pool.getMaximumPoolSize()) {
    Thread.sleep(短暂等待);
}
queue.put(task);  // 等到有空闲 worker 才放入
```
这样保证了在任何时刻，队列里的任务数 = 0（被立即取走）或主线程在等待，内存中不会有堆积。

### 2.3 Mafka 分区扩容 200 → 400

**Kafka 分区与并发度的关系**（底层原理，面试必考）：
- Kafka 一个分区在同一个 Consumer Group 内只能被一个消费者消费
- 200 分区 = 最多 200 个并发消费线程，天花板打死了
- 扩容到 400 分区，消费并发度上限翻倍，传输侧瓶颈打开

**扩容过程注意点**：
- Kafka 只能增加分区，不能减少（减少会导致数据丢失）
- 扩容后已有数据不会重新分布，只有新写入的消息才会用新的 hash 路由到新分区
- 消费者需要重新做 rebalance，分配到新分区，有短暂的停顿窗口

### 2.4 效果

| 指标 | 改造前 | 改造后 |
|------|--------|--------|
| 小时抓取量 | 2.5 万 | 96 万+ |
| 提升倍数 | — | **38 倍** |
| 日均新链发现 | — | 最高 **75 亿** |

## 三、三级限流体系：解决大站挤兑小站

### 3.1 业务问题描述

Sitemap 任务是按站点维度投递的，淘宝一个 Sitemap 文件可能有 5000 万条 URL，解析一次要占用线程池几十分钟，期间其他站点（包括高价值小站）完全饿死。

**固定阈值的缺点**：不感知线程池实时负载，阈值设小了限流过严（浪费资源），设大了无效（大站仍然挤兑）。

### 3.2 三级递进限流架构

```
请求进入系统
    ↓
① 集群层 Rhino 限流
   — 对整个下游服务设全局 QPS 上限，防止打崩下游
    ↓
② 单机层 Rhino 限流
   — 每台机器独立限频，防止单机过载
    ↓
③ 站点层 Redis + Lua 令牌桶
   — 精确限制每个站点的访问频率，解决大站挤兑
    ↓
④ 前置无效流量拦截（DSL规则引擎）
   — 空 Sitemap、参数爆炸的作弊站点在消耗任何资源前直接 return
```

为什么三级而不是一级：
- 一级只有全局 QPS，无法区分「一个大站消耗了 80% 的配额」和「80 个小站各消耗 1%」
- 三级递进：先保护整体，再保护单机，最后按站点精细化控制

### 3.3 Redis + Lua 令牌桶实现原理

**为什么要用 Lua 脚本**：
令牌桶的每次消费需要三步：读当前令牌数 → 计算补充量 → 扣减令牌写回。
三步非原子，两个线程并发执行会出现"double spend"（两个请求都读到同一个余量，都认为有令牌，都扣减成功）。
Redis 单线程执行 Lua 脚本，三步原子化，没有竞争。

**令牌桶 vs 漏桶**（面试必问对比）：

| | 令牌桶 | 漏桶 |
|---|---|---|
| 机制 | 以固定速率补充令牌，请求消耗令牌 | 请求入桶，以固定速率漏出处理 |
| 突发流量 | ✅ 允许积累令牌，可以突发消耗 | ❌ 匀速出水，削平突发 |
| 适合场景 | API 限频、爬虫（允许积累再批量处理） | 流量整形（严格匀速） |
| 为什么选令牌桶 | Sitemap 站点有周期性更新，允许短期突发抓取 | — |

**Lua 脚本伪逻辑**：
```lua
local now = tonumber(ARGV[1])          -- 当前时间戳（毫秒）
local rate = tonumber(ARGV[2])         -- 每毫秒补充令牌数
local capacity = tonumber(ARGV[3])     -- 桶容量

local tokens = tonumber(redis.call('hget', KEYS[1], 'tokens') or capacity)
local last = tonumber(redis.call('hget', KEYS[1], 'last') or now)

-- 按时间差补充令牌，不超过容量
tokens = math.min(capacity, tokens + (now - last) * rate)

if tokens >= 1 then
    redis.call('hset', KEYS[1], 'tokens', tokens - 1, 'last', now)
    return 1   -- 允许通过
else
    redis.call('hset', KEYS[1], 'last', now)
    return 0   -- 拒绝
end
```

### 3.4 自适应限流：Daemon 线程 + 环形缓冲

**为什么需要自适应（固定令牌速率还不够）**：
大站的 Sitemap 解析时间是不确定的（有的几秒，有的几分钟），固定速率无法感知「线程池快满了」的状态。

**实现原理**：

```
Daemon 线程（不阻塞 JVM 退出）
  每 500ms 采样一次：健康度 = activeCount / maximumPoolSize
      ↓
  写入 RingBuffer[N]（环形缓冲，固定大小，满了覆盖最旧的）
      ↓
  检查最近 3 次采样是否全部 > 80%（水位线）
  ├── 是：触发配额收缩（减少站点令牌速率）
  └── 否：检查最近 3 次是否全部 < 50%
      ├── 是：触发配额恢复（增加令牌速率）
      └── 否：维持当前配额
```

**为什么是环形缓冲 + 连续 3 次，而不是单次采样**：
- 单次采样：GC Pause 导致短暂卡顿，线程池活跃数瞬时 100%，误触发降速
- 环形缓冲连续 3 次：3 次 × 500ms = 1.5 秒窗口，过滤掉 GC 等瞬时抖动，只响应真实的持续高负载

**RingBuffer 的数据结构**：
```java
int[] samples = new int[N];    // 固定大小数组
int cursor = 0;                // 写指针，写满后回到 0 覆盖

// 每次采样
samples[cursor % N] = healthPercent;
cursor++;

// 判断最近 3 次
boolean allAbove80 = true;
for (int i = 1; i <= 3; i++) {
    if (samples[(cursor - i + N) % N] <= 80) { allAbove80 = false; break; }
}
```

### 3.5 效果

- 大站挤兑小站问题基本解决，调度公平性显著提升
- 结合频度打分策略，日新链产出从 10~70 亿提升至 **100~200 亿**

## 四、深挖问题清单（按难度排序）

### Level 1 — 基础概念

**Q: SynchronousQueue 和 BlockingQueue 的区别是什么？**
> SynchronousQueue 没有存储空间，put 必须等 take；BlockingQueue 有缓冲区，满了才阻塞。
> SynchronousQueue 的背压是即时的，BlockingQueue 的背压是滞后的（填满缓冲区后才开始阻塞）。

**Q: Kafka 分区数增加会有什么影响？**
> 正向：消费并发度上限提升，吞吐增加。
> 负向：分区增多后 ZooKeeper/Controller 维护元数据压力增大；消费者 rebalance 时有短暂停顿；分区数不能减少（减少会丢数据）。

**Q: 令牌桶和漏桶的区别？各自适合什么场景？**
> 令牌桶允许突发（积累令牌），漏桶强制匀速。API 限频选令牌桶，流量整形选漏桶。

### Level 2 — 设计决策

**Q: 为什么是 3 次采样而不是 5 次？80% 水位是怎么定的？**
> 3 次 × 500ms = 1.5 秒，足以过滤 GC（通常 <200ms），又不会反应太慢（高负载持续 1.5 秒才触发）。
> 80% 水位是留出 20% 缓冲余量，100% 时任务已经在排队，系统已经在承压；80% 是提前预警点。
> 实际这两个参数都应该是可配置的，根据业务压测结果调整。

**Q: 自适应限流的收缩和恢复是对称的吗？**
> 不是。收缩要谨慎（连续3次超80%才收缩），恢复也应该保守（连续3次低于50%才恢复），
> 避免「频繁收缩-恢复-收缩」的振荡。实际上可以把恢复阈值设得更低（如40%），让系统在低负载下充分恢复再扩容。

**Q: 令牌桶的令牌速率如何确定？每个站点一样吗？**
> 不一样，按站点频度等级差异化配置，HIGH 等级站点令牌速率高，LOW/DISUSE 等级站点令牌速率低。
> 令牌速率本身也受自适应模块动态调整，是一个「静态分配 + 动态微调」的双层控制。

### Level 3 — 故障场景

**Q: Redis 挂了，令牌桶失效，系统会怎样？**
> 令牌桶读 Redis 失败时，应该有降级策略：
> 方案一：降级为本地计数（单机令牌桶），失去跨机器一致性但不影响可用性
> 方案二：降级为放行所有请求，配合下游 Rhino 全局限流兜底
> 当时的处理是：Redis 异常时记录告警日志，本地降级为放行，Rhino 兜底

**Q: 如果一个大站的 Sitemap 解析异常卡死了一个 worker 线程怎么办？**
> 每个 worker 的解析任务都应该有超时控制（Future.get(timeout)）。
> 超时后 cancel Future，释放线程，记录该站点解析失败，下次调度周期重试。
> 没有做超时控制的话，worker 线程会一直被占用，相当于线程泄漏，最终线程池耗尽。

**Q: Mafka 消息重复消费怎么处理？**
> Mafka 和 Kafka 语义一样，at-least-once，消费失败会重投。
> 处理重复：URL 写 DB 时用唯一索引（url_hash），插入时 INSERT IGNORE 或 ON CONFLICT DO NOTHING，
> 天然幂等，重复消费不会产生重复 URL 记录。

### Level 4 — 延伸扩展

**Q: 如果要支持优先级队列（高频站点优先），SynchronousQueue 就不够用了，怎么改？**
> 换成 `PriorityBlockingQueue`，按站点频度等级排序，高等级任务优先被消费。
> 代价：PriorityBlockingQueue 无界（需要配合总量控制），且堆操作有 O(logN) 开销。

**Q: 这套系统能支持多大的规模？有没有遇到单点瓶颈？**
> Redis 令牌桶是按站点 key 分散的，单机 Redis QPS 在 10 万级别，对于我们的场景（几万个站点轮换抓取）完全够用。
> 真正的瓶颈是 DB 写入（新链记录入库），高峰期需要批量写入（batch insert）+ 写缓冲（先写内存队列，定期 flush）。

### 关于 SynchronousQueue + 并发重构

**Q: SynchronousQueue 默认是公平的还是非公平的？有什么区别？**
> 默认**非公平**（`new SynchronousQueue(false)`）。
> 非公平：put 进来的线程随机被某个 take 方取走，吞吐更高。
> 公平（`new SynchronousQueue(true)`）：FIFO 队列，按 put 顺序依次匹配，延迟更均匀但吞吐低。
> 爬虫场景对顺序无要求，选默认非公平模式，吞吐优先。

**Q: put() 一直阻塞的话，Mafka 消费者的 ACK 超时会怎样？**
> Mafka（基于 Kafka）的 ACK 是在消息**处理完后**手动提交 offset 的。
> 如果主线程阻塞在 `put()`，消费者既没 ACK 也没 NAK，Mafka Broker 会认为消息"还在处理中"。
> 超过 `max.poll.interval.ms` 后，Broker 判断消费者失活，触发 Rebalance，把这个分区重新分配给其他消费者，消息会被重投。
> **所以主线程不能无限自旋**，要设超时上限，超时后主动 NAK 让消息重投，而不是死锁。

**Q: 主线程"自旋等待线程池水位"，是忙等待（while true）吗？CPU 占用怎么办？**
> 纯忙等待会把一个 CPU 核跑满，不可取。
> 正确做法是 `Thread.sleep(N ms)` 间隔采样，每 N 毫秒检查一次线程池水位，在等待期间让出 CPU。
> N 的选取要权衡：太小（1ms）接近忙等待，太大（500ms）响应慢，通常选 10~50ms。

**Q: Mafka 分区从 200 扩容到 400，Key 的哈希路由会变吗？会影响顺序消费吗？**
> **会变**。Kafka 默认按 `hash(key) % partitionCount` 路由，分区数变了，同一个 key 可能路由到新分区。
> 对于需要顺序消费的场景（比如同一个 URL 的多次更新按顺序处理），扩容后顺序保证会被打破。
> 但 Sitemap 新链发现不关心顺序（URL 去重靠 DB 唯一索引），所以扩容没有顺序问题。

**Q: Rebalance 期间会不会丢消息？**
> 不会丢，但会有短暂停顿（Stop-The-World Rebalance）。
> Rebalance 期间所有消费者暂停消费，等待分区重新分配完成。期间消息积压在 Broker，不丢失。
> 用 Kafka 2.4+ 的 Incremental Cooperative Rebalance 可以减少停顿时间（不是所有分区同时暂停，而是分批迁移）。

### 关于三级限流 + 自适应

**Q: Redis Lua 脚本里的"当前时间"用客户端传入还是 Redis `TIME` 命令？**
> 应该用**客户端传入**（`System.currentTimeMillis()` 通过 ARGV 传给 Lua）。
> 原因：`Redis TIME` 命令返回的是 Redis 服务器时间，多台 Redis 主从节点时间可能有微秒级偏差；
> 而且 Redis Lua 里不允许调用不确定性命令（TIME 是非确定性命令，不能在 Lua 里用）。
> 客户端传入时间的缺点：多台应用服务器时钟如果不同步，令牌计算会出偏差——**所以机器要做 NTP 时间同步**。

**Q: 令牌桶的桶容量（burst size）怎么设？设太小会有什么问题？**
> 桶容量 = 允许的最大突发量。
> 设太小：高频站点一次性发来 100 个 URL，桶里只有 10 个令牌，90 个被拒绝，需要等下次补充才能继续，导致抓取不及时。
> 设太大：突发量太高，虽然令牌桶层面放行了，但下游线程池可能撑不住，和自适应限流的收缩逻辑冲突。
> 实践上，桶容量 = 速率 × N 秒，N 取决于业务允许的突发时间窗口，通常 5~30 秒。

**Q: Daemon 线程是什么？用 Daemon 线程的原因是什么？如果用普通线程会怎样？**
> Daemon 线程（守护线程）：当 JVM 里所有非 Daemon 线程都结束时，JVM 自动退出，Daemon 线程强制终止。
> 用 Daemon 线程的原因：采样线程是辅助功能，不应该阻止 JVM 正常退出。
> 如果用普通线程：JVM 关闭时（如 Ctrl+C），采样线程不退出，JVM 一直挂着无法关闭，需要强制 kill -9。
> 设置方式：`thread.setDaemon(true)` 必须在 `thread.start()` 之前调用。

**Q: 环形缓冲的大小 N 是多少？这个值怎么确定？**
> 代码里 N 通常取 10（可配置）。
> N 的含义：用最近 N 次采样（每次间隔 500ms）来判断，相当于看最近 N × 500ms = 5 秒内的趋势。
> N 太小（3次=1.5s）：反应灵敏但容易被短暂抖动误触发。
> N 太大（20次=10s）：抗抖动强但对真实高负载的响应慢，高负载已经持续 10 秒才降速，损失大。
> 实际上连续 3 次超阈值才触发，而不是所有 N 次，这是两个独立的参数，组合控制灵敏度。

**Q: 自适应收缩"配额"具体指什么？是修改 Redis 里令牌桶的速率吗？**
> 是的，收缩配额 = 动态调低 Redis 令牌桶的补充速率（每秒补充多少令牌）。
> 实现上：通过配置中心或直接更新 Redis 里存储速率的字段，Lua 脚本每次执行时读取最新速率。
> 另一种方案：不修改速率，而是直接减少向令牌桶提交的请求数（在提交前过滤掉一部分），避免修改共享状态。

### 关于 GZIP 解析

**Q: `read()` 返回 -1 和 `read()` 抛 IOException，有什么区别？**
> `-1`：流正常结束，所有数据已读完。
> `IOException`：读取过程中发生错误（网络断开、文件损坏、GZIP 数据不完整等）。
> 两种情况要分别处理：`-1` 是正常退出循环；`IOException` 要 catch 后记录日志并标记解析失败。

**Q: 如果 .gz 文件本身损坏（不是合法的 GZIP 格式），会发生什么？**
> `GZIPInputStream` 构造时或第一次 `read()` 时抛 `java.util.zip.ZipException`（`IOException` 的子类），
> 内容是 "Not in GZIP format" 或 "Corrupt GZIP trailer"。
> 应在 catch IOException 里处理，记录日志，标记该 Sitemap 解析失败，跳过而不是崩溃整个流程。

**Q: ByteArrayInputStream 和 GZIPInputStream 都是 InputStream，有什么区别？**
> `ByteArrayInputStream`：把 byte[] 包装成 InputStream 接口，读取的是内存里的原始字节，不做任何解码。
> `GZIPInputStream`：装饰器模式，包装另一个 InputStream，读取时实时解压 GZIP 数据。
> 两者组合：`new GZIPInputStream(new ByteArrayInputStream(gzBytes))`，
> 相当于告诉 GZIPInputStream"你的数据源是这个字节数组，请流式解压给我"。

**Q: 1KB 的缓冲区大小是怎么选的？太小会怎样，太大会怎样？**
> 1KB（1024字节）是一个常用的保守值。
> 太小（如16字节）：每次 `read()` 系统调用开销占比大，IO 效率低，循环次数多。
> 太大（如1MB）：缓冲区本身占内存，但 GZIPInputStream 解压是流式的，缓冲区只是中转站，内存占用不会累积。
> 实践上：HTTP流式读取通常用 4KB 或 8KB（匹配操作系统 Page Size），本地内存操作 1KB 够用。

### 关于频度调度

**Q: 新站点没有历史数据，三维打分会不会永远打低分（冷启动问题）？**
> 是一个真实的冷启动问题。
> 解法：新站点入库时赋予一个**默认初始分**（比如 compositeScore=0.5，对应 3 级 LOW 频度），而不是 0 分。
> 同时在第一次抓取后，根据实际发现的新链数量修正初始分，让系统快速感知该站点的真实价值。
> 这类似于 Bandit 算法里的"探索"策略——对新站点保持适度的抓取频率，收集足够数据再稳定评分。

**Q: Redis TTL 方案如何保证多台机器同时调度时，同一个站点只被投递一次？**
> 用 Redis 的 `SET NX EX`（SETNX + 过期时间原子操作）：
> ```
> SET station:{domain} 1 NX EX {ttl_seconds}
> ```
> `NX`（Not eXist）：只有 key 不存在时才设置成功，成功则投递；失败（key 已存在）则跳过。
> 这是分布式锁的最简形式：多台机器同时执行这条命令，只有一台 SET 成功，天然互斥。

**Q: 如果一个站点的 Sitemap 抓取失败了，TTL 还在，下次要等 TTL 到期才能重试吗？**
> 是一个设计缺陷。抓取失败时应该**主动删除 Redis key**，让调度系统可以立刻重试，而不是等 TTL 自然到期。
> 更完整的方案：抓取结果回写时分两种情况——成功则更新 TTL（正常冷却），失败则删 key 或设一个短 TTL（快速重试间隔）。

**Q: compositeScore 的权重 0.5/0.5 是怎么确定的？做过 A/B 测试吗？**
> 坦白说初版是经验拍的（新链接价值和留存质量对等考虑）。
> 严格做法是：
> 1. 先用历史数据回放，对比不同权重组合下，高频站点的实际新链产出和资源消耗比
> 2. 然后小流量 A/B 测试，验证哪组权重下整体新链质量（留存率）更高
> 当时项目周期有限没有做完整 A/B，权重是可配置的，后续可以动态调整。

### 跨模块综合追问

**Q: 整个系统日均 75 亿新链，写 DB 的压力怎么处理的？**
> 75 亿条 URL 不能每条都同步写 DB，会把 DB 打死。
> 实际链路：新链先写 Redis Set（内存去重），积累到一定数量后**批量 INSERT** 到 DB（batch insert）。
> 批量写入减少 DB 连接次数，每批几百到几千条，DB 写入 QPS 从几十万降到几千。
> 另外 URL 表加了 `url_hash` 唯一索引，批量写用 `INSERT IGNORE`，天然幂等去重。

**Q: 简历上写"日均新链发现最高达 75 亿"，这个数字是怎么统计的？**
> 通过系统的埋点日志统计：每条消息处理完后打点（新链数量、站点 domain、时间戳），
> 日志聚合到 Kafka → 日志平台，按天汇总得出日均新链数。
> "最高达"说明是峰值，平均值更低（受站点更新频率影响，比如新闻类站点更新快，周末流量低）。
