## 一、实习经历介绍（美团 Friday 数据组）

### 1.1 整体定位（30秒版，开场必备）

> "我在美团 Friday 数据组实习了将近一年，主要负责 Sitemap 新链发现环路的后端开发。
> 简单说，就是从海量网站的 Sitemap 文件里找到新 URL，喂给 LongCat 大模型做预训练语料。
> 我参与了从抓取、解析、清洗到调度的整个链路建设，重点产出了并发重构、限流体系、频度调度等几个核心需求。"

---

### 1.2 五大核心产出（每个控制在 1-2 分钟）

---

#### ① 多线程并发重构 + Mafka 扩容（重点，并发必考）

**背景**：原来系统是单线程同步消费 Mafka 消息，每条消息同步处理耗时约 15 秒，吞吐严重不足，小时抓取量只有 2.5 万。

**我做了什么**：
- 架构改为「回调线程 + 业务线程池」异步并行模型
- 用 **SynchronousQueue** 作为中间队列，它没有缓冲，天然有背压效果——业务线程池满时主线程会自旋等待，既防止消息堆积，又保证不丢消息
- 同步把 Mafka 从 200 分区扩容到 400 分区，消除了传输侧的瓶颈

**效果**：小时抓取量从 **2.5 万飙升到 96 万+**，日均新链发现最高达 **75 亿**。

**面试可能追问**：
- *为什么用 SynchronousQueue 而不是 ArrayBlockingQueue？*
  → SynchronousQueue 每次 put 必须等对应的 take，天然实现流控；ArrayBlockingQueue 有缓冲，线程池满之前堆积不可见。
- *如何保证消息不丢？*
  → 主线程自旋等待而不是直接丢弃；提交失败时记录日志+重试，结合 Mafka 的消费确认机制。

---

#### ② 三级限流 + 动态自适应限流体系（架构题）

**背景**：大站（如淘宝）因为 Sitemap 文件超多，会把线程池占满，挤兑小站资源。固定阈值无法感知实时负载。

**我做了什么**：

三级递进限流：
1. **集群层 + 单机层**：用 Rhino（美团内部限流框架）做粗粒度保护下游服务
2. **站点层**：用 **Redis + Lua 令牌桶**精确限制每个站点的访问频率
3. **前置拦截**：无效流量（空 Sitemap、格式错误等）在消耗任何资源前就拦截掉

自适应调速：
- 用 **Daemon 线程**定时采样线程池当前活跃线程数（健康度 = 活跃/总数）
- 用**环形缓冲**记录最近 N 次采样，连续 3 次超过 **80% 水位**才触发配额收缩
- 避免了单次抖动就修改线程池带来的频繁震荡

**效果**：大站挤兑小站问题基本解决，调度公平性显著提升。

**面试可能追问**：
- *为什么要连续3次才触发，一次超阈值不行吗？*
  → 防止瞬时抖动（比如 GC 暂停）误触发调速，引入不必要的震荡。
- *令牌桶为什么用 Lua 脚本？*
  → 保证 Redis 上"查剩余令牌 + 扣减 + 更新"三步原子执行，避免并发竞争。

---

#### ③ GZIP 压缩 Sitemap 解析（问题发现 + 快速落地）

**背景**：发现日志里大量 `.gz` 格式的 Sitemap 被直接丢弃，打点后发现日均流失 **400 万+ 新链**。

**我做了什么**：
- 用 **GZIPInputStream** 流式解压，避免把整个 gz 文件加载到内存
- 字节数组经 `ByteArrayInputStream → GZIPInputStream → 1KB 缓冲` 循环读取，转 UTF-8 后无缝接入原有解析链路

**效果**：推全后新链发现从 **3.79 亿激增到 52.6 亿**，14 倍产出增长。

**面试可能追问**：
- *为什么用流式而不是一次性解压到内存？*
  → 大型 Sitemap 压缩前可能几百 MB，一次性加载会 OOM；流式读取内存占用始终是缓冲区大小（1KB）。

---

#### ④ 站点频度调度策略（调度系统设计）

**背景**：原来每天固定全量调度一次，高频更新的站点遗漏新链，低频的站点白白浪费资源。

**我做了什么**：
- 设计**三维打分模型**：`新链接分 × 0.5 + (留存率分 × 0.5 + 规模分 × 0.5) × 0.5`，得出 compositeScore
- 划分 **5 级频度**（HIGH → PENDING），平滑降级（每次最多降 1 级，防止过度惩罚）
- 抓取侧用 **Redis TTL** 差异化控制每个站点的重复抓取间隔
- 多定时任务支持一天多轮投递，高频站点一天可多次调度

**效果**：Sitemap 日新链产出从 **10~70 亿提升至 100~200 亿**。

---

#### ⑤ DSL 规则引擎治理（质量 + 性能）

**背景**：质检发现大量参数爆炸、路径随机的作弊站点混入链路，污染训练语料。

**我做了什么**：
- `@PostConstruct` 阶段**正则表达式一次性预编译缓存**，避免每次请求重复编译
- 用 `@MdpConfigListener` 监听配置中心变更，变更时自动重编译，**秒级热更新**规则
- 拦截逻辑**前置于所有资源消耗操作**（DB 查询、线程池提交等）之前

**效果**：抽样高质量站点率从 **4.1% 提升到 11.9%**，接近 3 倍提升。

## 二、个人项目介绍（智析 RAG）

### 2.1 整体定位（30秒版）

> "智析 RAG 是我自研的一个企业级检索增强生成对话系统，基于 Spring AI 框架构建。
> 核心能力是把 PDF/Markdown/TXT 文档解析入库后，支持语义问答。
> 我重点做了多通道并行检索、多模型熔断路由、意图树三级分类、对话记忆摘要压缩这几个核心模块，
> 整个 RAG 流水线从接收问题到返回答案，每个步骤都有链路追踪记录。"

---

### 2.2 系统架构 — 先给面试官一张脑图

```
用户问题
   ↓
① 查询改写（QueryRewriter）      ← LLM 改写，提升召回质量
   ↓
② 意图分类（IntentClassifier）   ← LLM + 三级意图树，判断知识库归属
   ↓
③ 短路判断                       ← 系统/闲聊意图 → 直接 LLM 回复，跳过向量检索
   ↓
④ 多通道并行检索（MultiChannelRetriever）
   ├── 全局向量检索（覆盖全量知识库）
   └── 意图定向检索（按 kb_id 过滤，精度高）
   ↓
⑤ LLM 重排序（DocumentReranker） ← 语义相关性打分，取 Top-3
   ↓
⑥ Prompt 组装（RAGPromptService）← 拼接上下文 + 格式化文档片段
   ↓
⑦ 路由流式输出（RoutingChatService + 熔断器）← SSE 推送
```

---

### 2.3 五大核心模块详解

---

#### ① 多通道并行检索（高频考点：并发 + 检索）

**问题**：单通道全局向量检索，精度低；但如果只做意图定向，知识库分错了召回率就崩了。

**解法**：用 `CompletableFuture` 同时发起两条通路：
- **全局通道**：覆盖全量向量空间，保底召回率
- **意图定向通道**：按 `kb_id` 字段过滤，精准定位目标知识库
- 两路结果合并时，意图定向结果优先放在前面，再去重（按 document id）
- 意图置信度低于 0.5 时，不传 kb_id，只走全局通道

**关键代码思路**：
```java
CompletableFuture<List<Document>> globalFuture  = CompletableFuture.supplyAsync(() -> globalSearch(...));
CompletableFuture<List<Document>> intentFuture  = CompletableFuture.supplyAsync(() -> intentDirectedSearch(...));
// 设置 10 秒超时，超时降级为单走全局通道
List<Document> global = globalFuture.get(10, TimeUnit.SECONDS);
List<Document> intent = intentFuture.get(10, TimeUnit.SECONDS);
```

**面试追问**：
- *超时了怎么办？* → cancel 两个 future，降级为同步全局检索。
- *为什么意图定向结果要放前面？* → 精度更高，重排序时给它更好的初始排名。

---

#### ② Chat & Embedding 双维熔断路由（高可用设计）

**问题**：AI 模型 API 会偶发限流、超时、返回空流，单模型挂了整个系统就挂了。

**解法**：为 Chat 和 Embedding 分别实现**三态熔断器**：
- `CLOSED`（正常）→ 连续失败 N 次 → `OPEN`（熔断，拒绝调用）
- `OPEN` 超过配置的等待时间 → `HALF_OPEN`（半开，放行一个探测请求）
- 探测成功 → 回 `CLOSED`；探测失败 → 重回 `OPEN`

Chat 路由额外引入**首包探测**（ProbeStreamBridge）：
- 缓冲第一个 SSE chunk，如果是空或错误则立刻切换下一个候选模型
- 防止脏数据已经开始发送给用户才发现模型故障

每个模型独立维护熔断状态，用 `ConcurrentHashMap<candidateId, BreakerEntry>` 存储。

**面试追问**：
- *为什么 Chat 要额外做首包探测？* → HTTP 200 状态码不代表流式内容正常，模型可能返回空流；首包探测比等整个响应失败更快发现故障。
- *多模型候选如何配置？* → 在 application.yaml 的 `ai.chat.candidates` 列表里按优先级配置，框架自动按序路由。

---

#### ③ 意图树三级分类（缩小检索空间）

**问题**：用户问题类型多样，全库检索精度低，但手动维护分类规则成本极高。

**解法**：构建**领域 → 类目 → 话题**三级意图树，存储在 DB + Redis 缓存（内存树结构）：
- 将意图树序列化成文本，拼入 Prompt，让 LLM 对用户问题分类，返回叶子节点 ID
- 系统/闲聊意图直接短路返回，不走向量检索，降低无效调用
- 置信度低于阈值时不传 kb_id，防止分错类比不分类更糟

**面试追问**：
- *意图树放 Redis 有什么好处？* → 意图树更新后 Redis 同步刷新，所有实例秒级感知，无需重启。
- *为什么用 LLM 分类而不是传统分类器？* → 意图树节点描述是自然语言，LLM 的语义理解能力更适合，且不需要准备训练数据。

---

#### ④ LLM 重排序提升上下文质量

**问题**：向量相似度（余弦距离）只衡量语义接近程度，不等于"回答这个问题最有用"。

**解法**：向量检索召回多个文档片段后，再用 LLM 对每个片段与问题的相关性打分（0~10），按分数降序取 **Top-3** 注入 Prompt。

**实现细节**（代码层面可以直接讲）：
- 对每个召回文档**串行**调用一次 LLM 打分，超过 800 字的内容先截断，防止单个 prompt 过长
- 评分失败的文档默认赋分 0，排在末尾而不是丢弃
- 最终用 `Comparator.comparingDouble(score).reversed().limit(topK)` 取 Top-3

**`enableRerank` 开关的含义**：
- `RagPipelineContext` 里有一个 `boolean enableRerank` 字段，由调用方（前端请求/API）在创建上下文时传入
- 开关关闭时，流水线直接对检索结果截取前 3 条，跳过 LLM 打分步骤，节省 N 次 API 调用的延迟
- 也就是说**重排序不是默认必须开启的**，调用方可以根据场景选择：对延迟敏感的场景关掉，对精度要求高的场景开启
- 这是一种**渐进增强**设计思路：核心链路（检索 + 回答）保证可用，重排序是可插拔的质量提升层

**面试追问**：
- *串行打分延迟会不会太高？* → 召回 6 条文档就要调用 6 次 LLM，确实是明显开销。可以改进为并行打分（CompletableFuture 并发），但要控制对下游模型的 QPS 冲击；或者换成专用的 rerank 模型（如 BGE-Reranker），延迟比 Chat 模型低得多。
- *为什么不直接用 Spring AI 的 Reranker 接口？* → 当时做的时候 Spring AI 的 Reranker 抽象还不完善，自己实现更灵活，也更好理解整个打分逻辑。

---

#### ⑤ 持久化对话记忆 + 摘要压缩（Token 控制）

**问题**：多轮对话历史全部塞进 Prompt，Token 数量随对话轮数线性增长，成本爆炸，且大部分模型有上下文窗口上限。

**两层设计**：

**第一层 — historyKeep（窗口截断）**：
- `get()` 方法每次从 DB 只取最近 **20 条**消息注入 Prompt（可配置）
- 相当于一个滑动窗口，保证每次调用的 token 量有界
- 但仅靠截断会丢失早期的关键上下文

**第二层 — 摘要压缩（解决截断丢信息问题）**：
- 每次 `add()` 写入消息后，检查该会话消息总条数
- 超过 **summaryStartTurns × 2**（默认 10 轮 = 20 条）时触发压缩
- 压缩策略：取最旧的**一半**消息 → 调用 LLM 生成不超过 200 字的摘要 → 以 `SystemMessage("[对话摘要]\n...")` 写回 DB → 删除被摘要的原始消息

**两层配合的效果**：
```
早期对话                     近期对话
[摘要: 用户问了XXX, 结论是YYY] [最近20条原始消息...]
     ↑ 压缩后只占1条              ↑ 滑动窗口保留
```
这样无论对话多长，注入 Prompt 的内容始终是：1条摘要 + 最近 N 条原始消息，token 量受控。

**历史加载与保存的完整时序**（这是最容易被问到的）：

整个读写由 Spring AI 内置的 `MessageChatMemoryAdvisor` 自动完成，挂在 `ChatClient` 的 advisor 链上，业务代码不感知：

```
用户发消息 → streamChat(prompt, conId)
    ↓
[调用前] MessageChatMemoryAdvisor
    → chatMemory.get(conId)       ← 从 DB 取最近 historyKeep 条，拼到消息头
    ↓
LLM 收到 [历史 + 当前问题] → 生成回答
    ↓
[调用后] MessageChatMemoryAdvisor
    → chatMemory.add(conId, [用户消息, AI回答])  ← 写入 DB（每轮 +2 条）
    → tryCompress()               ← 检查是否触发摘要压缩
    ↓
SSE 推送结果给前端
```

**压缩频率不是每次都触发** — 有自然节流：

```
初始：DB = 20 条，条件是 total > 20 才压缩，所以此时不触发

第 21 条写入后：total = 22 → 触发
  压缩：删除最旧 11 条 → 写入 1 条摘要 → total = 12

之后每轮 +2：12→14→16→18→20→22 → 大约再过 5 轮才再次触发
```

结论：**每隔约 5 轮触发一次压缩**，不是每次提问都压缩。

**关键实现细节**：
- 用 `JdbcTemplate` 直接操作 PG，无 ORM 依赖，轻量
- 摘要生成失败时**静默跳过**，不影响主流程（容错设计）
- 摘要 ID 插入在被删除消息之后，保证时间顺序正确

**面试追问**：
- *历史是每次请求都从 DB 查吗，有没有缓存？* → 当前实现每次都查 DB，没有额外缓存。如果 QPS 高可以加 Redis 缓存该 conId 的最近 N 条，但要处理缓存和 DB 的一致性问题（add 时同步更新缓存）。
- *为什么压缩最旧的一半，而不是全部？* → 保留最近的对话连贯性，只压缩距离当前较远但又不想丢弃的历史。
- *如果摘要生成本身也很慢怎么办？* → 可以改为异步压缩，当前请求不等待，后台线程完成后下次对话才生效；代价是有一次请求的 token 稍多。
- *historyKeep 和 summaryStartTurns 的关系是什么？* → 两者独立控制：summaryStartTurns 控制何时触发压缩（写入侧），historyKeep 控制注入 Prompt 几条（读取侧）。默认配置 summaryStartTurns=10、historyKeep=20，超过 10 轮就压缩旧历史，但每次最多注入 20 条给模型。

#### ⑥ SSE 流式响应实现原理

**问题**：LLM 生成回答是逐 token 输出的，如果等全部生成完再返回，用户要等十几秒才看到第一个字，体验极差。

**解法**：用 **Server-Sent Events（SSE）** 实现服务端实时推送。

**整体链路**：

```
LLM 模型（Flux<String> 响应流）
    ↓ 每生成一个 token
subscribe.onNext(chunk)
    ↓
emitter.send(SseEmitter.event().data(chunk))
    ↓ HTTP 响应头: Content-Type: text/event-stream
前端 EventSource 持续接收，逐字渲染
```

**服务端关键代码逻辑**（`RoutingChatService`）：

```java
// ChatClient.stream() 返回 Flux<String>，每个元素是一个 token chunk
Flux<String> flux = buildSpec(...).stream().content();

flux.subscribe(
    chunk -> {
        // ① 首包探测：第一个 chunk 到达 → 证明模型正常
        if (probeCompleted.compareAndSet(false, true)) {
            circuitBreaker.markSuccess(entry.id());
            probeFuture.complete(true);  // 通知主线程探测成功
        }
        // ② 实时推送给前端
        emitter.send(SseEmitter.event().data(chunk));
    },
    error -> {
        // 失败：触发熔断，切换下一个候选模型
        circuitBreaker.markFailure(entry.id());
        probeFuture.complete(false);
    },
    () -> emitter.complete()  // 流结束，关闭 SSE 连接
);

// 主线程等待首包，最多等 10 秒
boolean success = probeFuture.get(10_000, TimeUnit.MILLISECONDS);
```

**为什么用 CompletableFuture + probeFuture 做首包探测？**

因为 `flux.subscribe()` 是**异步非阻塞**的，主线程调用 subscribe 后会立刻返回，不等流结束。
但路由逻辑需要知道"这个模型有没有成功出第一个 token"，才能决定是否切换候选模型。
所以用 `probeFuture.get()` 让主线程阻塞等待，第一个 chunk 到达或超时后再决策。

**与 WebSocket 的区别**：
- SSE 是单向推送（服务端 → 客户端），基于普通 HTTP 长连接，实现简单，天然支持 CDN/代理
- WebSocket 是双向全双工，适合实时聊天室等需要客户端主动推送的场景
- 对话 AI 的回答流只需要服务端单向推，SSE 完全够用，且不需要 WS 的握手升级协议

**面试追问**：
- *SSE 连接断了怎么办？* → 客户端 `EventSource` 默认会自动重连；服务端 `emitter.send()` 抛 IOException 时捕获并 dispose 订阅，避免资源泄漏（代码里有这个处理）。
- *Spring 的 SseEmitter 是在哪个线程完成的？* → subscribe 的回调跑在 Reactor 的 IO 线程上，不是 Spring MVC 的请求线程；SseEmitter 内部有锁，线程安全。
- *如果模型返回了 HTTP 200 但流里全是错误怎么办？* → 这正是首包探测解决的问题：空流（onComplete 但没有任何 chunk）也被判定为失败，`probeFuture.complete(false)`，触发切换候选模型。

### 2.4 数据流 + 技术栈一句话总结（结尾用）

> "整个 RAG 系统用 Spring Boot + Spring AI 搭建，向量库用 PgVector（可切换 Milvus），
> 存储用 PostgreSQL + Redis，消息队列用 RocketMQ 触发异步入库，
> 文档解析用 Apache Tika 支持 PDF/Markdown/TXT，
> 前端通过 SSE 实时接收流式回答。"

## 三、通用追问准备

### 项目最难的地方是什么？
> "我觉得最难的是熔断路由和流式响应结合的部分。普通熔断是同步调用，好判断成功失败；
> 但流式 SSE 是持续推送的，HTTP 200 不代表内容正确，可能流到一半 token 就停了，或者一开始就是空流。
> 我设计了一个首包探测机制，缓冲第一个 chunk，如果检测到异常就立刻 cancel 当前流，切换下一个候选模型，
> 避免把错误内容已经发送给用户。"

### 如果让你重新设计，会改什么？
> "意图分类目前是同步调用 LLM 的，每次问答都有一次额外的 API 调用开销。
> 如果重新设计，可以考虑把意图分类做成异步并行——和查询改写同时发起，
> 改写完就可以直接用意图结果，不需要串行等待。
> 另外重排序也可以做成流式并行，检索到一批就开始重排，不需要等全部检索完。"

### 项目难点 vs 实习难点的区别？
> "实习更多是工程复杂度：系统规模大、链路长、需要考虑分布式场景下的并发安全和背压；
> 自研 RAG 更多是 AI 系统特有的挑战：模型输出不确定性、流式响应的错误感知比较难、
> 以及如何在检索精度和覆盖率之间做取舍。"
