### 难点 1：SynchronousQueue 背压 vs 其他队列（并发设计）

**场景**：单线程消费 Mafka → 改为「回调线程 + 业务线程池」异步模型，用什么队列连接两者？

**选 SynchronousQueue 的理由**：
- SynchronousQueue **没有缓冲区**，每次 put 必须等到有 take 才能返回
- 天然背压：业务线程池满时，回调线程的 put 会阻塞，主线程自旋等待，消息不会积压也不会丢
- 相当于「直连管道」，生产速度自动跟着消费速度走

**对比其他方案**：

| 方案 | 缺点 |
|------|------|
| `ArrayBlockingQueue(N)` | 有缓冲，线程池满之前积压不可见，OOM 风险 |
| `LinkedBlockingQueue` | 无界或有界，满时才背压，响应慢 |
| `直接 submit + 拒绝策略` | 拒绝时消息丢失，需要额外重试逻辑 |
| `SynchronousQueue` ✅ | 无缓冲直连，天然背压，最简单可靠 |

**面试可能追问**：
- *SynchronousQueue put 阻塞会不会把 Mafka 回调线程卡死？*
  → 主线程自旋检测线程池水位，不是在回调线程里直接 put；Mafka 的 ACK 机制保证消息不丢。
- *Mafka 扩容 200→400 分区为什么能提升吞吐？*
  → 分区是 Kafka 并行消费的最小单元，分区数 = 最大消费者并行度上限；原来 200 分区限制了最多 200 个并发消费线程，扩容后打开了传输侧瓶颈。

### 难点 2：三级限流体系设计（限流架构）

**三级递进逻辑**：

```
请求进来
  ↓
① 集群层 Rhino（保护下游服务整体 QPS）
  ↓
② 单机层 Rhino（防止单机过载）
  ↓
③ 站点层 Redis+Lua 令牌桶（精确限制每个站点频率）
  ↓
④ 前置无效流量拦截（DSL规则引擎，空Sitemap/作弊站点早退）
```

**为什么站点层用 Redis + Lua 令牌桶而不是本地限流**：
- 多台机器同时抓同一个站点，本地计数无法汇总
- Redis 统一计数，Lua 脚本保证「查余量 + 扣减 + 写回」三步原子执行，无并发竞争

**令牌桶 vs 漏桶对比**：
- 漏桶：匀速出水，严格限制输出速率，突发流量被削平
- 令牌桶：允许积累令牌，可以应对突发（比如站点刚发布大量新 URL），更适合网络爬虫场景

**自适应限流核心设计点**：
- 用 Daemon 线程（不阻塞 JVM 退出）定时采样线程池健康度 = 活跃线程数 / 总线程数
- 用**环形缓冲**记录最近 N 次采样，而非单次采样，原因：**防止 GC Pause、网络抖动等瞬时因素误触发**
- 连续 3 次超过 80% 水位才收缩配额，避免「单次超标 → 频繁调整 → 线程池抖动」的震荡问题

**面试可能追问**：
- *为什么是 80% 水位而不是 100%？*
  → 100% 时线程池已经排队，已经在损害性能；80% 是提前预警，给系统留出反应时间。
- *令牌桶 Lua 脚本大概怎么写？*
  → 原子地：读当前令牌数和上次补充时间 → 按时间差补充令牌（不超过桶容量）→ 若有余量则扣减一个令牌返回成功，否则返回失败。

### 难点 3：GZIP 流式解析 vs 一次性加载（内存管理）

**为什么用流式，不一次性解压到内存**：
- 大型 Sitemap 文件压缩前可能几百 MB，一次性解压到 byte[] 会 OOM
- `GZIPInputStream` 流式读取：每次只读 1KB 缓冲，内存占用始终恒定

**调用链**：
```
byte[] rawBytes
  → ByteArrayInputStream（把字节数组包装成 InputStream）
  → GZIPInputStream（流式解压层）
  → 1KB byte[1024] 循环 read()
  → 每次 read() 返回实际读取字节数，返回 -1 表示流结束（不是 null！）
  → 拼接为 UTF-8 字符串，接入原有解析链路
```

**面试可能追问**：
- *read() 返回 -1 还是 null 表示结束？*
  → **返回 int -1**，不是 null。`read()` 返回的是实际读取的字节数（≥1），-1 表示已到流末尾。（曾经答错过，重点）
- *为什么不用 Files.readAllBytes 然后再解压？*
  → 文件字节已经在 byte[] 里（从 Mafka 消息拿到），问题是解压后的尺寸；流式解压解决的是解压后内存膨胀的问题。

### 难点 4：站点频度调度三维打分模型（调度系统设计）

**为什么要打分而不是简单按抓取量排序**：
- 单看抓取量：大站天然占优，小站永远低频
- 三维组合：新链接分（增量价值）+ 留存率分（质量）+ 规模分（体量），综合评估站点健康度

**打分公式**：
```
compositeScore = newUrlScore × 0.5 + fuzzyScore × 0.5
fuzzyScore     = rateScore × 0.5 + scaleScore × 0.5
```

**为什么降级每次最多降 1 级**：
- 防止某个站点因一次网络抖动或临时停更被降到最低级，再也没机会恢复
- 平滑降级，配合多轮观察（Ring Buffer 思想）避免误判

**Redis TTL 差异化控制重复抓取间隔的原理**：
- 每个站点抓取后在 Redis 设 key，TTL = 该站点等级对应的冷却时间
- 调度时检查 key 是否存在，存在则跳过（在冷却期），不存在则可以重新投递
- 5 级站点 TTL 各不同，高频站 TTL 短（如 6 小时），低频站 TTL 长（如 7 天）

**面试可能追问**：
- *多定时任务并发投递同一站点怎么避免重复？*
  → Redis 的 SET NX（如果不存在则设置）操作，只有一个任务能拿到锁，其他任务跳过该站点。

### 难点 5：DSL 规则引擎正则预编译 + 热更新（性能 + 运维）

**为什么要预编译**：
- `Pattern.compile()` 很耗时（涉及正则编译为 NFA/DFA），每次请求编译 = 每次都做一次重型 CPU 操作
- `@PostConstruct` 阶段一次性编译，结果缓存到 Map，请求时直接 `pattern.matcher(url).matches()`，O(1) 获取 Pattern

**为什么 Pattern 不能存 HashSet**：
- `Pattern` 类没有重写 `equals()` 和 `hashCode()`，两个相同正则字符串的 Pattern 对象 `equals` 结果为 false
- 应该用 `Map<String, Pattern>`，用正则字符串作 key

**热更新为什么能做到秒级**：
- `@MdpConfigListener` 监听配置中心推送，配置变更时立刻触发回调
- 回调里重新 compile 正则、替换 Map 中的旧 Pattern，整个替换是原子的（ConcurrentHashMap 或加锁）
- 不需要重启服务，0 停机时间更新规则

**面试可能追问**：
- *正则替换时，如果有请求正在用旧的 Pattern 怎么办？*
  → 旧 Pattern 对象已被线程引用，不会立刻 GC；新请求用新 Pattern；最终旧 Pattern 无引用后被回收，不影响正确性。
- *Pattern 实例是线程安全的吗？*
  → `Pattern` 本身是**线程安全**的（不可变对象），`Matcher` 不是（每次 `matcher()` 创建新实例即可）。

### 难点 6：查询改写（Query Rewrite）解决多轮对话检索退化

**问题根源**：
多轮对话中用户常说「它是什么」「上面那个原理」等指代性表达，这类句子直接做向量检索，向量化后的语义几乎是「空的」，召回率极差。

**解法**：在检索前用 LLM 把问题改写为「独立的完整语义查询」：
```
原始问题：「它的底层原理是什么？」
改写后：「Spring AOP 的底层实现原理是什么？」（根据上下文补全指代）
```

**设计细节**：
- 改写通过 Prompt 模板（`query-rewrite.st`）驱动，模板里有改写规则说明
- 改写失败时**降级使用原始 query**，不中断流程
- `enableRewrite` 开关控制是否启用（同 rerank，灵活可配）

**面试可能追问**：
- *改写和不改写，效果差多少？*
  → 对短指代句子（「它」「那个」「上面说的」）效果差异极大，几乎0召回 vs 正常召回；对完整问题影响不大。
- *改写会不会改错，把问题改偏？*
  → 有这个风险，所以改写失败或改写结果为空时降级为原始 query；实际使用中改写正确率取决于 Prompt 设计质量。

### 难点 7：三态熔断器的并发安全设计（高频考点）

**三态转换规则**（必须熟背）：
```
CLOSED → 正常放行所有请求
  连续失败 >= threshold
OPEN → 拒绝所有请求
  等待 openDurationMs
HALF_OPEN → 只放行一个探测请求
  探测成功 → CLOSED
  探测失败 → OPEN（重新计时）
```

**并发安全细节**（代码里 `synchronized` 的原因）：
- `allowCall / markSuccess / markFailure` 三个方法都加了 `synchronized`
- 因为状态变更是「读取 + 判断 + 修改」的复合操作，必须原子执行
- 例如：两个线程同时进入 HALF_OPEN 的 allowCall，如果不加锁可能同时拿到 `probeInFlight = false`，都放行，变成两个探测并发，违反「只放行一个探测」的语义

**`probeInFlight` 字段的作用**：
- 标记「已经有一个探测请求在途中」
- HALF_OPEN 状态下第二个 allowCall 进来，发现 `probeInFlight = true`，直接返回 false
- 探测结束（成功或失败）后，`markSuccess / markFailure` 把它重置为 false

**面试可能追问**：
- *为什么用 synchronized 而不是 CAS？*
  → 熔断器的状态变更是多字段联动（state + failureCount + openedAt + probeInFlight），CAS 只能原子更新单个变量，多字段用 synchronized 更清晰可靠；且熔断器调用频率不高，synchronized 锁竞争不是瓶颈。
- *BreakerEntry 里的 state 字段为什么是 volatile？*
  → `state` 的读取在 `allowCall` 里加了 synchronized，所以并发读写本来是安全的。但代码里有 `volatile` 是防止 JIT 过度优化（寄存器缓存）把 state 的更改对其他线程不可见，属于防御性编程。

### 难点 8：文档入库 ETL 流水线 + 双策略分块（文档处理）

**完整入库流水线**（上传文件触发的异步链路）：

```
用户上传文件（MultipartFile）
  ↓ @Transactional
① 文件字节写入 DB（t_knowledge_document_file）
② 文档元数据写入 DB（状态 pending）
③ ingestionService.ingest(docId)  ← @Async，立刻返回响应
  ↓ （异步线程池 ingestionExecutor 中执行）
④ 从 DB 读取文件字节
⑤ 按文件类型解析为纯文本
   - PDF：PagePdfDocumentReader → 如文字图层为空 → Tesseract OCR 兜底
   - Markdown：MarkdownDocumentReader（保留代码块、引用块结构）
   - TXT：直接 UTF-8 解码
⑥ 选择分块策略：
   - Markdown → StructureAwareChunker（结构感知，按标题/代码块边界切分）
   - 其他 → FixedSizeChunker（固定大小，按字符数切分 + overlap）
⑦ 元数据增强（可选）：关键词提取 / LLM 摘要生成
⑧ 逐块调用 VectorStore.add()
   → RoutingEmbeddingService（带熔断路由）→ Ollama bge-m3 向量化
   → 写入 PgVector 向量库（附带 doc_id, kb_id 等 metadata）
⑨ 更新文档状态：success / failed
```

**为什么 Markdown 要单独设计结构感知分块器**：
- 固定大小分块可能把一个代码块切成两半，或把标题和内容分到不同 chunk
- 检索时 LLM 拿到半截代码块或孤立标题，答案质量极差
- 结构感知分块在**块边界**切分（标题、代码围栏、空行），保证每个 chunk 语义完整

**结构感知分块三步走**：
1. **扫描**：线性扫描文本，识别 Heading / CodeFence / Atomic / Para 四类结构块，记录各块的 [start, end) 坐标
2. **打包**：按 min/target/max 预算合并相邻块，不在块内部切割
3. **物化**：把坐标区间转成字符串，追加 overlap（把上一块尾部 N 个字符加到下一块开头，保证相邻 chunk 有重叠上下文）

**Overlap 的作用**：
- 向量检索基于语义，如果一句话被切到两个 chunk 边界，两个 chunk 都只有半句话，语义不完整
- 在下一块开头重复上一块的尾部内容，保证语义连续性，提升召回率

**面试可能追问**：
- *图片型 PDF 怎么处理？*
  → PDF 有两种：文字 PDF（有文字图层，直接提取文字）和图片 PDF（扫描件，只有图片）。代码里先尝试文字图层提取，若结果为空则降级用 Tesseract OCR 逐页渲染 300DPI 图片后识别，支持中英文混合。
- *为什么逐块调用 VectorStore.add() 而不是批量 add(all)？*
  → 单块失败不终止整体入库，每块独立处理可以精确记录哪块失败并跳过，比批量 add 更容错。
- *vectorStore.add() 内部向量化是怎么触发的？*
  → Spring AI 的 VectorStore 内部持有 EmbeddingModel，add() 时先调用 EmbeddingModel 对文本向量化得到 float[]，再把向量和 metadata 写入 PgVector。我们的 EmbeddingModel 被替换为带熔断的 `CircuitBreakerEmbeddingModel`，透明接入了路由降级。

### 难点 9：意图树三级分类缩小检索空间（RAG 精度优化）

**为什么需要意图分类**：
- 一个企业知识库通常有多个领域（产品文档、技术文档、FAQ 等）
- 不分类直接全局检索：结果混杂，无关 chunk 占位，降低 LLM 答题质量
- 分类后定向到目标知识库检索：精度更高，token 消耗更少

**三级树的设计**：
```
领域（Domain）
  └── 类目（Category）
        └── 话题（Topic，叶子节点，对应具体知识库 kbId）
```

**LLM 分类的 Prompt 设计关键**：
- 将整棵意图树序列化为文本（树形缩进格式），连同用户问题一起送给 LLM
- LLM 只需返回一个整数（叶子节点 ID）或 -1（闲聊/通用）
- 输出格式极简，解析不会出错（`Long.parseLong(response.strip())`）
- 解析失败（非整数）时降级为 `IntentResult.unknown()`，不抛异常

**系统意图短路的价值**：
- 闲聊（「你好」「今天天气怎样」）、系统指令（「清除记忆」）走另一条路
- 跳过向量检索、重排序等耗时步骤，直接用 LLM 回答，延迟从 ~2s 降到 ~0.3s

**置信度阈值 0.5 的作用**：
- 当 LLM 返回的节点 ID 对应的知识库与用户问题明显不符时（置信度低），不传 kbId 给定向通道
- 防止「分错了知识库 → 定向检索 → 精度比全局检索还差」的反效果

**面试可能追问**：
- *意图树更新了（新增/删除节点），怎么不重启服务？*
  → 意图树加载后存入 Redis 缓存（`IntentTreeCacheManager`），DB 变更后手动或通过接口触发缓存刷新，所有实例下次请求时重新加载。
- *意图树特别大（几百个节点）时，Prompt 会不会超长？*
  → 是一个真实问题，树越大 Prompt 越长，token 消耗越多，分类耗时越长。优化方向：两阶段分类（先分领域，再在该领域内分类目），每阶段 Prompt 只包含子树。

### 难点 10：SSE 首包探测 + 流式切换（高可用流式输出）

**问题**：
- HTTP 200 ≠ 流式内容正常，模型可能返回空流（0 个 token）
- 如果等流结束才判断失败，用户已经盯着空白屏等了几秒
- 如果已经开始推送 token 再发现故障，脏内容已送达客户端

**首包探测的精妙之处**：

```java
CompletableFuture<Boolean> probeFuture = new CompletableFuture<>();

flux.subscribe(
  chunk -> {
    if (probeCompleted.compareAndSet(false, true)) {
      // 首包到达 → 证明模型正常
      probeFuture.complete(true);
    }
    emitter.send(chunk);  // 边探测边推送，不引入额外延迟
  },
  error -> {
    probeFuture.complete(false);  // 错误
  },
  () -> {
    if (probeCompleted.compareAndSet(false, true)) {
      probeFuture.complete(false);  // 空流（0 chunk 就结束了）
    }
  }
);

boolean success = probeFuture.get(10_000, MILLISECONDS);  // 阻塞等首包
```

**关键设计点**：
- `compareAndSet(false, true)` 保证只执行一次，防止 onNext 和 onComplete 都触发 probeFuture
- 主线程阻塞等待（`probeFuture.get()`），而不是 subscribe 后立刻返回，因为路由逻辑需要知道这个候选是否成功
- 首包探测和内容推送**同时进行**，第一个 token 到达时既完成探测又已经推送给用户，零额外延迟

**面试可能追问**：
- *为什么用 CompletableFuture 而不是 CountDownLatch？*
  → CompletableFuture 可以携带布尔值（success/failure），CountDownLatch 只能表示「完成」，无法区分是正常首包还是错误触发。
- *首包探测期间主线程在 HTTP 请求线程上阻塞，会不会耗尽 Tomcat 线程？*
  → 是一个真实问题。SSE 本来就是长连接，占用 Tomcat 线程；超时设置 10s，是可以接受的范围。进阶优化：配合 Spring WebFlux（响应式非阻塞），整个链路不占 Tomcat 线程。

## 三、高频通用追问（两个项目都适用）

### Q：你做的这个方案有没有缺点？现在回头看会怎么改？

**实习项目回答**：
> 三级限流体系里，站点层令牌桶的参数（令牌速率、桶容量）是静态配置的，
> 更好的做法是根据站点历史表现动态调整，比如抓取成功率高的站点自动提高配额，
> 这需要结合频度打分的结果做闭环，当时时间有限没有做到。

**RAG 项目回答**：
> DocumentReranker 目前是串行逐文档打分（6 个文档 = 6 次 LLM 调用），是延迟的主要来源。
> 改进方向有两个：
> 1. 改为并行打分（CompletableFuture.allOf），但要控制对下游 LLM 的 QPS 冲击
> 2. 换成专用的 rerank 模型（如 BGE-Reranker），延迟比 Chat 模型低 10 倍以上，且不消耗 Chat 配额

### Q：遇到最难的问题是什么，怎么解决的？

**实习参考**：
> GZIP 解析上线后，有少量 Sitemap 解析乱码，排查发现部分站点 .gz 文件内部编码不是 UTF-8 而是 GBK。
> 解法：解析前读取 BOM 头或检测编码，对 GBK 编码做转换后再接入链路。

**RAG 参考**：
> 流式 SSE 和熔断路由结合时出现了一个 bug：模型返回了第一个 token（探测成功），
> 但后续流中途出错，此时 emitter 已经发送了部分内容给用户，再发 error 事件前端不知道如何处理。
> 解法：约定前端只要收到 `name=error` 的 SSE 事件就显示「生成中断，请重试」，
> 并在服务端用 `emitter.completeWithError()` 通知前端关闭连接。
